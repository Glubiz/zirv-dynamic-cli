# Context Management

> [!tip] Quick Reference
> - `zirv ctx` exists because long-running AI-agent sessions rot: as the context window fills, instruction-following slips, tools get called in loops, hallucinations appear — and built-in auto-compaction fires only after degradation has already started.
> - A pure, deterministic **rot engine** scores a normalized event stream and hands a verdict (`healthy`/`advise`/`compact`/`restart`) to one of three **supervisors** (`loop`, `exec`, `wrap`), which act on it — compacting, restarting with a distilled handoff, or leaving the session alone.
> - **Usage pacing** keeps autonomous work from dying mid-run when a subscription usage window runs dry.
> - `.zirv/context/` is the canonical instruction source for every Zirv-launched session; `zirv context sync` is the explicit, opt-in bridge to native `CLAUDE.md`/`AGENTS.md` for direct (non-zirv) launches; `zirv context status` reports exactly what Zirv-managed context a session would receive, without starting one.
> - This page is the *why*; for the *how* see [[Ctx Subsystem]] (verb tree/dispatch), [[Rot Engine]] (scoring internals), [[Ctx Supervisors]] (loop/exec/wrap mechanics), [[Ctx Adapters]] (agent-specific plumbing), and [[Usage and Pacing]].

## The problem it replaces

Before `zirv ctx`, the mitigation was a shell Stop-hook "canary" watching for a fixed reply-prefix marker — a single noisy signal that sometimes misfired and, on trigger, could only warn; it had no way to clean up context itself. Recovery meant a manual `/compact` or session restart. Two use cases made this acute: a long-lived orchestrator session whose context grows every loop cycle, and headless workers that can rot mid-run on a single large task.

## The rot engine: score, don't guess

`zirv ctx score` is a pure function: transcript in, verdict out, same input always producing the same output — no clock, no filesystem, no environment reads inside the scoring logic itself (`rot.rs`). It combines several signals over a trailing window of turns:

- **Real context size** (a gate, not a vote): the most recent reported input-token count. Below a floor the verdict is always `healthy`; above a ceiling it's at least `compact`.
- **Tool-failure rate**: fraction of tool results that errored in the window.
- **Repetition loops**: the same `(tool, input)` pair repeating, a classic sign of a stuck agent.
- **Instruction-following marker** (optional, capability-gated): miss rate of a configured reply-prefix, when the agent supports the hook that emits it.

Determinism is what makes this testable and trustworthy: the canary's synthetic test transcripts port directly into unit tests. See [[Rot Engine]] for the exact thresholds and event model.

## Agent-agnostic by design

Everything agent-specific — how to launch a session, where its transcript lives, how to parse it into normalized events, how to inject a compaction command — sits behind an `AgentAdapter` trait, so the rot engine and supervisors never know which agent they're watching. Claude Code is implemented; Codex is not yet (tracked as issue #11, and `zirv ctx --help` says so explicitly rather than implying otherwise). See [[Ctx Adapters]].

## Supervisors: acting on a verdict without making things worse

Three supervisors turn a verdict into action, each suited to a different session shape:

- **`wrap`** babysits an *interactive* TUI session over a PTY, proxying keystrokes byte-for-byte. Intervention only happens at a verified turn boundary *and* while the user is idle, so the wrapped experience is indistinguishable from an unwrapped one until it actually intervenes. Its escalation ladder: `advise` prints a one-line note, `compact` injects the adapter's compaction command with focus instructions, `restart` distills a handoff, quits, and relaunches with that handoff as the opening prompt. The governing invariant — stated directly in project convention — is that a wrapped session must never be worse than an unwrapped one; any supervision failure degrades to plain passthrough.
- **`exec`** supervises one *headless* run: tails its transcript, scores periodically, and on a `restart` verdict or timeout kills, distills, and relaunches with a bounded restart budget before giving up and exiting non-zero for the caller's own policy to handle.
- **`loop`** replaces a long-lived orchestrator session outright: every cycle launches a *fresh* headless session with a clean context, so orchestrator-side rot becomes structurally impossible rather than something to detect and fix.

See [[Ctx Supervisors]] for the mechanics of each.

## Handoff and resume: never ask a rotted session to summarize itself

Distillation always runs as a **fresh** headless model call over the transcript tail -- never the rotting session itself -- using a cheap model and a versioned prompt template, producing a Task/Constraints/Done/Remaining/Blocked/Key-decisions/Verification/Next-step/Files-read/Files-modified/Gotchas markdown handoff (v3, issue #280, v3.11.0). Distillation also takes the repo's own previously-stored handoff as context, so a chain of restarts carries an earlier constraint or decision forward instead of losing it once it ages out of the transcript tail being distilled -- see [[Ctx Subsystem]]. If that call fails, a structural fallback extracts a handoff mechanically (recent user messages plus files touched), so a restart always has *something* to stand on. `zirv ctx resume` starts a clean interactive session with the latest handoff for the current repo injected as the opening prompt -- the seamless-handoff experience the score/handoff/resume/status verbs exist to support: a human or an automation can inspect state (`status`), force a restart with continuity preserved (`handoff` + `resume`), without losing task context across the boundary.

## Handoff vs memory: task continuity vs repository facts

Distillation produces two kinds of durable text, and zirv keeps them in two different stores on purpose:

- **A handoff is task continuity.** It answers "what was this specific task doing, and how does a fresh session pick it back up" — Task, Done, Remaining, Next step, Files touched, Gotchas learned. It is written once per restart and is only ever useful to the one session resuming that one task; nothing about it is meant to outlive the task.
- **Memory is repository facts.** It answers "what is true about this repository regardless of which task is running" — a build command, where a credential lives, a project convention, a gotcha about how a dependency behaves. `zirv ctx remember`/`recall`/`forget` read and write it directly, and it is injected into every session's composed prompt as its own layer (see "A consistent session prompt" below), the same way mail and the repo prompt layer are.

Confusing the two is the failure mode both designs guard against: task state leaking into memory pollutes a bank every future session reads regardless of task, and a repository fact stuck inside one handoff is lost the moment that task's handoff is no longer the latest one.

**Handoff-to-memory harvesting** is the one place the two stores touch, and it is opt-in (`[memory] harvest = true`, default off) rather than automatic. Right after a rot restart in `exec`/`wrap` distills a *genuine* handoff (never the mechanical structural fallback, which has nothing durable to offer), one extra cheap-model call looks only at that handoff's `Gotchas learned`/`Files touched` sections and is explicitly instructed to answer with durable repository facts only, and with nothing at all when nothing qualifies. Harvesting defaults off for the same reason a cheap model's output is never treated as authoritative anywhere else in this project (see [[Untrusted Configuration]]): a confidently wrong guess landing in a bank every future session reads unreviewed is a worse failure mode than simply not harvesting.

## Usage pacing

Autonomous loops must not die mid-run because a subscription usage window (a rolling 5-hour or 7-day limit) ran dry. `zirv ctx usage` layers three sources of truth — a server-authoritative collector (fed by tee-ing the statusline), a token-count estimator fallback, and an output-matching circuit breaker as the last resort — and supervisors pace work so a window reaches at most a configured percentage before waiting out the reset. See [[Usage and Pacing]].

## A consistent session prompt

Every session zirv starts (`wrap`, `exec`, `loop`, `resume`) gets a small injected system prompt so behavior is consistent run to run: a shipped default floor, optionally extended by a user layer and a repo layer. `--simple` skips all of it. The repo layer crosses a trust boundary worth its own page — see [[Untrusted Configuration]].

**The context compiler (`compile.rs`, issue #44)** is what actually assembles that prompt for every one of the six session launch paths (`chat`'s dashboard orchestrator pane, `wrap`, `exec`, `loop`, the dashboard's own worker panes, and `resume`) — one deterministic call in place of six independent hand-rolled recipes. It wraps `prompt.rs`'s own layering (`compose`, mail, report-back, command-line merge, injection) rather than replacing it, and adds two things no launch path assembled before: the canonical `.zirv/context/{common,claude,codex}.md` layer (repo-owned, untrusted, ordered common-then-harness-specific by `context::PrecedenceTier` — see [[Untrusted Configuration]]) and zirv's own honest policy report (`policy::evaluate`, [[Ctx Subsystem]]'s "Canonical policy" section) as structured data alongside the composed text. Two things this deliberately keeps separate: the canonical layer's prose can steer a session but can never touch the policy report, and the policy report is never rendered as prose telling the model it is "sandboxed" — an adapter that cannot actually enforce a stance says so (`Support::Unsupported`), rather than the compiler inventing false reassurance. `resume` is the one path that calls `compile::compile_with_harness_roster` instead of `compile::compile` directly, to keep its pre-existing no-harness-roster behavior. See [[Ctx Subsystem]]'s "The Context Compiler" section for the mechanics.

**A durable, repo-scoped objective is its own prompt layer (`PromptSource::Objective`, issue #285, v3.11.0).** `zirv ctx objective set|show|close` (plus `--objective <text>` on `exec`/`loop`) persists one record per repo -- text, token budget, deadline, spend so far, status -- independent of any one running session, so a restart, handover, or nudge relaunch doesn't lose track of what the operator actually asked for. The compiler folds it in last, after the memory layer, since its own counters change on every recompose; it is labeled operator-supplied data, never a higher-priority instruction. Crossing the budget or deadline flips the record's status and swaps in a fixed wrap-up instruction rather than killing the run -- completion itself is never model-asserted: `objective close` refuses unless the repo's latest verification evidence is fresh and passing. See [[Ctx Subsystem]]'s `objective` verb entry and [[Ctx Supervisors]] for the re-injection/reload cadence.

## Prefix stability: the session prompt is a cache-cost invariant, not just prose

Everything a real provider's prompt cache prices is the *prefix* -- the bytes a harness sends unchanged from one turn (or one relaunch) to the next. Every layer above that can perturb the composed prompt -- a memory harvest, a harness-roster refresh, mail arriving, a canonical `.zirv/context/` edit -- is therefore also, silently, a cache-cost decision: a byte moved earlier than it needs to be voids every downstream layer's own cache entry too. Issue #299 turns that into a testable property instead of a hope, one deliberately narrow claim: **the bytes emitted before a given layer's own declared start must never move when only a later layer changes.** `compile::layers_of` (test-only, `#[cfg(test)]`) resolves the byte range of the five layers whose own fixed header makes this attributable (`Harnesses`, `Context`, `Workflow`, `Memory`, `Mail`) from an already-composed prompt, by searching for those layers' existing header constants (`prompt::HARNESS_ROSTER_LAYER_HEADER`, `compile::CONTEXT_LAYER_HEADER`, `prompt::WORKFLOW_LAYER_HEADER`, `prompt::MEMORY_PRIVATE_LAYER_HEADER`/`MEMORY_SHARED_LAYER_HEADER`, `prompt::PEER_MAIL_HEADER`/`PARENT_MAIL_HEADER`) -- never a second, hand-rolled walk of the layering `compose`/`with_canonical_context_layer` already perform. Everything before the first resolved anchor (`Default`, and when present `Adapter`/`Harness`/`User`/`Repo`) folds into one leading `Default`-attributed range: those layers have no header of their own, or (`Adapter`) are spliced in after composition rather than appended in order, so resolving them byte-exactly is out of this issue's scope.

`compile::test_support::prefix_diff` is the shared comparison helper (`compile.rs`'s test module, reused by `prompt.rs`'s): the first byte offset two prompts diverge at, plus 32 bytes of escaped context either side of it from both -- "prefix drifted" with no offset is not actionable. `compile::test_support::assert_change_confined_to_layer` builds on it for the "declared suffix" gate: a state change is asserted to perturb its own emitted layer and nothing before it, and the panic on a violation names the exact offset, both sides' escaped context, and the layer whose declared start was crossed. `src/commands/ctx/compile.rs`'s and `src/commands/ctx/prompt.rs`'s own test modules carry the concrete cases: repeated compiles of one session are byte-identical; a memory harvest, a roster refresh, and mail arriving each perturb only their own declared suffix; a deliberately injected one-byte change inside `common.md` is correctly attributed to the canonical-context layer; and `.zirv/context/common.md` failing to stay under its 4096-byte injection budget (`context.max_common_bytes`) is a test failure, not just something the truncator quietly fixes at runtime.

The fixture half lives in `tests/fixtures/fake-agent.sh`'s `FAKE_AGENT_PROMPT_LOG` variable (POSIX `sh`, `#[cfg(unix)]`-only in practice): each run appends `\x1e<turn-index>\x1e` followed by the exact bytes of whichever adapter mechanism actually delivered the composed prompt to that process -- `--append-system-prompt <text>` or `--append-system-prompt-file <path>` for claude, `-c developer_instructions=<json>` for codex -- byte-exact, no normalization, no shell interpolation of the payload. See [[Testing Guide]] for how to drive it.

## Compatibility outside zirv: `zirv context sync`

The canonical `.zirv/context/` layer only ever reaches a session through the compiler above — and the compiler only ever runs when zirv itself launches the session. Claude Code and Codex can both be started **directly**, bypassing zirv entirely, in which case the only instructions they ever see are their own native files: `CLAUDE.md` for Claude, `AGENTS.md` for Codex. Left alone, that's a real gap — canonical content a project spent effort authoring simply would not exist for a developer (or another tool) that launches the harness natively.

`zirv context sync` (a **top-level command family**, `zirv context <verb>`, not a `zirv ctx` verb — see [[Ctx Subsystem]]'s own section on it) is the explicit, opt-in bridge, issue #45 ("Context 7/8"). It never runs implicitly — no autogeneration at launch, no side effect on `compile::compile` — and offers three separately-named modes rather than one command that tries to guess what the user wants:

- **Report** (the default) inspects both sides and prints what's there and where they disagree, reusing `drift.rs`'s existing duplicate/contradiction/precedence-shadowing analysis rather than a second comparison engine. Read-only.
- **Import** brings a hand-maintained native file's content into canonical `.zirv/context/`, for a project that already has a `CLAUDE.md`/`AGENTS.md` and wants to make it the seed of its canonical layer instead of starting over.
- **Generate** renders canonical content back out into native `CLAUDE.md`/`AGENTS.md`, for a project that wants direct-launch compatibility once canonical content exists.

The one safety property that matters most: **generation must never silently destroy a hand-maintained native file.** Every file `zirv context sync --generate` writes carries a stable, deterministic marker as its first line; a native file that exists without that marker is refused, not overwritten, and only an explicit `--force` lifts the refusal — the same "an explicit human choice, never a default" posture the rest of this project takes toward anything destructive. Generation is otherwise pure and idempotent: the same canonical content always renders the same bytes, so regenerating with nothing changed writes nothing.

Content routing follows the same common/harness-specific split the canonical layer itself already has: common content reaches both generated files, but a Claude-specific canonical addition can only ever land in the generated `CLAUDE.md`, and a Codex-specific one only in the generated `AGENTS.md` — there is no code path for one to leak into the other's output.

**A generated file is prose, nothing else.** It never states or implies a permission, sandbox, or enforcement claim, and never serializes `policy::EffectivePolicy`/`Support` state — the moment a harness is launched outside zirv, there is no zirv process left to enforce anything it might have claimed. This is the same "Markdown instructions are advisory context, never enforcement" line `policy.rs` draws for the canonical layer's own injected prose, extended to what compatibility mode writes to disk.

See [[Ctx Subsystem]]'s "`zirv context sync`" section for the exact flags, the managed-marker mechanics, and file references.

## Linting the composed prompt: `zirv context lint` (issue #275, v3.12.0)

A third verb on the same `zirv context` tree as `sync` and `status` above, sitting between "compare canonical to native" (`sync --report`) and "measure what a session receives" (`status`): `zirv context lint [--json] [--budget compact|standard|full] [--fix-plan]` is pure, read-only analysis over the identical instructional layers a real launch composes — the built-in default/harness prompts, `.zirv/context/{common,claude,codex}.md`, and native `CLAUDE.md`/`AGENTS.md` — producing five stable-id findings: **CTX001** (per-layer budget headroom, warn at 90%/error on overflow), **CTX002** (cross-layer duplicate imperative sentences), **CTX003** (cross-layer contradiction candidates, negation-marker heuristic), **CTX004** (per-layer imperative/narrative/code proportionality, informational), and **CTX005** (a dedupe leak — a managed native file's embedded canonical hash claims a match its actual bytes don't honour, so compile-time dedupe silently won't fire and canonical content gets injected twice). Only CTX001 and CTX005 are blocking (exit `1` on any `Severity::Error` finding); CTX002-CTX004 never affect the exit code. `context_lint.rs` itself holds to the same purity discipline as `rot.rs`/`compile.rs` (no fs/clock/env) — `context_cli.rs`'s `gather_layers`/`run_lint_with` do the actual reading. See [[Built-in Commands]] for the full flag/check table, `context.lint_max_pairs` (the sentence-pair comparison cap, default 20,000, `REPO_FORBIDDEN`), and the `--fix-plan` output shape.

Two seams tie `lint` into the rest of this page's machinery rather than re-deriving anything: CTX004 slices its per-layer counts out of an already-**compiled** prompt via `CompiledContext::emitted_layers()` (see "The Context Compiler" on [[Ctx Subsystem]]) instead of a second file read, and `zirv context sync --report` folds any CTX001/CTX005 blocking finding into its own drift report so an operator comparing canonical-to-native content sees a budget overflow or a dedupe leak in the same place, not a second command to remember. The workflow verify gate discovers it too: `CheckKind::ContextLint` (`zirv context lint`, always run at `--budget standard` regardless of what an operator's own CLI invocation requests) is present whenever `.zirv/context/` exists, so a repository that adopts canonical context automatically gets a real/fail-closed check in its own verification report rather than an opt-in the operator has to remember to wire up.

## Making context measurable: `zirv context status`

Everything above — the canonical layer, the compiler, memory, mail, the harness roster, the honest per-harness policy report — is invisible to a team unless someone reads source or launches a real session and inspects its prompt. `zirv context status` (issue #46, "Context 8/8", the second verb on the same `zirv context` tree as `sync`) closes that gap: a compact, read-only report of exactly what Zirv-managed context a session would receive, built entirely from machinery issues #42-#45 already produced (`compile::compile`, `drift::analyze`, `policy::evaluate`) rather than a second collection pass. It never starts a session, spawns the agent binary, or makes a network call — so it is useful in CI, in a PR review, or on a machine with no agent installed at all.

Three design commitments run through the whole report:

- **Bytes are measured, tokens are estimated, and the two are never conflated.** Every byte figure comes from an actual `.len()` on text read from disk or state; every token figure is a fixed, documented divisor (`bytes / 4.0`, rounded up) labeled `(est.)` everywhere it appears, with the method and its limits (not a real tokenizer; vendor/model/language/content-type all move the real number) stated in the rendered output itself — not just in a doc page. No tokenizer crate was added to `Cargo.toml`.
- **Zirv only knows what it injects.** The report's closing section states plainly that each harness's own hidden system prompt and built-in tool scaffolding are unknown to zirv and never folded into any figure above. The bare phrase "total context" never appears anywhere in the output — only "total zirv-managed context estimate", always qualified, and a test (`unknown_vendor_context_is_disclosed_and_no_total_context_claim_is_made`) pins both halves of that promise.
- **No false equivalence between harnesses.** The per-harness section prints each adapter's own `PolicyReport::render()` (see [[Ctx Subsystem]]'s "Canonical policy" section) verbatim: claude reports `Enforced`/`Unsupported` where codex reports `Degraded`/`Unsupported` for the identical capability and stance, and the report does nothing to paper over that difference.

**Oversized surfaces are flagged, not buried.** Every discovered instruction surface (canonical `.zirv/context/*.md`, native `CLAUDE.md`/`AGENTS.md`, nested or global) is measured against the applicable budget — the canonical layer's own real, enforced caps (`context.max_common_bytes`/`max_harness_bytes`) for canonical files, and `context.max_harness_bytes` reused as a reference size for native files that have no budget of their own, since zirv never injects those directly. A surface over its threshold is marked `[OVERSIZED]` inline, before it silently eats budget rather than after.

**The one genuinely new budget.** Every other layer already had a configured cap (`prompt.max_repo_bytes`, `context.max_common_bytes`/`max_harness_bytes`, `mail.max_delivered_bytes`, `memory.max_injected_bytes`) before this issue; the derived harness roster (`PromptSource::Harnesses`) did not. `context.max_harness_roster_bytes` (default 4096) fills that gap, wired exactly like `context.max_common_bytes` (`REPO_FORBIDDEN`, its own env override, the exhaustive key test, a line in the sample `.zirv/ctx.toml`) — and, as of the same-day follow-up, it is a **real, enforced** budget: `prompt::compose` truncates the joined roster with the exact same UTF-8-safe byte cut (`crate::utils::truncate_bytes`, no line-boundary special case) `read_layer`/`with_memory_layer` already use for `prompt.max_repo_bytes`/`memory.max_injected_bytes`, via a small pure helper (`prompt::harness_roster_injection`) both `compose` and the compiler call so the two can never disagree. A roster already under the cap renders byte-identical to before this budget existed. `CompiledContext` carries the same raw/delivered/truncated shape `ContextProvenance` uses for canonical context (`harness_roster: Option<prompt::HarnessRosterInjection>`), and the status report's harness-roster and per-harness sections read the truncation off it directly rather than estimating a second time.

See [[Ctx Subsystem]]'s "`zirv context status`" section for the exact report sections and the file/function references.

## zirv as a meta-harness: chat, delegation, and a mailbox

`zirv ctx chat` (also reachable as the top-level alias `zirv chat`, or as bare `zirv` in a repo with a `.zirv` directory and a real terminal attached — see [[Built-in Commands]]) is the interactive seat: a `wrap`-supervised session tagged `PromptRole::Orchestrator`, which is what makes it — and only it — eligible for the harness-teaching prompt layer (`HARNESS_PROMPT` in `prompt.rs`). That layer is what turns zirv from "a supervisor watching one session" into a small meta-harness the orchestrator session is told about directly: it names `zirv ctx agent` for delegating a task to another enabled harness, `zirv ctx send`/`zirv ctx inbox` for leaving and reading short notes between sessions, and `zirv ctx status` for checking which harnesses are enabled and whether mail is waiting. It also (2026-08-16) tells the session to use zirv on its own initiative — delegate substantial work, poll status/inbox at natural checkpoints, steer a live worker, persist durable facts to memory — and states zirv's own review policy: finish substantive development with the harness's own native full-diff review plus one review worker per other enabled harness, triaging and re-reviewing only what fixes touched, with a hard stop after two fix rounds. Immediately after `HARNESS_PROMPT`, an Orchestrator session (only, and only when `cfg.prompt.harnesses` is on and the rendered roster is non-empty) also gets a derived **harness roster** layer — one line per registered adapter naming whether it's enabled and ready to receive `zirv agent <name> "<prompt>"` right now, rendered by `adapters::harness_prompt_lines` and folded in as `PromptSource::Harnesses` — so the session does not have to run `zirv ctx status` just to learn what it can delegate to. See [[Ctx Adapters]] for `harness_prompt_lines` and [[Ctx Subsystem]] for the `prompt.harnesses` config key.

**The checkpoint bullet has moved twice since v11, both times narrowing what a session pays to poll status: v12 (issue #225) pointed it at `zirv ctx status --brief`, and v13 (issue #246, v3.4.0) at `zirv ctx status --brief --diff`** — `--diff` prints only the report sections that changed since this session's own previous `--diff` call, so a session polling at every natural checkpoint (task start, after long steps, before reporting done) pays a small "no change" one-liner on the checkpoints that land on an unchanged report instead of the full `--brief` render each time. See [[Ctx Subsystem]]'s `status` verb entry for the snapshot mechanics.

**`HARNESS_PROMPT` v11 (issues #204/#205, 2026-08-30) added two bullets.** The **design-review gate** (#204): when the operator hands the session a design- or UX-shaped task — a UI redesign, a visual or interaction overhaul, or any change where look/layout/interaction is the point — the session is taught to audit the current state first, then present representative target designs (mockups or a design document) to the operator and wait for explicit approval before dispatching implementation. This gates operator-facing design *direction* only: it does not reintroduce a kickoff question for work the operator asked to be done autonomously end-to-end with no design dimension — an autonomous frontend baseline, for example, still proceeds without asking. The **autonomous lifecycle** bullet (#205): when no `zirv workflow` is active and the incoming task is substantial (an issue to implement, a feature, a multi-step change), the session is taught to start the lifecycle itself — `zirv workflow start <kind> --task "<summary>"`, choosing the kind (feature/bugfix/refactor/spike/review) and trusting `classify.rs`'s size-adaptive gating to right-size what the workflow demands, rather than ceremonializing a trivial or single-file task. Because the injected prompt does not refresh once a session is running, the bullet also tells the session to consult `zirv workflow status` (and the work artifacts for the active step) after starting a workflow mid-session, instead of expecting this injected text to reflect it. See [[Workflows]] for the lifecycle itself and the size-adaptive classification `classify.rs` performs.

- **Delegation.** `zirv ctx agent <name> <prompt>` (also `zirv agent`) is a one-shot dispatch to a supervised headless worker on another enabled harness, reusing `exec`'s full pacing/rot/restart machinery. A delegated run is always tagged `PromptRole::Worker`, never `Orchestrator` — so it never gets the harness-teaching layer, and (2026-08-19) it gets the adapter's own **worker** layer in place of the orchestrator one (claude's `WORKER_PROMPT`: execute the brief, never delegate onward, no fork subagents, report compactly) plus the operator's separate `~/.zirv/system-prompt.worker.md` rather than their interactive `system-prompt.md`. Three layers pointing the same way, so a worker cannot itself be taught to delegate further. This is the same "don't make things worse" instinct as `wrap`'s own safety contract, applied to recursion instead of raw-mode terminals. Inside a dashboard the same invocation becomes an attached pane instead, and that pane's prompt carries one extra layer no other session gets: `prompt::with_report_back_layer`, zirv's own plumbing instruction telling the worker to close the loop with `zirv ctx send --to-session <requester> --message '<summary>'` when it finishes. It is added only when the requesting session is actually identifiable, and it is what backs the harness layer's claim that a pane's results come back by mail — see [[Ctx Supervisors]].
- **Mailbox.** `zirv ctx send`/`zirv ctx inbox` let agent sessions on the same machine leave each other short markdown notes, scoped to the current repo, optionally addressed to one specific live session (`send --to-session <prefix>`, resolved against the session registry below). Full message bodies are delivered into a headless **Worker** session's composed prompt as its own layer (after the repo layer and the canonical `.zirv/context/` layer the compiler adds, before the command-line layer) — `zirv ctx exec` (including a delegated `zirv ctx agent` run) once at launch, `zirv ctx loop` fresh every cycle — labeled as information from another session, not as an instruction, and consumed right after so it is not redelivered (see [[Untrusted Configuration]]). An interactive **Orchestrator** session (`zirv ctx chat`, via `wrap`) never gets message bodies in its own prompt at all: it gets a one-line unread-count advisory on the announcement channel instead (broadcast and direct-to-this-session counted separately), since the orchestrator seat is where a human decides what to go read.
- **The session registry and intervening from outside.** Every supervised session (`wrap`/`exec`/`loop`/`chat`) registers itself under the state dir for as long as it is alive, keyed by the same short id its turn-signal socket is named after (`sessions.rs`; see [[Ctx Subsystem]]). This is what makes it possible to *address* a specific running session rather than only its repo or its agent name — both `send --to-session` and `zirv ctx nudge <prefix>` resolve a short-id prefix against it. A nudge is the one deliberate way an operator can interrupt a session from outside its own loop: the payload is ordinary, durable, session-addressed mail (so it survives however long it takes to be noticed, and shows up in `zirv ctx inbox` even if the wake-up itself is missed), plus a separate wake-up marker so a supervisor blocked on its own poll interval does not have to wait out the interval. For a headless (`exec`) session, a nudge costs the in-flight turn — the session is stopped and relaunched with a handoff distilled from the transcript so far, the exact same recovery path a rot restart uses, just triggered on demand rather than by the rot engine, and capped by its own budget (`supervise.max_nudges`) separate from the ordinary restart budget since a nudge is not rot. For an interactive (`wrap`) session, a nudge is advisory only — it never restarts or types into the agent, only surfaces on the status bar and event channel that something arrived.
- **Discoverability.** `zirv ctx status` (see [[Ctx Subsystem]]) reports the whole story without a human having to remember the verbs: a `chat:` line naming the adapter `zirv ctx chat` would actually launch and the rule that picked it, a `mail: N unread` count for the current repo, a `sessions:` block from the live registry, a `memory:` line summarizing the memory bank (see [[Untrusted Configuration]] for why its content — as opposed to its size — never appears in `zirv ctx optimize`'s own report), and, since issue #295, a "recent memory writes" block: a short key/op/scope/byte-delta line per recent `remember`/`forget`/`verify`/`promote`/`rollback`, read from that bank's own journal tail.
- **A per-session memory tier (issue #295).** A bare `zirv ctx remember`/`zirv memory remember` — no `--repo`/`--shared`/`--global` — now writes to a fourth, ephemeral `MemoryScope::Session` tier instead of the private one whenever a session id is present in the environment, and that entry is visible only to `zirv ctx recall` calls made under the SAME session id; it is removed outright once that session's own registry entry retires (see [[Ctx Subsystem]]'s "Sessions and Memory" section for the write path, the journal that backs `zirv memory rollback`/`promote`, and the documented residual that this tier is not yet threaded into the launch-time compiler's own injected core/retrieval layers).

See [[Ctx Subsystem]] for the `chat`/`agent`/`send`/`inbox` verbs themselves, and [[Ctx Supervisors]] for how the role parameter, mail advisory, and terminal chrome (banner, status bar, `zirv ▸` event channel) fit into the `wrap` pump loop that actually drives an interactive session.
