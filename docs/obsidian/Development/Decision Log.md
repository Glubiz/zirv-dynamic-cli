# Decision Log

**Entry shape (hard cap ~15 lines):**

```
### YYYY-MM-DD — Short title
**Context:** 2–3 sentences on the situation.
**Decision:** 2–3 sentences on what was chosen.
**Rejected:** one or two lines per alternative with a *concrete* reason. "Felt over-engineered" is not a reason.
**Consequences:** 2–3 lines — the forward-looking implication, not a rehash of the decision.
**Spec / link:** path to the spec or Known Issues entry if relevant.
```

## Guardrails

- Self-contained: a reader should understand the entry without reading three prior ones; link prior context, don't recap it.
- No generic rationale: cut "for simplicity" / "to reduce complexity"; state the actual constraint that made the other option worse.
- Supersede by deletion, not by appending: if a later decision overrides an earlier one, delete the superseded entry; git log preserves history.
- If the entry is longer than the cap, the "why" is a spec, not an ADR — write it under `docs/superpowers/specs/` and link to it.

## Decisions

### 2026-08-31 — Workflow adoption is detected in the Stop/Prompt hooks and delivered per-policy, not through announce/mail (issue #223, v3.2.0)
**Context:** Sessions routinely do substantial edit work with no active `zirv workflow` at all, so the methodology this subsystem owns is simply never invoked. Neither the `zirv ▸` announcement channel nor mail reaches a model's own context, so detecting the gap is useless without a delivery path that a model actually reads.
**Decision:** A pure detector, `commands/workflow/adoption.rs` (mirroring `rot.rs`'s no-fs/clock/env/net discipline), counts edit-like tool calls and turns off `NormalizedEvent`s and calls work substantial at 5+ edit calls or 12+ turns with one edit. `AdoptionPolicy` (`Off < Advise < Nudge < Enforce`, default `Nudge`) is operator-only, `REPO_FORBIDDEN`. Detection rides the existing `Stop`/`Prompt` hooks, folding signals into a per-session state-dir record; `Advise` delivers a Stop-hook `systemMessage` (operator-visible), `Nudge` an `additionalContext` line on `UserPromptSubmit` (model-visible, re-checked live so an already-started workflow suppresses it), and `Enforce` additionally refuses `zirv agent` delegation while the calling session is substantial-without-workflow. A delegated worker (`ZIRV_CTX_WORK_GROUP` set) is exempt.
**Rejected:** Coupling detection into the rot engine — rot answers "is this session degrading," a different question from "is this session using the right methodology," and coupling them would make `rot.rs` impure or force a second scoring pass. A repo-settable adoption knob — a checkout tightening or loosening its own governance pressure is the same asymmetry `agent`/`handoff.model` already close.
**Consequences:** The enforce gate only ever holds a session the hooks have already been nudging (it needs a session identity and an existing record), so an operator running `zirv agent` from a plain shell is never blocked. `zirv workflow stats` gets a durable adoption-rate signal (`AdoptionDetected`/`AdoptionRecovered` telemetry) for free from the same detector.
**Spec / link:** `src/commands/workflow/adoption.rs`; `src/commands/ctx/{hook,agent}.rs`; [[Workflows]]'s "Workflow adoption" section; [[Ctx Subsystem]]; [[Untrusted Configuration]]; issue #223.

### 2026-08-31 — Steady-state session cost gets a reproducible measurement surface before further trimming (issue #225, v3.2.0)
**Context:** Every session pays a composed prompt prefix and a per-turn hook line on top of it, but nothing measured either cost — a proposed trim had no baseline to prove it actually shrank anything, or by how much.
**Decision:** `zirv ctx compile --measure` composes exactly as a real orchestrator launch would and prints a deterministic per-layer byte/~token table straight off that one `CompiledContext`'s own provenance (default/harness prompt, roster, canonical context layers, memory, total, per-turn hook line) — never a second, hand-rolled walk of the same layering. `zirv ctx status --brief` collapses the status report's unbounded sections (work groups, sessions, decisions) for cheap checkpoints. The per-turn `UserPromptSubmit` marker sentence was reworded 170→89 bytes with no change to `marker_miss_rate`'s detection contract (prefix-only match).
**Rejected:** Trimming `HARNESS_PROMPT`'s prose wholesale to cut bytes — it is read once per session and cached by the provider, so cutting it saves nothing steady-state while risking losing instructions an orchestrator actually needs; the per-turn, uncached hook line was the one line worth trimming for its byte cost alone.
**Consequences:** `docs/benchmarks/token-cost.md` §6 is now the reproducible baseline every future prompt-shape change should re-measure against, rather than an estimate. `zirv workflow stats`/`zirv ctx usage` cache-hit lines (schema v2 formula) give steady-state cache efficiency the same measured-not-guessed treatment.
**Spec / link:** `src/commands/ctx/{compile,hook,status,usage}.rs`; `src/commands/workflow/telemetry.rs`; `docs/benchmarks/token-cost.md` §6; [[Ctx Subsystem]]; [[Usage and Pacing]]; issue #225.

### 2026-08-31 — Codex's own error text splits into three restart-worthy classes, not one (issue #227, v3.1.0)
**Context:** `exec.rs`/`pace.rs` already recognized one class of codex trouble text, a genuine usage-window trip (`is_limit_hit`, park and wait for reset). Two other message shapes were being read the same way: a transient per-model capacity error, and a hard account/billing-quota stop — neither of which a window-reset wait actually addresses.
**Decision:** Two new pattern classes sit beside the existing one. `CAPACITY_PATTERNS` ("model is at capacity" and overload variants) restarts the same-repo session in place within `--max-restarts` on a capped 15/30/60s backoff, never touching window/collector state, exiting `EXIT_CAPACITY_EXHAUSTED` (78) with a structured reason on budget exhaustion. `ACCOUNT_EXHAUSTED_PATTERNS` (`insufficient_quota` and OpenAI's documented billing-error shape) is an immediate hard stop, `EXIT_ACCOUNT_EXHAUSTED` (79), spending no restart budget. A headless delegation exiting non-zero for any reason now mails the structured reason back to the spawning session, previously a dashboard-pane-only, success-only behavior.
**Rejected:** Treating a capacity error as a usage-window trip (park and wait for a `resets_at` that will never come — capacity has nothing to do with the account's quota). Treating account exhaustion as retryable (burning restart budget against a billing stop no restart can fix). Matching `"503 Service Unavailable"` as a capacity pattern — it was in the table during implementation and was dropped by a review round: that generic HTTP status line can come from a proxy, a local dev server, or any other tool this worker's output happens to contain, unrelated to the harness's own provider account.
**Consequences:** `zirv ctx loop` still only recognises the original `LIMIT_HIT_PATTERNS` class — filed as a residual, not fixed here (see [[Known Issues]]). The account-exhaustion strings follow OpenAI's own documented shape, not a captured zirv transcript, so they are a best-effort match rather than a verified one.
**Spec / link:** `src/commands/ctx/{pace,exec,agent,window}.rs`; [[Ctx Supervisors]]; [[Usage and Pacing]]; [[Ctx Adapters]]; [[Known Issues]]; issue #227.

### 2026-08-31 — `ZIRV_REVIEW_RESULT` ingestion degrades per finding and salvages raw output, rather than rejecting the whole envelope (issues #229/#232, v3.1.0)
**Context:** A three-way review round against a ~2.2k-line diff found `zirv workflow review run`'s own ingestion unusable at that scale: `deny_unknown_fields` rejected a reviewer payload carrying one harmless extra field, the compact package dropped every `src/` hunk in source order before it ever reached a code hunk, and a mid-run edit to the untracked `plan.md` (workflow-owned state, not reviewed code) tripped the staleness guard.
**Decision:** Parsing tolerates an unknown field per finding and accepts documented severity/disposition synonyms case-insensitively; a genuinely unrecognized value degrades to `major`/`open` with the raw value appended to the summary rather than rejecting the finding. Any ingestion failure (parse, staleness, no envelope, nonzero exit) persists the reviewer's raw output to `.zirv/work/<id>/review/raw-<ts>-<agent>.txt` before erroring, so findings are recoverable via `review add`. Package truncation orders `src`/code hunks first, then tests, config, docs, then renames, reading the raw diff up to 8 MiB before ordering. `.zirv/work/**` is excluded from both the package and the staleness fingerprint (`classify::is_workflow_work_path`).
**Rejected:** Keeping `deny_unknown_fields` and just widening the schema — the next harmless field addition breaks the same way; a per-finding-lenient parser has no such coupling to an exact field list. Discarding a failed ingestion's output — a reviewer that did real, valid analysis before hitting a parse edge case had its whole verdict thrown away with nothing to recover.
**Consequences:** A future reviewer-payload field addition is safe without a parser change. Package truncation now reflects what a reviewer actually needs to see (code) rather than diff order, which happened to bury the code hunks behind config/doc churn on this diff.
**Spec / link:** `src/commands/workflow/{review,classify,verification}.rs`; [[Workflows]]'s "Ingestion is lenient per finding" section; [[Known Issues]]; issues #229/#232.

### 2026-08-31 — `--workdir`/`--headless` on `zirv agent` refuse loudly instead of silently demoting a pane spawn (issue #228, v3.1.0)
**Context:** A dashboard pane spawn already silently dropped to the plain headless path the moment an invocation carried any flag beyond a bare `--model` pin — reasonable when the dropped flags didn't matter to the operator's intent, but `--workdir` (a new flag naming the worker's actual run directory) changes what the delegation even means, so silently discarding it would run the worker in the wrong place with no error.
**Decision:** `--workdir <dir>` is canonicalised and hard-refused (naming the flag and the reason) unless it exists, is a directory, and is inside a git repository — no escape hatch for a non-repo directory, matching the trust posture every other zirv-launched worker already requires. Inside a dashboard, `--model` and `--workdir` are now the two pane-supported trailing flags; any other one (`--max-restarts`, `--timeout-secs`, `--budget-tokens`, `--max-tool-calls`, trailing `-- flags`) is a named hard error pointing at the new `--headless` flag, which forces a supervised headless worker even from inside a pane. `SpawnRequest.workdir` (new, `#[serde(default)]`) is re-validated server-side by `resolved_spawn_cwd` under the identical rule, never trusted from the request.
**Rejected:** Silently demoting to headless on any unsupported flag, as before — correct for flags a pane genuinely cannot honour and the operator likely didn't need honoured; wrong for `--workdir`, where silently ignoring it changes where the worker's writes land with no way for the operator to notice.
**Consequences:** A forged `SpawnRequest.workdir` widened the accepted #179 filesystem-intake trust boundary (a same-uid sibling process could point a worker's writes at any git repo the dashboard user can reach, not only the dashboard's own repo family) — recorded, then narrowed same-day by a workdir-roots confinement fix (see the entry directly below), since closing it fully still needs #179's own unix-socket/pid-ancestry attribution work. See [[Known Issues]].
**Spec / link:** `src/commands/ctx/{agent,dash/mod,dash/spawnreq}.rs`; [[Ctx Subsystem]]'s `agent.rs` verb entry; [[Ctx Supervisors]]'s dashboard section; [[Untrusted Configuration]]; [[Known Issues]]; issue #228.

### 2026-08-31 — A pane's `--workdir` is confined to operator-owned workdir roots, not merely "any git repository" (issue #228 review-round fix, v3.1.0)
**Context:** The entry above gave a pane spawn's `--workdir` the same validation the headless path already had (exists, is a directory, is inside a git repository) — necessary but, on its own, far too wide: it let a forged `SpawnRequest.workdir` point a worker pane's writes at any git checkout the dashboard's own user account could reach, not only a repo related to the dashboard's own launch, found by this branch's own security review.
**Decision:** `dash::resolved_spawn_cwd` now also confines a pane's `workdir` to `workdir_roots(cfg, repo)`: by default the dashboard's own canonicalised repo root plus that root's parent directory (`default_workdir_roots`, so sibling checkouts work with zero operator config), unioned with whatever the operator names in `[dash] workdir_roots = [...]` (`~/.zirv/ctx.toml`, `REPO_FORBIDDEN`) or the comma-separated `ZIRV_CTX_DASH_WORKDIR_ROOTS`, which replaces the merged value outright. Containment (`workdir_within_roots`) compares canonicalised path COMPONENTS via `Path::starts_with`, not string bytes, so `D:\GitHub\zirv`'s roots never match a sibling `D:\GitHub\zirv-other`. The headless `zirv agent --workdir` path (outside a dashboard, or with `--headless`) is deliberately exempt — it runs as the operator's own command, not a pane spawn request, so `agent.rs`'s `validate_workdir` stays exists/dir/git-repo only.
**Rejected:** Confining `workdir` to only the dashboard's own repo (matching `accepted_spawn_cwd`'s rule for `cwd`) — too narrow for the feature's own point: `--workdir` exists so a worker can run against a *different* repo than the dashboard's, and an operator with related sibling checkouts (a monorepo split across directories, a fork alongside the original) would otherwise have no config path to that at all, only the "any git repo" hole. A single flat allowlist with no default roots — would make every dashboard unusable for the common sibling-checkout case until an operator hand-configured it. Explicit per-sibling allowlisting instead of the whole parent directory (codex round-2 finding) — rejected for the identical reason: it would defeat the sibling-delegation use case `--workdir` exists for, forcing hand-enumeration of every sibling checkout instead of a zero-config default.
**Consequences:** A same-uid sibling process can still forge a `workdir` pointing anywhere *inside* the configured roots (e.g. any sibling checkout under the dashboard's own parent directory) — narrowed, not closed; still needs issue #179's own unix-socket `SO_PEERCRED`/pid-ancestry attribution to close fully; that pid-ancestry work, not a smaller default-roots allowlist, is the accepted real fix (codex round-2 finding, recorded as a residual, not addressed here — see [[Known Issues]]). `dash.workdir_roots` joins `sandbox.extra_allow`'s privilege-widening asymmetry: a repo checkout naming a root here would hand its own compromised pane write authority over anything under it, so the key is `REPO_FORBIDDEN` outright, no repo union counterpart the way `sandbox.extra_deny` gets. `default_workdir_roots`'s parent-directory widening only ever applies via `sibling_root_for`, which returns no widening at all when the parent is itself a filesystem/drive root (`/`, `C:\`, `\\?\C:\`) — a second claude round-2 finding, fixed, closing what would otherwise have made a checkout directly below the root (`/workspace/repo`, `C:\repo`) accept every absolute path as "inside the roots."
**Spec / link:** `src/commands/ctx/dash/mod.rs`'s `default_workdir_roots`/`workdir_roots`/`workdir_within_roots`; `src/commands/ctx/config.rs`'s `DashConfig::workdir_roots`; [[Ctx Supervisors]]'s dashboard section; [[Untrusted Configuration]]; [[Known Issues]]; issue #228.

### 2026-08-31 — A verification check's own child process gets an explicit, operator-only environment passthrough allowlist (issue #233, v3.1.0)
**Context:** An operator's own `git`/`gpg`-signing check inside `zirv verify`/`zirv test` couldn't reach their SSH agent. Root cause: `run_check` never scrubbed the child's environment at all — the check already inherited zirv's whole process environment — so the real gap was that zirv's own launch environment simply lacked `SSH_AUTH_SOCK` in the first place (a login-session variable, not one a terminal-launched process always carries).
**Decision:** `DEFAULT_CHECK_ENV_PASSTHROUGH` (`SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `SSH_ASKPASS`, `GPG_TTY`, `GNUPGHOME`) is explicitly set on every check child. `[workflow] check_env_passthrough` in `~/.zirv/ctx.toml` (`REPO_FORBIDDEN`) ADDS names to that set; `ZIRV_CTX_WORKFLOW_CHECK_ENV_PASSTHROUGH` (comma-separated) REPLACES the merged value, the operator's final word. Per allowlisted name: zirv's own process env first, then (macOS only, bounded 3s, no shell) `launchctl getenv <NAME>` announced on stderr when it fires, else unset — never overriding a value already present.
**Rejected:** Leaving the check child's environment fully unscrubbed (the pre-fix behavior) — an unbounded inherit is a worse default even though it happened to work once `SSH_AUTH_SOCK` was present in zirv's own environment; an explicit allowlist makes what a repo-authored check can read from the operator's session an inspectable, operator-controlled list instead of "whatever zirv itself happened to have." A repo-settable passthrough list — a repo checkout already runs its own check commands with real credentials once `repo_checks_enabled` is on; letting it also choose which *extra* operator environment variables reach that child would widen, not narrow, the checkout's own trust boundary. A codex review round's finding that the allowlist itself "violates the operator-only trust boundary" — dismissed: the finding conflated the allowlist (a *guarantee* that named variables are present, resolved from the macOS login session via `launchctl getenv` when zirv's own process lacks one) with an isolation/scrubbing mechanism; the check child already inherits zirv's whole process environment unscrubbed, by design, the same trust posture `repo_checks_enabled` already grants it, so the allowlist narrows nothing and widens nothing about that inherited surface.
**Consequences:** A check needing a new credential-adjacent variable needs an explicit operator opt-in, not a code change. The macOS `launchctl` fallback is unverified against a real GUI-launched macOS zirv process — recorded as a residual, not blocking. See [[Command Safety]] and [[Untrusted Configuration]] for the "guarantee, not a boundary" framing spelled out for future readers of this allowlist.
**Spec / link:** `src/commands/workflow/verification.rs`'s `DEFAULT_CHECK_ENV_PASSTHROUGH`/`run_check`; `src/commands/ctx/config.rs`'s `check_env_passthrough`; [[Workflows]]'s Verification section; [[Untrusted Configuration]]; [[Command Safety]]; issue #233.

### 2026-08-31 — Reserved zirv built-ins are trusted; repo scripts and direct gh auth are not (issue #224)
**Context:** Supervised Claude sessions were prompted twice for Zirv's own mandatory commands: the safety hook turned their sandbox retry into `<sandbox: unsandboxed retry>`, and the generated settings kept credential-dependent `zirv report` inside the sandbox. The old issue #98 `Bash(zirv *)` workaround also silently allowed every repo-defined script.
**Decision:** Derive one built-in allow/native permission/sandbox-exclusion pattern per case-insensitive `utils::RESERVED_COMMANDS` name, because main dispatch handles those names before script lookup and a checkout cannot shadow them. Preserve `deny`/`ask` precedence so a repo may narrow; leave non-reserved `zirv <script>` unmatched. Exclude the outer `zirv report` process, whose implementation makes a fixed captured `gh auth token --hostname github.com` lookup, rather than allowing direct `gh auth *` or blanket `gh *`.
**Rejected:** Keep `Bash(zirv *)` — crosses the repo-script trust boundary. Add `~/.config/gh/hosts.yml` to sandbox `allowRead` — exposes the credential file to every sandboxed subprocess. Add `gh *` to `excludedCommands` — lets arbitrary GitHub CLI mutations and credential commands bypass containment.
**Consequences:** A new reserved name automatically enters every projection by changing the existing dispatch source of truth and therefore changes the policy fingerprint. Codex remains unchanged because it has no verified symmetric per-command settings projection.
**Spec / link:** `src/utils.rs::RESERVED_COMMANDS`; `safety.rs::reserved_zirv_command_patterns`; `claude.rs::launch_settings_value`; [[Command Safety]]; [[Ctx Adapters]]; issue #224.
### 2026-08-31 — Scripts move to `.zirv/commands/` via a hard cutover, no transitional root fallback (issue #212, v3.0.0)
**Context:** Every zirv script lived directly at the `.zirv` root alongside its config files (`ctx.toml`, `.settings.toml`, `verify.toml`, `.shortcuts.yaml`), so "is this file a script" depended on excluding a growing, hand-maintained reserved-name list rather than on where the file lived — the same class of fragility `RESERVED_ZIRV_FILES`/`is_reserved_zirv_file` already existed to paper over.
**Decision:** Scripts now resolve ONLY from `<repo>/.zirv/commands/` then `~/.zirv/commands/` (same local-shadows-global precedence as before), with no root fallback and no auto-migrate. `zirv init` creates `.zirv/commands/` at both scopes; `zirv create`/`--global` writes new scripts there; `.shortcuts.yaml` and every config file stay at the `.zirv` root, unaffected. The not-found error now names any stray root-level script file (up to 10, config never listed) with an explicit move instruction, rather than silently treating it as gone.
**Rejected:** A transitional period honoring both the root and `commands/` (script-at-root wins, or `commands/` wins with a root fallback) — would keep "is this file a script" ambiguous exactly as before, just for a defined grace window instead of forever, and would need its own removal PR later to actually finish the cutover. Auto-migrating root scripts into `commands/` on first run — a write-on-launch side effect an operator did not ask for, and indistinguishable from data loss if it moved the wrong file in an unusual layout.
**Consequences:** "Nothing at the `.zirv` root is a script" is now a simple, permanent invariant — no reserved-name list to keep in sync as new config files are added. This is a breaking change (v3.0.0, not a minor bump): an already-installed pre-3.0 binary cannot find a checkout's scripts once they move, since it still looks at the root — see [[Known Issues]]. This repo's own 11 `.zirv/*.yaml` scripts were `git mv`'d into `.zirv/commands/` in the same change.
**Spec / link:** `src/utils.rs`'s `COMMANDS_DIR_NAME`/`candidate_names_in_dir`/`script_like_files_at_root`; `src/input.rs`'s `find_script_in_dir`/`not_found_error`; `src/commands/{create,init,help}.rs`; [[Known Issues]]; issue #212.

### 2026-08-31 — `wrap` owns bracketed-paste mode on the operator terminal itself, instead of trusting the wrapped child's own request (issue #206)
**Context:** `wrap` only ever relayed a wrapped child's own DECSET 2004 request (`ESC[?2004h`) onto the operator's terminal, never issuing it itself — so bracketing only held once some child had asked and the request had landed: not before the agent finished starting, not during a relaunch's kill-then-respawn gap, and not at all for a harness build that never asks. Outside a bracketed span a pasted `\r` is indistinguishable from Enter, so an unbracketed multiline paste submitted one line per CR instead of landing as one paste — reproduced against the real probe-pty → `zirv ctx wrap` → ConPTY → `claude.exe` stack.
**Decision:** `term.rs`'s `RawGuard` now owns DECSET 2004 for the whole life of a wrap/chat session, independent of the child: `ESC[?2004h` on `enter` (Windows: only once VT output processing is confirmed on), `ESC[?2004l` on `restore`, idempotent across every exit arm, `Drop`, and the external-kill restore handler, tracked by a new `BRACKETED_PASTE` flag (the same shape as `KBD_ENHANCED`/`BAR_ACTIVE`), gated on stdout being a real terminal. A new `PasteGuard` filter, beside `CprFilter` on the operator-stdin thread, reassembles an `ESC[200~ … ESC[201~` span across arbitrary read boundaries — including a marker split across two reads — and forwards it as one write with markers preserved and contents untouched, bounded by a 1 MiB cap and a 5s deadline, never withholding a fragment under 3 bytes so a lone `ESC`/`ESC[` (an interrupt, an arrow key) is still delivered immediately.
**Rejected:** Newline-translating or otherwise reinterpreting a bare `\r` heuristically inside the pump — indistinguishable from a real Enter in the general case, and would need per-adapter tuning to avoid mangling legitimate single-line submissions. Adapter-specific key mapping — both claude and codex parse the same `ESC[200~`/`ESC[201~` markers, so nothing about the fix needs to know which harness is running.
**Consequences:** Bracketing now holds for the operator's entire session, including the pre-launch and relaunch windows a child-driven request could never cover. Any future terminal-mode concern with the same "some children ask, some don't, and the gap matters" shape should be owned by `RawGuard` the same way, rather than trusted to the wrapped program. Residual: no real human paste in Windows Terminal was exercised in the agent environment that built this fix — one manual paste on the built binary is recommended before merge.
**Spec / link:** `src/commands/ctx/term.rs`'s `RawGuard`/`BRACKETED_PASTE`; `src/commands/ctx/wrap.rs`'s `PasteGuard`; [[Ctx Supervisors]]'s "wrap" section; [[Known Issues]]; issue #206.

### 2026-08-31 — An oversized headless launch's WHOLE argv is budgeted, reusing #213's stdin fallback rather than a new mechanism (issue #220)
**Context:** Issue #213 (2026-08-30) shrunk an oversized composed system-prompt to `INLINE_ARGV_PROMPT_BUDGET_BYTES` before it ever reached an adapter's argv, but `exec.rs::build_headless` still routed the operator's own task prompt to argv unconditionally off a shim launch — a large task prompt (an operator's own, or a workflow review package's diff-heavy one) riding beside a near-budget system prompt on the same command line could still overflow Windows' `CreateProcessW` ~32KB ceiling (`os error 206`), the exact failure #213 was meant to close.
**Decision:** `build_headless` now measures `headless_argv_len` — the byte length of the whole assembled command (program plus every argument, the #213 system-prompt layer included) — and delivers the prompt via `adapter.headless_cmd_stdin` whenever that total exceeds the SAME `INLINE_ARGV_PROMPT_BUDGET_BYTES` #213 already established, in addition to the existing shim trigger. The child is spawned with piped stdio, never a PTY, for this delivery path.
**Rejected:** A private temp file for the prompt (mirroring claude's file-based system-prompt delivery) — `headless_cmd_stdin` already exists, is already exercised on every shim launch, and needs no new file-lifetime/cleanup contract. A separate, smaller budget just for the task prompt — the two texts share one command line, so only their combined length is the real constraint; budgeting them independently could still overflow the same ceiling.
**Consequences:** `build_headless` is the one chokepoint every headless launch, relaunch, nudge, and park reuses, so this fix covers all of them uniformly rather than needing a fix per call site. Any future inline-argv-only adapter constraint should measure the WHOLE assembled command, not one argument in isolation — the same lesson #213's own review round already learned for the system-prompt layer alone.
**Spec / link:** `src/commands/ctx/exec.rs`'s `headless_argv_len`/`headless_prompt_via_stdin`/`build_headless`; `src/commands/ctx/prompt.rs`'s `INLINE_ARGV_PROMPT_BUDGET_BYTES` (reused, not duplicated); [[Ctx Subsystem]]'s "Chat, Agent and Mail" section; [[Ctx Adapters]]; issue #220.

### 2026-08-31 — Directed mail follows its delivery envelope; mailbox-scoped mail does not follow a session across cwd slugs (issues #219/#226)
**Context:** Issues #219 and #226 were the same addressed-mail failure through different cwd drift (worktree and subdirectory): delivery filed under the target's registered repo slug, while readers started from the cwd slug. Main first widened reads to both mailboxes; PR #234 independently resolved the addressed file through its delivery envelope, and merging both duplicated directed results while the registered-mailbox scan also exposed undirected mail across slugs.
**Decision:** `list(..., for_session = Some(short))` unions the cwd mailbox with only session/role delivery-envelope targets naming `short`, then sorts/deduplicates by path. `unread_counts` and consuming inbox reads reuse that list; `--peek` keeps its broad cwd view and unions only the caller's own directed paths. `consume` derives `read/` from the message's actual path.
**Rejected:** Keep both scans — double-counts and can consume a directed message twice. Keep only the registered-slug scan — broadens undirected and claim-once visibility beyond the cwd mailbox, contrary to #226's boundary. Canonicalize worktree paths — changes every other `repo_slug`-keyed state surface.
**Consequences:** A session receives addressed mail from any cwd and `send --status` advances, without widening undirected, claim-once, or fan-out delivery. Future per-session read surfaces should reuse envelope targets rather than scan a second whole mailbox.
**Spec / link:** `src/commands/ctx/mail.rs`'s `directed_paths_for`/`list`/`consume`/`run_inbox_with`/`unread_counts`; [[Ctx Subsystem]]; [[Known Issues]]; issues #219/#226.

### 2026-08-30 — The test/deploy gate's baseline is operator-owned under `~/.zirv`, subset-of-names semantics, explicit recording only (issue #215)
**Context:** `zirv workflow advance`'s test/verify step demanded an outright-passing `zirv test` report, hard-failing on any named test failure — structurally unpassable on a host with a documented, pre-existing per-host baseline of failing test names (this Windows dev machine's own `wrap`/`exec` set), even when a branch introduces zero new failure names.
**Decision:** A gate that would otherwise fail may still pass when every failing test *name* in the report is a member of an operator-recorded `TestBaseline`, stored at `~/.zirv/test-baseline/<repo_slug>.json` — never under `<repo>/.zirv/`, since a checkout is untrusted and may only narrow what it can do, never grant itself an exemption from its own tests. ### 2026-08-27 — Dedupe proof is byte-exact against a fresh render, not the native file's self-declared header hash (issue #155, Phase 3, v2.35.0)
**Context:** Independent review of the first `native_file_already_carries_canonical` (commit `90523d3`) found it compared the native file's OWN embedded `<!-- zirv:canonical-sha256:... -->` header claim against a hash of the current `.zirv/context/` sources — but never checked the native file's actual BODY against anything. A probe confirmed the exploit: generate `CLAUDE.md` correctly, then hand-edit only the body while leaving the marker/hash header lines untouched (no change to `.zirv/context/`) — the header's claim still matched the sources, dedupe fired, and the session received zero of the real canonical text.
**Decision:** The header hash is now only a cheap pre-filter (skip the expensive path fast when the sources have plainly moved on). **Consequences:** `native_file_already_carries_canonical` now literally re-renders the expected file on every check. Cheap in practice (`.zirv/context/` files are capped at 4096 bytes each by the existing injection budget), so this was not treated as a perf concern. `context_status.rs`'s per-harness report also gained a `[DEDUPED]` marker (checked after `[TRUNCATED]`) — the prior code showed a deduped surface as "NB raw, 0B delivered" with no flag at all, indistinguishable from a bug.

### 2026-08-26 — Memory becomes one deduped layer, moved to the composed-prompt tail (issue #155, v8, v2.33.0)
**Context:** `prompt::compose` used to splice memory in early as two separate layers — core (private+shared bank) and retrieval (working-tree-relevant recall) — even though an entry selected by both rendered its whole `describe()` text twice, and because retrieval's own ranking reads changed working-tree paths, that early placement invalidated a provider's prompt cache for every layer composed after it on every turn a file changed.
**Decision:** `compile.rs` now composes memory itself, after `prompt::compose` and after the canonical `.zirv/context/` layer: `gather_memory` selects core, then folds in only the retrieved entries the core selection didn't already claim (`merge_memory_layers`, keyed on `(shared, key)`), and `prompt::with_memory_layer` renders that one list once, capped at `core_max_bytes + retrieval_max_bytes`. ### 2026-08-25 — The heavy-worker budget refuses outright rather than queueing a launch over the limit (issue #133)

### 2026-08-24 — The injection settle gap is a hardcoded const, enforced as a polled deadline, not a blocking sleep (issue #114, v2.25.2; amended same day, review F1/F2/F4, PR #116)
**Context:** Fixing codex's paste-burst CR-fold (see [[Known Issues]]) needed a delay between writing an injected line and writing its submitting `\r`. A `.zirv` config key would fit this repo's usual pattern for a timing knob (e.g. `dash.idle_quiet_ms`), but this machine's own documented gotcha is that an older, already-installed zirv binary hard-fails outright on an unknown settings key — so shipping a new key here would force every operator through a coupled binary-then-config rollout for a value nobody is actually expected to tune. The value's shape as a delay, not just its config-vs-const status, turned out to need its own decision: the first cut of this fix (`write_two_phase_injection`) enforced the gap by blocking the *calling* thread for `INJECTION_SUBMIT_DELAY` between its two writes — on the dashboard that thread is the single UI thread every sweep shares (`mail_sweep`, `report_back_reminder_sweep`, `deliver_queued_nudges`, each iterating every pane in one tick), so a handful of injections in the same tick could serially freeze redraw and input for the sum of their delays — up to ~1.35s across nine panes and three sweeps (finding F1). It also stamped `injected_awaiting_turn`/`last_local_input_at` only after the blocking second write succeeded, so a failed phase-2 write left both flags unset and a retry sweep typed a whole second line on top of the still-unsubmitted first (finding F2).
**Decision:** `pane::INJECTION_SUBMIT_DELAY` stays a plain `const Duration = Duration::from_millis(50)` in `pane.rs` — the const-vs-config-key call is unchanged — but the mechanism became a **deferred, tick-drained submit** instead of a blocking sleep: `write_injection_phase1` writes only the line and returns immediately; `Pane::inject_visible` stamps pane state (`injected_awaiting_turn`, `last_local_input_at`) right away and records a `pending_submit` deadline (`Instant::now() + INJECTION_SUBMIT_DELAY`); a new `drain_pending_submits`, called every tick from `dash::mod::run_dashboard` (unthrottled — a 50ms deadline needs checking far more often than the ~1s facts cadence), writes the lone `\r` via `write_submit_cr` once the deadline has passed, and `Pane::write_operator_input` also drains a pane's own pending submit eagerly before an operator's keystroke reaches the composer. A failed `\r` write leaves the deadline set for a safe retry — `write_submit_cr` never re-sends phase 1, so a retry's worst case is one harmless extra Enter keypress, never a doubled line. **Superseded 2026-08-25 (issue #118):** `wrap.rs`'s own local `PendingSubmit { deadline, kind }` sharing this shape for `Action::Compact` and the T13 mail advisory (review F4) was later reverted — see the 2026-08-25 entry below for what `wrap.rs` does instead and why.
**Rejected:** A new `dash.injection_submit_delay_ms` key mirroring `idle_quiet_ms` — correct in spirit, but ships a footgun for exactly the operators this fix is meant to help (an un-upgraded binary reading a repo/home `ctx.toml` that already has the new key); this half of the original decision still stands. Keeping the blocking-sleep shape and just shortening the delay, or moving the sleep onto a background thread — a shorter delay does not fix F1's freeze, only shrinks it, and a background-thread sleep re-introduces exactly the "stamp state only after the delay" ordering that caused F2's double-type, just off the UI thread.
**Consequences:** The 50ms figure can still only be changed by shipping a new binary, not by editing config. The gap the child's TUI actually sees may now run one dashboard tick longer than 50ms under load, which is fine — nothing about the paste-fold fix requires the gap to be exact, only that it not collapse to zero. `Pane::pending_submit` must be cleared on any path that invalidates the child a `\r` was owed to (`Pane::handover` does this; see [[Ctx Supervisors]] "Pane model").
**Spec / link:** `src/commands/ctx/dash/pane.rs`'s `INJECTION_SUBMIT_DELAY`/`write_injection_phase1`/`write_submit_cr`/`Pane::{pending_submit,pending_submit_due,submit_pending}`; `src/commands/ctx/dash/mod.rs`'s `drain_pending_submits`; [[Ctx Supervisors]] "Injection semantics"; [[Known Issues]]; issue #114; PR #116.

### 2026-08-24 — The supervisor's final drain is a bounded blocking read, not another non-blocking one (v2.25.1)
**Context:** `exec.rs`'s and `run_loop.rs`'s post-`supervise_child` "final drain" existed specifically to catch a fast-exiting child's last output line (a usage-limit notice) before `pace::scan_for_limit` gave up — but it called `OutputTap::try_lines()`, the same pure, instantaneous, non-blocking drain every regular poll tick already uses, which has no synchronization against `spawn_tapped`'s reader threads actually reaching EOF. It could lose exactly the race it was written to close, and a deterministic repro (`supervise.rs`'s test module) proved it did.
**Decision:** Added `OutputTap::drain_to_eof(budget)`: drains whatever is already queued, then blocks — only as long as it actually takes — for the reader thread(s) to either deliver more lines or disconnect (`recv_timeout` against a deadline), up to `supervise::FINAL_DRAIN_BUDGET` (500ms). The short id is therefore identical before and after a swap from e.g. claude/sonnet to codex/gpt-5.6-terra, by construction rather than by a check. Cross-harness argv/turn-env assembly is factored into `handover::resolve_swap_launch`/`build_turn_env`, called by both live-swap sites so they cannot drift.
**Rejected:** Minting a fresh session id and re-registering under a new short (mirroring `exec`'s per-restart identity) -- `exec` can afford that because nothing outside the process addresses a headless run by its old id; an interactive seat's whole point here is staying reachable at a *stable* address across the swap.
**Consequences:** A handover is indistinguishable, from the registry's point of view, from an ordinary restart -- any future change to `adopt_child_pid`'s contract must keep holding for this seam too. Both models are named in the decision-log entry the swap itself writes (`verb: "wrap", action: "handover"`) and in the `zirv ▸ handover: ...` announcement.
**Spec / link:** `wrap.rs`'s `perform_handover_swap`; `handover.rs`; `dash/pane.rs`'s `Pane::handover`; [[Ctx Subsystem]], [[Ctx Supervisors]]; issue #84.

### 2026-08-23 — `[safety]` folds `deny`/`ask` as a union, `allow`/`default` as REPO_FORBIDDEN, not one uniform stance fold (issue #83)
**Context:** `[policy]`'s existing fold (`max` over an ordered `Stance`) works because every capability has one scalar with a single "more restrictive" direction. `[safety]` has three lists plus a default verdict; a repo adding a `deny`/`ask` pattern is always narrowing (both are checked before `allow`), but adding an `allow` pattern or changing `default` has no narrowing reading at all — there is nothing for a `max`-style fold to bound either against.
**Decision:** `deny`/`ask` are lifted whole out of each `ctx.toml` layer and unioned (the same treatment `sandbox.extra_deny` already gets); `allow`/`default` are `REPO_FORBIDDEN` outright, mirroring `sandbox.extra_allow`. The built-in rule set is derived from `adapters::SHIPPED_POSTURE_ALLOW`/`_DENY` (stripping each `Bash(...)` wrapper) rather than duplicated, and `ClaudeAdapter::default_sandbox_args` now projects the resolved `SafetyPolicy` back onto claude's vocabulary — byte-identical to the old hardcoded projection under the shipped default (pinned by a dedicated test).
**Rejected:** One uniform `Stance`-style fold for all four fields — would either forbid `deny`/`ask` from being repo-narrowable at all (losing real narrowing capability) or require inventing a `max` over glob-pattern lists, which isn't a meaningful operation.
**Consequences:** The claude `PreToolUse` hook (`zirv ctx safety check`, wired by `zirv setup apply`, claude only — codex has no verified equivalent of the `permissionDecision` JSON contract) is now the single evaluator backing the CLI, the adapter projection, and the wired hook.
**Spec / link:** `src/commands/ctx/safety.rs`; [[Command Safety]]; [[Untrusted Configuration]]'s "A third fold, now for `[safety]`"; issue #83.

### 2026-08-23 — `zirv ctx send --all` fans out via per-session read tracking, not per-session copies (issue #94)
**Context:** An undirected `zirv ctx send` (`to_session: None`) is deliberately first-come-first-served (2026-08-22 entry below) — right for the work-queue case, wrong for "notify every live session," which had no real mechanism of its own. Adding one meant choosing between storing a separate copy per live session at send time, or storing once with per-session read state.
**Decision:** Per-session read tracking. `--all` stores one message under the mailbox's own `fanout/` subdirectory (`store_fanout`, sharing `store_to`'s truncation/pruning/collision logic via a new `store_into`); `mail::list` shows it to any session whose own `<base>.read/<short>` marker is absent, and `consume_reading` (used by both `consume_and_log` and `zirv ctx inbox`) marks that marker instead of moving the file, so one session's read never affects another's. No new `Message` field, so none of the ~40 existing `Message { .. }` literals across the codebase needed touching.
**Rejected:** Per-session copies at send time — cannot serve a session that has not launched yet (no address to copy to), and duplicates storage/pruning logic `store_to` already has.
**Consequences:** Late-joiner rule falls out for free: a session that only registers after the send simply has no read marker yet, so it sees the message as unread on its first read, identical to every session that was already live. Undirected `to: "any"` is untouched — a separate code path, separate directory, separate tests.
**Spec / link:** `mail.rs`'s `list`/`store_fanout`/`consume_reading`; `SendArgs::all`; [[Ctx Subsystem]]'s mail section; `prompt.rs`'s `HARNESS_PROMPT` (v9).

### 2026-08-23 — A parse failure in `ctx.toml` degrades one layer, *except* a broken HOME layer for a verb that launches a harness
**Context:** A stray keystroke in the untrusted repo `.zirv/ctx.toml` (e.g. a bare `1`) made `toml::from_str` error inside `CtxConfig::load`, which propagated out of every one of its ~30 call sites — including `zirv help`... no, including `zirv ctx status`, the verb an operator would reach for to diagnose exactly this. `status` also caught every kind of `CtxConfig::load` error identically (inline on the `chat:` line, always exit 0), unlike every other ctx verb (exit 1 on any load error) — no distinction between a security refusal and a merely-broken file. The first fix (below, superseded in its "either layer, always skip" half) made a broken *home* layer degrade to defaults the same way as a broken *repo* layer — but the home layer is the operator's own stricter `[pace]`/`[policy]`/`[sandbox]` settings, and a launching verb (`wrap`, `exec`, ...) silently falling back to permissive defaults right before spawning a harness under them is a security regression a review round (finding #1) caught.
**Decision:** `read_layer` catches a TOML *syntax* error per layer (home or repo) and returns it as an `UnparsableLayer { path, message, is_home }` instead of propagating: that layer contributes nothing, defaults/the other layer apply, and `CtxConfig::unparsable_layers` records it — announced once per process (`Event::ConfigUnparsable`) and surfaced by `status`/`optimize`. Plain `CtxConfig::load` still treats both layers identically (skip and continue) — used by read-only/diagnostic verbs (`status`, `optimize`, `safety list`/`explain`). A new `CtxConfig::load_for_launch` wraps `load` and additionally refuses outright (naming the file, line:col, and the fix) if any entry has `is_home == true`; every verb that actually launches or supervises a harness (`chat`, `wrap`, `exec`, `loop`, `agent`, `handover`, and `dash` via `wrap::run_with`) calls this instead of plain `load`. A `REPO_FORBIDDEN` rejection (a key that *did* parse) still fails the load outright either way and is distinguishable via `config::is_repo_forbidden`. `status` uses the kind split: still renders fully either way (it's the diagnostic verb), but exits `1` with a prominent `CONFIG REJECTED: ...` line only for a `REPO_FORBIDDEN` `Err`; a skipped-unparsable layer (no longer even an `Err`, and `status` itself never calls `load_for_launch`) or any other load error keeps the pre-existing "exit 0, name it inline" behaviour.
**Rejected:** Keeping the layer's parse failure fatal everywhere and only softening `status`'s handling — leaves every other verb (`hook`, plain script `Agent` steps) still broken by a repo-layer stray keystroke, which is untrusted input the checkout controls, not the operator's own file. Making *every* parse failure (home or repo) fatal for a launching verb — would turn a stray repo keystroke, reachable by anyone who can put a `.zirv/ctx.toml` in a checkout, into a denial-of-service against `wrap`/`exec` themselves. Adding a `load_mode` enum parameter to `load` instead of a second entry point — every one of `load`'s ~30 call sites would need updating to pass a mode explicitly; a wrapping function only the six launching verbs opt into is a smaller, more auditable diff.
**Consequences:** `workflow::repo_gates`'s fail-closed `Err` arm no longer fires for a pure repo-layer syntax error (it now reads the operator's real home/default values instead, since `repo_checks_enabled`/`repo_skills_enabled` are `REPO_FORBIDDEN` regardless) — only for a genuinely unreadable/rejected config, or (for the workflow subsystem's own `load` calls, which stay on plain `load`) never for a home-layer parse failure either. `zirv ctx optimize` reports each unparsable layer as a `Finding` rather than its old blanket "config load failed" line. A future launching verb must remember to call `load_for_launch`, not `load` — there is no compiler check that forces this, only the convention and this entry.
**Spec / link:** `config.rs`'s `read_layer`/`UnparsableLayer`/`is_repo_forbidden`/`load_for_launch`; `status.rs`'s `run_with`; `announce.rs`'s `Event::ConfigUnparsable`; [[Untrusted Configuration]], [[Ctx Subsystem]].

### 2026-08-23 — Unmeasurable workflow risk fails safe (escalate one band), not open
**Context:** Classification's Git-based safety net treated "I could not measure the blast radius" (no repository, or one with no commits) as identical to "I measured it and it was fine": `classify.rs`'s declared-scope path and `engine.rs`'s `reclassify_at_gate` both silently kept the declared/prior risk band when Git measurement failed, so a mis-declared low-risk scope stood unchallenged exactly where zirv can see least (issue #88).

### 2026-08-22 — `pace.enabled`/`max_percent`/`soft_percent` become repo-narrowing-only (T9), revisiting the "already theater" call
**Context:** An operator reported sessions running past their usage window limit despite pacing being on. Investigation found the gate itself failed open on no/stale data (fixed separately, T8) and, checking hypothesis 5, that `pace.enabled`/`max_percent`/`soft_percent` were plain repo-mergeable — a checked-out repo could set `enabled = false` and silently disable the spend gate for anyone running zirv there. `soft_percent`'s own doc comment had accepted this as fine ("a repo can already set `enabled = false`, so forbidding the band alone is security theater") back when pacing was advisory; it is a spend gate now.

### 2026-08-22 — `zirv setup restore` always takes its own backup before overwriting anything
**Context:** `restore` recovers a `reset`/`apply` backup by writing it back over the current state, but the operator may have made real changes since — a plain restore could silently destroy work to bring back older work, "moving the problem" rather than solving it (issue #80's design intent).
**Decision:** `restore_run` calls the same `write_backup_run` helper `reset`/`apply` use, with `kind: "restore"`, over the current on-disk state of every target it is about to touch, *before* any target is written — landing in the same versioned root the restored run came from. So a restore is itself one more entry in `restore --list`, undoable by a further restore.
**Rejected:** An opt-in `--backup-first` flag — makes the unsafe path the default, exactly the "never silently" property `reset` already established for this whole surface. Skipping the self-backup when `--list` classifies the target as `identical` — an extra branch to save one small, cheap copy, for no real safety gain.
**Consequences:** Every restore leaves behind one more backup run; issue #95 (2026-08-23, see below) closed the unbounded-growth consequence with count-cap retention on every write.

### 2026-08-23 — Backup retention pins the oldest run and excludes it from the cap entirely
**Context:** Issue #95: `.zirv/backups/ai-reset` grew unbounded (see the 2026-08-22 entry above), and a restore now takes its own backup too, roughly doubling the rate. A naive "keep the newest N" would eventually delete the operator's original, pre-zirv configuration — the one backup restore exists to protect.
**Decision:** `prune_backup_runs` sorts runs by `manifest.created`, always keeps the single oldest regardless of `keep`, and applies the cap only to the rest (`keep` bounds runs *after* the pinned one, so `keep + 1` total typically survive). Called from inside `write_backup_run` itself (all four call sites get it for free), resolved fresh via a new `[setup] backup_retention_runs` config key clamped like `workflow.telemetry_max_events` (`resolve_backup_retention_runs`). `restore --list`/`print_restore_list` never calls it, so listing stays read-only.
**Rejected:** A time-window cap (mirroring `telemetry_retention_days`) — a backup run's value is its position in the sequence ("the last N configs"), not its age. A separate pruning implementation — reuses `discover_runs`'s existing manifest-driven enumeration instead.
**Consequences:** `.zirv/backups/ai-reset` is now bounded per root; the oldest run is permanent unless removed by hand. `setup.backup_retention_runs`/`memory_harvest_offered`/`statusline_wrap_offered` are deliberately NOT `REPO_FORBIDDEN` — none of them gate execution of repository content or spend, only local disk bookkeeping and whether a guided prompt re-asks.

### 2026-08-22 — An undirected `zirv ctx send` is first-come-first-served, inherited from the work-queue mechanism, not chosen for broadcast
**Context:** `mail::run_send_with` with no `--to-session` stores `to_session: None`, visible to every session `mail::list`'s `session_visible` rule matches — but every consumer (a worker's sweep, `zirv ctx inbox`, exec/loop's drain) is single-shot: whichever session reaches the message first consumes it, and every other eligible session sees nothing, silently. The 2026-08-19 entry below endorses only a narrower claim ("broadcast mail addressed to `\"any\"` worker of an agent is deliberately still claimable by any matching session") — a work-queue reading, "assign to whichever worker is free" — not a fully undirected send meant to notify several live sessions at once.
**Decision:** Treat this as emergent, not deliberate: the storage model was built for the queue use case, and the fully-undirected case inherited its semantics as a side effect of the same `to_session: None` mechanism. Keep the existing storage/consumption model (it is genuinely correct for the queue case, and still lets a session that has not launched yet pick a message up later) and make the behavior visible instead: `run_send_with`'s confirmation line and `HARNESS_PROMPT`'s `zirv ctx send` bullet (v8) now both say plainly that an undirected send is claimed by exactly one session, and name `--to-session` as the way to mean one specific session.
**Rejected:** Fan out to every live session — a snapshot at send time cannot reach a session that starts later, which the queue mechanism depends on, and it multiplies storage per recipient. Requiring an explicit target — breaks the legitimate "whichever worker is free" queue case and is a breaking CLI change.
**Consequences:** A genuine "notify every live session" primitive is new functionality, filed separately, not a fix to this mechanism.
**Spec / link:** `mail.rs`'s `run_send_with`; `prompt.rs`'s `HARNESS_PROMPT` (v8); the 2026-08-19 entry below.

### 2026-08-21 — Stacked topic branches merge by retargeting to `main` and merging only the stack's top PR
**Context:** The memory and context reworks were each developed as a stack of small, reviewable PRs (memory: #57→#58→#62→#64→#66; context: #60→#61→#63→#65, then #67 on top of that). Merging each PR into `main` in sequence would cost one version bump and one release per PR — five releases for one coherent topic.
**Decision:** Retarget every PR in a stack's base to `main`, then merge only the top PR; GitHub resolves the lower PRs in the stack as merged too, since their commits are already ancestors of the top's once the stack lands. One version bump and one CI/release cycle per topic, not per PR.

### 2026-08-21 — `memory.enabled` is a master switch over both scopes; `shared_enabled` only narrows the shared one
**Context:** The shared, repo-committed memory scope had to compose with the pre-existing private scope's own on/off flag without an operator who disabled memory before the shared scope existed silently starting to receive repo-controlled prompt content on upgrade.
**Decision:** `MemoryScope::enabled(cfg)` is the sole choke point: `cfg.memory.enabled == false` disables both scopes outright; `cfg.memory.shared_enabled` is a second, shared-only toggle consulted only once the master switch is already on. Both fields are `REPO_FORBIDDEN`.
**Rejected:** Two independent flags with no ordering — a caller reading `shared_enabled` on its own could get the shared scope on despite the operator's own master switch being off, since nothing forced the check through one function.
**Consequences:** Every scope-gated caller (`memory_cli.rs`'s verbs, the prompt injection layer) must call through `MemoryScope::enabled`/`disabled_reason` rather than reading either config field directly, or a new call site could reintroduce the ordering bug this closes.

### 2026-08-21 — Private memory structurally outranks shared, by partition and suppression, never by score
**Context:** A shared, repo-committed memory scope sits alongside the operator's own private one in the same injected prompt block. A repo-controlled entry could otherwise compete for budget on equal footing with a private fact, pick the same key to shadow what that key means to the reader, or embed a copy of the block's own closing marker to forge where untrusted content ends.
**Decision:** `select_memory_within_cap` fills the private group's budget first and gives shared only what remains (a structural partition, not a weighted score); a shared entry whose key case-insensitively collides with a private one is dropped entirely, and so is a shared entry whose body contains the block's `SHARED_BLOCK_END_MARKER` (case-insensitively).
**Rejected:** A trust-weighted score that ranks private above shared but still lets a strong shared entry win when private has little content — reintroduces the "trusting the data" failure mode partitioning exists to avoid; a repo can already control how much content it produces.
**Consequences:** A repo with no shared memory (or an all-private selection) renders exactly as before the shared scope existed. Both suppressions count toward the same shared-omitted total `with_memory_layer` reports, so a suppressed entry is not silently invisible.
**Spec / link:** `src/commands/ctx/prompt.rs`'s `select_memory_within_cap`; [[Known Issues]] for the residual it does not close.

### 2026-08-21 — The always-injected core memory layer ranks on verification recency, not the `importance` field
**Context:** Two different consumers read the same memory entries: the core layer injected at every launch seam (budget-capped, no query to rank against) and the query-driven `zirv memory recall` retrieval engine. `importance` is repo/operator-supplied text on a shared entry, the same untrusted-signal class `Source`/`Written-By` already are.
**Decision:** The core layer's `ranked_by_recency` sorts strictly by `verified` then `written` (most recently confirmed first) and never reads `importance`. The separate retrieval engine (`retrieval.rs`) does use `importance`/`confidence` — but only as a modifier refining an already-relevant match, never as a way to manufacture relevance from an empty or unrelated query.
**Rejected:** Letting the core layer's selection read `importance` too — a repo-writable field would then let a shared entry buy guaranteed injection regardless of staleness, the trust asymmetry the retrieval engine's own "modifier, not floor" rule was built to avoid.
**Consequences:** An operator who wants to pin a specific fact into every session has no lever for that today beyond keeping it verified; revisit if that need becomes concrete, without touching the retrieval engine's own, already-shipped use of `importance`.
**Spec / link:** `src/commands/ctx/prompt.rs`'s `ranked_by_recency`; `src/commands/ctx/retrieval.rs`'s scoring; issues #31–38.

### 2026-08-21 — An unreadable ctx config closes the repo-input gates rather than opening them
**Context:** The `[workflow]` gates each resolved the config on their own. On an unparseable `.zirv/ctx.toml` — a file the repository checkout itself supplies a layer of — the skill gate defaulted to *enabled* (a malformed config forced the untrusted layer back on) while verification propagated the error (the same file bricked `zirv test`/`zirv verify` in that checkout). Two different wrong answers from one condition.
**Decision:** One resolver, `workflow::repo_gates`, fails closed on both: no repo-provided checks, no repo-provided skills, a `zirv ▸` notice naming the parse error, and everything zirv owns itself (built-in skills, discovered toolchain checks) still working. The vacuity question is answered separately and deliberately: a `final_check` of `true` stays *visible* (per-check provenance in every report) rather than rejected, because "is this command a real test" is not decidable and a plausible-looking command can be equally vacuous.
**Rejected:** Fail open on an unreadable config — a checkout can write the file that fails to parse, so that is a widening primitive. Propagate the error — a repository would be able to disable its own verification entirely, which is worse than running fewer checks. Heuristics over command bodies (reject `true`, `:`, `exit 0`) — trivially evaded, and they would give a false sense that surviving checks are meaningful.
**Consequences:** An operator with a broken config gets a degraded but working workflow subsystem and a notice, not a hard stop. `repo_checks_enabled` stays default-true on purpose: executing a repository's own checks is the feature, the same posture as executing its `.zirv/` scripts, with the key as a `mail.enabled`-style kill-switch.
**Spec / link:** [[Workflows]], [[Untrusted Configuration]], PR #59.


### 2026-08-21 — Repository-authored checks and skills answer to operator-only `[workflow]` keys
**Context:** PR #59's review found the workflow subsystem's untrusted-input handling weaker than the rest of the codebase's: `.zirv/verify.toml` commands and `package.json` scripts reached `sh -c` with repo-chosen timeouts up to 24h and no operator switch, a repo skill silently replaced a built-in's methodology text by id, and telemetry retention came from plain `ZIRV_WORKFLOW_TELEMETRY*` environment reads any repo script could set for itself.
**Decision:** A new `[workflow]` config section, `REPO_FORBIDDEN` per key, mirroring `mail.enabled`: `repo_checks_enabled` (off = repo-supplied checks listed with a skip line, never executed, never passing evidence), `repo_skills_enabled`, and three `telemetry_*` keys. Caps that hold regardless of the gate: repo timeouts clamped to 900s, repo checks truncated to 32, both noted in the report; every check records its source (`repo-config`, `discovered-script`, `discovered-toolchain`). A repo skill may only add ids; a collision is ignored and warned.
**Rejected:** Refuse an over-long repo timeout outright — a clamp keeps the check useful and the note keeps it honest. Treat Cargo and npm discovery identically — `npm run <id>` executes a body written in the checkout's own package.json, while the Cargo commands are zirv's text; collapsing them would either over-gate the toolchain or under-gate repo scripts. Let a repo skill override with the untrusted label as the only guard — a label does not stop the text from replacing `review`'s or `verify`'s methodology.
**Consequences:** An operator who disables repo checks still sees what the repository wanted to run. A skipped check cannot satisfy a step gate, so a disabled gate fails closed. Adding a `[workflow]` key means adding it to `REPO_FORBIDDEN` too, or the section's guarantee is only partly true.
**Spec / link:** [[Workflows]], [[Untrusted Configuration]], PR #59.

### 2026-08-21 — Risk is re-measured at gated steps and declared inputs can only raise it
**Context:** Classification was computed once at `workflow start` and frozen. For the usual order of work — start the workflow, then write the code — that measured an empty tree, so the review step was decided before the change existed. Separately, `--path`/`--changed-lines` switched Git measurement off entirely, so declaring a README edit talked a real auth-file change from High down to Low and dropped its review step.
**Decision:** Declared and measured classifications are both computed and the higher risk band wins, with `declared_scope: true` recorded. Advancing *into* a review or verify step re-measures and takes the max, adding a missing review/verify step if the new band requires one. `classify` now shares `review`'s merge-base diff base so both subsystems mean the same thing by "the change".
**Rejected:** Refuse a declared scope that disagrees with the tree — a dirty unrelated file would then block a legitimate declared classification. Re-materialize the full step list at a gate — a design approval gate appearing after the implementation is finished is ceremony, not safety, so only Review/Verify steps are added. Re-measure on every advance — the gated steps are where the decision actually matters.
**Consequences:** A workflow's risk band can rise mid-flight and never falls; the reason line records why. A repository with no Git history keeps the start-time classification, and the reason says the measurement was unavailable.
**Spec / link:** [[Workflows]], PR #59.

### 2026-08-20 — Workflow history is durable state; only the current skill is prompt context
**Context:** A methodology implemented as an always-loaded handbook consumes tokens every turn, and conversation-only progress repeats completed work after compaction/resume. The pending shared Context Compiler must not own workflow state itself.
**Decision:** Persist schema-versioned workflow steps/status/attempts/approvals/findings under Zirv's private state directory. `engine::active_skill_context` renders only the current step's dependency-resolved skill stack; prompt v6 adds that one replaceable layer. Skills name logical Zirv capabilities and never provider tools.

### 2026-08-20 — Deterministic mechanics live in Zirv; model judgment is bounded to selected skills
**Context:** Repeatedly asking models to rediscover test commands, choose review depth, carry raw logs, and run open-ended fix loops caused latency and token overhead. Those decisions have stable repository signals and safety limits.
**Decision:** Zirv classifies path/line/sensitive-surface risk deterministically, selects workflow steps, maps changed paths to configured/discovered checks with full fallback, fingerprints verification, caps review diff/log payloads and retries, and retains only structured telemetry. Models receive concise judgment instructions for the active phase.

### 2026-08-19 — Dashboard click-drag text selection copies via OSC 52, scoped to panes that don't want the mouse themselves (uncommitted, extends PR #29)
**Context:** Enabling any mouse reporting at all (`?1000`/`?1006`) already displaced the terminal's own native click-drag text selection, and nothing in the dashboard offered a replacement — selecting text out of a pane was simply impossible, a real regression against a plain terminal.
**Decision:** Turn on `?1002` (button-drag tracking — motion reported only while a button is held, unlike `?1003`'s free-running flood) and give it a consumer: a left click-drag over a pane whose child does **not** itself want mouse reporting (`Pane::wants_mouse`) selects text (REVERSED highlight, `Selection`'s ordered `(row, col)` pair), and release copies it to the system clipboard via an OSC 52 escape sequence written to the host stdout — inline base64, capped at 64 KiB, best-effort. ### 2026-08-19 — The dashboard's adaptive input-poll wait is refreshed only by operator input, never by pane output
**Context:** The event loop's first `event::poll` wait was a flat 50ms every tick. Keystrokes still reached a pane's pty instantly, but the repaint showing the child's own echo of them waited out the same 50ms, so typing felt debounced. The fix needed a "hot" short-poll window without multiplying the loop's wakeup rate for a dashboard that is otherwise idle or busy streaming a response.
**Decision:** `input_poll_wait(since_activity)` picks 10ms inside 300ms of the last activity, else the old flat 50ms; `last_activity` is a plain `Instant` refreshed **only** when the event actually read from crossterm is a `Key` or `Mouse` event. Pane output (a child streaming, an animated spinner, an injected mail/nudge line) never touches it.
**Rejected:** Refreshing the window on any pane activity too, so a busy pane also got fast repaints — a streaming response or spinner is the *normal* state of an active dashboard, not a rare burst like a keystroke; doing this would hold the whole tick (pane drains, spawn-request `read_dir`, sidebar rebuild, draw) at ~100/s for as long as any pane kept producing output, which is most of a session's wall-clock time, not the ~300ms a burst of typing costs.
**Consequences:** Idle and streaming CPU are provably unchanged by this fix — only genuine operator keystrokes/mouse events cost the extra ticks, bounded to 300ms after the last one. A future input-adjacent latency fix should refresh the same clock rather than inventing a second one; a fix that wants pane-output responsiveness too needs its own justification against the CPU cost this decision explicitly rejected.

The adapter layer was role-blind, so a delegated headless worker received claude's `ORCHESTRATOR_PROMPT` — "delegate every substantive piece of work to subagents" — which is exactly the recursion `zirv agent` workers must not do, and the operator's `~/.zirv/system-prompt.md` went to workers whether or not it was written for one.

Exactly one adapter layer reaches any launch. The bare `zirv ctx wrap` verb switched from `Worker` to `Orchestrator`, which is what it always was in substance — an operator driving a command themselves, the seat CLAUDE.md classes with `chat`.
**Rejected:** Keeping one shared user file and letting the adapter layer stay role-blind — the layer's own text is what invites the recursion, so scoping the harness layer alone was never the whole fix. ### 2026-08-18 — Live mail delivery still never hands an orchestrator a message body, only a one-line advisory
**Context:** Mail delivery had stayed advisory-only for every interactive session (`chat`/`wrap`, and a dashboard's orchestrator pane) since the original mail design — a human at the keyboard could always run `zirv ctx inbox`. That advisory previously only ever reached stderr/a header segment, so an operator not watching the chrome could miss it indefinitely, and a signal-less (codex) pane could never even be swept because it never reported `Idle`.
**Decision:** Live delivery closes the latency gap without touching the trust boundary: `wrap`'s pump now polls the mailbox on its own cadence and types **one** labelled advisory line (count + newest sender, never the body) into the child at a verified-idle turn boundary; the dashboard's mail sweep does the same for an attached orchestrator pane via `advise_one_pane`. ### 2026-08-16 — Windows process-tree lifecycle needs three layers, not one: tree-kill, close-handler sweep, and Job Objects (supersedes the 2026-08-14 Job-Object rejection)
**Context:** The 2026-08-14 entry rejected a Windows Job Object in favor of `taskkill /T /F /PID`, scoped narrowly to "how does `supervise::terminate` kill a tree it already knows about." Reaping every teardown path (`fix/process-lifecycle`, `c843891`/`222b24f`) found three *different* gaps `taskkill` alone cannot close: `wrap`'s and the dashboard's pty seams never ran any tree-kill at all (`Child::kill()` only, orphaning an npm shim's node grandchild); the Windows console-close handler (X-button/logoff/shutdown) killed zirv itself but nothing it supervised, since a pane's child lives on its own ConPTY and never receives `CTRL_CLOSE_EVENT`; and neither mechanism runs at all when zirv itself is killed with no user code executing (`taskkill /F` against zirv, a crash, `panic = "abort"`).
**Decision:** Layer three mechanisms, each covering what the others cannot. (P1) `supervise::kill_tree` (the renamed, now `pub(crate)` `taskkill_tree`) runs ahead of the narrow kill at every pty seam too (`wrap::quit_child`, `dash::pane::Pane::finish_shutdown`, the distiller's timeout escalation), not just `exec`/`loop`. (P2) A cross-platform supervised-pid registry (`supervise::{register,deregister}_child_pid`) is swept by the console-close handler on the three *terminal* events only (`CTRL_CLOSE`/`LOGOFF`/`SHUTDOWN` — deliberately not `CTRL_C`/`CTRL_BREAK`, which is the operator interrupting the agent, not tearing down); a Windows console-control handler runs on an ordinary thread, so spawning `taskkill` from it is legal, unlike in a POSIX signal handler. (P3) A Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is adopted per supervised child, post-spawn, via `ChildGuard`/`JobGuard` — the kernel becomes the killer when zirv's own process disappears with no code of its own running, which P1 and P2 structurally cannot reach.
**Rejected:** Job Objects alone, replacing `taskkill` — `AssignProcessToJobObject` only covers descendants created *after* assignment; a shim's grandchild spawned before the job lands (a race, not a guarantee — portable-pty offers no `CREATE_SUSPENDED` seam to close it) escapes the job, while `taskkill /T` walks the tree as it stands *at kill time* and catches it. Job Objects requiring a spawn-path change — this round's actual implementation needed none: `AssignProcessToJobObject` runs on an already-spawned pid, so `portable-pty`'s and `std::process`'s own spawn paths are untouched, which is what makes the 2026-08-14 rejection's stated reason moot rather than wrong for what it was actually deciding.
**Consequences:** All three layers must be kept, not consolidated: dropping P1/P2 leaves the shim-grandchild race exposed on every ordinary kill; dropping P3 leaves the "zirv itself died" case unrecoverable. A dropped `ChildGuard` closes its job handle, which on Windows **kills the child** — every holder must outlive the child it guards, a new invariant every future caller of `ChildGuard::adopt` has to hold (see [[Known Issues]]).
**Spec / link:** [[Ctx Supervisors]] ("The Windows process-tree lifecycle" section); [[Known Issues]] ("`supervise::terminate`/tree-kill…", "Dropping a `ChildGuard`…", "Job-Object assignment is a race…"); `supervise.rs`'s `ChildGuard`/`JobGuard`/`kill_tree`/`kill_registered_trees`; `term.rs`'s `console_ctrl_handler`.

### 2026-08-14 — State-dir writes go through temp-file-plus-rename, not truncate-in-place
**Context:** `state::write_private` (registry records, mail, memory, handoffs) was create-truncate-then-write. **Rejected:** A file lock around the read/write pair — every reader (`sessions::list`, `mail::list`, `memory::recall`) would need to take it too, multiplying the surface for a bug versus one seam (the writer) fixing itself.
**Consequences:** Every private-state writer gets this for free (one shared helper); no reader anywhere needs to change. `prune_to_cap` was separately hardened to never delete an entry it can't parse, closing the matching read-side half of this race — see [[Known Issues]].
**Spec / link:** [[Known Issues]] "`state::write_private` used to leave a zero-length window…"; `state.rs`'s `write_private`.

### 2026-08-14 — `nested_session_evidence`'s dashboard signal requires a live `owner.pid`, not mere directory existence
**Context:** `sessions::nested_session_evidence` treated the existence of `<state>/dash/<short>-<token>/` (from `ZIRV_CTX_DASH_REQUESTS`) as proof a live dashboard owns this terminal. A dashboard killed externally (not through its own quit path) left the directory behind, so every later `zirv chat`/`zirv ctx wrap` run from a surviving pane shell refused to start, permanently, until something manually cleaned it up.
**Decision:** The dashboard now writes `owner.pid` (its own pid, decimal ASCII) into that same directory at startup, and sweeps sibling directories whose `owner.pid` names a dead process. `nested_session_evidence` requires the pidfile to be present, readable, parseable, **and** the pid alive; missing/unreadable/unparseable/dead all mean no evidence.
**Rejected:** A heartbeat file refreshed periodically — solves the same staleness problem but needs a timer and a "how stale is too stale" constant; a liveness probe on a pid already answers the question exactly, with no clock involved.
**Consequences:** New shared contract, worth pinning down for any future reader of this directory: `ZIRV_CTX_DASH_REQUESTS` = `<state>/dash/<short>-<token>/requests`, and the pidfile lives one level up at `<state>/dash/<short>-<token>/owner.pid`. `agent::try_join_dashboard`'s own liveness check now matches this reader exactly, closing the prior case where the two disagreed about what "set" meant.
**Spec / link:** [[Ctx Supervisors]] "Nesting guard and the missing Ctrl-C rung"; `sessions.rs`'s `nested_session_evidence`; `dash/mod.rs`'s startup owner.pid write and sibling sweep.

### 2026-08-14 — cmd.exe argv reparse: keep untrusted content off the argv, guard is only a backstop
**Context:** The first fix for the Windows `cmd.exe /c <shim>` argv-reparse RCE was a single fail-closed guard (`guard_cmd_shim_reparse`) applied over the whole downstream argv at each spawn seam. Adversarial review found it both **bypassable** (`resume` spawned directly via `command.status()`, never passing through any guarded seam, so a repo `system-prompt.md` with `&` folded into the composed prompt reached cmd.exe) and **over-broad** (the guard sat over the operator's own task prompt too, so a normal headless `zirv ctx agent "do foo() and bar()"` was refused on an npm `.cmd` install — the `()` are cmd metacharacters).
**Decision:** Stop relying on the guard to sit over untrusted-or-legitimate content it cannot tell apart; **remove the untrusted content from the reparsed argv** instead — scoped precisely to the launch shape that reparses (the `cmd.exe /c <shim>` form, `adapters::launches_through_cmd_shim`), since a direct `.exe`/`sh` launch is handed argv verbatim by CreateProcess with no shell reparse and inline is safe there. (A) On the shim form force claude's `--append-system-prompt-file <path>` form for the composed prompt regardless of the `--help` probe, fail closed if the file can't be written — repo-sourced prompt text never touches the reparsed argv, at every seam at once. (B) Deliver the headless `-p` prompt (and any folded mail) on the child's **stdin** on the shim form, the distiller's proven mechanism, so a normal prompt with punctuation works. (C) Keep the guard as the fail-closed backstop for the one residual free-text slot — an interactive positional prompt — and add it to `resume`'s direct spawn. (D) Extend it to the `powershell -File` shim, defense-in-depth.
**Rejected:** Narrowing the guard to skip the prompt slot but leave it on argv — cmd.exe would still *reparse* a `&` in the prompt (corruption, and re-opens the injection), so the prompt has to leave argv, not just be exempted. Forcing the file form for *every* Windows launch (not just the shim) — tried first; it broke non-shim `sh`-based tests, whose `\\?\`-prefixed prompt-file path a spawned `sh` cannot read, for no security gain since those launches are never reparsed. Threading a hard error through the two `PaneSpec`/`SpawnRefusal`-returning dash callers was accepted (not avoided) so FIX A can fail closed uniformly.
**Consequences:** The composed prompt is off argv on the shim form everywhere; the guard now only ever fires on an interactive positional prompt (rare, rephrase). FIX A and FIX B are both gated on `launches_through_cmd_shim`, so off-Windows and non-shim (`sh`-stub, direct-`.exe`) launches are byte-identical to before and the real shim path is unexercised by the suite (no test may spawn real cmd.exe/claude); it is covered by pure-function tests over a temp `.cmd`.
**Spec / link:** [[Known Issues]] "cmd.exe argv reparse"; `prompt::injection_args_for_session`, `adapters::{launches_through_cmd_shim,headless_cmd_stdin,guard_cmd_shim_reparse}`.

### 2026-08-13 — Dashboard panes use embedded `vt100` emulation, not raw passthrough; one non-configurable `Ctrl+A` prefix
**Context:** The dashboard needed a persistent sidebar (session list always visible, decided during brainstorming), which means a child's raw output cannot be passed straight to the real terminal: interactive harness TUIs use absolute cursor addressing and the alternate screen, so raw passthrough into a sub-region would paint over the sidebar — the existing `wrap`/`chrome` scroll-region trick only reserves rows, it doesn't sub-window a whole pane. Separately, the dashboard needed one keystroke to distinguish "control the dashboard" from "type into the active child," and the vt100 fidelity spike (`docs/superpowers/notes/2026-08-13-vt100-spike.md`) found `Ctrl+Q` arriving on Windows as the raw DC1 byte `Char('\x11')` with no `CONTROL` modifier at all (VT input mode), not just the classic modifier+char shape.
**Decision:** Each pane parses its child's output into an in-memory `vt100::Screen` (like any real terminal multiplexer) and ratatui renders that grid inside the pane's own rect, spike-gated first (`vt_spike --check` against a recorded real ConPTY capture, plus a human probe) before Wave 1 implementation began. The dashboard's one prefix key, `Ctrl+A`, is a hardcoded constant, not configurable in v1 (recorded YAGNI in the plan's own self-review — `[dash] prefix` was dropped from the spec's original config surface). `filter_key`/`is_prefix_key` match `Ctrl+A` in both shapes a real terminal can deliver it: `Char('a')`/`Char('A')` + `CONTROL`, or the raw control byte `Char('\u{01}')` with no modifier at all — carrying the spike's Ctrl+Q finding forward rather than re-discovering it against Ctrl+A in production.
**Rejected:** Extending the DECSTBM scroll-region chrome `wrap`/`chrome.rs` already has — rows-only, no way to sub-window a whole pane region for arbitrary child output. A configurable prefix key — no user request for it, and it multiplies the key-matching surface (shape variants) for no proven benefit; YAGNI.
**Consequences:** A terminal-emulation dependency (`vt100` 0.16) is now load-bearing, not optional — see [[Technology Stack]]. Any future control key added to the dashboard's own vocabulary must be checked against both the modifier-flag and raw-control-byte shapes, the same way `Ctrl+A`/`Ctrl+Q` were.
**Spec / link:** `docs/superpowers/specs/2026-08-13-zirv-dashboard-design.md` ("Why emulation is required"), `docs/superpowers/notes/2026-08-13-vt100-spike.md`; [[Ctx Supervisors]].

### 2026-08-13 — `chat.model` is repo-settable; every other model key stays repo-forbidden
**Context:** The dashboard's orchestrator pane needed a way to pick a model (`AgentAdapter::model_args`), and every existing model key in `ctx.toml` (`handoff.model`, `optimize.model`) is `REPO_FORBIDDEN` because it drives an automatic, unwatched background spawn — a repo checkout must not be able to spend the operator's tokens silently.
**Decision:** `[chat] model`/`ZIRV_CTX_CHAT_MODEL` is a new config key that is deliberately **not** added to `REPO_FORBIDDEN`. It only shapes an interactive session the operator deliberately launched (`zirv ctx chat`, dashboard or plain `wrap`), and the chosen model is disclosed at launch on the `zirv ▸` events channel (`chat::announce_model_choice`, emitted before either launch path), plus the banner and the dashboard header, rather than spent invisibly in the background the way the forbidden keys are. This repo's own `.zirv/ctx.toml` sets `[chat] model = "fable"` as the worked example of a repo layer actually using this one allowed key.
**Rejected:** Forbidding it by the same blanket rule as `handoff.model`/`optimize.model` — would block a legitimate, repo-scoped, human-visible preference ("this repo's orchestrator should default to model X") for no trust benefit, since the human at the keyboard sees and can override the choice before spending anything.
**Amended 2026-08-14:** the disclosure originally rested on the banner alone, and `chrome.banner` is not repo-forbidden — so one repo layer could set the model *and* hide it. The exemption now rests on `chrome.events`, which is repo-forbidden; a repo-settable key whose justification is visibility must be disclosed on a channel the repo cannot also turn off.
**Amended 2026-08-14 (review round 4):** the floor is not absolute — an operator running `ZIRV_CTX_QUIET` in a sub-80-column terminal, in a repo that turned the banner off, sees no model disclosure at all (events silenced by the operator, banner by the repo, header segment dropped for width). Accepted as operator-over-repo: every silencing surface left is one the operator chose. Flagged here because the exemption's own justification is visibility.
**Amended 2026-08-14 (security):** the value is now **charset-validated** at the end of `CtxConfig::load` — `[A-Za-z0-9-._:/@]`, non-empty, ≤128 bytes — because a repo-settable string that reaches an argv `resolve_program` may route through `cmd.exe /c` on Windows is a command-injection path (see [[Known Issues]] "cmd.exe argv reparse"). The validated charset can express no shell/cmd metacharacter, so the exemption cannot carry a payload; real model ids (`us.anthropic.claude-…-v1:0`, `claude-…@20250101`, `fable`) only use that charset, so the disclosed operator-in-repo model-choice purpose survives. A charset allowlist, **not** adding the key to `REPO_FORBIDDEN`: banning it would remove a legitimate, disclosed preference to close a hole a narrower guard closes without loss.
**Consequences:** Any future interactive-only config key can cite this same test ("does a human see it, on a surface the repo cannot silence, before it spends anything?") rather than defaulting to repo-forbidden out of caution; a future *headless* per-run model key would not qualify and belongs back in `REPO_FORBIDDEN`.
**Spec / link:** `docs/superpowers/specs/2026-08-13-zirv-dashboard-design.md` ("Orchestrator model"), `src/commands/ctx/config.rs`'s `ChatConfig` doc comment; [[Untrusted Configuration]], [[Ctx Subsystem]].

### 2026-08-13 — A supervisor's registry short id is its stable delivery address
**Context:** `SessionGuard::refresh_session` rotated `Record.short` alongside `Record.session` — every `loop` cycle and every `exec` restart. But the short id is what `resolve_prefix` hands a sender, what `send --to-session`/`nudge` store on a message, and what a human types from `zirv ctx status`. A message addressed to a live session therefore became undeliverable the instant that session was replaced: the sender resolved a real address and the supervisor stopped answering to it. `loop` had worked around this by listing mail with `for_session = None`, which meant it also swallowed *and consumed* mail addressed to other sessions entirely.
**Decision:** `refresh_session` rotates the session id and leaves `short` (and the record's path) alone, so the address is minted once per supervised run and outlives every cycle and restart. Every delivery listing a supervisor performs on its own behalf is scoped to that stable short — `exec`'s launch and nudge-relaunch listings, `loop`'s per-cycle listing — as is `exec`'s nudge-marker claim, which had the same rotation bug.
**Rejected:** Keeping `None` for `loop` and accepting the cross-talk — it is not merely over-broad reading, it *consumes* (moves to `read/`) another session's directed mail, so the intended recipient never sees it. Re-addressing stored mail on every rotation — rewrites durable message files on a hot path to chase a value that never needed to change.
**Consequences:** A registry short now identifies a *supervisor*, not a session; `Record.session` is the field that answers "which session is it running right now". `sessions::list`'s sweep also removes orphaned `.nudge` markers, which matters more now that a short id can be reused by a later run.
**Spec / link:** `sessions.rs`'s `refresh_session`/`sweep_orphaned_markers`, `exec.rs`'s `registry_short`, `run_loop.rs`'s `registry_short`/`nudge_address`; [[Ctx Supervisors]], [[Known Issues]].

### 2026-08-13 — Markdown header blocks end at the first blank line
**Context:** `mail::parse_markdown` and `memory::parse_markdown` skipped blank lines while still in header mode, so a body whose first line was a `- key: value` bullet was absorbed as header. Both bodies are agent-authored text, so this was a trust boundary: a mail message could re-address itself (`- To-session: victim`) or forge its sender, and a memory entry could rewrite the key it is filed under or promote itself from `handoff` to `explicit`. It also silently swallowed any honest bulleted body.
**Decision:** The header block ends at the **first** blank line after the `## Message`/`## Memory` heading — the one `to_markdown` already writes — and everything after it is body, verbatim. A document with no blank separator still ends the block at its first non-bullet line, so hand-written and older files keep parsing.
**Rejected:** Validating header keys against a whitelist after the fact — the parser would still have to decide where the header *ends*, and a body bullet naming a known key would still win. Refusing to parse a body that starts with a bullet — punishes a legitimate and common shape to work around a grammar bug.
**Consequences:** Both parsers now share one stated grammar rule; any new header field must be added inside the block, and the terminator rule left intact.
**Spec / link:** `mail.rs`/`memory.rs` `parse_markdown`; [[Untrusted Configuration]], [[Known Issues]].

### 2026-08-13 — No Ctrl-C rung in `quit_child`; interactive verbs refuse to nest
**Context:** A `zirv chat` started inside an already-supervised session killed the **outer** session. Two independent mechanisms, both confirmed by evidence: (a) the nested `wrap`'s `SignalServer::bind` failed, and since `CommandBuilder::new` seeds itself from `std::env::vars_os`, its child inherited the outer `ZIRV_CTX_SESSION`/`ZIRV_CTX_SOCKET` and posted phantom turns into the outer rot engine until it verdicted `Restart` and `quit_child` killed the outer agent; (b) `quit_child`'s middle rung wrote `\x03\x03` into the pty master, and on Windows conhost turns that into a console control event broadcast to **every** process attached to the pseudoconsole — portable-pty 0.9.0 spawns without `CREATE_NEW_PROCESS_GROUP`, so there is no group to narrow it to.
**Decision:** `quit_child`'s ladder is now quit sequence → grace → `child.kill()`, with no control-byte rung at all. Independently, `wrap` and `chat` refuse to start when `sessions::nested_session_evidence` finds `ZIRV_CTX_SESSION`, `ZIRV_CTX_SOCKET`, or the `CLAUDE_PID`+`CLAUDECODE` pair, overridable with `--allow-nested` / `ZIRV_ALLOW_NESTED=true`. Every supervisor also scrubs `sessions::SUPERVISION_ENV` off each child command before setting whichever of it it actually owns, so "no socket of my own" degrades to *unsupervised*, never to *supervised by somebody else*.
**Rejected:** Narrowing the Ctrl-C to the child's own process group — portable-pty 0.9.0 does not expose the spawn flag, and vendoring a pty implementation to gain one flag puts it under our maintenance forever. Gating the headless verbs too — `zirv ctx agent` delegating to a worker *from inside* a session is the feature, and a worker never takes over the shared console. Relying on the env scrub alone — it closes the phantom-turn path but not the "two interactive supervisors fighting over one console" one, which is its own hazard.
**Consequences:** `quit_child` has one fewer chance to end a stubborn TUI politely; the kill now lands one grace period sooner. Anything that legitimately nests (a wrapper script, a test harness) must pass `--allow-nested` explicitly. `wrap`'s pty test helpers scrub the evidence variables so a suite run from inside an agent session does not trip the guard instead of running the test.
**Spec / link:** `wrap.rs`'s `quit_child`/`apply_session_env`, `sessions.rs`'s `nested_session_evidence`/`nesting_refusal`/`SUPERVISION_ENV`; [[Ctx Supervisors]], [[Known Issues]] ("portable-pty's Windows `do_kill`...").

### 2026-08-12 — Bare `zirv` becomes an alias, not a usage error
**Context:** `Input::command` is clap's required positional, so a bare `zirv` (no arguments) was a usage error, exit 2. With `zirv chat`/`zirv ctx chat` now the fastest way to start a session, requiring the extra word every time undercuts the "just run `zirv`" pitch this wave is named for. An independent review (2026-08-12) found the first cut too permissive on both axes: it treated a *global* `~/.zirv` as enough to call any directory "a zirv-managed repo," and it checked only stdin for a real terminal, so `zirv | less` (interactive stdin, redirected stdout) would have opened a chat session into the pipe.
**Decision:** A bare invocation is intercepted on raw argv, before clap: `zirv ctx chat` when a **local** `./.zirv` directory exists and **both** stdin and stdout are a real terminal, else `zirv help` — both exiting 0. A global `~/.zirv` alone no longer counts (matches the approved design's own wording, "in a repo with a `.zirv` directory"); `zirv chat`/`zirv agent` are separate top-level aliases for `zirv ctx chat`/`zirv ctx agent`, not subject to either check, and reserved (`utils::RESERVED_COMMANDS`, compared case-insensitively) so a script can never shadow them.
**Rejected:** Making the bare form always open chat regardless of `.zirv`/TTY — would hang a CI job or a piped invocation waiting on an interactive session nothing is there to drive. Counting a global `~/.zirv` — would open a chat session for a bare `zirv` in literally any directory for anyone who has ever run `zirv create --global` once, which says nothing about the directory actually being run from. Checking stdin alone — misses the `zirv | less` case, an interactive terminal with a redirected destination.
**Consequences:** Any script or automation piping into bare `zirv` now gets help text instead of an error, silently, since both are exit 0 — an agent workflow that wants a specific verb should keep naming it (`zirv ctx chat`, `zirv ctx status`, ...) rather than relying on the bare form's exit code to distinguish outcomes.
**Spec / link:** `src/main.rs`'s `bare_invocation_target`/`zirv_dir_present`/`top_level_ctx_alias`; [[Built-in Commands]], [[Architecture/Script Resolution]].

### 2026-08-12 — Mail is agent-authored text, not repo config: delivered to Worker only, labeled per batch, two keys repo-forbidden
**Context:** `zirv ctx send`/`inbox` adds a fourth untrusted-text surface (after `ctx.toml`'s repo layer, `.settings.toml`'s repo layer, and the repo system-prompt layer), but it doesn't come from a checkout — it's written by another agent session. An independent review (2026-08-12) also found the initial cut let a disabled mailbox still get folded into a launch prompt, let a repo raise its own delivered-mail cap or silence the announcement channel, and let two same-second sends silently overwrite one another on disk.
**Decision:** Mail bodies are delivered only into a headless **Worker** session's composed prompt (`exec`/`loop`, gated by `cfg.mail.enabled`), never into the interactive **Orchestrator** seat (`chat`/`wrap`), which gets a one-line unread-count advisory instead. `with_mail_layer` wraps the whole delivered batch in an explicit label, the same pattern the repo prompt layer uses (not per message — the repo layer is a single block; mail is a stream of independent messages, so one label per batch covers the same ground without repeating boilerplate). Delivered mail is consumed (`mail::consume`) right after, so a later launch/cycle does not see it again; a failed consume is swallowed, not fatal. `mail.enabled` and `mail.max_delivered_bytes` are `REPO_FORBIDDEN` (mirroring `prompt.max_repo_bytes`'s rationale): without the second, the untrusted layer could raise its own cap; without the first, a repo could re-enable delivery an operator turned off, or (read the other way) a repo could not be trusted to leave delivery on either. Mail filenames get a collision-free suffix (`_001`, `_002`, ...) on a same-second collision, sorting after the unsuffixed file so oldest-first order survives it.
**Rejected:** Delivering mail into the orchestrator's own prompt (the original design) — a human is already at the keyboard in that seat and can just run `zirv ctx inbox`; folding unreviewed agent-to-agent text straight into the one session steering delegation decisions is a bigger blast radius for a manipulative note than a headless worker that has no further harnesses to steer. A `REPO_FORBIDDEN`-style forbidden-*key* list for mail's own content — mail carries no configuration keys to forbid, only text; what needed forbidding was the two config knobs governing delivery, not the messages themselves.
**Consequences:** If mail ever grows structure beyond free text (e.g. a message that could request a config change), that structured case would need its own review — free-text notes alone don't need it.
**Spec / link:** `src/commands/ctx/mail.rs`, `src/commands/ctx/exec.rs`, `src/commands/ctx/run_loop.rs`; [[Untrusted Configuration]]'s "Mail" section, [[Ctx Supervisors]].

### 2026-08-12 — `.settings.toml` per-agent gate: AND-fold, not deep merge; warn vs error
**Context:** Adding agent enable/disable needed a repo-vs-operator trust rule like `ctx.toml`'s `REPO_FORBIDDEN`, but a boolean toggle (not a value a repo is simply blocked from setting) has to let the operator override in *either* direction while still letting a repo narrow.
**Decision:** Each layer (`~/.zirv/.settings.toml`, `<repo>/.zirv/.settings.toml`) is parsed on its own, never deep-merged; the three answers fold as `env(name) if set else home(name).unwrap_or(true) && repo(name).unwrap_or(true)`, so a repo's `enabled = true` is a silent no-op. Unknown agent names and unknown top-level sections warn (forward-compat); an unknown key inside a known `[agents.<name>]` table hard-errors (`deny_unknown_fields`) since that's a typo, not a future feature.
**Rejected:** Deep-merging all layers into one table like `ctx.toml` does — collapses "repo said true, operator said nothing" and "repo said true, operator said false" into the same merged value, losing which layer to blame in the refusal message. Denying unknown agent names outright — breaks a future repo shipping a `.settings.toml` that names an adapter this build predates.
**Consequences:** Any second `.settings.toml` section will need its own fold rule stated explicitly; the AND-fold here is specific to a boolean "may zirv use this" switch, not a general merge pattern to copy.
**Spec / link:** `src/settings.rs` module doc.

### 2026-08-13 — A nudge is two independent writes: durable mail plus a separate wake-up marker
**Context:** `zirv ctx nudge` needed to interrupt a live session from outside its own poll loop without either losing the message (if the wake-up is missed) or making delivery depend on the supervisor being awake at the exact moment it's sent.
**Decision:** `run_nudge_with` stores the nudge's text as an ordinary, durable, session-addressed mail message first (`mail::store`), then writes a separate empty marker file (`<short>.nudge`) second. `claim_nudge_marker` removes the marker atomically (`std::fs::remove_file` as the claim), so exactly one observer ever acts on a given wake-up. A supervisor's tick checks the marker in the same tick as its ordinary rot/limit checks, so latency is bounded by the existing poll interval rather than needing a new one.
**Rejected:** A single combined write (message text inside the marker file itself) — couples the fast path (wake-up) to the durable path (message); losing or racing the one file loses both, and the message would no longer show up in `zirv ctx inbox` independent of whether the wake-up was ever claimed. A dedicated notification channel (new socket message type) — turn signals already exist for a different purpose (transcript-derived verdicts from *inside* the agent); a nudge originates *outside* it, from an operator, and reusing the socket would conflate the two origins.
**Consequences:** Losing the marker (a crash between the two writes, or nobody claiming it before the state dir is swept) never loses the message — it's just picked up at the next natural poll or cycle instead of immediately. `exec`'s nudge-restart is budget-free by the same design split: it is not rot, so it must never spend the rot-restart budget.
**Spec / link:** `src/commands/ctx/sessions.rs`'s N4 module doc comment; [[Ctx Subsystem]], [[Ctx Supervisors]].
