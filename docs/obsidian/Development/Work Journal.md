# Work Journal

## How to use

- **Reading:** check the last 2–3 entries at the start of a session for recent context.
- **Writing:** entry after any non-trivial change (feature, refactor, bug fix, infra). Skip if a commit message already captures it.
- **Cap:** keep new entries to ~10 lines. If you need more, it's a spec or a [[Decision Log]] entry, not a journal note. Link out; don't inline.
- **Rotation:** when the active journal grows past ~10 entries, move the oldest ones to a quarterly file under `journal-archive/` (frontmatter `archived: true`, header stating the covered date range).

## Format

### YYYY-MM-DD: short title
**What:** one or two sentences.
**Key changes:** files/services touched.
**Follow-up:** anything unfinished (optional).

### 2026-09-07: two operator-reported latency/trust bugs -- shared dashboard tick budget, seat-vs-worker scheduling posture, self-update integrity (`fix/3.30.0-input-latency-defender`, v3.30.0)
**What:** Two operator reports, three commits. (1) Dashboard typing lag traced to the tick's own duration: `run_dashboard`'s single UI thread did machine-wide disk sweeps (`sessions::list` parsing every session record and probing each orphan socket synchronously) and up to 256 KiB of vt100 parsing *per pane* between a keystroke and the `event::poll` that would have read it. Fixed by moving the machine-wide facts (mail, memory count, session registry, work groups) to a background `zirv-dash-facts` thread that publishes a snapshot on the existing `FACTS_THROTTLE` (1s) cadence, swapped in non-blocking by the tick; the spawn-request intake drops from the render loop's own cadence to a 250ms poll (forced when no panes remain); and `DRAIN_BUDGET_BYTES` becomes one 256 KiB budget shared across the whole tick (focused pane first, then round-robin), not 256 KiB per pane. Root cause: a single-threaded event loop with no notion of "cheap per-frame work" vs. "expensive machine-wide work." (2) Same lag had a second cause once the dashboard tick was off the disk: the seat's own threads, the dashboard UI thread, and every worker's cargo build all ran at equal OS priority, so a busy build starved the operator's own keystrokes. Fixed by `ctx::priority`, a pure role-decided posture with no config escape hatch: the interactive seat raises its own threads (never its process class); every delegated worker (`exec`/`loop`/`agent`/script `agent:` steps/dashboard worker panes) lowers its whole process class one notch so its cargo children inherit it for free. (3) A third, unrelated report -- Windows Defender twice quarantining `zirv.exe` as a trojan -- got this release's mitigation too: `build.rs` embeds a `VERSIONINFO` resource via `winresource`, CD publishes a `.sha256` per release artifact, and `zirv update`/`install.sh` verify the digest before replacing the running binary, failing closed (never silently skipping) on a release with no published checksum at all.
**Key changes:** `src/commands/ctx/dash/{mod,pane}.rs` (background facts refresher, shared drain budget, spawn-intake poll, `KeyLog` `dur=`/`(slow)`); `src/commands/ctx/priority.rs` (new), `mod.rs`, `{agent,exec,run_loop,wrap}.rs`, `src/script_runner/agent_command.rs` (scheduling posture call sites); `build.rs` (new), `Cargo.toml` (`winresource` build-dependency), `.github/workflows/cd.yaml` (`.sha256` generation/upload), `src/commands/update.rs` (`verify_checksum`), `install.sh`.
