# Ctx Adapters

## Quick Reference

- **Files:** `src/commands/ctx/adapters/mod.rs`, `src/commands/ctx/adapters/claude.rs`, `src/commands/ctx/adapters/codex.rs`, `src/commands/ctx/adapters/{gemini,opencode,pi,copilot,droid,qwen}.rs` (issues #384-#389, umbrella #396, the six wave-1/2 harness adapters — see "The wave-1/2 harness adapters" below), `src/commands/ctx/catalogue.rs` (issue #381, the pure model catalogue every adapter delegates its ladder to), `src/commands/ctx/transcript_source.rs` (issue #382, the shadow-JSONL materializer `opencode.rs`'s `transcript_path` calls for its SQLite database), `src/commands/ctx/native_hooks.rs` (issue #418, the generic native-hooks installer `AgentAdapter::native_hooks` feeds), `src/commands/ctx/hook_project.rs` (issue #418, the non-claude payload projection/envelope translation `hook.rs`/`safety.rs` share)
- **Used by:** [[Ctx Supervisors]] (`exec.rs`, `wrap.rs` build agent argv and relaunch through an adapter; `dash/mod.rs` and `dash/roster.rs` call `model_args`/`resume_args` for the dashboard's orchestrator pane and its quit/restore roster; `wrap.rs` and `chat.rs`'s `dash_orchestrator_pane` call `adapters::harness_prompt_lines` to render the derived harness-roster prompt layer for an Orchestrator launch), [[Script Runner]] (`src/script_runner/agent_command.rs` calls `adapters::select`/`adapters::all` to run a wrapped agent command from a script), [[Ctx Subsystem]] (`handoff.rs` calls `distiller_cmd` to build the summarization child; `score.rs` calls `parse_events`/`structural_context`)
- **Depends on:** [[Ctx Subsystem]] for `CtxResult`, `CtxConfig` and the `event` types (`SessionId`, `SessionRef`, `NormalizedEvent`, `StructuralContext`, `Capabilities`), [[Utilities]] for `home_dir()`, `src/settings.rs` (`AgentGate`, via `cfg.agents`) for the enable/disable gate `select` checks
- **Tests:** inline `#[cfg(test)] mod tests` in all three files — `mod.rs` (adapter selection, Windows launcher rewriting, `program_invocation`), `claude.rs` (transcript parsing, command building, private launch-settings materialization/attestation, distiller restrictions), `codex.rs` (verified command shapes, shim/stdin paths, capability-probed approval and automatic review)
- **If changed:** [[Ctx Supervisors]], [[Ctx Subsystem]], [[Untrusted Configuration]], [[Command Safety]] (`default_sandbox_args`'s `SafetyPolicy` projection), [[Usage and Pacing]] (`provider()`/`provider_for_model()`, the shared rollout collector), [[Rot Engine]] (codex's derived events), [[Architecture/Technology Stack|Technology Stack]] (`rusqlite`, issue #382), [[Known Issues]] (issue #11 tracks the remaining codex event residual: tool calls/results, compaction, marker/turn-signal), [[Decision Log]] (the I6 distiller-restriction fix round; the catalogue/shadow-transcript design choices, issues #381/#382)
- **Gotchas:** `distiller_cmd`'s tool restriction is a security control, not cosmetic — see below; it must stay a single `=`-bound `--disallowedTools=...` argv token, and `Bash` must stay in the deny list, or the restriction silently stops working. The `codex` adapter is **supported, with a narrower degraded surface than before (issue #86, 2026-08-23)**: `ready()` only checks that the `codex` program resolves (mirrors claude), so `--agent codex` launches and supervises fine, and `capabilities().events` is now honestly `true` — `parse_events`/`structural_context` derive turn boundaries and token totals from the codex rollout JSON (see "The codex adapter" below). Direct launches support injected developer instructions and lifecycle hooks; tool-call/tool-result/compaction event mapping, the marker signal, and the turn-signal socket mechanism remain tracked in issue #11.

## Purpose

This module is the seam between zirv's ctx subsystem and whatever coding-agent CLI is actually being wrapped. Everything that needs to spawn an agent process, parse its transcript, or know what it's capable of goes through the `AgentAdapter` trait rather than hard-coding "claude" or "codex" logic elsewhere.

## The `AgentAdapter` trait

Defined in `mod.rs`, with `Debug` as a supertrait (so `Box<dyn AgentAdapter>` can appear in test assertions). Required methods:

- `name()` — the adapter's short identifier (`"claude"`, `"codex"`), used for `--agent` selection and error messages.
- `provider()` (2026-08-15) — the **account**/vendor whose rate limits this adapter spends, a stable lowercase slug (`"anthropic"` for claude, `"openai"` for codex): deliberately not `name()`, since two harnesses can sit on one billed account and would then legitimately share one provider's usage windows. Required with no default, so a new adapter cannot silently inherit someone else's usage — see [[Usage and Pacing]] for `state::usage_for`/`window::load_for`, the per-provider storage this feeds.
- `provider_for_model(model)` (issue #383, 2026-09-07) — the per-LAUNCH sibling of `provider()`: which account THIS launch actually bills, given the `model` it pins. Default implementation ignores `model` and returns `self.provider()` — correct for claude/codex, whose account never varies with the model argv names. A future multi-provider adapter (one CLI whose `provider/model` argument can pin a different vendor per launch — the OpenCode/Pi/Goose/Droid shape the wave-1 adapter tracks target) overrides this to read the vendor prefix out of `model` instead, so `StateDir::usage_for`/`poll_marker_for`, pacing, and the token-reservation ledger all file that launch under the account it is actually billed to. `model: None` always falls back to `provider()`. `adapters::provider_for_agent_and_model(name, model)` is the model-aware sibling of `provider_for_agent_name`, and `provider_for_usage_readout(cfg)` now resolves through `provider_for_model(cfg.chat.model.as_deref())` rather than the static `provider()`. Both current adapters (claude, codex) leave the trait default in place — see the equivalence tests in `adapters/mod.rs`.
- `ready()` — returns `Err` when the adapter exists but isn't safe to use yet, so callers fail loudly instead of scoring garbage. Both current adapters implement this identically: `resolve_program(&self.program)?; Ok(())` — the only failure mode either has is an unlaunchable binary (see below).
- `detect(command)` — whether a wrapped argv looks like this adapter's binary, by filename.
- `headless_cmd(prompt, session, extra)` — builds the one-shot, non-interactive command (`exec`'s launch shape).
- `interactive_cmd(initial_prompt, extra)` — builds the TUI command (`wrap`'s launch shape). **What goes into `initial_prompt` for a handoff launch is decided by `prompt::interactive_handoff_prompt`, not by the caller (issue #220, 2026-09-06).** A handoff/restart packet is long and always multi-line, so it is no longer handed to an adapter positionally when there is anywhere better to put it: if the adapter delivers its system prompt through a private file (`system_prompt_file_flag` plus a shim launch or a passing `supports_system_prompt_file` probe — the same condition `injection_args_for_session` applies, now named `prompt::delivers_system_prompt_by_file`), the packet is folded into that file, the launch's existing `--append-system-prompt-file` occurrence is **repointed** rather than duplicated (a repeated flag keeps only its last value), and `initial_prompt` becomes one short metacharacter-free line. Otherwise it stays positional, bounded by `INLINE_ARGV_PROMPT_BUDGET_BYTES` and labelled when truncated. This is what makes a rot restart, a handover swap or `zirv ctx resume` work at all on a Windows npm `.cmd` install, where `guard_cmd_shim_reparse` refuses any multi-line argv token — see [[Ctx Supervisors]] and [[Known Issues]].
- `policy_support(capability, stance, mode)` / `default_sandbox_args(sandbox, safety, mode)` — report and project the canonical policy for an explicit `LaunchMode`; the mode is supplied by each real-launch seam rather than inferred.
- `distiller_cmd(model)` — builds the command for the small judgment/summarization model child used by handoff distillation and `optimize`.
- `read_only_args()` — the flags that keep this agent from writing files or running shell commands (claude `--disallowedTools=Write,Edit,Bash,NotebookEdit`, codex `--sandbox read-only`, plus `--ignore-rules --ignore-user-config` when the installed codex-cli's own `--help` documents them — issue #89, see "The distiller/reviewer sandbox residual" below). `distiller_cmd` applies them, and so does any other child whose prompt embeds untrusted repository text — the workflow reviewer, handed a repository diff (see [[Workflows]]). No trait default: a new adapter has to answer deliberately rather than inherit "no restriction" by omission. **`interactive_read_only_args()` (bug fix, 2026-09-06)** is the interactive-launch counterpart, defaulting to `read_only_args()` unchanged: codex overrides it to drop the `exec`-only ignore-flag pair, which the top-level interactive launch a dashboard pane uses rejects outright — see "`--ignore-rules`/`--ignore-user-config` are `codex exec`-only" below.
- `dispatch_agent(manifest, task)` — provider-neutral workflow-seat dispatch. The default implementation reloads effective `CtxConfig`, verifies every required logical capability against canonical policy, projects the adapter's normal headless sandbox/policy arguments, adds only an explicitly operator/caller-pinned model id, injects the manifest instruction layer, and appends `read_only_args()` last for read-only seats. Manifests describe methodology and requirements; they never grant permissions.
- `sandbox_residual_note()` (2026-08-23, issue #89) — names a known, recorded gap in this adapter's own `read_only_args()` pin for the operator's currently-resolved binary, or `None` when there is nothing to disclose. Default `None` (claude's own answer: `--disallowedTools` is the whole restriction claude needs). Consulted by `adapters::announce_sandbox_residual_once` whenever this adapter is resolved as the distiller or the workflow reviewer.
- `system_prompt_args(prompt)` — argv that appends `prompt` to the agent's system prompt for one run; empty when the adapter has no verified mechanism.
- `transcript_path(session)` — where this agent's own transcript file lives on disk. **Contract extended for issue #382 (2026-09-07):** an adapter whose harness keeps its transcript as a JSON snapshot file or a SQLite database — not naturally line-local JSONL — materializes newly seen rows into a `transcript_source::ShadowTranscript` (`sync_json_array`/`sync_sqlite`) from inside this call and returns the resulting shadow path instead of its harness's native file, so `parse_events` stays line-local JSONL for every adapter regardless. No new trait method: this is existing precedent (`CodexAdapter::transcript_path` already performs I/O inside this call, pinning a resolved rollout under `StateDir::rollouts()`). When no `StateDir` resolves, the native path is returned instead (degraded). See "The model catalogue and shadow transcripts" below — no in-tree adapter calls into `transcript_source` yet; it lands with the wave-1 adapters (issues #384-#386).
- `parse_events(jsonl)` / `structural_context(jsonl, last_n)` — turn a raw transcript into the ctx subsystem's normalized event stream and rolling structural summary. Must be line-local (each line's events depend only on that line), because `score.rs` feeds adapters only the bytes appended since the last incremental pass. **Both adapters emit wall-clock timestamps for speed telemetry (issue #293, v3.12.0):** `TurnStart`/`AssistantFinal`/`ToolCall` carry an `at_ms` (unix milliseconds, via `window::parse_iso8601_utc_ms`, `None` on an unparseable line — never guessed), and each parser also emits the new sibling variants `AssistantFirstText { at_ms }` (right before an `AssistantFinal` whose text is non-empty) and `ToolResultTimestamp { at_ms }` (right after the `ToolResult` it times) — not claude-only, both `ClaudeAdapter`/`CodexAdapter` do this. These feed `score::derive_speed_metrics` only; `rot.rs` treats the two new variants as no-ops (see [[Rot Engine]]'s "Speed metrics" section).
- `transcript_usage(jsonl)` / `transcript_usage_is_cumulative()` — expose bounded workflow phase token telemetry independently from rot scoring. Claude sums per-response input/cache/output usage in the supplied transcript fragment; Codex reads the latest cumulative `token_count.info.total_token_usage` snapshot and Zirv subtracts its checkpoint. **"Per response" is literal as of 2026-09-06** — see "Usage is folded once per API response, not once per row" below.
- `model_hint(jsonl)` (issue #155, review finding D1, 2026-08-27) — the most recently observed live model id inside `jsonl`, or `None` when this adapter has no per-transcript model signal (the default) or the fragment carries none. Must be line-local exactly like `parse_events`, since `score.rs` feeds a poll only the bytes appended since the last one — a caller keeps the last value it resolved across polls rather than reading a fragment with no hit as "no model at all." Claude's own implementation scans an assistant row's `message.model` field newest-to-oldest, so a live `/model` switch mid-session is reflected. This is what lets a live scoring path resolve `capabilities_for_model` with a real model string instead of always falling back to the conservative "unstated model" default — see "Capacity-aware rot gates" below and [[Rot Engine]].
- `context_window_tokens(model)` / `capabilities_for_model(model)` (issue #155, Phase 6(a)) — a model's real context-window capacity as a capability, so it can reach `rot.rs` without adding fs/clock/env access to the pure engine. `capabilities_for_model` is `capabilities()`'s counterpart for a *known* model string; `capabilities()` itself always calls `context_window_tokens(None)`, the adapter's own conservative default for an unstated model. **Both adapters' answers now delegate to `catalogue::context_window` (issue #381, 2026-09-07)** — see "The model catalogue and shadow transcripts" below; the returned numbers are byte-identical to the pre-catalogue hand-written values (equivalence-tested). See "Capacity-aware rot gates" below.
- `context_window_hint(jsonl) -> Option<u64>` (fixed 2026-09-05) — line-local like `model_hint`: a session's OWN reported context window, read fresh off the transcript fragment handed to this call, carried across incremental polls the same way `IncrementalScorer` already carries `model_hint`'s resolved model. Default `None`; codex is the only adapter that answers it today, reading `info.model_context_window` off the newest `token_count` line. `score.rs`'s `caps_with_window` layers this onto `Capabilities::context_window_tokens` when present — the session's own stated window outranks the adapter's static per-model default, since it is direct evidence from the harness itself. See [[Rot Engine]]'s token-gate resolution order.
- `counts_tool_calls()` (issue #155, review finding C2, 2026-08-27) — whether `parse_events` can ever emit `NormalizedEvent::ToolCall` for this agent, i.e. whether `--max-tool-calls` (see [[Ctx Supervisors]]'s "Delegated-worker budgets") has any real signal to count against. Default `true` (most adapters' `parse_events` are built directly off verified tool-call records); `CodexAdapter` overrides it `false`, since its own `parse_events` has no verified rollout shape for a tool call at all and deliberately never emits one. Checked once, at argument-validation time in `exec::run_with_clock`, before anything is spawned — a codex worker refuses `--max-tool-calls` outright rather than accepting a ceiling that would silently never fire. Deliberately outside `Capabilities`: nothing in `rot.rs` or anything scored reads it.
- `native_artifact_presentation(path, interactive_required)` — a verified harness-owned output-artifact channel that needs no browser/server. The default is none; both current adapters retain it because image *input* support is not an output presentation API.
- `compact_command()`, `quit_sequence()`, `capabilities()`, `register_turn_signal(session, socket)` — the remaining agent-specific knobs the supervisors need (whether the agent supports `/compact`, how to send it a clean quit, its `Capabilities` flags, and how to wire up the turn-signal socket via `TurnSignalSetup { env, instructions }`).
- `model_args(model)` — argv tokens that select `model` for one interactive launch. `chat.rs::extra_with_model` folds them into the launch's **extra arguments**, so `interactive_cmd` emits them after the positional prompt; they are deliberately *not* spliced in at `launch_prefix_len()`, which counts only the argv the operator wrote and does not count the tokens `base()` prepends when it routes a `.cmd`/`.ps1` shim through a launcher (see [[Ctx Supervisors]] and [[Untrusted Configuration]]). Default is empty (no verified flag, no guess); both current adapters override it.
- `resume_args(session_id)` — argv tokens that resume `session_id`'s own conversation, for the dashboard's quit/restore roster (`dash::roster::restore_argv`). Default `None` means this agent's resume story is unverified: a restore falls back to a plain prompt-carrying relaunch instead of a guessed flag; only `claude.rs` overrides it today (see below).
- `session_pin_args(session)` — argv tokens that make the agent adopt zirv's own session uuid as the id of the conversation it is about to start, so a later `resume_args` against that uuid finds something. Appended **only** to a freshly launched dashboard pane (`chat.rs::dash_orchestrator_pane` and `dash::pane_launch_extra`, the two seams that mint their own uuid), never inside `interactive_cmd` itself: `wrap`'s relaunch path deliberately lets the harness mint a fresh conversation on every restart, and a *restored* pane already carries `resume_args`, which a pin would contradict. Default is empty; only `claude.rs` overrides it (`--session-id <uuid>`, the same flag `headless_cmd` already pins every headless run with). Without it the roster stored a uuid the harness had never heard of and every restored claude pane died on `--resume` with "no conversation found".
- `review_model_below(seat)` (2026-08-18) — this adapter's own verified model ladder, one tier below `seat` (the orchestrator seat's own model, `cfg.chat.model`, or `None`/unrecognised — read as "assume the top tier," a deliberate spend-up default the operator can override). Default is `""`, meaning "no verified ladder" (the same "nothing verified to guess" answer `default_distiller_model`'s `None` gives); both registered adapters override it with real ladders (see below), each now delegating to `catalogue::rung_below` (issue #381 — see "The model catalogue and shadow transcripts" below). The sole caller is `resolve_review_model` in `harness_prompt_lines` below, used only when the operator has not set `review.<agent>` explicitly.
- `default_worker_model()` (2026-08-18) — this adapter's own hard-coded model for a delegated headless worker (`zirv ctx agent`, and the dashboard's own spawn-request pane variant) when the operator has not set `worker.<name>` explicitly. Default is `None` — the same "nothing verified to guess" answer as `default_distiller_model` and `review_model_below`'s empty-ladder default — meaning the launch omits `--model` entirely and the agent's own configuration picks. The sole caller is `resolve_worker_model` (see "The delegated-worker model default" below).

- `worker_system_prompt()` (2026-08-19) — this adapter's own layer for a delegated **Worker** session, the role-scoped counterpart to `base_system_prompt()`. `prompt::with_adapter_layer` splices exactly one of the two per launch, chosen by `PromptRole`, so a worker never receives the orchestrator layer's own delegate-everything coaching. Default `None`, the same "no verified mechanism" shape every other optional layer uses; only `claude.rs` overrides it (see below).

Several methods have trait-default implementations that only `claude.rs` currently overrides: `base_system_prompt()` (`None` by default — an unverified agent gets no layer of any kind, not another agent's instructions), `user_system_prompt_flag()`, `system_prompt_file_flag()`, `supports_system_prompt_file(launch)` (defaults to `false`, i.e. "fail open to argv delivery"), `launch_prefix_len()` (defaults to `1`, the count of leading argv tokens that are the program invocation itself rather than operator flags — used when a relaunch has to strip the program off an argv it didn't build), `resume_args()` and `session_pin_args()` (see above). **`worker_system_prompt()`/`sub_orchestrator_system_prompt()` are no longer claude-only (wrapper behaviour redesign round 2, 2026-09-01):** both default to `None`, but `codex.rs` now overrides them too, mirroring `claude.rs` — see "The codex adapter" below.

### Selection

`adapters::all(bin)` returns one boxed adapter per `ADAPTERS` row, in registry order — eight as of issues #384-#389 (claude, codex, copilot, droid, gemini, opencode, pi, qwen). `adapters::select(name, command, cfg: &CtxConfig)` picks one adapter, in priority order: an explicit `--agent` name, else `detect()` against the wrapped command's argv, else the registry's fallback (`resolve_default`, below — claude first in registry order, `cfg.agent_bin` supplies the adapter's `bin` override). In every arm, before the chosen adapter's own `ready()` is called, `select` checks `cfg.agents.refusal(adapter.name())` (the `.settings.toml` gate — see below) and returns that refusal as an `Err` if the agent is disabled. An adapter whose own program does not resolve to a launchable binary is still rejected at selection time by `ready()`, just after the gate check rather than before — every registered adapter shares this one failure mode today (`resolve_program`), so none is unready by construction.

`command_matches_adapter(adapter, agent_explicit, command)` is the trust gate used before injecting adapter-specific flags (like `--append-system-prompt`) into a wrapped command: it's true only when the operator named the agent explicitly or `detect()` matched, never merely because `select()`'s last resort had to default to claude with nothing backing it.

### The registry table and `resolve_default`

`ADAPTERS: &[(&str, AdapterCtor)]` (`mod.rs`) is the single source of truth for which adapters exist — a name paired with a constructor function:

| Name | Constructor |
|---|---|
| `"claude"` | `make_claude` → `ClaudeAdapter::new(bin)` |
| `"codex"` | `make_codex` → `CodexAdapter::new(bin)` |
| `"copilot"` | `make_copilot` → `CopilotAdapter::new(bin)` |
| `"droid"` | `make_droid` → `DroidAdapter::new(bin)` |
| `"gemini"` | `make_gemini` → `GeminiAdapter::new(bin)` |
| `"opencode"` | `make_opencode` → `OpenCodeAdapter::new(bin)` |
| `"pi"` | `make_pi` → `PiAdapter::new(bin)` |
| `"qwen"` | `make_qwen` → `QwenAdapter::new(bin)` |

`all(bin)`, `select`'s fallback, `describe_known_adapters`, `resolve_default`, and `readiness_note` all walk this table rather than naming adapters by hand, so none of them can drift from it or from each other — adding a new adapter is one entry here plus its own module. (Registration order above is alphabetical except `codex`, which stays second for historical reasons — every reader of `ADAPTERS` walks it in this same order, so `claude`/`codex` remain the two adapters a bare `resolve_default` prefers.)

**`readiness_note` (`zirv ctx --help`'s `about` text) has two generated clauses.** The first names every adapter whose own `ready()` still fails. The second names every ready adapter whose `capabilities()` is not fully true. Codex now reports system-prompt support because direct launches use `developer_instructions`; `system_prompt_supported(launch)` narrows that answer for shell shims. Its remaining static gaps are rot score, usage, and turn signal.

Codex has no file-based `developer_instructions` mechanism, so its composed system prompt always lands on argv (`-c developer_instructions=<json>`) — an oversized composed prompt used to hard-fail the whole launch on Windows (`os error 206`, the command line exceeding `CreateProcessW`'s ~32KB ceiling) under a workflow-heavy session with several accepted artifacts. Since issue #213 (2026-08-30), `prompt::injection_args_for_session` shrinks any inline-delivered composed prompt to a 24KB budget before it ever reaches the adapter, stripping memory/context/workflow layers in priority order rather than failing the launch — see [[Utilities]]'s "Inline-argv delivery is budgeted" section. Claude's file-based delivery path is unaffected.

`resolve_default(cfg: &CtxConfig) -> CtxResult<(Box<dyn AgentAdapter>, DefaultOrigin)>` is the fallback `select` calls when neither an explicit `--agent` nor argv detection named an adapter, but it also stands on its own — callers that want to *explain* the default rather than just use it (`zirv ctx status`'s `chat:` line, `zirv ctx chat`'s own resolution) call it directly:

1. If `cfg.agent` names an adapter, that one is used (after the gate check and its own `ready()`), tagged `DefaultOrigin::Configured`.
2. Otherwise, the first registry entry that is both gate-enabled and `ready()` wins, tagged `DefaultOrigin::FirstEnabledReady`.
3. If nothing qualifies, the error aggregates one line per adapter naming why it was skipped (the gate's refusal text, or the adapter's own `ready()` text) rather than reporting only the first failure — this is the same aggregated message `zirv ctx status` reuses (see [[Ctx Subsystem]]) instead of inventing its own wording.

`DefaultOrigin` is coarser than `chrome.rs`'s own `HarnessRule` (see [[Ctx Supervisors]]): `HarnessRule` adds a third case, `Explicit`, for an operator-named `--agent`, which never reaches `resolve_default` at all since `select`'s explicit-name arm short-circuits before the fallback.

### The `.settings.toml` enable/disable gate

`src/settings.rs` owns `AgentGate`, loaded once per `CtxConfig::load` into `cfg.agents` and consulted by `select` before every `ready()` call. Its module doc lays out the full layering (`~/.zirv/.settings.toml`, then `<repo>/.zirv/.settings.toml`, then `ZIRV_AGENT_<NAME>_ENABLED`) and the per-agent AND-fold trust rule (a repo may only narrow, the environment is the operator in both directions). What matters here: the gate is operator *policy* ("may zirv use this adapter"), separate from `ready()`'s implementation *state* ("does this adapter work yet"), and policy is checked first — a disabled codex reports the disable, not whatever `ready()` would have said. `select`'s three arms all honor it identically: an explicit `--agent codex` with codex disabled refuses outright (no fallback), and so does an argv `detect()` match — an operator-disabled adapter never silently falls back to a different one. The unknown-agent error's adapter list also marks disabled names, e.g. `known adapters: claude, codex (disabled)`. `zirv ctx status` prints one line per adapter from `AgentGate::states()`, enabled or disabled plus the file/variable responsible.

Three call sites use this registry: `src/script_runner/agent_command.rs` (a script's `agent_command` option runs a wrapped agent via `adapters::select`), and the two supervisors in `src/commands/ctx/exec.rs` and `src/commands/ctx/wrap.rs` (headless and interactive sessions respectively — see [[Ctx Supervisors]]).

**`[agents.<name>]` also carries an optional `capacity` key (2026-08-18).** The only recognized file value is `"small"` (absent means full capacity); it marks a harness capacity-limited, rendered in the harness roster as `-- small tasks only` (see `harness_prompt_lines` above) so an orchestrator routes only small, bounded briefs its way, for both review and `zirv agent` delegation. `AgentState::capacity_small` and `AgentGate::is_capacity_small(name)` carry the fold's answer; the trust shape mirrors `enabled` exactly, with one asymmetry: there is no `"full"` value a file can write, since absence already means full, so a repo file that is silent on capacity can never widen a home-narrowed `"small"` back — only `ZIRV_AGENT_<NAME>_CAPACITY` (`"small"`/`"full"`, either direction, an invalid value rejected loudly and scoped to that one agent) can. Both current `load` variants (the ordinary layered load and the operator-only fallback) fold it identically to `enabled`, and `.zirv/.settings.toml`'s own template documents the key next to `enabled`.

**A repo-only disable of the default agent must not silently select a different one (G, 2026-08-15).** `resolve_default`'s empty-`--agent` fallback used to skip a disabled candidate and simply continue to the next registry entry, without asking *who* disabled it. Once codex became ready too (see above), a repo checkout's own `.settings.toml` disabling claude was enough to make the fallback silently pick codex instead -- a different vendor account, with none of claude's capabilities -- which is exactly the "repo may narrow, not select" trust boundary this codebase holds everywhere else (see [[Untrusted Configuration]]). `AgentGate::disabled_only_by_repo(name)` reads provenance already computed by `load`'s own fold (`AgentState::disabled_by`, `Source::RepoFile` specifically, never `OperatorFile`/`Env`) to tell the two cases apart cheaply, with no second settings read. `resolve_default` now refuses outright -- naming both the narrowed adapter and what it would otherwise have silently picked -- the moment its fallback loop would land on a *different* adapter than a repo-only-disabled one; it is unaffected when nothing later in the registry qualifies either (no different provider was ever chosen, so the ordinary aggregated "no agent is both enabled and ready" error still applies and still names every candidate), and unaffected when the same agent was disabled by the operator or the environment instead (their own choice to make). `select`'s other two arms (explicit `--agent`, argv `detect()`) were never affected -- they already refuse a disabled agent outright rather than falling back to anything.

### The derived harness roster (`harness_prompt_lines`, 2026-08-16)

`adapters::harness_prompt_lines(cfg, current_adapter)` walks `ADAPTERS` in the same registry order as `readiness_note`, and renders one line per adapter describing whether an Orchestrator session may delegate to it right now via `zirv agent <name> "<prompt>"`: `- {name}: enabled, ready -- initiate with \`zirv agent {name} "<prompt>"\`` (plus a `(degraded: no ...)` suffix from `missing_capability_labels` when `capabilities()` isn't fully `true`), `- {name}: not installed (no '{program}' found)`, `- {name}: installed? not ready ({reason})` for an installed-but-otherwise-failing adapter, or `- {name}: disabled ({location})` for a gate-disabled one — naming where the disable came from (`AgentState::location`) rather than silently omitting the line, so an operator reading the prompt can tell "not offered because disabled in `.zirv/.settings.toml`" from "not offered because not installed." Unlike `readiness_note`, which never mentions a disabled adapter at all, this function's whole point is to be complete: it is the roster an Orchestrator session reads to decide what it can delegate to.

**A ready, enabled line also carries a capacity note (2026-08-18).** When `cfg.agents.is_capacity_small(name)` (the `[agents.<name>] capacity = "small"` marker in `.zirv/.settings.toml` — see "The `.settings.toml` enable/disable gate" below), an otherwise-ready line reads `- {name}: enabled, ready -- small tasks only -- initiate with ...` (or, for the self line, `enabled, ready -- small tasks only (this session's harness)`) instead of the plain "ready" wording. `HARNESS_PROMPT`'s final paragraph tells an orchestrator to route only small, bounded briefs to a harness marked this way, for both a cross-harness review request and a `zirv agent` delegation.

**A "ready" line only claims that after a real presence check, layered on top of `ready()`.** `AgentAdapter::ready()` is deliberately fail-open for a program name it cannot resolve — `resolve_program`/`ready()` still return `Ok` for a not-yet-real path, since several callers rely on that to fall through by name rather than error early. A roster line is a concrete invitation an orchestrator can act on immediately, so `harness_prompt_lines` layers `adapters::program_is_present(adapter.program())` on top: an explicit path or a `PATH` lookup (`PATHEXT`-aware on Windows) that must find a real file, never in place of `ready()`. `AgentAdapter::program()` (new, required, both adapters delegate to their own `self.program`) is what lets this caller — which only has `&dyn AgentAdapter` — ask what binary `ready()` actually resolved to. **Nit, not a bug:** off Windows the check is `Path::is_file()` only, with no executable-bit check, so it errs toward fail-open (a present-but-non-executable file still reads as "ready").

**This session's own harness never invites itself.** `current_adapter` (the resolved adapter's own `name()`, threaded in by both call sites below) marks its own line `- {name}: enabled, ready (this session's harness)` instead of the `zirv agent` invitation — `HARNESS_PROMPT` frames delegation as going to *other* harnesses, and a session cannot review-round itself.

**A global `agent_bin` override is handed only to the adapter it actually names.** Every `ctor(bin)` call used to reuse the operator's one `cfg.agent_bin` override for every adapter in the registry, which put one real binary's presence verdict onto every other adapter's line too. `agent_bin_names_a_different_adapter(bin, name)` checks whether `bin`'s basename names a *different* registered adapter than the one about to be built; when it does, that adapter is built with `None` instead, so its presence is judged from its own default program name exactly as if no override were configured.

The caller renders the lines and hands them to `prompt::compose` as data (`compose` itself stays free of the adapter registry and the settings gate); `wrap::run_with` and `chat.rs::dash_orchestrator_pane` both call it (passing their own resolved `adapter.name()`) only when `role == PromptRole::Orchestrator`, passing `Vec::new()` for a Worker launch — a delegated worker must not learn what it could delegate to in turn, the same recursion guard `HARNESS_PROMPT` itself already enforces. See [[Context Management]] and the prompt-composition ordering in `prompt.rs` (`PromptSource::Harnesses`, appended right after the harness layer, gated on `cfg.prompt.harnesses` and a non-empty roster).

**`HARNESS_PROMPT` (v6, 2026-08-22) states cross-harness delegation parity explicitly.** The delegation bullet's own tone used to be far terser than `ORCHESTRATOR_PROMPT`'s (claude-only) native-subagent-dispatch guidance — an emphasis asymmetry that read as "native dispatch is the real option, cross-harness delegation is an afterthought" even though nothing named a harness unfavourably. It now says plainly that delegating via `zirv agent` gets the same bar and the same confidence as a native subagent dispatch, with no extra hesitation for landing on a different vendor's model. `HARNESS_PROMPT` itself stays vendor-neutral by construction (it never names a model or tier vocabulary — that lives only in each adapter's own `base_system_prompt`), asserted by a regression test (`harness_prompt_never_names_vendor_specific_models`, `prompt.rs`).

### The review-routing line (`review_roster_line`, 2026-08-18)

`harness_prompt_lines` appends one trailing line after its per-adapter lines, naming which model runs code review for every *enabled* harness: `resolve_review_model(cfg, name, adapter)` picks the operator's own `cfg.review.claude`/`cfg.review.codex` when set (`REPO_FORBIDDEN` — see [[Untrusted Configuration]]), else `adapter.review_model_below(cfg.chat.model.as_deref())`. Each entry renders as `{name} -> "{model}" ({note})`, and the whole line states the routing rule: "run every code review on the named model, never on an orchestrator seat's own model" — softened to "never on a model above the named one" whenever any entry's resolved model text equals the seat's, case-insensitively (`equals_seat`). That equality happens two ways, both legitimate: a harness's ladder default is already at its floor tier (seat `"haiku"` resolves claude's own default to `"haiku"` too — the note reads "floor tier: the seat is already at the bottom rung" instead of "default: one tier below the seat"), or the operator explicitly configured `review.<agent>` equal to the seat (their call — the note reads `(configured)`). A disabled harness has no entry at all (absence, not silence, matching the per-harness line's own convention), and `review_roster_line` returns `None` — no line, not an empty one — when no harness is enabled. Claude's `ORCHESTRATOR_PROMPT` review bullet and its `.claude/agents pin their own models` clause were reworded to point at this line and carve out the one exception that outranks it (see below).

**`resolve_review_model` is now also the reviewer's own launch-time enforcement seam, not just this advisory line's source (`pub(crate)`, harness iteration round 3, 2026-09-02).** Before, an operator or a wrapped session could read the roster's routing line and still have the automated reviewer run on whatever model the adapter's bare CLI happened to default to — the line was advisory text, never enforced. `workflow::review::reviewer_argv` now calls `resolve_review_model` directly and appends `adapter.model_args(&review_model)` to the reviewer's own launch argv, before the read-only floor so no later argument can weaken it — see [[Workflows]]'s "Bounded reviewer workers" section for the launch-side detail. Practical consequence: with `chat.model` unset, a fresh install's automated reviewers now literally launch on the ladder's top tier (`opus` for claude) rather than an unpinned CLI default — an operator decision surfaced, not a new default invented — see the 2026-09-02 [[Decision Log]] entry.

### The delegated-worker model default (`worker_model_args`, 2026-08-18)

A delegated headless worker (`zirv ctx agent <name> "<prompt>"`, and the dashboard's own spawn-request pane variant, `dash::mod::fulfill_spawn_request`) used to silently inherit whatever model the operator's own interactive default happened to be — often a far pricier model than the delegated task needs. `adapters::resolve_worker_model(cfg, name, adapter)` picks the operator's own `cfg.worker.claude`/`cfg.worker.codex` when set (`REPO_FORBIDDEN` as a whole table — see [[Ctx Subsystem]] and [[Untrusted Configuration]]), else `adapter.default_worker_model()`: claude hard-codes `Some("sonnet")`, codex has none (`None`, so its own CLI/config default applies untouched). `worker_model_args(cfg, name, adapter)` turns the resolved model into argv (`AgentAdapter::model_args`) or returns empty when nothing resolves. Unlike `resolve_review_model`, there is no ladder: a delegated worker has no orchestrator seat to be "one tier below," so the adapter-owned default is a fixed name, not a function of `cfg.chat.model`.

Two callers apply it, each guarding the operator's own explicit choice first:

- **`agent.rs`'s `worker_launch_flags`** (the `zirv ctx agent` headless path) checks `flags_pin_model` first — a bare `--model`/`-m`, or the joined `--model=value`/`-m=value` form, anywhere in the operator's own trailing flags — and leaves `flags` untouched if so; codex's `-m` short alias is recognised too, so a configured `worker.codex` cannot end up prepending a conflicting `--model` ahead of an operator's own `-m <value>` (fixed in the same round `seat_model_env` gained effective-model tracking, below). Otherwise `worker_model_args`'s result is prepended ahead of `flags` as trailing extras — the same discipline `chat.rs::extra_with_model` uses for the orchestrator seat — never spliced into a launcher prefix.
- **`dash::mod::pane_model_args`** (called by `fulfill_spawn_request`) prefers the request's own `model` field over `worker_model_args`. A spawn request carries no trailing flags of the operator's own except that one: since 2026-08-19 `agent::try_join_dashboard` recognises a **lone** `--model` pin (any spelling `adapters::model_only_flags` reads) and puts it in the request, while a request carrying anything else still declines the pane and runs headless — see [[Ctx Supervisors]]'s spawn-request protocol. The pin is re-checked at the authority side rather than trusted (a blank or flag-shaped value falls back to the resolved default), the same defense in depth the request's prompt gets from `argv_unsafe_prompt`. Without this, `HARNESS_PROMPT`'s new "name the cheapest model on every delegation" guidance would have cost a dashboard session its visible pane on every delegated task.

`worker.claude`/`worker.codex` are charset/length/leading-dash validated the same way `chat.model`/`review.*` are (`validate_model_str`), since — unlike `review.*`, which only ever lands in injected prompt *text* — these keys reach a real launch argv directly.

### Windows launcher rewriting

`mod.rs` also owns `resolve_program`/`ResolvedProgram`, used by both adapters' `base()` helpers. Off Windows it's the identity. On Windows, `std::process::Command` only ever appends `.exe`, so an npm-installed `claude` (actually `claude.cmd`) fails to spawn directly (`CreateProcessW` error 193); `resolve_program` walks `PATH`/`PATHEXT` the way the shell would and routes `.cmd`/`.bat` through `cmd.exe` and `.ps1` through PowerShell. A name that resolves to an unlaunchable extension is reported as a named `ready()`-style error before spawning; a name that resolves to nothing at all is left alone so the OS's own "not found" still surfaces.

Whenever `resolve_program` (or an already-resolved shim argv — `adapters::launch_reparses_through_shim`, fixed 2026-08-14) routes a launch through `cmd.exe /c`, that command line is **re-parsed by cmd.exe itself** before the shim ever runs, which is a real command-injection surface for any repo-controlled text riding along on the argv. `adapters::guard_cmd_shim_reparse` is the fail-closed backstop over that surface at every spawn seam; the full defense-in-depth mechanism (forced system-prompt-file delivery, stdin-delivered headless prompts, the backstop itself, and the two round-9 gaps closed in it — an unguarded `--help` probe, and the shim-detection false negative that left the file-form defense inert on `zirv chat`/bare `zirv`/the dashboard orchestrator) is documented in full on [[Known Issues]] ("Windows `cmd.exe` argv reparse…"), not duplicated here.

## The model catalogue and shadow transcripts (issues #381/#382, 2026-09-07)

**`catalogue.rs` is one pure per-vendor model catalogue replacing four hand-written ladders** that used to live separately in `adapters::claude`, `adapters::codex`, `handover::tier_default`, and `price::built_in_table` — no fs/clock/env/net access, so identical lookups give identical answers everywhere, the same purity discipline `rot.rs` holds. A `Vendor` (`anthropic`, `openai`, plus ten survey-dated priced vendors: google, xai, qwen, moonshot, mistral, deepseek, zhipu, minimax, meta, amazon, all `as_of: Some(CATALOGUE_AS_OF = "2026-09-07")`, plus three rungless local-runtime vendors an `[endpoint.<agent>]` override can name — `ollama`, `lmstudio`, `vllm` (issue #395, 2026-09-09), no fixed lineup or published price so each carries empty rungs, no prices, and no default context window) carries a strength-ordered ladder of `Rung`s. Key functions: `rung_of`/`rung_below`/`strength` (substring-on-lowercased match, same rule both adapters used to implement by hand), `context_window` (a rung's own window, else the vendor's fallback — `None` when neither states one, which is every OpenAI rung today, since no static per-model capacity is verified for codex), `tier_model` (the rung tagged `Cheap`/`Standard`/`Deep`, what `handover::tier_default` now resolves through instead of its old per-agent match), and `built_in_prices()` (feeds `price::built_in_table`). `normalize_id`/`vendor_of` strip OpenRouter/Bedrock/Vertex decoration off a real-world model string and resolve its vendor — carried `#[allow(dead_code)]` today, since their first caller lands with the wave-1 adapters (issues #384-#386), not this track. `anthropic`/`openai` carry the exact prices/strengths/windows/ids the four call sites priced before this module existed, pinned by equivalence tests in `adapters::claude`, `adapters::codex`, `handover`, and `price` — claude and codex's own answers through `review_model_below`/`model_strength`/`default_worker_model`/`default_distiller_model`/`context_window_tokens` are byte-identical to the pre-catalogue hand-written ladders. Claude keeps its own `[1m]`/`-1m` long-window marker check layered on top of `catalogue::context_window`, since that is a claude-specific convention, not part of the ladder.

**`transcript_source.rs`'s `ShadowTranscript`** materializes a harness's own JSON-array snapshot or SQLite database into a zirv-owned shadow JSONL file (`<state>/shadow/<short>.jsonl` + `StateDir::shadow()`), so the unchanged, JSONL-based rot engine can score a harness whose native transcript isn't naturally line-local, without teaching `supervise::Watcher`/`score::IncrementalScorer`/any `parse_events` about JSON arrays or SQL. `sync_json_array(source, extract)` counts the shadow's own lines as its position (no sidecar cursor file: a crash between two writes therefore never replays rows) and rewrites from scratch on a shrink (a new session reusing the file, or a genuine truncation) — `Watcher::read_appended` already reads same-or-shorter length as a restart. `sync_sqlite(db, query)` opens the database with a plain `SQLITE_OPEN_READ_ONLY` connection rather than `?immutable=1` — a WAL reader never blocks a writer and never needs the immutable promise, and unlike `immutable=1` it DOES attach the `-wal` file, so a committed-but-uncheckpointed row is visible immediately; `?immutable=1` is kept only as a fallback for a read-only containing directory that cannot create the `-shm` file a plain open still needs. Blob columns are skipped (no base64 dependency for bytes nothing downstream reads). Both sync methods fail soft — a missing/mid-write source file, or a database that won't open under those flags, leaves the shadow untouched and simply returns its path, never taking a supervised session down over a transcript-read hiccup. Shadow files idle past `SHADOW_RETENTION_DAYS` (30, mirroring the safety-decision log's own retention) are pruned by mtime on `ShadowTranscript::for_session`. New dependency `rusqlite 0.40` (`bundled`) — see [[Architecture/Technology Stack|Technology Stack]]. `#![allow(dead_code)]` module-wide: nothing in the binary calls into it yet outside its own tests until a wave-1 adapter (issues #384-#386) lands.

### Endpoint overrides (issue #395, 2026-09-09)

An operator-only `[endpoint.claude]`/`[endpoint.codex]` table in `~/.zirv/ctx.toml` (never a repo layer — `REPO_FORBIDDEN` as a whole table, see [[Untrusted Configuration]]) points claude and/or codex at an Anthropic-/OpenAI-compatible vendor endpoint instead of that adapter's own native account: GLM (`zhipu`), Kimi (`moonshot`), DeepSeek, Qwen, Mistral, MiniMax, or a local Ollama/LM Studio/vLLM runtime (three rungless catalogue vendors added alongside this feature, since a self-hosted runtime has no fixed lineup or published price). `EndpointTarget { vendor, base_url, credential_env, model, wire_api }` (`config.rs`) names a real `catalogue::vendor` slug (validated at load, so every downstream lookup is infallible in practice), the endpoint URL, and the NAME of an environment variable holding the vendor's API key — never the secret itself, never read or logged during validation. Review finding (#395 follow-up): `validate_endpoint_target` also refuses a `base_url` containing whitespace, `'`, `"`, or any `adapters::CMD_REPARSE_METACHARS` character (`&|<>^()%!` plus `\n`/`\r`) — codex's own launch renders `base_url` into a `-c model_providers.<vendor>.base_url=<toml_quoted_string(...)>` argv token, whose escaped-basic-string fallback (triggered by an embedded `'`) introduces a raw `"` and other reparse metacharacters `guard_cmd_shim_reparse` would otherwise have to fail closed on at launch time; the same rule applies to `endpoint.claude` too, for one shared list rather than two that could drift.

**Both adapters carry the resolved target as an `Option<EndpointTarget>` instance field**, attached post-construction by the new `AgentAdapter::apply_endpoint(&mut self, endpoint)` trait method (default no-op; overridden by `ClaudeAdapter`/`CodexAdapter` to store it and by `endpoint_vendor()` to expose the attached vendor slug to a caller holding only `&dyn AgentAdapter`). `adapters::apply_endpoint_override` is the one helper `select`/`resolve_default` call, right after constructing the chosen adapter and before its own `ready()` check, so a launch surface — `zirv ctx chat`/`wrap`/`exec`/`zirv agent`, and the harness-roster liveness probe — never needs its own copy of "which `cfg.endpoint.<name>` matches this adapter." `ready()` is also where a MISSING credential fails loudly, before any child is spawned: both adapters now check `adapters::require_endpoint_credential`, which reads the named variable and refuses by NAME only (never a value) when it is unset or empty — the identical pre-spawn gate an unlaunchable binary already goes through.

**`EndpointTarget::pin_model(requested)`** is the one helper both adapters' `model_args` funnel every `--model`/`-m` emission through: the operator's own `model` when set, else the endpoint vendor's strongest catalogue rung id (rungs are stored strongest-first). A `requested` model — `chat.model`, a handoff ladder tier, an operator `--model` — is honoured only when it resolves on the ENDPOINT VENDOR's own ladder by alias or id; otherwise it is silently replaced by that vendor's own default, so a claude alias like `opus` (or a codex tier like `gpt-5.6-sol`) can never reach a GLM/DeepSeek/etc. endpoint. Load-time validation (`config.rs`'s `validate_endpoint_target`) makes `model` REQUIRED for a rungless vendor (`ollama`/`lmstudio`/`vllm`), since there is then no ladder to default from at all.

Review finding (#395 follow-up): `model_args` calls through a new `AgentAdapter::pin_model_for_endpoint(model)` trait method (default no-op; `ClaudeAdapter`/`CodexAdapter` override it to call `EndpointTarget::pin_model`) — three more call sites now route through the SAME pinning rather than a copy of it: both adapters' `distiller_cmd` (previously hardcoded claude's `--model haiku`, or emitted codex's native cheap alias unpinned, regardless of any attached endpoint — the one judgment/distillation child every rot-scoring pass spawns would otherwise send a vendor a model id that isn't valid on that account) and `adapters::review_roster_line` (attaches the same `apply_endpoint_override` a real launch gets before computing its advisory review-model text, so the roster line can never name a native-ladder model for a harness the operator retargeted at a vendor endpoint, even though the real review launch already pins via `model_args`).

**`provider()`/`provider_for_model()`** report the endpoint vendor's own catalogue slug rather than the adapter's static `"anthropic"`/`"openai"` whenever an endpoint is attached, so `StateDir::usage_for`/the cost ledger/pacing all attribute the launch to the account it actually bills — see [[Usage and Pacing]]'s "Spend-only providers" section for what that means for the usage-window surfaces (there is structurally no window collector for a vendor endpoint, so it renders "spend-only" rather than "unknown"). The harness roster (`harness_prompt_lines`) and `zirv ctx status` both surface the override without ever printing the base URL or the credential: a roster line reads `- claude: enabled, ready ... (endpoint: zhipu)`, and `status` prints a dedicated `endpoint: claude -> zhipu (<base_url>, key from $<credential_env>)` line per configured agent.

**Claude's own launch (`base()`)** sets `ANTHROPIC_BASE_URL` and, reading the named variable fresh at spawn time, `ANTHROPIC_AUTH_TOKEN` on the child's environment. **Codex's own launch** instead registers a named `model_providers.<vendor>` config entry and selects it via `-c` overrides — `model_provider=<vendor>`, `model_providers.<vendor>.{name,base_url,env_key,wire_api}` — so codex itself reads the key from the registered `env_key` rather than zirv ever placing the secret on argv; every token is TOML-quoted the same way `read_only_sandbox_args`'s own state-root path already is, so it passes `guard_cmd_shim_reparse` on a shim launch. `wire_api` defaults to `"chat"` (`"responses"` also accepted).

## The `claude` adapter

`ClaudeAdapter` (in `claude.rs`) wraps a `program` plus `bin_args` (so `ZIRV_CTX_AGENT_BIN="sh /tmp/stub.sh"` or `/usr/bin/env claude` both work) and an optional `home` override for tests. Every command starts from a shared `base()` that applies the program, its leading args, and the Windows resolution above uniformly.

- **`headless_cmd`** builds `claude -p <prompt> --session-id <id> <extra...>` — this is what pins a specific `SessionId` onto the launched process for `exec`.
- **`interactive_cmd`** builds `claude [<initial_prompt>] <extra...>`, the positional form `wrap` uses to start or resume a TUI session.
- **`ready()`** just calls `resolve_program` — claude is always considered implemented; the only failure mode is an unlaunchable binary.
- **Attested `--settings` layer** (`launch_settings_path`/`launch_settings_value`): materializes the fingerprinted policy-snapshot/settings pair every supervised launch attests (see [[Command Safety]] for the full attestation/hook mechanism). Two issue #147 (2026-08-26) changes to that layer's own content: it no longer injects a native `permissions.ask` rule naming `Bash(dangerouslyDisableSandbox:true)` (documented Claude behavior makes a native settings rule independent of a `PreToolUse` hook's decision, so that rule silently defeated every hook-side sandbox-escape `allow` — the attested safety hook is now the sole zirv-side decision point for an escape), and `launch_settings_value` gained a third parameter, `mail_write_dir: Option<&Path>` (`launch_settings_path` resolves it from `state.mail()`, best-effort), which adds `sandbox.filesystem.allowWrite` scoped to only that directory so `zirv ctx send` succeeds inside a sandboxed session. **Issue #168 (2026-08-27) briefly widened that parameter to `allow_write_dirs: &[PathBuf]`** (also passing `state.memory()`/`state.logs()`/`state.groups()`/`state.handoffs()`), **then reverted it on code review** the same day: with `is_reserved_zirv_escape_safe` (named `is_zirv_ctx_escape_safe` until issue #224; see [[Command Safety]]) restricted to an explicit non-subprocess-launching verb allow-list, every `zirv ctx <state-verb>` already rides the ALWAYS-ALLOWED unsandboxed retry, so the OS-sandbox `allowWrite` widening bought no operator-facing benefit while giving up defense-in-depth (an unlisted/unmatched command that isn't `zirv ctx` at all still can't write to memory/logs/groups/handoffs from inside the sandbox). The policy-snapshot/attestation directory (under the operator's HOME, not the state root) stays deliberately never allow-listed either way. `#[cfg(not(windows))]` code — both the widening and the revert were verified on `rust:1-bookworm` (non-root) per this repo's own Linux/Docker convention.
- **Sibling-repo/worktree write grants, the subprocess env scrub, and re-opened ssh files — all issue #329 (2026-09-03).** `LaunchEnvironment::resolve()` now derives `workspace_write_roots`: the launch repository's own linked worktrees (`linked_worktree_roots`, the discovery half `linked_worktree_args` already used for `--add-dir`, now shared) plus its **sibling checkouts** — every direct child of the repo's parent directory that is itself a git checkout — followed by each sibling's own linked worktrees, read straight from `<sibling>/.git/worktrees/*/gitdir` with no `git worktree list` process per sibling (`sibling_repo_roots`/`linked_worktrees_from_git_dir`). These roots land in BOTH `sandbox.filesystem.allowWrite` and `permissions.additionalDirectories` as literal paths — never `--add-dir` (a sibling's own `.claude/` hooks must not load into this session) and never a glob (`additionalDirectories` has no glob support on any platform, and `allowWrite` silently drops glob entries on Linux/WSL2). Scope is deliberately narrow: never the parent directory itself, nothing when the parent is a filesystem root or the home directory, nothing at all when no home directory resolves (fail closed), capped at `MAX_SIBLING_REPOS` (32) siblings and `MAX_LINKED_WORKTREES` (16) worktrees per repo. Trust boundary (codex review round on #329): a sibling is repo-owned, so a `gitdir` entry is only believed when the named worktree's own `.git` file links BACK to that exact `.git/worktrees/<name>` directory (the mutual link git keeps) — a sibling cannot nominate `~` or `/` as a worktree; a sibling reached through a symlink is skipped (its canonical path must be a direct child of the parent); and every root passes `is_grantable_root` — never a filesystem root, the home directory or an ancestor of it, or the launch repo, an ancestor of it, or a path inside it. This supersedes the prior scope ("other repositories remain out of scope; callers use `zirv agent --workdir`") — see the 2026-09-03 [[Decision Log]] entry. **`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` is no longer set by default** in the same launch settings: reading the installed Claude Code binary (2.1.259) showed the switch strips `SSH_AUTH_SOCK`/`SSH_AGENT_PID`/`GIT_SSH_COMMAND`/`GH_CONFIG_DIR`/`DOCKER_CONFIG`/`KUBECONFIG`/`GNUPGHOME` and the like from EVERY Bash subprocess and silently forces the permission mode to `default` — exactly why the settings file's own `env.SSH_AUTH_SOCK` export never reached a `git fetch`. It is now the operator-only `[sandbox] scrub_subprocess_env` (default `false`, `REPO_FORBIDDEN`, `ZIRV_CTX_SANDBOX_SCRUB_SUBPROCESS_ENV`) — see [[Untrusted Configuration]] for the full rationale. **`~/.ssh/known_hosts`/`~/.ssh/config` are re-opened via `sandbox.filesystem.allowRead`** (`SSH_NON_SECRET_READ_PATHS`): `denyRead`'s blanket `~/.ssh` entry used to block even the two non-secret files ssh needs to verify a host, so a sandboxed `git fetch`/`push` died before it ever reached authentication; Claude resolves overlapping read rules by specificity, so naming these two files re-opens exactly them while every private key under `~/.ssh` stays denied by the broader rule.
- **Compact output — the `PostToolUse` hook (`zirv ctx hook posttool`, issue #326, current).** `launch_settings_value` wires one more hook alongside the `PreToolUse` entries above, on its own event: matcher `Bash`, command `zirv ctx hook posttool`, registered **synchronously** (never `"background": true` — a replacement that arrives after the result has already reached the model replaces nothing). `zirv setup` writes the same entry through `CLAUDE_COMPACT_OUTPUT_HOOK`, claude-only for a stronger version of `CLAUDE_SAFETY_HOOK`'s own reason: it depends on claude's documented `hookSpecificOutput.updatedToolOutput` contract, and codex has no `PostToolUse` event at all (which is why `zirv ctx run --compact` exists as the explicit, harness-neutral spelling — see [[Ctx Subsystem]]). The handler stores the result's combined stdout+stderr verbatim in the same `outputs/` store `zirv ctx run` uses, then returns `updatedToolOutput` carrying the compact summary as `stdout`, an EMPTIED `stderr` (the summary already folds both streams; leaving the original stderr beside it would put back the exact bytes this hook exists to remove), the original `interrupted` (a fact about the run, not the output), and `isImage: false`. That shape is load-bearing: claude validates a built-in tool's replacement against the tool's own output schema and **ignores** a value that does not match, using the original — so a schema mistake here degrades to "no compaction", never to a broken result. **What may be compacted at all is decided per command, not per byte count** (`output::classify_compaction`). A READER — `cat`, `sed`, `head`/`tail`, `grep`/`rg`, `find`/`fd`, `ls`, `jq`, the `diff` CLI tool, `git blame|grep`, an operator's own `[output] verbatim` entry, or anything carrying a pipe or redirect — is **never** compacted at any size: a model reads that output verbatim and then edits against it, so a head/tail summary does not cost tokens, it corrupts the edit, and the model has no way to notice. zirv's own retrieval surface (`zirv ctx output …`, `zirv ctx run --full`) is verbatim for the same reason squared: compacting it produced a second summary, and no `--range` could then reach the original. A KNOWN build/test/log family (cargo/nextest/rustc, npm/pnpm/yarn/npx, pytest, go, dotnet, make, mvn/gradle, tsc, eslint, docker, `git fetch|pull|push|clone|status`) compacts from `[output] compact_min_bytes` (4096), because the summary provably keeps that shape's own signal — since issue #413 (v3.36.0), a cargo/nextest/pytest/vitest/jest/go-test result additionally runs through `testrun.rs`'s per-family extractor first, replacing the generic diagnostic scan with exact (name, location, message) triples once that family's own markers confirm the argv-based guess. Everything else compacts only past `[output] compact_generic_min_bytes` (16384), and its summary states explicitly which lines it dropped (`N lines omitted between line A and line B -- fetch with zirv ctx output show <id> --range A-B`), so a cut is never something to infer. **`git diff`/`show`/`log -p`/`format-patch` are a fourth scope, `Diff` (issue #412, v3.36.0), not `Verbatim`**: their omitted middle is exactly the part a model is about to edit against, so below `[output] diff_max_bytes` (default 65536, narrow-only rather than `REPO_FORBIDDEN`) the diff reaches the model untouched, and above it `output_diff.rs` replaces it with a bounded per-file `path +N -M` listing derived from the diff's own grammar, capped at 200 files, never a `@@` hunk header or body line — see [[Ctx Subsystem]] for the scan/render detail. Segments come from `safety::normalize_segments`, so a reader hidden behind `sh -c`, an env prefix or a launcher is still found. Every `[output]` key is `REPO_FORBIDDEN` **except `diff_max_bytes`**, which is narrow-only (a repo checkout may only lower it, `ZIRV_CTX_OUTPUT_DIFF_MAX_BYTES` is the operator's own final override) — see [[Untrusted Configuration]]. Fails open by printing nothing and exiting 0 on every path it does not fully understand: an unparseable payload, a non-`Bash` tool, `isImage`, output below the threshold, a result claude has ALREADY truncated and spilled itself ("Output too large … saved to"), binary or non-UTF-8-shaped content (issue #411, `output_shape::sniff_is_binary`), an unresolvable state dir, a failed persist, or a summary whose own mandatory failure content would not fit the cap (see [[Ctx Subsystem]]). The persist-then-replace ordering is the contract: nothing is ever replaced unless the full original is already on disk, so a summary can never be the only surviving copy. Distinct from the `PreToolUse` guards in every direction — it runs after the tool, cannot express a `permissionDecision`, and never sees a command before it runs. **Every `Bash` result this hook inspects is also recorded into a durable savings ledger (`<state>/ledger.sqlite`, issue #422)** — fail-open, never affecting the hook's own return value — feeding `zirv ctx savings` and a `compaction:` line on `zirv ctx status`; see [[Ctx Subsystem]]'s `savings` verb entry.

### Usage is folded once per API response, not once per row (2026-09-06)

Claude Code >= 2.1.209 writes **one transcript row per CONTENT BLOCK** of one API response — thinking, text and each `tool_use` land on their own rows, and every one of them repeats that response's identical `message.usage` object under the same `message.id`. `fold_assistant_usage` summed per row, so it multiplied a session's real spend by however many blocks its responses happened to carry: on the committed fixture, 48 assistant rows across 20 distinct `message.id`s summed to 10,592,616 tokens against a real 4,922,703 (x2.15); a live transcript measured x2.55.

Every reader of `transcript_usage` was wrong by that factor: `exec.rs`'s `evaluate_worker_budget` (so `--budget-tokens N` stopped a claude worker at roughly 40% of the budget the operator asked for), the delegation cost ledger, `ctx status`'s work-group totals, dash pane usage, and workflow phase telemetry. The fold now tracks the last-seen **response identity** — `message.id`, falling back to `requestId` — and adds a row's usage only when that identity changes. Tracking the last id rather than a set keeps it streaming-safe over an append-only transcript. A row carrying neither id has no response identity to dedupe on and still counts on its own, so a transcript recorded before the block split reads exactly as it always did.

The same rule reaches `window.rs`'s own per-row folds — `sum_file` (the trailing 5h/7d usage windows) and `session_spend_of` (the per-session spend breakdown, see [[Usage and Pacing]]) — through the shared `claude::response_identity`, so the usage windows and the adapter can never disagree about what one response is.

### Subagent spend lives in the `subagents/` directory (2026-09-06)

`sidechain_transcript_usage` folds `isSidechain: true` rows out of the main transcript, but current Claude Code writes **none there at all** — 0 of 15,510 rows across twelve recorded real sessions — so `workflow::engine::sidechain_usage_since`, and with it every phase's sidechain telemetry bucket, was permanently `None`. Subagent turns now live in sibling files: `<transcript-dir>/<session-id>/subagents/agent-<id>.jsonl` (plus an `agent-<id>.meta.json`), whose rows *do* carry the flag.

`claude::subagent_transcript_usage(transcript, main_range)` folds that directory. `main_range` is the caller's own phase slice of the main transcript; its first parseable `timestamp` is the phase floor, so the answer keeps the "since the checkpoint" meaning the byte-range read gave the in-file branch, and a slice with no parseable timestamp yields `None` rather than attributing a whole session's subagent spend to one phase. Rows are deduped per API response like every other usage fold, a subagent row with no timestamp of its own is skipped (the convention `window::sum_file` already applies), and the scan is bounded by `MAX_SUBAGENT_TRANSCRIPTS` (256 files) and `MAX_SUBAGENT_BYTES` (32 MiB) with the newest files read first. The in-file fold stays as the **preferred legacy branch**: a transcript recorded by an older harness still reads exactly as before, and the directory is consulted only when it answers `None`.

**Residual:** a phase whose subagent rows straddle the byte caps reports what it read. `parse_events`' own line-locality is untouched — this fold is a separate, path-taking function, never part of the incremental event pass.

### Thinking blocks are sized from the reported thinking tokens (2026-09-06)

`AssistantThinking { byte_len }` measured `message.content[].thinking`, which current Claude Code writes as `""` with only a `signature` — 124 of 124 blocks across six recorded real sessions, and 18 of 18 in the committed fixture. `breakdown::attribute_window`'s thinking bucket therefore read zero for every live session, and its weight silently went to the other buckets. When a row carries a thinking block whose text is stripped (or a `redacted_thinking` block), the event is now sized from that response's own `usage.output_tokens_details.thinking_tokens`, scaled to the **byte** unit every other breakdown weight is in at this codebase's 4-bytes-per-token estimate (the same ratio `compile.rs` and `context_status::BYTES_PER_TOKEN` use). Real thinking text still sizes itself, and a row with no thinking block at all is never credited with the response's thinking tokens. **Residual:** a single response splitting its thinking across two block rows would be credited its reported total twice, because `parse_events` must stay line-local.

- **`ToolCallRead`/`ToolCallEdit` (issue #294, `zirv ctx measure`):** two more sibling events emitted right after `ToolCall`, the same pattern `ToolCallPath`/`ToolResultSize` (issue #312, above) already established — never a new field on `ToolCall` itself, which several call sites match with exhaustive field patterns. `ToolCallRead { ranged }` fires for a `Read` tool_use block, `true` when its `input` carries an `offset` and/or `limit`. `ToolCallEdit { old_bytes, new_bytes, core_bytes }` fires for `Edit` (its `old_string`/`new_string` lengths) or `MultiEdit` (summed across every element's own pair); `core_bytes` is `measure::core_change_bytes(old, new)` — what remains of both strings after stripping their shared prefix and suffix, `0` for a genuine no-op edit. Neither variant is emitted for `codex`, which has no verified `ToolCall` shape at all (see the `codex` adapter section below). `rot.rs`/`score.rs` fold both into their existing catch-all arms — neither is a rot signal.
- **Session ids**: claude accepts an explicit `--session-id` on the headless path, so zirv controls the id up front; there's no equivalent for `interactive_cmd`, which relies on claude's own session management plus the transcript-scanning fallback above.
- **`model_args`** emits `--model <model>`, verified against the real CLI (`claude --help`, v2.1.220) — under an `[endpoint.claude]` override (issue #395, see "Endpoint overrides" above), the model is pinned through `EndpointTarget::pin_model` first and `base()` also carries `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`. **`session_pin_args`** emits `--session-id <uuid>` (the flag `headless_cmd` already uses, offered to interactive dashboard panes so the roster's stored uuid *is* the claude conversation id). **`resume_args`** emits `--resume <session_id>` — not a fresh claim: `wrap::extra_launch_flags` already strips `--resume` on every restart (it pins a launch to an existing conversation) and `exec.rs`'s `RESUME_FLAGS_WITH_VALUE` already treats it as a two-token flag, so this only wires up an already-verified flag for the dashboard's own restore path.
- **`context_window_tokens(model)`** (issue #155, Phase 6(a)) maps a model id to a capacity: `DEFAULT_CONTEXT_WINDOW_TOKENS` (200_000, conservative) for every id it does not recognise as a long-window seat and for `None` (unstated model), `LONG_CONTEXT_WINDOW_TOKENS` (1_000_000) for one carrying a `[1m]`/`-1m` marker (case-insensitive substring match). Conservative by design: an overstated capacity raises the restart ceiling past what the seat can actually hold, and overrunning the real window is a far worse outcome than rotating slightly early. **`model_hint(jsonl)`** (issue #155 review finding D1, 2026-08-27) reads the last `message.model` field off an `assistant`-typed transcript row, scanned newest-to-oldest — the newest wins so a live `/model` switch mid-session is reflected rather than the session's original model — off the same lines `parse_events`/`transcript_usage` already walk, no separate pass.

## The `codex` adapter

`CodexAdapter`, in `codex.rs`, is a **supported adapter with an honestly degraded capability set**, not a stub. `ready()` mirrors `ClaudeAdapter::ready` exactly, so `--agent codex` succeeds wherever the program resolves. `capabilities().system_prompt` is true for the adapter overall, while `system_prompt_supported(launch)` rejects shell-shim launches. `capabilities().events` is now `true` (issue #86, 2026-08-23 — see below); marker signal and the turn-signal socket mechanism remain false/unimplemented (`register_turn_signal` is still a no-op), tracked as the residual half of issue #11. `context_window_tokens(_)` explicitly reports `None` (issue #155, Phase 6(a)) — no STATIC per-model capacity is verified for codex — but `context_window_hint(jsonl)` (fixed 2026-09-05, above) reads the session's own reported `info.model_context_window` off its rollout JSON, so a live codex session's token gate scales to the seat it actually holds rather than falling all the way back to `ScoreConfig`'s absolute defaults; those defaults still apply when the transcript never reports a window at all (see [[Rot Engine]]). `counts_tool_calls()` reports `false` (issue #155, review finding C2, 2026-08-27): `parse_events` never emits `NormalizedEvent::ToolCall` for codex — no verified rollout shape exists for one — so `--max-tool-calls` is refused up front for this adapter rather than accepted and silently never enforced (see [[Ctx Supervisors]]'s "Delegated-worker budgets").

**`capabilities().token_usage` staying `false` does not mean codex has no usage data (2026-08-16).** That flag describes in-process event parsing, while `window::refresh_codex_usage` scans rollout files separately for the usage-*window* percentages (a different number from the rot engine's own token gate). `base_system_prompt()` remains `None` because Zirv's Claude-specific base layer names tools Codex does not have; agent-neutral composition is delivered on direct launches by `system_prompt_args` as `-c developer_instructions=<TOML string>`. Shell-shim launches fail closed onto the task-prompt-text fallback — see "The Windows npm-shim injection fallback is now surfaced" below (issue #85). The distiller (and, via `read_only_args`, the workflow reviewer) is pinned to `--sandbox read-only`, plus `--ignore-rules --ignore-user-config` when the installed codex-cli's own `--help` documents them — see "The distiller/reviewer sandbox residual is now surfaced and closes on a newer codex-cli" below (issue #89).

**`capabilities().defer_injection_submit` is `true` for codex, `false` for claude (issue #118, 2026-08-25).** A new `Capabilities` field naming whether this adapter's own composer folds a same-write trailing `\r` into pasted text, so a caller injecting text into it must write the line and its submitting `\r` as two genuinely separate writes rather than one burst. Verified `true` for codex against its ratatui composer — the same paste-fold `dash::pane`'s own visible injections already close (issue #114/PR #116) — and `false` for claude, whose composer submits a same-burst trailing `\r` correctly. The one production caller this changes behavior for is `wrap::write_mail_advisory` (the T13 mail-advisory injection); `wrap::inject_compact`/`Action::Compact` never consults the field at all and stays unconditionally single-burst, since that call site is only ever reachable for a turn-signal-capable adapter (claude) in the first place. See [[Ctx Supervisors]]'s "Mail advisory" and "Injection semantics" sections for the mechanism, and the shared `INJECTION_SUBMIT_DELAY` constant (now defined once in `ctx/mod.rs`, re-exported by `dash::pane`) both modules write the deferred `\r` after.

**Codex event parsing derives real rot/usage events from the rollout JSON (issue #86, 2026-08-23).** `window::parse_rollout_record` (in `window.rs`, see [[Usage and Pacing]]) is the single shared collector both the usage-window reader (`parse_rollout_line`) and `CodexAdapter::parse_events`/`structural_context`/`transcript_usage` now parse a rollout line through, so the transcript is read once per line rather than by drifting, independent readers. Only the two shapes verified in `docs/superpowers/notes/2026-07-31-codex-cli-facts.md` ("Turn boundary", "Token usage") are mapped, onto the EXISTING `NormalizedEvent` vocabulary — no codex-specific variant, and `rot.rs` gains no codex knowledge at all:

- `task_started` → `NormalizedEvent::TurnStart` (verified: "`task_started` and `task_complete` bracket a turn and share a `turn_id`").
- `task_complete` → `AssistantFinal { text: last_agent_message.unwrap_or_default(), input_tokens: <most recent cumulative total this parse has seen> }`. `last_agent_message` is `null` on a failed turn, which reads as empty text — honest, not guessed.
- `token_count` (whenever `info.last_token_usage` is present) → its own `AssistantFinal { text: "", input_tokens }`, so `rot::context_tokens` (the token gate) tracks codex's real PER-REQUEST context occupancy between turn boundaries too, not just at them. **Fixed 2026-09-05 (F-1):** this used to read `info.total_token_usage.input_tokens`, the session's CUMULATIVE input spend added across every turn — a figure that only ever grows and eventually crosses the token gate's ceiling regardless of the model's real context size, permanently tripping `compact` after a handful of turns on every codex session. `info.last_token_usage.input_tokens` is the one request's own prompt size instead — real context occupancy — and `cached_input_tokens` is deliberately never added on top of it, since codex already reports `input_tokens` inclusive of the cached portion. `transcript_usage`/`transcript_usage_is_cumulative()` (above) are UNCHANGED and still report the cumulative total — the two are now two genuinely different figures read for two different purposes, not the same number reused. **The round-1 fix wired the WRONG signal into that `LaunchMode` for `dash::worker_pane_extra_args`, reproducing the identical crash (review round 1, same day).** The first attempt resolved the read-only floor against `SpawnRequest::interactive` — the same signal that gates `default_sandbox_args`'s permissive-vs-fail-closed *approval* posture — but `dash::mod::fulfill_spawn_request` builds this pane's real harness child via `adapter.interactive_cmd` **unconditionally**, never gated on `req.interactive` at all (only `PaneSpec`'s argv construction reads it, always through `interactive_cmd`). Command shapes, per comments citing `docs/superpowers/notes/2026-07-31-codex-cli-facts.md` and `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md` (verified against `codex --help`/`codex exec --help`): `headless_cmd` builds `codex exec <prompt> <extra...>` (codex has no `--session-id` flag — it always mints its own id), `interactive_cmd` builds `codex [<prompt>] <extra...>`, `distiller_cmd` builds `codex exec [--model <model>] --sandbox read-only` (codex reads its prompt from stdin, so it's built the same way as claude's; `--model` is omitted entirely when `model` is empty — see the model-resolution paragraph below), `model_args` emits `-m/--model <model>` (verified present on top-level `codex --help` too, so the dashboard's orchestrator pane can select a model on codex the same way it does on claude), and `transcript_path` scans `~/.codex/sessions/<YYYY>/<MM>/<DD>/...` recursively by filename suffix, since codex nests transcripts under a date directory that a bare session id can't predict.

**`transcript_path` resolves and pins the rollout codex actually minted (2026-09-06).** Because no codex command surface accepts a session id, the filename-suffix scan above matches a `rollout-*-<zirv session id>.jsonl` that never exists — so every codex delegation read an absent transcript, recorded zero tokens, and (via `dash::pane_transcript_usage` returning `None`) left `account_reaped_pane_spend` early-returning without ever settling that pane's group or provider reservation. Three resolutions now run in descending order of certainty: (1) the id-suffix scan, kept because it is right the day codex honours an id zirv chose; (2) this session's own pin, `<state>/rollouts/<short>.path`; (3) the **earliest** rollout whose own first-record `session_meta` timestamp is at or after the moment `sessions::load_record` says this session was registered, preferring one whose recorded `cwd` is this session's — then written to the pin, so a later codex run can never move an already-resolved session onto a different transcript. Earliest, not newest: with two codex runs live at once, "newest after my start" hands the older session the younger one's transcript. The `session_meta` record's own UTC timestamp is read, never the filename's, which codex stamps in LOCAL time. Resolutions 2 and 3 are skipped entirely when no state dir resolves, leaving the pre-2026-09-06 behaviour. Residual: two codex runs started in the same directory within the same second cannot be told apart by any signal available here — which is exactly why the answer is pinned rather than recomputed.

**Resolution has to happen AFTER the child starts (review round 1, 2026-09-06).** All three resolutions above need something codex writes once it is running: the rollout itself, or the registry record `pinned_rollout` matches it against. `exec.rs` derived the transcript path once, before the spawn, so for `codex exec` all three answered nothing and the run polled the resolution-1 fallback (`rollout-<zirv id>.jsonl`) — a file that never appears — for its whole life, leaving budgets, rot and spend blind exactly as before the fix above. `supervise_run` now takes the derivation as a closure and re-asks it on each tick, gated on the current path not existing and the new answer naming a different file that does: one `exists()` per tick in the steady state, no redirect away from a transcript that is genuinely being written (an operator's own `--transcript` included), and the pin lands the moment codex writes its `session_meta`.

**A handover drops the pin and floors the next resolution (review round 1, 2026-09-06).** The pin is keyed on the session's short id, and a handover — `dash::pane::Pane::handover` or `wrap`'s own swap — replaces the child while keeping that id, so the successor kept reading the retired child's rollout for the rest of the run. Clearing the pin alone does not fix it: resolution 3 floors on the session's REGISTRATION time, which a handover does not move, so the dead child's rollout is still the earliest candidate and simply wins again. `codex::forget_transcript_pin(state, short, now_secs)` therefore drops `<state>/rollouts/<short>.path` AND writes `<short>.floor` (epoch ms), which resolution 3 takes the `max` of against `record.started_at`. Called from both swap sites: in `wrap` beside `TranscriptSource::forget`, which already declares the old session over; in a pane only after the successor is committed, so a swap that aborted earlier leaves the old child running with its own pin intact.

**A pane resolves against its OWN cwd (review round 1, 2026-09-06).** `dash::pane_transcript_usage` passed the DASHBOARD's `repo` as the `SessionRef.cwd` for every pane, and both adapters key a transcript on the directory the session runs in — claude by project slug, codex by the `cwd` its rollout's `session_meta` records, which resolution 3 above matches on. A worktree-hosted pane was therefore priced off whatever transcript lives under the root repo: another pane's spend, or none at all, feeding both `enforce_pane_token_budgets` and `account_reaped_pane_spend`. It passes `pane.cwd()` now, and the `repo` parameter is gone from both (the state/mailbox side of a pane still keys off the dashboard's repo — see `Pane::spawn`'s own doc comment for why those two must differ).

**Per-adapter distiller model default (2026-08-15).** `HandoffConfig.model` used to default to the literal `"haiku"` unconditionally, which reached `codex exec --model haiku` for a codex session and failed outright (falling back to codex's own empty `structural_context` for a near-empty handoff). It is now `Option<String>`, defaulting to `None`, and every caller (`handoff.rs`, `exec.rs`, `wrap.rs`, `optimize.rs`) resolves it through `handoff::resolve_distiller_model(explicit, adapter)` rather than reading the config field directly: the operator's own choice if set, else the resolved adapter's own `AgentAdapter::default_distiller_model()` (claude: `Some("haiku")`; codex: `None`, the trait default — zirv has no verified cheap-model name for codex's lineup). An empty result means "omit `--model` entirely," which `CodexAdapter::distiller_cmd` reads literally, letting codex's own `~/.codex/config.toml` default apply instead of zirv guessing a name that may not exist on the operator's account. No `session_pin_args` override either, for the same reason and one stronger: codex has no `--session-id` flag at all, so an interactive pane cannot be pinned and the trait default (empty) stands. No `resume_args` override: codex's own resume story (a `--last`/session-id flag for the interactive launch) is unverified against the real CLI, so the trait default (`None`) stands — `dash::roster::restore_argv` falls back to a plain prompt-carrying relaunch for this adapter.

**`review_model_below(seat)`** (2026-08-18) walks codex's own ladder, top to bottom: `gpt-5.6-sol` (the default when no `-m` is given) → `gpt-5.6-terra` → `gpt-5.6-luna` → `gpt-5.4-mini` (the older, hidden floor tier) — sourced from `codex debug models` in `docs/superpowers/notes/2026-07-31-codex-cli-facts.md`, captured on codex-cli **0.146.0** (brew), **not re-verified** against 0.105.0 (the npm-published build most operators actually get) — a version-split residual sibling to `distiller_cmd`'s existing `--ignore-rules`/`--ignore-user-config` gap; see [[Known Issues]]. ### Native hook seams (issue #418, 2026-09-09)

Copilot, droid and gemini each ship a documented, user-level hooks configuration file — distinct from claude's `~/.claude/settings.json` wiring in `setup.rs` — that zirv can install a `PreToolUse`-equivalent guard and (copilot only) a `PostToolUse`-equivalent compaction hook into. `AgentAdapter::native_hooks(&self, home: &Path) -> Option<native_hooks::NativeHooks>` (default `None`) supplies the file, whether zirv owns the whole file outright (`owned_file`), and the entries to ensure; `native_hooks.rs` is the generic, payload-agnostic installer (`install`/`uninstall`/`status`, pure over `serde_json::Value` plus `state::write_atomic`) shared by every adapter that implements it — `zirv ctx hook install <agent> [--show] [--uninstall] [--dry-run]` is the CLI surface. Idempotent: an entry already present (detected by a zirv-owned command string — any string value starting with `zirv ctx ` — already living in that entry's own target array) is never re-inserted; `uninstall` filters zirv-owned elements out of every array the file's entries target and, for `owned_file: true`, deletes the whole file only once that leaves NOTHING non-zirv anywhere in it (review round, 2026-09-09 -- the file is walked and every array checked before deleting, so an operator element added to a nominally zirv-owned file is never lost); an already-present operator entry is otherwise left byte-for-byte alone, and `ensure_array_at` never coerces an existing non-object/non-array value at its target path -- a wrongly-shaped operator file errors rather than being overwritten.

Every fact below is **DOCS-ONLY** (verified from official docs 2026-09-09, not against a live binary — copilot/droid/gemini are not installed on this machine, same posture as the wave-1/2 capability facts above).

The SAME claude-shaped guard/compaction bodies run for every agent — `hook::run_pretool`/`hook::run_posttool`/`safety::run_check`'s hook mode are untouched — via `hook_project.rs`'s one-place payload projection: an agent's own native tool-call payload is mapped onto claude's `PreToolPayload`/`PostToolPayload` shape (one small tool-name table per agent: copilot `bash`→`Bash`/`edit`→`Edit`/`create`→`Write`; droid `Execute`→`Bash`/`Edit`,`ApplyPatch`→`Edit`/`Create`→`Write`; gemini `run_shell_command`→`Bash`/`replace`,`write_file`→`Edit`,`Write`; an unrecognised tool name passes through unchanged, so the guards simply ignore it), the existing guard body runs unmodified, and the claude-shaped `hookSpecificOutput` envelope it produces is translated back into that agent's own documented response shape (see each adapter's own paragraph below) via `hook::run_pretool_for_agent`/`hook::run_posttool_for_agent`/`safety::run_check_hook_mode_for_agent` (`--agent <name>` on `zirv ctx hook pretool`/`zirv ctx hook posttool`/`zirv ctx safety check`, default `claude`, byte-for-byte unchanged when omitted). A `deny` or an `ask` decision produces output for a non-claude agent; `allow` (with or without `additionalContext`/`updatedInput`) always collapses to plain allow (no output), since none of the three agents' contracts have a verified non-blocking advisory or rewrite channel. **`ask` (review round, 2026-09-09) must not collapse to silence the way `allow` does — silence reads as allow on all three agents' own contracts, the wrong failure direction for a confirmation gate.** Copilot and droid both document a real `ask` decision and get it passed through with its reason; gemini has no `ask` concept at all, so its translation fails CLOSED to a deny naming the reason instead of silently allowing — see each adapter's own paragraph below for the exact envelope shapes.

Copilot's own `~/.copilot/hooks/zirv.json` (`$COPILOT_HOME` override honoured; zirv owns this file outright) carries three entries: the guard (`zirv ctx hook pretool --agent copilot`, no matcher — non-shell tool names are unverified so the guard must see every call), the safety check (`zirv ctx safety check --agent copilot`, `"matcher":"bash"`), and the compaction hook (`zirv ctx hook posttool --agent copilot`, `"matcher":"bash"`) — shape `{"version":1,"hooks":{"preToolUse":[{"type":"command","bash":"<cmd>","powershell":"<cmd>","timeoutSec":30}],"postToolUse":[{...}]}}`. A deny or ask is copilot's own TOP-LEVEL `{"permissionDecision":"deny"|"ask","permissionDecisionReason":"..."}` (not nested under `hookSpecificOutput`); a compaction replacement is `{"modifiedResult":{"resultType":"<preserved from the original toolResult, default "success">","textResultForLlm":"<summary>"}}`.

Droid's own `~/.factory/hooks.json` (shared with any operator entries already there — zirv patches, never owns) carries two entries in its top-level `PreToolUse` array — the guard (matcher `Execute|Edit|Create|ApplyPatch`) and the safety check (matcher `Execute` alone) — shape `{"PreToolUse":[{"matcher":"...","hooks":[{"type":"command","command":"<cmd>","timeout":30}]}]}` (seconds, the same `{matcher, hooks: [...]}` shape claude's own `settings.json` uses). A deny or ask is claude-identical verbatim (droid documents the same `hookSpecificOutput` shape for both). **No `PostToolUse` entry is installed at all** — droid's docs state outright that `PostToolUse` cannot replace a tool's result, hence `post_tool_hook: false`.

Gemini's own `~/.gemini/settings.json` (shared; zirv patches under the top-level `hooks` key) carries two entries in `hooks.BeforeTool` — the guard (matcher `run_shell_command|write_file|replace`) and the safety check (matcher `run_shell_command` alone) — shape `{"hooks":{"BeforeTool":[{"matcher":"...","hooks":[{"name":"zirv-guard","type":"command","command":"<cmd>","timeout":30000}]}]}}` (milliseconds, unlike copilot's/droid's seconds). A deny is `{"decision":"deny","reason":"..."}`; gemini has no `ask` concept, so an `ask` from the guard also translates to this same shape, with the reason prefixed `"zirv: confirmation required -- "` to disclose that it stands in for a prompt gemini's own contract cannot express. **No `AfterTool` entry is installed** — gemini's own docs give `AfterTool` only an `additionalContext` channel, no verified result-replacement mechanism, hence `post_tool_hook: false`.

## `policy_support` — translating zirv's policy honestly per launch mode (2026-08-24)

`AgentAdapter::policy_support(capability, stance, mode: LaunchMode)` is the per-adapter half of zirv's canonical permissions policy. An adapter answers with `Enforced` / `Degraded` / `Unsupported` / `OperatorControlled` plus the **named verified mechanism**, for the posture actually being launched. `PolicyReport` carries the same mode and renders the shipped interactive baseline only on interactive reports.

**The honesty rule is the point:** prompt text asking a session to respect a stance is advisory context, never enforcement, so an adapter with only that to offer reports `Unsupported` — whose own rendered label reads "not enforced (advisory only)". Never round a partial mechanism up to `Enforced`.

- **Claude:** `Deny` keeps the existing tool-pin answers. On an interactive launch, `Ask` for shell execution/approval is `Degraded` through `--permission-mode default` plus the `Bash|PowerShell` safety hook, and outside-repo writes are `Degraded` through the workspace-scoped native allow list; other tools still land on Claude's own settings. The hook and immutable policy snapshot are attested on every projected launch rather than depending on setup state. Headlessly the same asks are `OperatorControlled`—`dontAsk` cannot carry a prompt—while unverified network/git/path guarantees remain advisory.
- **Codex:** never reports `Enforced`. On an interactive launch whose capability probe supports `on-request`, shell/approval `Ask` is `Degraded`; when a second probe sees `--approve-for-me`, the mechanism text also names Codex's native security reviewer. The sandbox contains damage and Codex chooses escalation at its own boundary, with no per-command channel for Zirv's `[safety]` classification. If the probe cannot prove support, and on every headless launch, that ask mechanism is not claimed. Existing `Deny` descriptors remain scoped to what `read-only`/`never` actually do.

The asymmetry between the two is reported rather than smoothed over: `policy::evaluate` over one canonical policy yields two different, honest answers.

## `LaunchMode` and policy projection — applying policy to a real launch (2026-08-24)

`adapters::LaunchMode::{Interactive, Headless}` is the compiler-enforced answer to one question: is a human watching this harness and able to answer an approval? `policy_support`, `PolicyReport`, `compile`, `policy_launch_args`, and `default_sandbox_args` all receive that answer explicitly; none guesses from a TTY or adapter name.

| Real-launch seam | Mode | Why |
|---|---|---|
| `chat.rs::dash_orchestrator_pane` | Interactive | Dashboard orchestrator TUI is visible. |
| `wrap.rs` | Interactive | Wrap supervises the operator's TUI. |
| `dash/mod.rs::fulfill_spawn_request` | Interactive | Worker pane is visible inside the watched dashboard. |
| `handover.rs::resolve_swap_launch` | Interactive | Both callers swap a live interactive seat. |
| `exec.rs` | Headless | One supervised non-interactive run. |
| `run_loop.rs` | Headless | Fresh unattended session per cycle. |
| `agent.rs::worker_launch_flags` | Headless | Pane-less delegated-worker fallback; a dashboard worker instead uses the dash row. |

`policy_support` above answers the *report* question; `AgentAdapter::policy_args(&EffectivePolicy, LaunchMode)` and `AgentAdapter::default_sandbox_args(&SandboxConfig, &SafetyPolicy, LaunchMode)` answer the actual argv question. `adapters::policy_launch_args(cfg, adapter, flags, mode)` is the shared seam all seven call:

1. `flags_pin_policy(flags)` — if the operator's own trailing flags already name `--sandbox`/`-s`/`--ask-for-approval`/`-a`/`--permission-mode`/`--disallowedTools`/`--allowedTools` (bare or `=`-joined), nothing of zirv's own is prepended at all. The operator's own choice must demonstrably win, not merely survive because a CLI takes the last occurrence of a repeated flag.
2. Otherwise, `adapter.default_sandbox_args()` when `cfg.sandbox.enabled` (the shipped default since 2026-08-22 — see below), then `adapter.policy_args(&cfg.policy, mode)` for any *additional* restriction an explicit `[policy]` `Deny` stance asks for on top of the baseline. `policy_args` itself is unchanged from `[policy]`'s own honest-report semantics: `EffectivePolicy::default()` stays all-`Allow` ("zirv's per-capability policy declares nothing"), so it contributes nothing unless the operator has explicitly denied `repo_fs_write`/`shell_exec`. `policy_args` gained the `LaunchMode` parameter in issue #134 (2026-08-25) — see below — for the same reason `default_sandbox_args` already carries it: Codex's own projection is command-surface-dependent, not just posture-dependent.

**`mode` is one value shared by both halves, which silently assumes a caller's real launch surface always equals its own approval-permissiveness signal (issue #326, 2026-09-06).** That holds for six of the seven callers (`agent.rs`/`exec.rs`/`run_loop.rs` always launch headless; `chat.rs`/`wrap.rs`/`handover.rs` always launch interactive) but not for `dash::worker_pane_extra_args`: `dash::mod::fulfill_spawn_request` builds a pane's real harness child via `adapter.interactive_cmd` **unconditionally**, while `SpawnRequest::interactive` only ever governs whether this pane gets the permissive interactive *approval* posture or the fail-closed headless one (issue #230 finding 10) — an ordinary `zirv ctx agent` dispatch always sets `interactive: false` (that call site cannot vouch a human is watching whatever dashboard might pick the request up), so a live dashboard fulfilling such a request still built its argv against `LaunchMode::Headless`, even though the pane it built for is unconditionally the interactive CLI surface. `adapters::policy_launch_args_for_surface(cfg, adapter, flags, approval_mode, surface_mode)` is the general form: `policy_launch_args` (unaffected, still used by the other six) delegates to it with `approval_mode == surface_mode`; `worker_pane_extra_args` calls it directly with `approval_mode` still driven by `req.interactive` (default_sandbox_args's argv is safe either way, so no regression) and `surface_mode` hardcoded `LaunchMode::Interactive` (a pane's real surface, always) — which is what makes `CodexAdapter::policy_args`'s `read_only_args()`/`interactive_read_only_args()` pick land correctly. See "`--ignore-rules`/`--ignore-user-config` are `codex exec`-only" above for the concrete crash this closes, and its own doc comment on `policy_launch_args_for_surface` for the full reasoning.

The spec's interactive stance table is `EffectivePolicy::interactive_baseline()`, used for reporting only. It is deliberately not `EffectivePolicy::default()` and never enters `resolve`'s max fold: doing so would silently narrow headless launches and make an operator's `ZIRV_CTX_POLICY_*=allow` unable to loosen an inherited interactive ask.

**The shipped posture is now intentionally asymmetric:** interactive sessions minimize interruption—everyday and unknown commands run silently, a short closed list asks, and a shorter irreversible/self-destructive list denies—while headless sessions retain the fail-closed posture because nobody can answer.

- **Claude interactive:** `--permission-mode default`, non-command allow rules plus the scratchpad on `--allowedTools`, deny rules on `--disallowedTools`, and the ask set on neither. The inverted projection does not lengthen a finite Bash allow-list, because any finite list under `default` would prompt for the next unknown command. Instead the `Bash|PowerShell` safety hook is the sole per-command shell gate and emits explicit `"allow"` for ordinary/unknown commands. Every projected Claude launch now names fingerprinted atomic settings and policy-snapshot files under `~/.zirv/runtime/`: the hook verifies the SHA-256 snapshot, evaluates launch and current policies, and keeps the stricter answer, so tampering or partial attestation asks interactively/denies headlessly. The layer also denies common credential paths and scrubs cloud credentials from subprocesses. On macOS/Linux/WSL2 it enables auto-allow OS sandboxing and fails closed if it cannot start; native Windows gets the identical command classifier but omits Claude's unsupported kernel sandbox. Task 3's mandatory live probe used Claude Code 2.1.241 on 2026-08-24 and reached `permissionMode: default`, but the account rate limit fired before a Bash tool request, so ask-over-native-allow could not be established; the conservative **Design B** shipped—no blanket `Bash(*)` native allow, with the hook's explicit allow carrying ordinary commands.
- **Claude headless:** unchanged `--permission-mode dontAsk`; allowed commands are pre-approved and `deny ∪ ask` is folded into `--disallowedTools`, so an unanswerable prompt becomes a refusal.
- **Codex interactive:** `--sandbox workspace-write --ask-for-approval on-request` only when `ON_REQUEST_APPROVAL_SUPPORT` proves the installed CLI documents it; otherwise fail closed to `never`. An independent cached probe for `--approve-for-me` adds Codex's native automatic security reviewer when available, reducing boundary prompts without bypassing the sandbox; headless never enables it. `untrusted` was rejected because it prompts for everything outside Codex's narrow built-in trusted set—the exact polarity this work removes.
- **Codex headless:** `--sandbox workspace-write` paired with an approval-suppression argv from `approval_suppression_args` — see the exec-scoped probe below.

Both Codex probes run top-level `--help`, are cached per `ProbeKey`, bounded to three seconds, and treat absence/timeout/spawn failure as unsupported. No `[safety]` rule is projected onto Codex: there is no verified per-command channel. Its interactive `policy_support` is therefore `Degraded`, explicitly naming the sandbox-versus-classifier gap rather than implying Claude parity.

**`CodexAdapter::extra_writable_root_args(cwd, mail_dir)` always names the resolved git common dir as an explicit `sandbox_workspace_write.writable_roots` entry, for a main checkout as much as a linked worktree (issue #252, v3.8.0, regression fix).** Codex's own sandbox (seatbelt/landlock) keeps `<root>/.git` read-only inside every writable root it is handed — including `cwd` itself under `--sandbox workspace-write` — so a main checkout's own `<cwd>/.git` was never actually made writable by `cwd` alone; only naming the git dir explicitly lifts that. The prior cut only added `git_common_dir(cwd)` when it resolved OUTSIDE `cwd` (the linked-worktree shape), on the mistaken assumption a main checkout's own `.git` was "already covered" by the cwd root — the regression this fix closes surfaced as a git `index.lock` `EPERM` for every codex worker launched in a main checkout. `mail_dir` is still always added (deduplicated against the git dir, so the two never collide as separate entries when they happen to coincide). **Applied to headless `zirv agent` launches too, not only dashboard panes:** `dash::worker_pane_extra_args` has always called this method unconditionally for a dashboard-spawned worker pane, but a headless `zirv ctx agent`/`zirv agent` delegation went through a completely different launch seam (`agent.rs::run_with`) that never called it at all — a headless codex worker in a main checkout could neither write its own `.git` nor report back through `mail_dir`. `agent.rs::with_headless_extra_writable_roots` closes that gap by appending the same roots to the headless launch's own flags, right before `ExecArgs::command` is built; a no-op for every adapter but codex, since the trait default returns an empty `Vec` (a claude worker's headless flags are unaffected).

**Issue #134 (2026-08-25), the exec-scoped `--ask-for-approval` probe.** Current codex-cli (0.149.x) rejects `--ask-for-approval` outright on `codex exec` (`error: unexpected argument '--ask-for-approval' found`) even though the identical flag is still accepted on the top-level INTERACTIVE `codex [PROMPT]` launch — `zirv agent codex "..."` (a headless delegation, built via `headless_cmd`/`headless_cmd_stdin`) failed before the worker ever started. `ON_REQUEST_APPROVAL_SUPPORT` cannot answer this: it deliberately probes the TOP-LEVEL `codex --help`, gating whether the `on-request` VALUE is safe to pass on an interactive launch, a different command surface entirely. A new probe, `EXEC_ASK_FOR_APPROVAL_SUPPORT` (mirroring `IGNORE_FLAGS_SUPPORT`'s own `codex exec --help` shape exactly — same resolution, same fail-closed cmd-shim reparse guard, same three-second timeout, same "any doubt reads as unsupported" polarity), checks whether `codex exec --help` documents `--ask-for-approval` at all. `CodexAdapter::approval_suppression_args(mode, value)` is the shared helper both `policy_args` and `default_sandbox_args` now call: on a headless launch whose exec probe says unsupported, it emits `-c approval_policy=<value>` (verified to work on both interactive and `exec` surfaces, per `system_prompt_args`'s own `-c/--config key=value` doc comment) instead of the rejected flag pair; every other case (interactive, or headless where the flag is still documented) emits the plain `--ask-for-approval <value>` pair byte-for-byte unchanged. Interactive projection is completely unaffected — verified live on this machine's own installed codex-cli, which does not document the flag on `exec --help`, producing `--sandbox workspace-write -c approval_policy=never` for a real headless launch. Per repo convention, tests never assert an exact argv depending on the live probe; the forcing seam (`with_exec_ask_for_approval_forced`) pins both branches deterministically.

`adapters::SHIPPED_POSTURE_ALLOW`/`_ASK`/`_DENY` are the static source of the built-in classifier and Claude projection; issue #224's reserved zirv families are generated alongside them from `utils::RESERVED_COMMANDS`. Allow contains workspace/harness read-write scopes, web tools, everyday toolchain families/read utilities, plain `curl`/`wget`, and a launch-computed scratchpad. Ask is the short reversible-danger list. Deny contains irreversible publication/deletion, credential and privilege boundaries, pipe-to-shell, and zirv-self-destruction rules. They are an honest tripwire, not a sandbox: arbitrary-code interpreters can express effects a finite glob list cannot recognize. See [[Command Safety]] for the exact classification and SQL rules.

**Issue #224 (2026-08-31):** the former issue #98 `Bash(zirv *)` rule also pre-approved every repo-defined script. It is replaced by one generated rule per reserved name. Claude's launch-local settings now carry the same list in `permissions.allow` and `sandbox.excludedCommands`: reserved built-ins avoid the generic unsandboxed-retry prompt, while `zirv <script>` receives no native exception. `zirv report` itself is excluded rather than allowing `gh *`; its implementation invokes only fixed `gh auth token --hostname github.com`, captures the token, and sends through Zirv's fixed report path, so the credential file remains denied to arbitrary commands and direct `gh auth *` is not exposed. The independent PreToolUse hook remains in force, so repo `deny`/`ask` rules can still narrow built-ins. Codex has no matching per-command settings projection and is unchanged.

**Issue #111 (2026-08-23):** dangerous flag reordering and sibling-utility escapes remain covered by mid-string wildcard patterns. The 2026-08-24 split moved reversible git/find families to `Ask` while credential/irreversible `gh` families remain `Deny`; ordinary uses still stay `Allow`.

`cfg.sandbox.enabled` (`[sandbox] enabled = true`, `ZIRV_CTX_SANDBOX`) is `REPO_FORBIDDEN` — see [[Untrusted Configuration]] — the operator's own opt-out back to the pre-2026-08-22 behaviour (no zirv-applied argv at all; a launch's posture then comes entirely from the harness's own native config).

## `distiller_cmd` and the untrusted-CLAUDE.md trust boundary

`distiller_cmd` builds the command for a separate, usually cheaper model child process — spawned by `handoff::run_model` — whose only job is to read a distillation prompt from stdin and answer with plain text: either summarizing a session transcript into a handoff (`handoff::distill`/`distill_or_structural`) or making the judgment calls in `zirv ctx optimize`. That prompt embeds text that ultimately traces back to a repository's own `CLAUDE.md` (or similar repo-provided configuration) — content the ctx subsystem must treat as **untrusted input**, exactly like the general trust boundary described in [[Untrusted Configuration]].

`run_model` drains stdin, stdout, and stderr concurrently so no child pipe can deadlock the supervisor. Stderr is retained only up to 8 KiB, sanitized, reduced to a 2 KiB diagnostic, and any line copied from the model prompt is redacted. A non-zero child exit therefore reports both its status and a useful bounded reason (for example, a parent sandbox denying the nested CLI's home-state access) instead of the former opaque `status 1`; timeout and process-tree kill behavior is unchanged.

The concrete risk, and why it isn't just theoretical: this distiller child is otherwise launched with the operator's normal permission settings. If a hostile or careless `CLAUDE.md` can steer the distiller model's output (prompt injection) and that child still has tool access, the injection stops being "the model says something misleading" and becomes "the model actually writes a file, runs a shell command, or spawns further work" — a real code-execution path, not just a bad summary.

`ClaudeAdapter::distiller_cmd` closes that path for the claude adapter with one restriction, added and adversarially verified in what the code and notes call the "I6 fix round":

```
claude -p --model <model> --output-format text --disallowedTools=Write,Edit,Bash,NotebookEdit
```

Concretely, per `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`:

- **`--disallowedTools`** must name `Write`, `Edit`, `Bash`, and `NotebookEdit` together. Probing found that `Bash` alone, if left off the deny list, lets the model recreate a Write tool via a shell redirect (`echo ... > file`) even with `Write`/`Edit` blocked — so all four have to be denied, not just the two obvious ones.
- The value must be a **single `=`-bound argv token** (`--disallowedTools=Write,Edit,Bash,NotebookEdit`), never passed as two separate `Command::arg()` calls. The two-token form was verified against the real CLI to make claude's variadic tools parser swallow the *next* argv entry as part of the tool list, corrupting whatever followed it.
- Other candidate fixes were probed and rejected: an empty `--allowedTools=""` allow-list does **not** deny everything by default (a file was still created in the probe); `--permission-mode plan` doesn't complete cleanly in non-interactive `-p` mode at all (no `ExitPlanMode`/`AskUserQuestion`) and took 90+ seconds.
- The chosen restriction was re-verified adversarially: a prompt explicitly instructing the model to fall back to Bash, or to route around the restriction via Task/subagent delegation, still failed to create a marker file, with the model itself reporting it had exhausted every method.

The comment on `distiller_cmd` and the dedicated test `the_distiller_denies_the_tools_verified_to_matter` both exist specifically to keep this from regressing: the exact flag spelling, the exact four-tool set, and the single-token argv shape are all load-bearing, not stylistic. Codex's own `distiller_cmd` pins `--sandbox read-only` instead (verified against `codex exec --help`, codex-cli 0.105.0) — its own analogue of this restriction, and what backs `zirv ctx optimize`'s report-only guarantee for a codex judgment child. Not an identical guarantee, though: `--sandbox` restricts what a codex-*executed shell command* may touch, not which of codex's own tools may run at all, and this child's own repo AGENTS.md is still embedded in its prompt exactly like claude's distiller embeds CLAUDE.md.

This is verified against the real installed CLI (not just documentation), as recorded in `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`: the notes log the exact probe commands, exit codes, and file-creation outcomes for each candidate fix, including the baseline (no restriction) actually succeeding at writing a file, which confirms the risk is real under a normal user's own default permission settings before demonstrating the fix closes it.
