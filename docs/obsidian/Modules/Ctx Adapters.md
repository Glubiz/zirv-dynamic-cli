# Ctx Adapters

## Quick Reference

- **Files:** `src/commands/ctx/adapters/mod.rs`, `src/commands/ctx/adapters/claude.rs`, `src/commands/ctx/adapters/codex.rs`
- **Used by:** [[Ctx Supervisors]] (`exec.rs`, `wrap.rs` build agent argv and relaunch through an adapter; `dash/mod.rs` and `dash/roster.rs` call `model_args`/`resume_args` for the dashboard's orchestrator pane and its quit/restore roster; `wrap.rs` and `chat.rs`'s `dash_orchestrator_pane` call `adapters::harness_prompt_lines` to render the derived harness-roster prompt layer for an Orchestrator launch), [[Script Runner]] (`src/script_runner/agent_command.rs` calls `adapters::select`/`adapters::all` to run a wrapped agent command from a script), [[Ctx Subsystem]] (`handoff.rs` calls `distiller_cmd` to build the summarization child; `score.rs` calls `parse_events`/`structural_context`)
- **Depends on:** [[Ctx Subsystem]] for `CtxResult`, `CtxConfig` and the `event` types (`SessionId`, `SessionRef`, `NormalizedEvent`, `StructuralContext`, `Capabilities`), [[Utilities]] for `home_dir()`, `src/settings.rs` (`AgentGate`, via `cfg.agents`) for the enable/disable gate `select` checks
- **Tests:** inline `#[cfg(test)] mod tests` in all three files — `mod.rs` (adapter selection, Windows launcher rewriting, `program_invocation`), `claude.rs` (transcript parsing against a recorded fixture, command building, the distiller tool-restriction tests, the `--help` probe cache), `codex.rs` (command shapes verified against `codex --help`, the shim-launch and stdin-prompt tests)
- **If changed:** [[Ctx Supervisors]], [[Ctx Subsystem]], [[Untrusted Configuration]], [[Usage and Pacing]] (`provider()`), [[Known Issues]] (issue #11 tracks codex event parsing), [[Decision Log]] (the I6 distiller-restriction fix round)
- **Gotchas:** `distiller_cmd`'s tool restriction is a security control, not cosmetic — see below; it must stay a single `=`-bound `--disallowedTools=...` argv token, and `Bash` must stay in the deny list, or the restriction silently stops working. The `codex` adapter is **supported but degraded**: `ready()` only checks that the `codex` program resolves (mirrors claude), so `--agent codex` launches and supervises fine, but with no event parsing, rot score, usage source, turn signal or injected system prompt — see below and issue #11.

## Purpose

This module is the seam between zirv's ctx subsystem and whatever coding-agent CLI is actually being wrapped. Everything that needs to spawn an agent process, parse its transcript, or know what it's capable of goes through the `AgentAdapter` trait rather than hard-coding "claude" or "codex" logic elsewhere.

## The `AgentAdapter` trait

Defined in `mod.rs`, with `Debug` as a supertrait (so `Box<dyn AgentAdapter>` can appear in test assertions). Required methods:

- `name()` — the adapter's short identifier (`"claude"`, `"codex"`), used for `--agent` selection and error messages.
- `provider()` (2026-08-15) — the **account**/vendor whose rate limits this adapter spends, a stable lowercase slug (`"anthropic"` for claude, `"openai"` for codex): deliberately not `name()`, since two harnesses can sit on one billed account and would then legitimately share one provider's usage windows. Required with no default, so a new adapter cannot silently inherit someone else's usage — see [[Usage and Pacing]] for `state::usage_for`/`window::load_for`, the per-provider storage this feeds.
- `ready()` — returns `Err` when the adapter exists but isn't safe to use yet, so callers fail loudly instead of scoring garbage. Both current adapters implement this identically: `resolve_program(&self.program)?; Ok(())` — the only failure mode either has is an unlaunchable binary (see below).
- `detect(command)` — whether a wrapped argv looks like this adapter's binary, by filename.
- `headless_cmd(prompt, session, extra)` — builds the one-shot, non-interactive command (`exec`'s launch shape).
- `interactive_cmd(initial_prompt, extra)` — builds the TUI command (`wrap`'s launch shape).
- `distiller_cmd(model)` — builds the command for the small judgment/summarization model child used by handoff distillation and `optimize`.
- `system_prompt_args(prompt)` — argv that appends `prompt` to the agent's system prompt for one run; empty when the adapter has no verified mechanism.
- `transcript_path(session)` — where this agent's own transcript file lives on disk.
- `parse_events(jsonl)` / `structural_context(jsonl, last_n)` — turn a raw transcript into the ctx subsystem's normalized event stream and rolling structural summary. Must be line-local (each line's events depend only on that line), because `score.rs` feeds adapters only the bytes appended since the last incremental pass.
- `compact_command()`, `quit_sequence()`, `capabilities()`, `register_turn_signal(session, socket)` — the remaining agent-specific knobs the supervisors need (whether the agent supports `/compact`, how to send it a clean quit, its `Capabilities` flags, and how to wire up the turn-signal socket via `TurnSignalSetup { env, instructions }`).
- `model_args(model)` — argv tokens that select `model` for one interactive launch. `chat.rs::extra_with_model` folds them into the launch's **extra arguments**, so `interactive_cmd` emits them after the positional prompt; they are deliberately *not* spliced in at `launch_prefix_len()`, which counts only the argv the operator wrote and does not count the tokens `base()` prepends when it routes a `.cmd`/`.ps1` shim through a launcher (see [[Ctx Supervisors]] and [[Untrusted Configuration]]). Default is empty (no verified flag, no guess); both current adapters override it.
- `resume_args(session_id)` — argv tokens that resume `session_id`'s own conversation, for the dashboard's quit/restore roster (`dash::roster::restore_argv`). Default `None` means this agent's resume story is unverified: a restore falls back to a plain prompt-carrying relaunch instead of a guessed flag; only `claude.rs` overrides it today (see below).
- `session_pin_args(session)` — argv tokens that make the agent adopt zirv's own session uuid as the id of the conversation it is about to start, so a later `resume_args` against that uuid finds something. Appended **only** to a freshly launched dashboard pane (`chat.rs::dash_orchestrator_pane` and `dash::pane_launch_extra`, the two seams that mint their own uuid), never inside `interactive_cmd` itself: `wrap`'s relaunch path deliberately lets the harness mint a fresh conversation on every restart, and a *restored* pane already carries `resume_args`, which a pin would contradict. Default is empty; only `claude.rs` overrides it (`--session-id <uuid>`, the same flag `headless_cmd` already pins every headless run with). Without it the roster stored a uuid the harness had never heard of and every restored claude pane died on `--resume` with "no conversation found".
- `review_model_below(seat)` (2026-08-18) — this adapter's own verified model ladder, one tier below `seat` (the orchestrator seat's own model, `cfg.chat.model`, or `None`/unrecognised — read as "assume the top tier," a deliberate spend-up default the operator can override). Default is `""`, meaning "no verified ladder" (the same "nothing verified to guess" answer `default_distiller_model`'s `None` gives); both registered adapters override it with real ladders (see below). The sole caller is `resolve_review_model` in `harness_prompt_lines` below, used only when the operator has not set `review.<agent>` explicitly.
- `default_worker_model()` (2026-08-18) — this adapter's own hard-coded model for a delegated headless worker (`zirv ctx agent`, and the dashboard's own spawn-request pane variant) when the operator has not set `worker.<name>` explicitly. Default is `None` — the same "nothing verified to guess" answer as `default_distiller_model` and `review_model_below`'s empty-ladder default — meaning the launch omits `--model` entirely and the agent's own configuration picks. The sole caller is `resolve_worker_model` (see "The delegated-worker model default" below).

Several methods have trait-default implementations that only `claude.rs` currently overrides: `base_system_prompt()` (`None` by default — an unverified agent gets no base layer, not another agent's instructions), `user_system_prompt_flag()`, `system_prompt_file_flag()`, `supports_system_prompt_file(launch)` (defaults to `false`, i.e. "fail open to argv delivery"), `launch_prefix_len()` (defaults to `1`, the count of leading argv tokens that are the program invocation itself rather than operator flags — used when a relaunch has to strip the program off an argv it didn't build), `resume_args()` and `session_pin_args()` (see above).

### Selection

`adapters::all(bin)` returns `vec![ClaudeAdapter, CodexAdapter]` — the full registry. `adapters::select(name, command, cfg: &CtxConfig)` picks one adapter, in priority order: an explicit `--agent` name, else `detect()` against the wrapped command's argv, else the registry's fallback (`resolve_default`, below — claude first in registry order, `cfg.agent_bin` supplies the adapter's `bin` override). In every arm, before the chosen adapter's own `ready()` is called, `select` checks `cfg.agents.refusal(adapter.name())` (the `.settings.toml` gate — see below) and returns that refusal as an `Err` if the agent is disabled. An adapter whose own program does not resolve to a launchable binary is still rejected at selection time by `ready()`, just after the gate check rather than before — both adapters share this one failure mode today, so neither is unready by construction.

`command_matches_adapter(adapter, agent_explicit, command)` is the trust gate used before injecting adapter-specific flags (like `--append-system-prompt`) into a wrapped command: it's true only when the operator named the agent explicitly or `detect()` matched, never merely because `select()`'s last resort had to default to claude with nothing backing it.

### The registry table and `resolve_default`

`ADAPTERS: &[(&str, AdapterCtor)]` (`mod.rs`) is the single source of truth for which adapters exist — a name paired with a constructor function:

| Name | Constructor |
|---|---|
| `"claude"` | `make_claude` → `ClaudeAdapter::new(bin)` |
| `"codex"` | `make_codex` → `CodexAdapter::new(bin)` |

`all(bin)`, `select`'s fallback, `describe_known_adapters`, `resolve_default`, and `readiness_note` all walk this table rather than naming adapters by hand, so none of them can drift from it or from each other — adding a third adapter is one entry here plus its own module.

**`readiness_note` (`zirv ctx --help`'s `about` text) has two clauses, both generated (2026-08-15).** The first names every adapter whose own `ready()` still fails, exactly as before. The second — new — names every *ready* adapter whose `capabilities()` is not fully `true`: `missing_capability_labels` walks `events`/`token_usage`/`turn_signal`/`system_prompt` (not `marker_signal`, a sub-feature of `events`) and `join_with_or` renders the gaps as plain English (`"rot score, usage, turn signal, or injected prompt"`). Codex is what this discloses today — `ready()` succeeds but `capabilities()` is honestly all-`false` — without naming codex anywhere in the function itself; a third adapter with its own gaps, or codex closing one, changes the sentence with no edit here. `ctx_about()`'s process-wide `OnceLock` caching (`mod.rs`) is unchanged by this.

`resolve_default(cfg: &CtxConfig) -> CtxResult<(Box<dyn AgentAdapter>, DefaultOrigin)>` is the fallback `select` calls when neither an explicit `--agent` nor argv detection named an adapter, but it also stands on its own — callers that want to *explain* the default rather than just use it (`zirv ctx status`'s `chat:` line, `zirv ctx chat`'s own resolution) call it directly:

1. If `cfg.agent` names an adapter, that one is used (after the gate check and its own `ready()`), tagged `DefaultOrigin::Configured`.
2. Otherwise, the first registry entry that is both gate-enabled and `ready()` wins, tagged `DefaultOrigin::FirstEnabledReady`.
3. If nothing qualifies, the error aggregates one line per adapter naming why it was skipped (the gate's refusal text, or the adapter's own `ready()` text) rather than reporting only the first failure — this is the same aggregated message `zirv ctx status` reuses (see [[Ctx Subsystem]]) instead of inventing its own wording.

`DefaultOrigin` is coarser than `chrome.rs`'s own `HarnessRule` (see [[Ctx Supervisors]]): `HarnessRule` adds a third case, `Explicit`, for an operator-named `--agent`, which never reaches `resolve_default` at all since `select`'s explicit-name arm short-circuits before the fallback.

### The `.settings.toml` enable/disable gate

`src/settings.rs` owns `AgentGate`, loaded once per `CtxConfig::load` into `cfg.agents` and consulted by `select` before every `ready()` call. Its module doc lays out the full layering (`~/.zirv/.settings.toml`, then `<repo>/.zirv/.settings.toml`, then `ZIRV_AGENT_<NAME>_ENABLED`) and the per-agent AND-fold trust rule (a repo may only narrow, the environment is the operator in both directions). What matters here: the gate is operator *policy* ("may zirv use this adapter"), separate from `ready()`'s implementation *state* ("does this adapter work yet"), and policy is checked first — a disabled codex reports the disable, not whatever `ready()` would have said. `select`'s three arms all honor it identically: an explicit `--agent codex` with codex disabled refuses outright (no fallback), and so does an argv `detect()` match — an operator-disabled adapter never silently falls back to a different one. The unknown-agent error's adapter list also marks disabled names, e.g. `known adapters: claude, codex (disabled)`. `zirv ctx status` prints one line per adapter from `AgentGate::states()`, enabled or disabled plus the file/variable responsible.

Three call sites use this registry: `src/script_runner/agent_command.rs` (a script's `agent_command` option runs a wrapped agent via `adapters::select`), and the two supervisors in `src/commands/ctx/exec.rs` and `src/commands/ctx/wrap.rs` (headless and interactive sessions respectively — see [[Ctx Supervisors]]).

**`[agents.<name>]` also carries an optional `capacity` key (2026-08-18).** The only recognized file value is `"small"` (absent means full capacity); it marks a harness capacity-limited, rendered in the harness roster as `-- small tasks only` (see `harness_prompt_lines` above) so an orchestrator routes only small, bounded briefs its way, for both review and `zirv agent` delegation. `AgentState::capacity_small` and `AgentGate::is_capacity_small(name)` carry the fold's answer; the trust shape mirrors `enabled` exactly, with one asymmetry: there is no `"full"` value a file can write, since absence already means full, so a repo file that is silent on capacity can never widen a home-narrowed `"small"` back — only `ZIRV_AGENT_<NAME>_CAPACITY` (`"small"`/`"full"`, either direction, an invalid value rejected loudly and scoped to that one agent) can. Both current `load` variants (the ordinary layered load and the operator-only fallback) fold it identically to `enabled`, and `.zirv/.settings.toml`'s own template documents the key next to `enabled`.

**A repo-only disable of the default agent must not silently select a different one (G, 2026-08-15).** `resolve_default`'s empty-`--agent` fallback used to skip a disabled candidate and simply continue to the next registry entry, without asking *who* disabled it. Once codex became ready too (see above), a repo checkout's own `.settings.toml` disabling claude was enough to make the fallback silently pick codex instead -- a different vendor account, with none of claude's capabilities -- which is exactly the "repo may narrow, not select" trust boundary this codebase holds everywhere else (see [[Untrusted Configuration]]). `AgentGate::disabled_only_by_repo(name)` reads provenance already computed by `load`'s own fold (`AgentState::disabled_by`, `Source::RepoFile` specifically, never `OperatorFile`/`Env`) to tell the two cases apart cheaply, with no second settings read. `resolve_default` now refuses outright -- naming both the narrowed adapter and what it would otherwise have silently picked -- the moment its fallback loop would land on a *different* adapter than a repo-only-disabled one; it is unaffected when nothing later in the registry qualifies either (no different provider was ever chosen, so the ordinary aggregated "no agent is both enabled and ready" error still applies and still names every candidate), and unaffected when the same agent was disabled by the operator or the environment instead (their own choice to make). `select`'s other two arms (explicit `--agent`, argv `detect()`) were never affected -- they already refuse a disabled agent outright rather than falling back to anything.

### The derived harness roster (`harness_prompt_lines`, 2026-08-16)

`adapters::harness_prompt_lines(cfg, current_adapter)` walks `ADAPTERS` in the same registry order as `readiness_note`, and renders one line per adapter describing whether an Orchestrator session may delegate to it right now via `zirv agent <name> "<prompt>"`: `- {name}: enabled, ready -- initiate with \`zirv agent {name} "<prompt>"\`` (plus a `(degraded: no ...)` suffix from `missing_capability_labels` when `capabilities()` isn't fully `true`), `- {name}: not installed (no '{program}' found)`, `- {name}: installed? not ready ({reason})` for an installed-but-otherwise-failing adapter, or `- {name}: disabled ({location})` for a gate-disabled one — naming where the disable came from (`AgentState::location`) rather than silently omitting the line, so an operator reading the prompt can tell "not offered because disabled in `.zirv/.settings.toml`" from "not offered because not installed." Unlike `readiness_note`, which never mentions a disabled adapter at all, this function's whole point is to be complete: it is the roster an Orchestrator session reads to decide what it can delegate to.

**A ready, enabled line also carries a capacity note (2026-08-18).** When `cfg.agents.is_capacity_small(name)` (the `[agents.<name>] capacity = "small"` marker in `.zirv/.settings.toml` — see "The `.settings.toml` enable/disable gate" below), an otherwise-ready line reads `- {name}: enabled, ready -- small tasks only -- initiate with ...` (or, for the self line, `enabled, ready -- small tasks only (this session's harness)`) instead of the plain "ready" wording. `HARNESS_PROMPT`'s final paragraph tells an orchestrator to route only small, bounded briefs to a harness marked this way, for both a cross-harness review request and a `zirv agent` delegation.

**A "ready" line only claims that after a real presence check, layered on top of `ready()`.** `AgentAdapter::ready()` is deliberately fail-open for a program name it cannot resolve — `resolve_program`/`ready()` still return `Ok` for a not-yet-real path, since several callers rely on that to fall through by name rather than error early. A roster line is a concrete invitation an orchestrator can act on immediately, so `harness_prompt_lines` layers `adapters::program_is_present(adapter.program())` on top: an explicit path or a `PATH` lookup (`PATHEXT`-aware on Windows) that must find a real file, never in place of `ready()`. `AgentAdapter::program()` (new, required, both adapters delegate to their own `self.program`) is what lets this caller — which only has `&dyn AgentAdapter` — ask what binary `ready()` actually resolved to. **Nit, not a bug:** off Windows the check is `Path::is_file()` only, with no executable-bit check, so it errs toward fail-open (a present-but-non-executable file still reads as "ready").

**This session's own harness never invites itself.** `current_adapter` (the resolved adapter's own `name()`, threaded in by both call sites below) marks its own line `- {name}: enabled, ready (this session's harness)` instead of the `zirv agent` invitation — `HARNESS_PROMPT` frames delegation as going to *other* harnesses, and a session cannot review-round itself.

**A global `agent_bin` override is handed only to the adapter it actually names.** Every `ctor(bin)` call used to reuse the operator's one `cfg.agent_bin` override for every adapter in the registry, which put one real binary's presence verdict onto every other adapter's line too. `agent_bin_names_a_different_adapter(bin, name)` checks whether `bin`'s basename names a *different* registered adapter than the one about to be built; when it does, that adapter is built with `None` instead, so its presence is judged from its own default program name exactly as if no override were configured.

The caller renders the lines and hands them to `prompt::compose` as data (`compose` itself stays free of the adapter registry and the settings gate); `wrap::run_with` and `chat.rs::dash_orchestrator_pane` both call it (passing their own resolved `adapter.name()`) only when `role == PromptRole::Orchestrator`, passing `Vec::new()` for a Worker launch — a delegated worker must not learn what it could delegate to in turn, the same recursion guard `HARNESS_PROMPT` itself already enforces. See [[Context Management]] and the prompt-composition ordering in `prompt.rs` (`PromptSource::Harnesses`, appended right after the harness layer, gated on `cfg.prompt.harnesses` and a non-empty roster).

### The review-routing line (`review_roster_line`, 2026-08-18)

`harness_prompt_lines` appends one trailing line after its per-adapter lines, naming which model runs code review for every *enabled* harness: `resolve_review_model(cfg, name, adapter)` picks the operator's own `cfg.review.claude`/`cfg.review.codex` when set (`REPO_FORBIDDEN` — see [[Untrusted Configuration]]), else `adapter.review_model_below(cfg.chat.model.as_deref())`. Each entry renders as `{name} -> "{model}" ({note})`, and the whole line states the routing rule: "run every code review on the named model, never on an orchestrator seat's own model" — softened to "never on a model above the named one" whenever any entry's resolved model text equals the seat's, case-insensitively (`equals_seat`). That equality happens two ways, both legitimate: a harness's ladder default is already at its floor tier (seat `"haiku"` resolves claude's own default to `"haiku"` too — the note reads "floor tier: the seat is already at the bottom rung" instead of "default: one tier below the seat"), or the operator explicitly configured `review.<agent>` equal to the seat (their call — the note reads `(configured)`). A disabled harness has no entry at all (absence, not silence, matching the per-harness line's own convention), and `review_roster_line` returns `None` — no line, not an empty one — when no harness is enabled. Claude's `ORCHESTRATOR_PROMPT` review bullet and its `.claude/agents pin their own models` clause were reworded to point at this line and carve out the one exception that outranks it (see below).

### The delegated-worker model default (`worker_model_args`, 2026-08-18)

A delegated headless worker (`zirv ctx agent <name> "<prompt>"`, and the dashboard's own spawn-request pane variant, `dash::mod::fulfill_spawn_request`) used to silently inherit whatever model the operator's own interactive default happened to be — often a far pricier model than the delegated task needs. `adapters::resolve_worker_model(cfg, name, adapter)` picks the operator's own `cfg.worker.claude`/`cfg.worker.codex` when set (`REPO_FORBIDDEN` as a whole table — see [[Ctx Subsystem]] and [[Untrusted Configuration]]), else `adapter.default_worker_model()`: claude hard-codes `Some("sonnet")`, codex has none (`None`, so its own CLI/config default applies untouched). `worker_model_args(cfg, name, adapter)` turns the resolved model into argv (`AgentAdapter::model_args`) or returns empty when nothing resolves. Unlike `resolve_review_model`, there is no ladder: a delegated worker has no orchestrator seat to be "one tier below," so the adapter-owned default is a fixed name, not a function of `cfg.chat.model`.

Two callers apply it, each guarding the operator's own explicit choice first:

- **`agent.rs`'s `worker_launch_flags`** (the `zirv ctx agent` headless path) checks `flags_pin_model` first — a bare `--model`/`-m`, or the joined `--model=value`/`-m=value` form, anywhere in the operator's own trailing flags — and leaves `flags` untouched if so; codex's `-m` short alias is recognised too, so a configured `worker.codex` cannot end up prepending a conflicting `--model` ahead of an operator's own `-m <value>` (fixed in the same round `seat_model_env` gained effective-model tracking, below). Otherwise `worker_model_args`'s result is prepended ahead of `flags` as trailing extras — the same discipline `chat.rs::extra_with_model` uses for the orchestrator seat — never spliced into a launcher prefix.
- **`dash::mod::fulfill_spawn_request`** applies `worker_model_args` unconditionally: a spawn request never carries the operator's own trailing flags (a request with any set falls back to the headless `agent.rs` path before it ever reaches the dashboard — see [[Ctx Supervisors]]'s spawn-request protocol), so there is no "already pinned" case to detect on this path.

`worker.claude`/`worker.codex` are charset/length/leading-dash validated the same way `chat.model`/`review.*` are (`validate_model_str`), since — unlike `review.*`, which only ever lands in injected prompt *text* — these keys reach a real launch argv directly.

### Windows launcher rewriting

`mod.rs` also owns `resolve_program`/`ResolvedProgram`, used by both adapters' `base()` helpers. Off Windows it's the identity. On Windows, `std::process::Command` only ever appends `.exe`, so an npm-installed `claude` (actually `claude.cmd`) fails to spawn directly (`CreateProcessW` error 193); `resolve_program` walks `PATH`/`PATHEXT` the way the shell would and routes `.cmd`/`.bat` through `cmd.exe` and `.ps1` through PowerShell. A name that resolves to an unlaunchable extension is reported as a named `ready()`-style error before spawning; a name that resolves to nothing at all is left alone so the OS's own "not found" still surfaces.

Whenever `resolve_program` (or an already-resolved shim argv — `adapters::launch_reparses_through_shim`, fixed 2026-08-14) routes a launch through `cmd.exe /c`, that command line is **re-parsed by cmd.exe itself** before the shim ever runs, which is a real command-injection surface for any repo-controlled text riding along on the argv. `adapters::guard_cmd_shim_reparse` is the fail-closed backstop over that surface at every spawn seam; the full defense-in-depth mechanism (forced system-prompt-file delivery, stdin-delivered headless prompts, the backstop itself, and the two round-9 gaps closed in it — an unguarded `--help` probe, and the shim-detection false negative that left the file-form defense inert on `zirv chat`/bare `zirv`/the dashboard orchestrator) is documented in full on [[Known Issues]] ("Windows `cmd.exe` argv reparse…"), not duplicated here.

## The `claude` adapter

`ClaudeAdapter` (in `claude.rs`) wraps a `program` plus `bin_args` (so `ZIRV_CTX_AGENT_BIN="sh /tmp/stub.sh"` or `/usr/bin/env claude` both work) and an optional `home` override for tests. Every command starts from a shared `base()` that applies the program, its leading args, and the Windows resolution above uniformly.

- **`headless_cmd`** builds `claude -p <prompt> --session-id <id> <extra...>` — this is what pins a specific `SessionId` onto the launched process for `exec`.
- **`interactive_cmd`** builds `claude [<initial_prompt>] <extra...>`, the positional form `wrap` uses to start or resume a TUI session.
- **`ready()`** just calls `resolve_program` — claude is always considered implemented; the only failure mode is an unlaunchable binary.
- **System prompt injection**: `system_prompt_args` emits `--append-system-prompt <text>` (empty when the composed prompt is blank). `base_system_prompt()` returns `ORCHESTRATOR_PROMPT`, a claude-specific constant describing zirv's orchestrator conventions (delegate to the Agent tool, route work to cheaper models, verify in batches). It is model-agnostic everywhere except one rule (2026-08-18): every Agent-tool dispatch MUST set the `model` parameter explicitly to one of the tool's own fixed tiers — `haiku` for mechanical/bulk work, `sonnet` for ordinary exploration/implementation/test-writing, `opus` only for hard debugging/design exploration — because that parameter's enum is the harness's own vocabulary, not a vendor lineup that ages out; the rule also bans fork-type subagents outright (a fork always inherits the seat model and ignores `model`) and forbids naming the seat's own model. `fable`/`mythos` are deliberately not named — they are not one of the rule's three routing tiers. The layer still never asks for `--model` itself: that flag picks *this seat's* model, which stays the operator's choice. Other 2026-08-18 hardening: briefs must ask a worker to reply with compact structured findings (never raw file dumps) and this seat's own replies stay brief and decision-focused (token economy, both directions). Its final-review bullet is worded self-contained for **both** roles (2026-08-16, since this adapter layer is injected into a Worker launch too, not only an Orchestrator one): run this harness's own `/code-review` at a **single-reviewer effort level (low or medium)**, never a high-or-above fan-out (2026-08-18 — a fan-out forks agents that inherit the seat's expensive model; this is the same failure mode the `hook pretool` guard below exists to backstop deterministically, after prompt guidance alone let one fork fan-out burn roughly half a five-hour usage window), routed to the review model named in the harness roster and never this seat's own model, with cross-harness review layered *on top* of that, conditionally — only a session that also carries the (Orchestrator-only) `HARNESS_PROMPT` layer follows its bounded cross-harness review round as well. The model-routing bullet's ".claude/agents pin their own models; do not override those" clause carves out one exception: the harness roster's review-routing rule (`review_roster_line`, above) outranks it. `.zirv/claude.yaml`'s rule 8 was reworded the same way, for the same reason. See [[Context Management]] and [[Decision Log]]. `supports_system_prompt_file` probes the installed binary's own `--help` output (cached process-wide, keyed by resolved program + bin_args, bounded by a 3-second timeout) for `--append-system-prompt-file`, so injection can move off argv (visible to other users via `ps`) once the installed version supports it, without hard-coding a version cutoff. Any probe failure reads as "unsupported," which only ever falls back to argv delivery — it never blocks a launch. **`detect_help_flag` now runs `guard_cmd_shim_reparse` against the exact probe argv before spawning it** (fixed 2026-08-14): the probe itself used to spawn `cmd.exe /c <shim> <bin_args> --help` on Windows with no reparse guard at all, and since `program_invocation` forwards every positional before the first flag, a distilled `zirv chat --resume` handoff summary could put repo-controlled metacharacters into that probe before the real launch's own guard was ever reached — a live RCE independent of the launch-time defenses. A rejected probe now reports "unsupported" the same as any other probe failure. See [[Known Issues]].
- **`review_model_below(seat)`** (2026-08-18) walks claude's own ladder, top to bottom: `fable`/`mythos` (the orchestrator-tier aliases) → `opus` → `sonnet` → `haiku`. Matched by substring on `seat`, lowercased first so a mixed-case seat (`"claude-Opus-4-5"`) lands on the right rung; `haiku` maps to itself (already the floor); an absent or unrecognised seat assumes the top tier (`opus`), a deliberate spend-up default the operator can override via `[review]` or `chat.model`.
- **`default_worker_model()`** (2026-08-18) returns `Some("sonnet")` — the hard default a delegated headless worker gets when the operator has not set `worker.claude` (see "The delegated-worker model default" above). Unlike the ladder above, this is not a function of any seat: a worker has no seat of its own.
- **Transcript location**: `transcript_path` computes `~/.claude/projects/<slug of cwd>/<session-id>.jsonl`, where `project_slug` replaces every character outside `[A-Za-z0-9-]` with `-`. If the computed path doesn't exist (the slug rule is verified only for `/` and `.`, not every character), it falls back to scanning every project directory for a file matching `<session-id>.jsonl`.
- **Transcript parsing**: module-level `parse_events`/`structural_context`/`context_tokens_of` functions (which the trait methods just delegate to) read Claude Code's own JSONL transcript format — assistant/tool-call/token-usage shapes, compact boundaries, sidechain/meta line skipping — and are validated in tests both against hand-built JSON and against a recorded, credential-scrubbed real session fixture (`tests/fixtures/claude-real-session.jsonl`, re-recorded via `scripts/record-claude-fixture.py`).
- **Session ids**: claude accepts an explicit `--session-id` on the headless path, so zirv controls the id up front; there's no equivalent for `interactive_cmd`, which relies on claude's own session management plus the transcript-scanning fallback above.
- **`model_args`** emits `--model <model>`, verified against the real CLI (`claude --help`, v2.1.220). **`session_pin_args`** emits `--session-id <uuid>` (the flag `headless_cmd` already uses, offered to interactive dashboard panes so the roster's stored uuid *is* the claude conversation id). **`resume_args`** emits `--resume <session_id>` — not a fresh claim: `wrap::extra_launch_flags` already strips `--resume` on every restart (it pins a launch to an existing conversation) and `exec.rs`'s `RESUME_FLAGS_WITH_VALUE` already treats it as a two-token flag, so this only wires up an already-verified flag for the dashboard's own restore path.

## The `codex` adapter

`CodexAdapter`, in `codex.rs`, is a **supported adapter with an honestly degraded capability set**, not a stub. `ready()` mirrors `ClaudeAdapter::ready` exactly (`super::resolve_program(&self.program)?; Ok(())`), so `adapters::select(Some("codex"), ...)` — and thus `--agent codex` — succeeds wherever the `codex` program resolves to a launchable binary, the same contract claude gets. `capabilities()` is still all-`false` (`marker_signal`, `token_usage`, `turn_signal`, `system_prompt`, and (2026-08-15) `events`), and `parse_events`/`structural_context` are still stubbed to empty/default values: event parsing is out of scope for this round and tracked in [issue #11](https://github.com/Glubiz/zirv-dynamic-cli/issues/11), not a readiness gap.

**`capabilities().token_usage` staying `false` does not mean codex has no usage data (2026-08-16).** That flag describes in-process, transcript-derived event parsing through this trait's own `parse_events` — which codex genuinely has none of. Codex usage now comes from an entirely separate mechanism that never goes through the adapter at all: `window::refresh_codex_usage` scans the codex CLI's own session rollout files (`~/.codex/sessions/**/*.jsonl`) directly for rate-limit snapshots, out-of-band of anything this trait exposes. So a codex session can have a real, fresh reading in `usage-openai.json` — feeding the pacing gate, `zirv ctx usage`, `wrap`'s status bar, and the dashboard header — while `readiness_note`'s `missing_capability_labels` still, correctly, lists "usage" as missing for it: the capability flag and the passive collector answer two different questions and are not expected to agree. See [[Usage and Pacing]] for the collector itself (`parse_rollout_line`, `windows_from_rate_limits`, `parse_rfc3339_utc`) and the active `poll.rs` fallback layered on top of it. `capabilities().events == false` is what keeps `score.rs` from folding that permanently-empty parse into a fabricated `Healthy`/`0` verdict — see [[Rot Engine]]. `base_system_prompt()` returns `None` deliberately (not just via the trait default) because zirv's only base layer is written around Claude Code's own tools (the Agent tool, `.claude/agents`, the `/code-review` skill), none of which codex has, and `system_prompt_args` returns nothing because no per-run injection mechanism has been verified for codex — there is correspondingly no `system_prompt_file_flag` override either, since there is nothing to move off argv. Its `distiller_cmd` pins `--sandbox read-only` (verified, codex-cli 0.105.0) and omits `--model` entirely when none is resolved (`default_distiller_model` is `None` for codex) — see the distiller section below.

Command shapes, per comments citing `docs/superpowers/notes/2026-07-31-codex-cli-facts.md` and `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md` (verified against `codex --help`/`codex exec --help`): `headless_cmd` builds `codex exec <prompt> <extra...>` (codex has no `--session-id` flag — it always mints its own id), `interactive_cmd` builds `codex [<prompt>] <extra...>`, `distiller_cmd` builds `codex exec [--model <model>] --sandbox read-only` (codex reads its prompt from stdin, so it's built the same way as claude's; `--model` is omitted entirely when `model` is empty — see the model-resolution paragraph below), `model_args` emits `-m/--model <model>` (verified present on top-level `codex --help` too, so the dashboard's orchestrator pane can select a model on codex the same way it does on claude), and `transcript_path` scans `~/.codex/sessions/<YYYY>/<MM>/<DD>/...` recursively by filename suffix, since codex nests transcripts under a date directory that a bare session id can't predict.

**Per-adapter distiller model default (2026-08-15).** `HandoffConfig.model` used to default to the literal `"haiku"` unconditionally, which reached `codex exec --model haiku` for a codex session and failed outright (falling back to codex's own empty `structural_context` for a near-empty handoff). It is now `Option<String>`, defaulting to `None`, and every caller (`handoff.rs`, `exec.rs`, `wrap.rs`, `optimize.rs`) resolves it through `handoff::resolve_distiller_model(explicit, adapter)` rather than reading the config field directly: the operator's own choice if set, else the resolved adapter's own `AgentAdapter::default_distiller_model()` (claude: `Some("haiku")`; codex: `None`, the trait default — zirv has no verified cheap-model name for codex's lineup). An empty result means "omit `--model` entirely," which `CodexAdapter::distiller_cmd` reads literally, letting codex's own `~/.codex/config.toml` default apply instead of zirv guessing a name that may not exist on the operator's account. No `session_pin_args` override either, for the same reason and one stronger: codex has no `--session-id` flag at all, so an interactive pane cannot be pinned and the trait default (empty) stands. No `resume_args` override: codex's own resume story (a `--last`/session-id flag for the interactive launch) is unverified against the real CLI, so the trait default (`None`) stands — `dash::roster::restore_argv` falls back to a plain prompt-carrying relaunch for this adapter.

**`review_model_below(seat)`** (2026-08-18) walks codex's own ladder, top to bottom: `gpt-5.6-sol` (the default when no `-m` is given) → `gpt-5.6-terra` → `gpt-5.6-luna` → `gpt-5.4-mini` (the older, hidden floor tier) — sourced from `codex debug models` in `docs/superpowers/notes/2026-07-31-codex-cli-facts.md`, captured on codex-cli **0.146.0** (brew), **not re-verified** against 0.105.0 (the npm-published build most operators actually get) — a version-split residual sibling to `distiller_cmd`'s existing `--ignore-rules`/`--ignore-user-config` gap; see [[Known Issues]]. Matched by substring on `seat`, lowercased first, same as claude's ladder; `gpt-5.4-mini` maps to itself; an absent, unrecognised, or cross-adapter seat (e.g. a claude `chat.model` value) is read as "assume the seat is at the top tier," so it returns `gpt-5.6-terra` — the tier one below `gpt-5.6-sol` — same spend-up-default rationale as claude's own ladder.

**`default_worker_model()`** (2026-08-18) returns `None`, the trait default: codex has no adapter-owned hard default for a delegated worker either, so its own CLI/config default applies untouched when `worker.codex` is unset — see "The delegated-worker model default" above.

**The Windows `cmd.exe`-shim gap is closed.** `CodexAdapter::base()` now routes `self.program` through `resolve_program`, exactly like claude's own `base()` (see "Windows launcher rewriting" above and [[Known Issues]]). `launches_through_cmd_shim` is overridden the same way claude's is (`super::launches_through_cmd_shim(&self.program)`), so an npm-installed `codex.cmd` on Windows is recognised as the shim shape. `headless_cmd_stdin` builds the same `codex exec <extra...>` invocation `headless_cmd` does but with the positional prompt token dropped — codex's own verified stdin fallback (`codex exec` with `[PROMPT]` omitted, or `-`, reads from stdin) — so `exec.rs`/`run_loop.rs`'s FIX B branch (see [[Ctx Supervisors]]) delivers a headless prompt on stdin instead of an argv token cmd.exe would reparse, on exactly the shim-launch shape. `guard_cmd_shim_reparse` remains the fail-closed backstop at the spawn seams, not the primary mechanism, for codex exactly as it is for claude.

## `distiller_cmd` and the untrusted-CLAUDE.md trust boundary

`distiller_cmd` builds the command for a separate, usually cheaper model child process — spawned by `handoff::run_model` — whose only job is to read a distillation prompt from stdin and answer with plain text: either summarizing a session transcript into a handoff (`handoff::distill`/`distill_or_structural`) or making the judgment calls in `zirv ctx optimize`. That prompt embeds text that ultimately traces back to a repository's own `CLAUDE.md` (or similar repo-provided configuration) — content the ctx subsystem must treat as **untrusted input**, exactly like the general trust boundary described in [[Untrusted Configuration]].

The concrete risk, and why it isn't just theoretical: this distiller child is otherwise launched with the operator's normal permission settings. If a hostile or careless `CLAUDE.md` can steer the distiller model's output (prompt injection) and that child still has tool access, the injection stops being "the model says something misleading" and becomes "the model actually writes a file, runs a shell command, or spawns further work" — a real code-execution path, not just a bad summary.

`ClaudeAdapter::distiller_cmd` closes that path for the claude adapter with one restriction, added and adversarially verified in what the code and notes call the "I6 fix round":

```
claude -p --model <model> --output-format text --disallowedTools=Write,Edit,Bash,NotebookEdit
```

Concretely, per `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`:

- **`--disallowedTools`** must name `Write`, `Edit`, `Bash`, and `NotebookEdit` together. Probing found that `Bash` alone, if left off the deny list, lets the model recreate a Write tool via a shell redirect (`echo ... > file`) even with `Write`/`Edit` blocked — so all four have to be denied, not just the two obvious ones.
- The value must be a **single `=`-bound argv token** (`--disallowedTools=Write,Edit,Bash,NotebookEdit`), never passed as two separate `Command::arg()` calls. The two-token form was verified against the real CLI to make claude's variadic tools parser swallow the *next* argv entry as part of the tool list, corrupting whatever followed it.
- Other candidate fixes were probed and rejected: an empty `--allowedTools=""` allow-list does **not** deny everything by default (a file was still created in the probe); `--permission-mode plan` doesn't complete cleanly in non-interactive `-p` mode at all (no `ExitPlanMode`/`AskUserQuestion`) and took 90+ seconds.
- The chosen restriction was re-verified adversarially: a prompt explicitly instructing the model to fall back to Bash, or to route around the restriction via Task/subagent delegation, still failed to create a marker file, with the model itself reporting it had exhausted every method.

The comment on `distiller_cmd` and the dedicated test `the_distiller_denies_the_tools_verified_to_matter` both exist specifically to keep this from regressing: the exact flag spelling, the exact four-tool set, and the single-token argv shape are all load-bearing, not stylistic. Codex's own `distiller_cmd` pins `--sandbox read-only` instead (verified against `codex exec --help`, codex-cli 0.105.0) — its own analogue of this restriction, and what backs `zirv ctx optimize`'s report-only guarantee for a codex judgment child. Not an identical guarantee, though: `--sandbox` restricts what a codex-*executed shell command* may touch, not which of codex's own tools may run at all, and this child's own repo AGENTS.md is still embedded in its prompt exactly like claude's distiller embeds CLAUDE.md.

This is verified against the real installed CLI (not just documentation), as recorded in `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`: the notes log the exact probe commands, exit codes, and file-creation outcomes for each candidate fix, including the baseline (no restriction) actually succeeding at writing a file, which confirms the risk is real under a normal user's own default permission settings before demonstrating the fix closes it.
