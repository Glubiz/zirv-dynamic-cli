# Ctx Adapters

## Quick Reference

- **Files:** `src/commands/ctx/adapters/mod.rs`, `src/commands/ctx/adapters/claude.rs`, `src/commands/ctx/adapters/codex.rs`
- **Used by:** [[Ctx Supervisors]] (`exec.rs`, `wrap.rs` build agent argv and relaunch through an adapter; `dash/mod.rs` and `dash/roster.rs` call `model_args`/`resume_args` for the dashboard's orchestrator pane and its quit/restore roster; `wrap.rs` and `chat.rs`'s `dash_orchestrator_pane` call `adapters::harness_prompt_lines` to render the derived harness-roster prompt layer for an Orchestrator launch), [[Script Runner]] (`src/script_runner/agent_command.rs` calls `adapters::select`/`adapters::all` to run a wrapped agent command from a script), [[Ctx Subsystem]] (`handoff.rs` calls `distiller_cmd` to build the summarization child; `score.rs` calls `parse_events`/`structural_context`)
- **Depends on:** [[Ctx Subsystem]] for `CtxResult`, `CtxConfig` and the `event` types (`SessionId`, `SessionRef`, `NormalizedEvent`, `StructuralContext`, `Capabilities`), [[Utilities]] for `home_dir()`, `src/settings.rs` (`AgentGate`, via `cfg.agents`) for the enable/disable gate `select` checks
- **Tests:** inline `#[cfg(test)] mod tests` in all three files — `mod.rs` (adapter selection, Windows launcher rewriting, `program_invocation`), `claude.rs` (transcript parsing, command building, private launch-settings materialization/attestation, distiller restrictions), `codex.rs` (verified command shapes, shim/stdin paths, capability-probed approval and automatic review)
- **If changed:** [[Ctx Supervisors]], [[Ctx Subsystem]], [[Untrusted Configuration]], [[Command Safety]] (`default_sandbox_args`'s `SafetyPolicy` projection), [[Usage and Pacing]] (`provider()`, the shared rollout collector), [[Rot Engine]] (codex's derived events), [[Known Issues]] (issue #11 tracks the remaining codex event residual: tool calls/results, compaction, marker/turn-signal), [[Decision Log]] (the I6 distiller-restriction fix round)
- **Gotchas:** `distiller_cmd`'s tool restriction is a security control, not cosmetic — see below; it must stay a single `=`-bound `--disallowedTools=...` argv token, and `Bash` must stay in the deny list, or the restriction silently stops working. The `codex` adapter is **supported, with a narrower degraded surface than before (issue #86, 2026-08-23)**: `ready()` only checks that the `codex` program resolves (mirrors claude), so `--agent codex` launches and supervises fine, and `capabilities().events` is now honestly `true` — `parse_events`/`structural_context` derive turn boundaries and token totals from the codex rollout JSON (see "The codex adapter" below). Direct launches support injected developer instructions and lifecycle hooks; tool-call/tool-result/compaction event mapping, the marker signal, and the turn-signal socket mechanism remain tracked in issue #11.

## Purpose

This module is the seam between zirv's ctx subsystem and whatever coding-agent CLI is actually being wrapped. Everything that needs to spawn an agent process, parse its transcript, or know what it's capable of goes through the `AgentAdapter` trait rather than hard-coding "claude" or "codex" logic elsewhere.

## The `AgentAdapter` trait

Defined in `mod.rs`, with `Debug` as a supertrait (so `Box<dyn AgentAdapter>` can appear in test assertions). Required methods:

- `name()` — the adapter's short identifier (`"claude"`, `"codex"`), used for `--agent` selection and error messages.
- `provider()` (2026-08-15) — the **account**/vendor whose rate limits this adapter spends, a stable lowercase slug (`"anthropic"` for claude, `"openai"` for codex): deliberately not `name()`, since two harnesses can sit on one billed account and would then legitimately share one provider's usage windows. Required with no default, so a new adapter cannot silently inherit someone else's usage — see [[Usage and Pacing]] for `state::usage_for`/`window::load_for`, the per-provider storage this feeds.
- `ready()` — returns `Err` when the adapter exists but isn't safe to use yet, so callers fail loudly instead of scoring garbage. Both current adapters implement this identically: `resolve_program(&self.program)?; Ok(())` — the only failure mode either has is an unlaunchable binary (see below).
- `detect(command)` — whether a wrapped argv looks like this adapter's binary, by filename.
- `headless_cmd(prompt, session, extra)` — builds the one-shot, non-interactive command (`exec`'s launch shape).
- `interactive_cmd(initial_prompt, extra)` — builds the TUI command (`wrap`'s launch shape).
- `policy_support(capability, stance, mode)` / `default_sandbox_args(sandbox, safety, mode)` — report and project the canonical policy for an explicit `LaunchMode`; the mode is supplied by each real-launch seam rather than inferred.
- `distiller_cmd(model)` — builds the command for the small judgment/summarization model child used by handoff distillation and `optimize`.
- `read_only_args()` — the flags that keep this agent from writing files or running shell commands (claude `--disallowedTools=Write,Edit,Bash,NotebookEdit`, codex `--sandbox read-only`, plus `--ignore-rules --ignore-user-config` when the installed codex-cli's own `--help` documents them — issue #89, see "The distiller/reviewer sandbox residual" below). `distiller_cmd` applies them, and so does any other child whose prompt embeds untrusted repository text — the workflow reviewer, handed a repository diff (see [[Workflows]]). No trait default: a new adapter has to answer deliberately rather than inherit "no restriction" by omission.
- `dispatch_agent(manifest, task)` — provider-neutral workflow-seat dispatch. The default implementation reloads effective `CtxConfig`, verifies every required logical capability against canonical policy, projects the adapter's normal headless sandbox/policy arguments, adds only an explicitly operator/caller-pinned model id, injects the manifest instruction layer, and appends `read_only_args()` last for read-only seats. Manifests describe methodology and requirements; they never grant permissions.
- `sandbox_residual_note()` (2026-08-23, issue #89) — names a known, recorded gap in this adapter's own `read_only_args()` pin for the operator's currently-resolved binary, or `None` when there is nothing to disclose. Default `None` (claude's own answer: `--disallowedTools` is the whole restriction claude needs). Consulted by `adapters::announce_sandbox_residual_once` whenever this adapter is resolved as the distiller or the workflow reviewer.
- `system_prompt_args(prompt)` — argv that appends `prompt` to the agent's system prompt for one run; empty when the adapter has no verified mechanism.
- `transcript_path(session)` — where this agent's own transcript file lives on disk.
- `parse_events(jsonl)` / `structural_context(jsonl, last_n)` — turn a raw transcript into the ctx subsystem's normalized event stream and rolling structural summary. Must be line-local (each line's events depend only on that line), because `score.rs` feeds adapters only the bytes appended since the last incremental pass.
- `transcript_usage(jsonl)` / `transcript_usage_is_cumulative()` — expose bounded workflow phase token telemetry independently from rot scoring. Claude sums per-response input/cache/output usage in the supplied transcript fragment; Codex reads the latest cumulative `token_count.info.total_token_usage` snapshot and Zirv subtracts its checkpoint.
- `model_hint(jsonl)` (issue #155, review finding D1, 2026-08-27) — the most recently observed live model id inside `jsonl`, or `None` when this adapter has no per-transcript model signal (the default) or the fragment carries none. Must be line-local exactly like `parse_events`, since `score.rs` feeds a poll only the bytes appended since the last one — a caller keeps the last value it resolved across polls rather than reading a fragment with no hit as "no model at all." Claude's own implementation scans an assistant row's `message.model` field newest-to-oldest, so a live `/model` switch mid-session is reflected. This is what lets a live scoring path resolve `capabilities_for_model` with a real model string instead of always falling back to the conservative "unstated model" default — see "Capacity-aware rot gates" below and [[Rot Engine]].
- `context_window_tokens(model)` / `capabilities_for_model(model)` (issue #155, Phase 6(a)) — a model's real context-window capacity as a capability, so it can reach `rot.rs` without adding fs/clock/env access to the pure engine. `capabilities_for_model` is `capabilities()`'s counterpart for a *known* model string; `capabilities()` itself always calls `context_window_tokens(None)`, the adapter's own conservative default for an unstated model. See "Capacity-aware rot gates" below.
- `counts_tool_calls()` (issue #155, review finding C2, 2026-08-27) — whether `parse_events` can ever emit `NormalizedEvent::ToolCall` for this agent, i.e. whether `--max-tool-calls` (see [[Ctx Supervisors]]'s "Delegated-worker budgets") has any real signal to count against. Default `true` (most adapters' `parse_events` are built directly off verified tool-call records); `CodexAdapter` overrides it `false`, since its own `parse_events` has no verified rollout shape for a tool call at all and deliberately never emits one. Checked once, at argument-validation time in `exec::run_with_clock`, before anything is spawned — a codex worker refuses `--max-tool-calls` outright rather than accepting a ceiling that would silently never fire. Deliberately outside `Capabilities`: nothing in `rot.rs` or anything scored reads it.
- `native_artifact_presentation(path, interactive_required)` — a verified harness-owned output-artifact channel that needs no browser/server. The default is none; both current adapters retain it because image *input* support is not an output presentation API.
- `compact_command()`, `quit_sequence()`, `capabilities()`, `register_turn_signal(session, socket)` — the remaining agent-specific knobs the supervisors need (whether the agent supports `/compact`, how to send it a clean quit, its `Capabilities` flags, and how to wire up the turn-signal socket via `TurnSignalSetup { env, instructions }`).
- `model_args(model)` — argv tokens that select `model` for one interactive launch. `chat.rs::extra_with_model` folds them into the launch's **extra arguments**, so `interactive_cmd` emits them after the positional prompt; they are deliberately *not* spliced in at `launch_prefix_len()`, which counts only the argv the operator wrote and does not count the tokens `base()` prepends when it routes a `.cmd`/`.ps1` shim through a launcher (see [[Ctx Supervisors]] and [[Untrusted Configuration]]). Default is empty (no verified flag, no guess); both current adapters override it.
- `resume_args(session_id)` — argv tokens that resume `session_id`'s own conversation, for the dashboard's quit/restore roster (`dash::roster::restore_argv`). Default `None` means this agent's resume story is unverified: a restore falls back to a plain prompt-carrying relaunch instead of a guessed flag; only `claude.rs` overrides it today (see below).
- `session_pin_args(session)` — argv tokens that make the agent adopt zirv's own session uuid as the id of the conversation it is about to start, so a later `resume_args` against that uuid finds something. Appended **only** to a freshly launched dashboard pane (`chat.rs::dash_orchestrator_pane` and `dash::pane_launch_extra`, the two seams that mint their own uuid), never inside `interactive_cmd` itself: `wrap`'s relaunch path deliberately lets the harness mint a fresh conversation on every restart, and a *restored* pane already carries `resume_args`, which a pin would contradict. Default is empty; only `claude.rs` overrides it (`--session-id <uuid>`, the same flag `headless_cmd` already pins every headless run with). Without it the roster stored a uuid the harness had never heard of and every restored claude pane died on `--resume` with "no conversation found".
- `review_model_below(seat)` (2026-08-18) — this adapter's own verified model ladder, one tier below `seat` (the orchestrator seat's own model, `cfg.chat.model`, or `None`/unrecognised — read as "assume the top tier," a deliberate spend-up default the operator can override). Default is `""`, meaning "no verified ladder" (the same "nothing verified to guess" answer `default_distiller_model`'s `None` gives); both registered adapters override it with real ladders (see below). The sole caller is `resolve_review_model` in `harness_prompt_lines` below, used only when the operator has not set `review.<agent>` explicitly.
- `default_worker_model()` (2026-08-18) — this adapter's own hard-coded model for a delegated headless worker (`zirv ctx agent`, and the dashboard's own spawn-request pane variant) when the operator has not set `worker.<name>` explicitly. Default is `None` — the same "nothing verified to guess" answer as `default_distiller_model` and `review_model_below`'s empty-ladder default — meaning the launch omits `--model` entirely and the agent's own configuration picks. The sole caller is `resolve_worker_model` (see "The delegated-worker model default" below).

- `worker_system_prompt()` (2026-08-19) — this adapter's own layer for a delegated **Worker** session, the role-scoped counterpart to `base_system_prompt()`. `prompt::with_adapter_layer` splices exactly one of the two per launch, chosen by `PromptRole`, so a worker never receives the orchestrator layer's own delegate-everything coaching. Default `None`, the same "no verified mechanism" shape every other optional layer uses; only `claude.rs` overrides it (see below).

Several methods have trait-default implementations that only `claude.rs` currently overrides: `base_system_prompt()`/`worker_system_prompt()` (`None` by default — an unverified agent gets no layer of either kind, not another agent's instructions), `user_system_prompt_flag()`, `system_prompt_file_flag()`, `supports_system_prompt_file(launch)` (defaults to `false`, i.e. "fail open to argv delivery"), `launch_prefix_len()` (defaults to `1`, the count of leading argv tokens that are the program invocation itself rather than operator flags — used when a relaunch has to strip the program off an argv it didn't build), `resume_args()` and `session_pin_args()` (see above).

### Selection

`adapters::all(bin)` returns `vec![ClaudeAdapter, CodexAdapter]` — the full registry. `adapters::select(name, command, cfg: &CtxConfig)` picks one adapter, in priority order: an explicit `--agent` name, else `detect()` against the wrapped command's argv, else the registry's fallback (`resolve_default`, below — claude first in registry order, `cfg.agent_bin` supplies the adapter's `bin` override). In every arm, before the chosen adapter's own `ready()` is called, `select` checks `cfg.agents.refusal(adapter.name())` (the `.settings.toml` gate — see below) and returns that refusal as an `Err` if the agent is disabled. An adapter whose own program does not resolve to a launchable binary is still rejected at selection time by `ready()`, just after the gate check rather than before — both adapters share this one failure mode today, so neither is unready by construction.

`command_matches_adapter(adapter, agent_explicit, command)` is the trust gate used before injecting adapter-specific flags (like `--append-system-prompt`) into a wrapped command: it's true only when the operator named the agent explicitly or `detect()` matched, never merely because `select()`'s last resort had to default to claude with nothing backing it.

### The registry table and `resolve_default`

`ADAPTERS: &[(&str, AdapterCtor)]` (`mod.rs`) is the single source of truth for which adapters exist — a name paired with a constructor function:

| Name | Constructor |
|---|---|
| `"claude"` | `make_claude` → `ClaudeAdapter::new(bin)` |
| `"codex"` | `make_codex` → `CodexAdapter::new(bin)` |

`all(bin)`, `select`'s fallback, `describe_known_adapters`, `resolve_default`, and `readiness_note` all walk this table rather than naming adapters by hand, so none of them can drift from it or from each other — adding a third adapter is one entry here plus its own module.

**`readiness_note` (`zirv ctx --help`'s `about` text) has two generated clauses.** The first names every adapter whose own `ready()` still fails. The second names every ready adapter whose `capabilities()` is not fully true. Codex now reports system-prompt support because direct launches use `developer_instructions`; `system_prompt_supported(launch)` narrows that answer for shell shims. Its remaining static gaps are rot score, usage, and turn signal.

Codex has no file-based `developer_instructions` mechanism, so its composed system prompt always lands on argv (`-c developer_instructions=<json>`) — an oversized composed prompt used to hard-fail the whole launch on Windows (`os error 206`, the command line exceeding `CreateProcessW`'s ~32KB ceiling) under a workflow-heavy session with several accepted artifacts. Since issue #213 (2026-08-30), `prompt::injection_args_for_session` shrinks any inline-delivered composed prompt to a 24KB budget before it ever reaches the adapter, stripping memory/context/workflow layers in priority order rather than failing the launch — see [[Utilities]]'s "Inline-argv delivery is budgeted" section. Claude's file-based delivery path is unaffected.

`resolve_default(cfg: &CtxConfig) -> CtxResult<(Box<dyn AgentAdapter>, DefaultOrigin)>` is the fallback `select` calls when neither an explicit `--agent` nor argv detection named an adapter, but it also stands on its own — callers that want to *explain* the default rather than just use it (`zirv ctx status`'s `chat:` line, `zirv ctx chat`'s own resolution) call it directly:

1. If `cfg.agent` names an adapter, that one is used (after the gate check and its own `ready()`), tagged `DefaultOrigin::Configured`.
2. Otherwise, the first registry entry that is both gate-enabled and `ready()` wins, tagged `DefaultOrigin::FirstEnabledReady`.
3. If nothing qualifies, the error aggregates one line per adapter naming why it was skipped (the gate's refusal text, or the adapter's own `ready()` text) rather than reporting only the first failure — this is the same aggregated message `zirv ctx status` reuses (see [[Ctx Subsystem]]) instead of inventing its own wording.

`DefaultOrigin` is coarser than `chrome.rs`'s own `HarnessRule` (see [[Ctx Supervisors]]): `HarnessRule` adds a third case, `Explicit`, for an operator-named `--agent`, which never reaches `resolve_default` at all since `select`'s explicit-name arm short-circuits before the fallback.

### The `.settings.toml` enable/disable gate

`src/settings.rs` owns `AgentGate`, loaded once per `CtxConfig::load` into `cfg.agents` and consulted by `select` before every `ready()` call. Its module doc lays out the full layering (`~/.zirv/.settings.toml`, then `<repo>/.zirv/.settings.toml`, then `ZIRV_AGENT_<NAME>_ENABLED`) and the per-agent AND-fold trust rule (a repo may only narrow, the environment is the operator in both directions). What matters here: the gate is operator *policy* ("may zirv use this adapter"), separate from `ready()`'s implementation *state* ("does this adapter work yet"), and policy is checked first — a disabled codex reports the disable, not whatever `ready()` would have said. `select`'s three arms all honor it identically: an explicit `--agent codex` with codex disabled refuses outright (no fallback), and so does an argv `detect()` match — an operator-disabled adapter never silently falls back to a different one. The unknown-agent error's adapter list also marks disabled names, e.g. `known adapters: claude, codex (disabled)`. `zirv ctx status` prints one line per adapter from `AgentGate::states()`, enabled or disabled plus the file/variable responsible.

Three call sites use this registry: `src/script_runner/agent_command.rs` (a script's `agent_command` option runs a wrapped agent via `adapters::select`), and the two supervisors in `src/commands/ctx/exec.rs` and `src/commands/ctx/wrap.rs` (headless and interactive sessions respectively — see [[Ctx Supervisors]]).

**`[agents.<name>]` also carries an optional `capacity` key (2026-08-18).** The only recognized file value is `"small"` (absent means full capacity); it marks a harness capacity-limited, rendered in the harness roster as `-- small tasks only` (see `harness_prompt_lines` above) so an orchestrator routes only small, bounded briefs its way, for both review and `zirv agent` delegation. `AgentState::capacity_small` and `AgentGate::is_capacity_small(name)` carry the fold's answer; the trust shape mirrors `enabled` exactly, with one asymmetry: there is no `"full"` value a file can write, since absence already means full, so a repo file that is silent on capacity can never widen a home-narrowed `"small"` back — only `ZIRV_AGENT_<NAME>_CAPACITY` (`"small"`/`"full"`, either direction, an invalid value rejected loudly and scoped to that one agent) can. Both current `load` variants (the ordinary layered load and the operator-only fallback) fold it identically to `enabled`, and `.zirv/.settings.toml`'s own template documents the key next to `enabled`.

**A repo-only disable of the default agent must not silently select a different one (G, 2026-08-15).** `resolve_default`'s empty-`--agent` fallback used to skip a disabled candidate and simply continue to the next registry entry, without asking *who* disabled it. Once codex became ready too (see above), a repo checkout's own `.settings.toml` disabling claude was enough to make the fallback silently pick codex instead -- a different vendor account, with none of claude's capabilities -- which is exactly the "repo may narrow, not select" trust boundary this codebase holds everywhere else (see [[Untrusted Configuration]]). `AgentGate::disabled_only_by_repo(name)` reads provenance already computed by `load`'s own fold (`AgentState::disabled_by`, `Source::RepoFile` specifically, never `OperatorFile`/`Env`) to tell the two cases apart cheaply, with no second settings read. `resolve_default` now refuses outright -- naming both the narrowed adapter and what it would otherwise have silently picked -- the moment its fallback loop would land on a *different* adapter than a repo-only-disabled one; it is unaffected when nothing later in the registry qualifies either (no different provider was ever chosen, so the ordinary aggregated "no agent is both enabled and ready" error still applies and still names every candidate), and unaffected when the same agent was disabled by the operator or the environment instead (their own choice to make). `select`'s other two arms (explicit `--agent`, argv `detect()`) were never affected -- they already refuse a disabled agent outright rather than falling back to anything.

### The derived harness roster (`harness_prompt_lines`, 2026-08-16)

`adapters::harness_prompt_lines(cfg, current_adapter)` walks `ADAPTERS` in the same registry order as `readiness_note`, and renders one line per adapter describing whether an Orchestrator session may delegate to it right now via `zirv agent <name> "<prompt>"`: `- {name}: enabled, ready -- initiate with \`zirv agent {name} "<prompt>"\`` (plus a `(degraded: no ...)` suffix from `missing_capability_labels` when `capabilities()` isn't fully `true`), `- {name}: not installed (no '{program}' found)`, `- {name}: installed? not ready ({reason})` for an installed-but-otherwise-failing adapter, or `- {name}: disabled ({location})` for a gate-disabled one — naming where the disable came from (`AgentState::location`) rather than silently omitting the line, so an operator reading the prompt can tell "not offered because disabled in `.zirv/.settings.toml`" from "not offered because not installed." Unlike `readiness_note`, which never mentions a disabled adapter at all, this function's whole point is to be complete: it is the roster an Orchestrator session reads to decide what it can delegate to.

**A ready, enabled line also carries a capacity note (2026-08-18).** When `cfg.agents.is_capacity_small(name)` (the `[agents.<name>] capacity = "small"` marker in `.zirv/.settings.toml` — see "The `.settings.toml` enable/disable gate" below), an otherwise-ready line reads `- {name}: enabled, ready -- small tasks only -- initiate with ...` (or, for the self line, `enabled, ready -- small tasks only (this session's harness)`) instead of the plain "ready" wording. `HARNESS_PROMPT`'s final paragraph tells an orchestrator to route only small, bounded briefs to a harness marked this way, for both a cross-harness review request and a `zirv agent` delegation.

**A "ready" line only claims that after a real presence check, layered on top of `ready()`.** `AgentAdapter::ready()` is deliberately fail-open for a program name it cannot resolve — `resolve_program`/`ready()` still return `Ok` for a not-yet-real path, since several callers rely on that to fall through by name rather than error early. A roster line is a concrete invitation an orchestrator can act on immediately, so `harness_prompt_lines` layers `adapters::program_is_present(adapter.program())` on top: an explicit path or a `PATH` lookup (`PATHEXT`-aware on Windows) that must find a real file, never in place of `ready()`. `AgentAdapter::program()` (new, required, both adapters delegate to their own `self.program`) is what lets this caller — which only has `&dyn AgentAdapter` — ask what binary `ready()` actually resolved to. **Nit, not a bug:** off Windows the check is `Path::is_file()` only, with no executable-bit check, so it errs toward fail-open (a present-but-non-executable file still reads as "ready").

**This session's own harness never invites itself.** `current_adapter` (the resolved adapter's own `name()`, threaded in by both call sites below) marks its own line `- {name}: enabled, ready (this session's harness)` instead of the `zirv agent` invitation — `HARNESS_PROMPT` frames delegation as going to *other* harnesses, and a session cannot review-round itself.

**A global `agent_bin` override is handed only to the adapter it actually names.** Every `ctor(bin)` call used to reuse the operator's one `cfg.agent_bin` override for every adapter in the registry, which put one real binary's presence verdict onto every other adapter's line too. `agent_bin_names_a_different_adapter(bin, name)` checks whether `bin`'s basename names a *different* registered adapter than the one about to be built; when it does, that adapter is built with `None` instead, so its presence is judged from its own default program name exactly as if no override were configured.

The caller renders the lines and hands them to `prompt::compose` as data (`compose` itself stays free of the adapter registry and the settings gate); `wrap::run_with` and `chat.rs::dash_orchestrator_pane` both call it (passing their own resolved `adapter.name()`) only when `role == PromptRole::Orchestrator`, passing `Vec::new()` for a Worker launch — a delegated worker must not learn what it could delegate to in turn, the same recursion guard `HARNESS_PROMPT` itself already enforces. See [[Context Management]] and the prompt-composition ordering in `prompt.rs` (`PromptSource::Harnesses`, appended right after the harness layer, gated on `cfg.prompt.harnesses` and a non-empty roster).

**`HARNESS_PROMPT` (v6, 2026-08-22) states cross-harness delegation parity explicitly.** The delegation bullet's own tone used to be far terser than `ORCHESTRATOR_PROMPT`'s (claude-only) native-subagent-dispatch guidance — an emphasis asymmetry that read as "native dispatch is the real option, cross-harness delegation is an afterthought" even though nothing named a harness unfavourably. It now says plainly that delegating via `zirv agent` gets the same bar and the same confidence as a native subagent dispatch, with no extra hesitation for landing on a different vendor's model. `HARNESS_PROMPT` itself stays vendor-neutral by construction (it never names a model or tier vocabulary — that lives only in each adapter's own `base_system_prompt`), asserted by a regression test (`harness_prompt_never_names_vendor_specific_models`, `prompt.rs`).

### The review-routing line (`review_roster_line`, 2026-08-18)

`harness_prompt_lines` appends one trailing line after its per-adapter lines, naming which model runs code review for every *enabled* harness: `resolve_review_model(cfg, name, adapter)` picks the operator's own `cfg.review.claude`/`cfg.review.codex` when set (`REPO_FORBIDDEN` — see [[Untrusted Configuration]]), else `adapter.review_model_below(cfg.chat.model.as_deref())`. Each entry renders as `{name} -> "{model}" ({note})`, and the whole line states the routing rule: "run every code review on the named model, never on an orchestrator seat's own model" — softened to "never on a model above the named one" whenever any entry's resolved model text equals the seat's, case-insensitively (`equals_seat`). That equality happens two ways, both legitimate: a harness's ladder default is already at its floor tier (seat `"haiku"` resolves claude's own default to `"haiku"` too — the note reads "floor tier: the seat is already at the bottom rung" instead of "default: one tier below the seat"), or the operator explicitly configured `review.<agent>` equal to the seat (their call — the note reads `(configured)`). A disabled harness has no entry at all (absence, not silence, matching the per-harness line's own convention), and `review_roster_line` returns `None` — no line, not an empty one — when no harness is enabled. Claude's `ORCHESTRATOR_PROMPT` review bullet and its `.claude/agents pin their own models` clause were reworded to point at this line and carve out the one exception that outranks it (see below).

### The delegated-worker model default (`worker_model_args`, 2026-08-18)

A delegated headless worker (`zirv ctx agent <name> "<prompt>"`, and the dashboard's own spawn-request pane variant, `dash::mod::fulfill_spawn_request`) used to silently inherit whatever model the operator's own interactive default happened to be — often a far pricier model than the delegated task needs. `adapters::resolve_worker_model(cfg, name, adapter)` picks the operator's own `cfg.worker.claude`/`cfg.worker.codex` when set (`REPO_FORBIDDEN` as a whole table — see [[Ctx Subsystem]] and [[Untrusted Configuration]]), else `adapter.default_worker_model()`: claude hard-codes `Some("sonnet")`, codex has none (`None`, so its own CLI/config default applies untouched). `worker_model_args(cfg, name, adapter)` turns the resolved model into argv (`AgentAdapter::model_args`) or returns empty when nothing resolves. Unlike `resolve_review_model`, there is no ladder: a delegated worker has no orchestrator seat to be "one tier below," so the adapter-owned default is a fixed name, not a function of `cfg.chat.model`.

Two callers apply it, each guarding the operator's own explicit choice first:

- **`agent.rs`'s `worker_launch_flags`** (the `zirv ctx agent` headless path) checks `flags_pin_model` first — a bare `--model`/`-m`, or the joined `--model=value`/`-m=value` form, anywhere in the operator's own trailing flags — and leaves `flags` untouched if so; codex's `-m` short alias is recognised too, so a configured `worker.codex` cannot end up prepending a conflicting `--model` ahead of an operator's own `-m <value>` (fixed in the same round `seat_model_env` gained effective-model tracking, below). Otherwise `worker_model_args`'s result is prepended ahead of `flags` as trailing extras — the same discipline `chat.rs::extra_with_model` uses for the orchestrator seat — never spliced into a launcher prefix.
- **`dash::mod::pane_model_args`** (called by `fulfill_spawn_request`) prefers the request's own `model` field over `worker_model_args`. A spawn request carries no trailing flags of the operator's own except that one: since 2026-08-19 `agent::try_join_dashboard` recognises a **lone** `--model` pin (any spelling `adapters::model_only_flags` reads) and puts it in the request, while a request carrying anything else still declines the pane and runs headless — see [[Ctx Supervisors]]'s spawn-request protocol. The pin is re-checked at the authority side rather than trusted (a blank or flag-shaped value falls back to the resolved default), the same defense in depth the request's prompt gets from `argv_unsafe_prompt`. Without this, `HARNESS_PROMPT`'s new "name the cheapest model on every delegation" guidance would have cost a dashboard session its visible pane on every delegated task.

`worker.claude`/`worker.codex` are charset/length/leading-dash validated the same way `chat.model`/`review.*` are (`validate_model_str`), since — unlike `review.*`, which only ever lands in injected prompt *text* — these keys reach a real launch argv directly.

### Windows launcher rewriting

`mod.rs` also owns `resolve_program`/`ResolvedProgram`, used by both adapters' `base()` helpers. Off Windows it's the identity. On Windows, `std::process::Command` only ever appends `.exe`, so an npm-installed `claude` (actually `claude.cmd`) fails to spawn directly (`CreateProcessW` error 193); `resolve_program` walks `PATH`/`PATHEXT` the way the shell would and routes `.cmd`/`.bat` through `cmd.exe` and `.ps1` through PowerShell. A name that resolves to an unlaunchable extension is reported as a named `ready()`-style error before spawning; a name that resolves to nothing at all is left alone so the OS's own "not found" still surfaces.

Whenever `resolve_program` (or an already-resolved shim argv — `adapters::launch_reparses_through_shim`, fixed 2026-08-14) routes a launch through `cmd.exe /c`, that command line is **re-parsed by cmd.exe itself** before the shim ever runs, which is a real command-injection surface for any repo-controlled text riding along on the argv. `adapters::guard_cmd_shim_reparse` is the fail-closed backstop over that surface at every spawn seam; the full defense-in-depth mechanism (forced system-prompt-file delivery, stdin-delivered headless prompts, the backstop itself, and the two round-9 gaps closed in it — an unguarded `--help` probe, and the shim-detection false negative that left the file-form defense inert on `zirv chat`/bare `zirv`/the dashboard orchestrator) is documented in full on [[Known Issues]] ("Windows `cmd.exe` argv reparse…"), not duplicated here.

## The `claude` adapter

`ClaudeAdapter` (in `claude.rs`) wraps a `program` plus `bin_args` (so `ZIRV_CTX_AGENT_BIN="sh /tmp/stub.sh"` or `/usr/bin/env claude` both work) and an optional `home` override for tests. Every command starts from a shared `base()` that applies the program, its leading args, and the Windows resolution above uniformly.

- **`headless_cmd`** builds `claude -p <prompt> --session-id <id> <extra...>` — this is what pins a specific `SessionId` onto the launched process for `exec`.
- **`interactive_cmd`** builds `claude [<initial_prompt>] <extra...>`, the positional form `wrap` uses to start or resume a TUI session.
- **`ready()`** just calls `resolve_program` — claude is always considered implemented; the only failure mode is an unlaunchable binary.
- **Attested `--settings` layer** (`launch_settings_path`/`launch_settings_value`): materializes the fingerprinted policy-snapshot/settings pair every supervised launch attests (see [[Command Safety]] for the full attestation/hook mechanism). Two issue #147 (2026-08-26) changes to that layer's own content: it no longer injects a native `permissions.ask` rule naming `Bash(dangerouslyDisableSandbox:true)` (documented Claude behavior makes a native settings rule independent of a `PreToolUse` hook's decision, so that rule silently defeated every hook-side sandbox-escape `allow` — the attested safety hook is now the sole zirv-side decision point for an escape), and `launch_settings_value` gained a third parameter, `mail_write_dir: Option<&Path>` (`launch_settings_path` resolves it from `state.mail()`, best-effort), which adds `sandbox.filesystem.allowWrite` scoped to only that directory so `zirv ctx send` succeeds inside a sandboxed session. **Issue #168 (2026-08-27) briefly widened that parameter to `allow_write_dirs: &[PathBuf]`** (also passing `state.memory()`/`state.logs()`/`state.groups()`/`state.handoffs()`), **then reverted it on code review** the same day: with `is_reserved_zirv_escape_safe` (named `is_zirv_ctx_escape_safe` until issue #224; see [[Command Safety]]) restricted to an explicit non-subprocess-launching verb allow-list, every `zirv ctx <state-verb>` already rides the ALWAYS-ALLOWED unsandboxed retry, so the OS-sandbox `allowWrite` widening bought no operator-facing benefit while giving up defense-in-depth (an unlisted/unmatched command that isn't `zirv ctx` at all still can't write to memory/logs/groups/handoffs from inside the sandbox). The policy-snapshot/attestation directory (under the operator's HOME, not the state root) stays deliberately never allow-listed either way. `#[cfg(not(windows))]` code — both the widening and the revert were verified on `rust:1-bookworm` (non-root) per this repo's own Linux/Docker convention.
- **System prompt injection**: `system_prompt_args` emits `--append-system-prompt <text>` (empty when the composed prompt is blank). `base_system_prompt()` returns `ORCHESTRATOR_PROMPT`, a claude-specific constant describing zirv's orchestrator conventions (delegate to the Agent tool, route work to cheaper models, verify in batches). It is model-agnostic everywhere except one rule (2026-08-18): every Agent-tool dispatch MUST set the `model` parameter explicitly to one of the tool's own fixed tiers — `haiku` for mechanical/bulk work, `sonnet` for ordinary exploration/implementation/test-writing, `opus` only for hard debugging/design exploration — because that parameter's enum is the harness's own vocabulary, not a vendor lineup that ages out; the rule also bans fork-type subagents outright (a fork always inherits the seat model and ignores `model`) and forbids naming the seat's own model. `fable`/`mythos` are deliberately not named — they are not one of the rule's three routing tiers. The layer still never asks for `--model` itself: that flag picks *this seat's* model, which stays the operator's choice. Other 2026-08-18 hardening: briefs must ask a worker to reply with compact structured findings (never raw file dumps) and this seat's own replies stay brief and decision-focused (token economy, both directions). **Orchestrator sessions only, as of 2026-08-19** (`prompt::with_adapter_layer` is role-scoped — a Worker launch gets `WORKER_PROMPT` below instead, never this): its final-review bullet is nonetheless still worded self-contained, since a `chat`/`wrap` session may or may not also carry the `HARNESS_PROMPT` layer. That bullet: run this harness's own `/code-review` at a **single-reviewer effort level (low or medium)**, never a high-or-above fan-out (2026-08-18 — a fan-out forks agents that inherit the seat's expensive model; this is the same failure mode the `hook pretool` guard below exists to backstop deterministically, after prompt guidance alone let one fork fan-out burn roughly half a five-hour usage window), routed to the review model named in the harness roster and never this seat's own model, with cross-harness review layered *on top* of that, conditionally — only a session that also carries the (Orchestrator-only) `HARNESS_PROMPT` layer follows its bounded cross-harness review round as well. The model-routing bullet's ".claude/agents pin their own models; do not override those" clause carves out one exception: the harness roster's review-routing rule (`review_roster_line`, above) outranks it. `.zirv/commands/claude.yaml`'s rule 8 was reworded the same way, for the same reason. See [[Context Management]] and [[Decision Log]]. `supports_system_prompt_file` probes the installed binary's own `--help` output (cached process-wide, keyed by resolved program + bin_args, bounded by a 3-second timeout) for `--append-system-prompt-file`, so injection can move off argv (visible to other users via `ps`) once the installed version supports it, without hard-coding a version cutoff. Any probe failure reads as "unsupported," which only ever falls back to argv delivery — it never blocks a launch. **`detect_help_flag` now runs `guard_cmd_shim_reparse` against the exact probe argv before spawning it** (fixed 2026-08-14): the probe itself used to spawn `cmd.exe /c <shim> <bin_args> --help` on Windows with no reparse guard at all, and since `program_invocation` forwards every positional before the first flag, a distilled `zirv chat --resume` handoff summary could put repo-controlled metacharacters into that probe before the real launch's own guard was ever reached — a live RCE independent of the launch-time defenses. A rejected probe now reports "unsupported" the same as any other probe failure. See [[Known Issues]].
- **`review_model_below(seat)`** (2026-08-18) walks claude's own ladder, top to bottom: `fable`/`mythos` (the orchestrator-tier aliases) → `opus` → `sonnet` → `haiku`. Matched by substring on `seat`, lowercased first so a mixed-case seat (`"claude-Opus-4-5"`) lands on the right rung; `haiku` maps to itself (already the floor); an absent or unrecognised seat assumes the top tier (`opus`), a deliberate spend-up default the operator can override via `[review]` or `chat.model`.
- **`default_worker_model()`** (2026-08-18) returns `Some("sonnet")` — the hard default a delegated headless worker gets when the operator has not set `worker.claude` (see "The delegated-worker model default" above). Unlike the ladder above, this is not a function of any seat: a worker has no seat of its own.
- **`worker_system_prompt()`** (2026-08-19) returns `WORKER_PROMPT`, a deliberately much shorter sibling of `ORCHESTRATOR_PROMPT` and the only adapter layer a Worker launch ever receives: execute the brief directly and completely; never run `zirv agent` or spawn further zirv workers (this task was already routed here); route any subagent fan-out inside the task to the cheapest capable model, never above this session's own, and never to a fork-type subagent (which inherits the session model and ignores overrides); run review or verification passes only when the brief asks, since the orchestrator that spawned this worker owns review rounds; and treat the final message as the report — outcome first, self-contained, no raw file dumps. It carries none of `ORCHESTRATOR_PROMPT`'s delegate-everything coaching, which is the whole point: telling a delegated session its job is to delegate is what invited the recursion this split removes.
- **Transcript location**: `transcript_path` computes `~/.claude/projects/<slug of cwd>/<session-id>.jsonl`, where `project_slug` replaces every character outside `[A-Za-z0-9-]` with `-`. If the computed path doesn't exist (the slug rule is verified only for `/` and `.`, not every character), it falls back to scanning every project directory for a file matching `<session-id>.jsonl`.
- **Transcript parsing**: module-level `parse_events`/`structural_context`/`context_tokens_of` functions (which the trait methods just delegate to) read Claude Code's own JSONL transcript format — assistant/tool-call/token-usage shapes, compact boundaries, sidechain/meta line skipping — and are validated in tests both against hand-built JSON and against a recorded, credential-scrubbed real session fixture (`tests/fixtures/claude-real-session.jsonl`, re-recorded via `scripts/record-claude-fixture.py`).
- **Session ids**: claude accepts an explicit `--session-id` on the headless path, so zirv controls the id up front; there's no equivalent for `interactive_cmd`, which relies on claude's own session management plus the transcript-scanning fallback above.
- **`model_args`** emits `--model <model>`, verified against the real CLI (`claude --help`, v2.1.220). **`session_pin_args`** emits `--session-id <uuid>` (the flag `headless_cmd` already uses, offered to interactive dashboard panes so the roster's stored uuid *is* the claude conversation id). **`resume_args`** emits `--resume <session_id>` — not a fresh claim: `wrap::extra_launch_flags` already strips `--resume` on every restart (it pins a launch to an existing conversation) and `exec.rs`'s `RESUME_FLAGS_WITH_VALUE` already treats it as a two-token flag, so this only wires up an already-verified flag for the dashboard's own restore path.
- **`context_window_tokens(model)`** (issue #155, Phase 6(a)) maps a model id to a capacity: `DEFAULT_CONTEXT_WINDOW_TOKENS` (200_000, conservative) for every id it does not recognise as a long-window seat and for `None` (unstated model), `LONG_CONTEXT_WINDOW_TOKENS` (1_000_000) for one carrying a `[1m]`/`-1m` marker (case-insensitive substring match). Conservative by design: an overstated capacity raises the restart ceiling past what the seat can actually hold, and overrunning the real window is a far worse outcome than rotating slightly early. **`model_hint(jsonl)`** (issue #155 review finding D1, 2026-08-27) reads the last `message.model` field off an `assistant`-typed transcript row, scanned newest-to-oldest — the newest wins so a live `/model` switch mid-session is reflected rather than the session's original model — off the same lines `parse_events`/`transcript_usage` already walk, no separate pass.

## The `codex` adapter

`CodexAdapter`, in `codex.rs`, is a **supported adapter with an honestly degraded capability set**, not a stub. `ready()` mirrors `ClaudeAdapter::ready` exactly, so `--agent codex` succeeds wherever the program resolves. `capabilities().system_prompt` is true for the adapter overall, while `system_prompt_supported(launch)` rejects shell-shim launches. `capabilities().events` is now `true` (issue #86, 2026-08-23 — see below); marker signal and the turn-signal socket mechanism remain false/unimplemented (`register_turn_signal` is still a no-op), tracked as the residual half of issue #11. `context_window_tokens(_)` explicitly reports `None` (issue #155, Phase 6(a)) — no capacity is verified for codex, so rot's token gate falls back to `ScoreConfig`'s own absolute defaults for a codex session rather than a fabricated ratio-derived one (see [[Rot Engine]]). `counts_tool_calls()` reports `false` (issue #155, review finding C2, 2026-08-27): `parse_events` never emits `NormalizedEvent::ToolCall` for codex — no verified rollout shape exists for one — so `--max-tool-calls` is refused up front for this adapter rather than accepted and silently never enforced (see [[Ctx Supervisors]]'s "Delegated-worker budgets").

**`capabilities().token_usage` staying `false` does not mean codex has no usage data (2026-08-16).** That flag describes in-process event parsing, while `window::refresh_codex_usage` scans rollout files separately for the usage-*window* percentages (a different number from the rot engine's own token gate). `base_system_prompt()` remains `None` because Zirv's Claude-specific base layer names tools Codex does not have; agent-neutral composition is delivered on direct launches by `system_prompt_args` as `-c developer_instructions=<TOML string>`. Shell-shim launches fail closed onto the task-prompt-text fallback — see "The Windows npm-shim injection fallback is now surfaced" below (issue #85). The distiller (and, via `read_only_args`, the workflow reviewer) is pinned to `--sandbox read-only`, plus `--ignore-rules --ignore-user-config` when the installed codex-cli's own `--help` documents them — see "The distiller/reviewer sandbox residual is now surfaced and closes on a newer codex-cli" below (issue #89).

**`capabilities().defer_injection_submit` is `true` for codex, `false` for claude (issue #118, 2026-08-25).** A new `Capabilities` field naming whether this adapter's own composer folds a same-write trailing `\r` into pasted text, so a caller injecting text into it must write the line and its submitting `\r` as two genuinely separate writes rather than one burst. Verified `true` for codex against its ratatui composer — the same paste-fold `dash::pane`'s own visible injections already close (issue #114/PR #116) — and `false` for claude, whose composer submits a same-burst trailing `\r` correctly. The one production caller this changes behavior for is `wrap::write_mail_advisory` (the T13 mail-advisory injection); `wrap::inject_compact`/`Action::Compact` never consults the field at all and stays unconditionally single-burst, since that call site is only ever reachable for a turn-signal-capable adapter (claude) in the first place. See [[Ctx Supervisors]]'s "Mail advisory" and "Injection semantics" sections for the mechanism, and the shared `INJECTION_SUBMIT_DELAY` constant (now defined once in `ctx/mod.rs`, re-exported by `dash::pane`) both modules write the deferred `\r` after.

**Codex event parsing derives real rot/usage events from the rollout JSON (issue #86, 2026-08-23).** `window::parse_rollout_record` (in `window.rs`, see [[Usage and Pacing]]) is the single shared collector both the usage-window reader (`parse_rollout_line`) and `CodexAdapter::parse_events`/`structural_context`/`transcript_usage` now parse a rollout line through, so the transcript is read once per line rather than by drifting, independent readers. Only the two shapes verified in `docs/superpowers/notes/2026-07-31-codex-cli-facts.md` ("Turn boundary", "Token usage") are mapped, onto the EXISTING `NormalizedEvent` vocabulary — no codex-specific variant, and `rot.rs` gains no codex knowledge at all:

- `task_started` → `NormalizedEvent::TurnStart` (verified: "`task_started` and `task_complete` bracket a turn and share a `turn_id`").
- `task_complete` → `AssistantFinal { text: last_agent_message.unwrap_or_default(), input_tokens: <most recent cumulative total this parse has seen> }`. `last_agent_message` is `null` on a failed turn, which reads as empty text — honest, not guessed.
- `token_count` (whenever `info.total_token_usage` is present) → its own `AssistantFinal { text: "", input_tokens }`, so `rot::context_tokens` (the token gate) tracks codex's real cumulative context size between turn boundaries too, not just at them. The empty text never counts as a "turn" (`rot::turn_final_texts` only counts non-empty text) and has no effect on the marker signal, which stays capability-gated off for codex regardless.

NOT mapped, because no verified rollout shape exists for them: tool calls, tool results, and any compaction/summarization boundary — `ToolCall`/`ToolResult`/`Compaction` are simply never emitted for codex, so `tool_failure_rate`/`repetition_hits` always read `0.0` and only the token-ceiling escalation path still fires. `structural_context` is populated too, from the same verified `task_complete.last_agent_message` lines (`assistant_texts` only — `user_messages`/`files_touched`/`tool_errors` stay empty, no verified shape), which matters because `handoff.rs`'s eventless guard now lets a codex session reach the real distiller instead of the honest "no data" refusal it got before. A recorded, bounded residual: the mapping carries a tiny bit of cross-line state (the running `last_tokens` value) local to one `parse_events` call, which can be briefly stale immediately after an incremental poll's chunk boundary splits a `token_count` line from its `task_complete` — self-correcting at the next `token_count` line. A fixture (`tests/fixtures/codex-rollout-turn-events.jsonl`) and `codex.rs`'s own tests (`parse_events_derives_turn_boundaries_and_token_updates_from_the_rollout_json`, `a_derived_event_stream_scores_through_the_rot_engine`, `structural_context_carries_the_verified_assistant_text_only`) pin the exact event sequence and end-to-end rot scoring. See [[Rot Engine]], [[Known Issues]].

**Codex's own error text splits into three message classes, only one of which is a usage window (issue #227, 2026-08-31).** Codex is billed under one of three modes with different window shapes — API credits (no rolling windows at all; a quota error there is a hard account stop), Pro (a 5-hour session window plus a 7-day weekly window, the same two `window.rs` already models), and premium tiers (weekly only, no 5-hour window). `window::windows_from_rate_limits` already keys each window purely on its own `window_minutes` field rather than assuming both are always present, so a weekly-only premium-tier account correctly yields `five_hour: None` and never fabricates a 5-hour reading from weekly data — this needed no code change, only new tests pinning the behavior against a synthetic weekly-only snapshot. The adapter/pacing layer now also distinguishes codex's error text itself into three classes, all matched over live output the same way `pace::is_limit_hit` already scans for a usage-window message: the existing `LIMIT_HIT_PATTERNS` (a real rate-limit window trip — park and wait for reset, unchanged), a new `CAPACITY_PATTERNS` class (six needles, final after a review round dropped a seventh: `"Selected model is at capacity"`, `"model is at capacity"`, `"is at capacity. Please try a different model"`, `"currently at capacity"`, `"overloaded_error"`, `"The model is overloaded"` — `"503 Service Unavailable"` was removed before merge since a non-provider process, like a test hitting `localhost`, could print that generic HTTP line too; see [[Usage and Pacing]]) — a transient, model-level condition with no relation to any window, so `exec.rs` restarts the same-repo session with capped backoff instead of parking it against a window that was never actually hit — and a new `ACCOUNT_EXHAUSTED_PATTERNS` class (`"insufficient_quota"`, `"exceeded your current quota"`, `"check your plan and billing details"`, following OpenAI's own documented `insufficient_quota` error shape, not a captured zirv transcript) — a hard account/billing stop that spends no restart budget at all. See [[Ctx Supervisors]]'s "`exec` — supervising one headless run" section for the restart/exit-code mechanics and [[Known Issues]] for the `zirv ctx loop` residual this leaves open.

**An interactive `untrusted` approval posture gets one advisory, never a config rewrite (issue #222, v3.5.0).** Codex has no per-command approval mechanism zirv can pre-clear the way #224 pre-approves reserved claude built-ins — approval posture is entirely operator-owned via `~/.codex/config.toml`'s `approval_policy` key, which codex itself consults on every interactive command. `resolve_codex_approval_posture(home) -> CodexApprovalPosture { Untrusted, OnRequest, Never, Unknown }` best-effort reads that key (any read/parse failure or unrecognised value reads `Unknown`, never a guess); `codex_approval_advisory(posture)` is the pure decision, `Some` only for `Untrusted`. `wrap::run_with`, on an interactive (not `--no-supervise`, not an unmatched wrapped command) codex launch whose posture resolves `Untrusted`, emits the advisory once via the existing `Announcer` (`Event::CodexApprovalAdvisory`) suggesting `approval_policy = "on-request"` (or `"never"`) in `~/.codex/config.toml` — zirv never rewrites that file itself. Covers both `zirv chat`'s wrap fallback and a direct `zirv ctx wrap`, since both funnel through this one function; the dashboard's own orchestrator pane path does not go through `wrap::run_with` and is not covered. Headless codex launches are unaffected — they already run with `--ask-for-approval never`. See [[Command Safety]]'s "Codex has no per-command approval mechanism" note and [[Untrusted Configuration]].

**The Windows npm-shim injection fallback is now surfaced (issue #85, 2026-08-23).** On a shim-resolved launch (`system_prompt_supported(&[]) == false`), zirv already folded the composed session context onto the task-prompt text instead (`prompt::task_prompt_with_composed_fallback`, wired into `chat.rs`'s orchestrator path, `exec.rs`, `run_loop.rs`, and `dash::compose_worker_prompt`) — that part predates this round. What was silent: `zirv ctx status` now prints a persistent `{name}: context via task-text fallback (npm shim launch cannot carry the injected system prompt safely)` line (`status.rs`'s `describe_injection_fallback`, adapter-neutral: any adapter with `capabilities().system_prompt` true but `system_prompt_supported(&[])` false), and `prompt::injection_event`/`log_injection`'s own `(Some(_), false)` branch was reworded to match, so the transient `zirv ▸` announcement (already fired at every `wrap`/`exec`/`loop` launch decision) and the persistent status line never disagree. **File-form injection was investigated and rejected, not deferred:** the only candidate on the real installed CLI, `-p/--profile <NAME>` (layers `$CODEX_HOME/<name>.config.toml`), would require zirv to write into the operator's own `$CODEX_HOME` — a directory this codebase holds read-only everywhere else — or redirect `$CODEX_HOME` entirely, which would also move `auth.json` and break authentication. See [[Known Issues]].

**The distiller/reviewer sandbox residual is now surfaced and closes on a newer codex-cli (issue #89, 2026-08-23).** `CodexAdapter::read_only_args` probes the installed binary's own `codex exec --help` (`ignore_flags_supported`, cached by program+bin_args, the same `--help`-probe-over-hardcoded-version-cutoff shape `ClaudeAdapter::supports_system_prompt_file` uses, and for the identical reason — the real minimum supporting version between 0.105.0 and 0.146.0 was never captured) and appends `--ignore-rules --ignore-user-config` only when it finds both documented; any doubt (binary missing, timeout, only one flag present) reads as unsupported. `distiller_cmd` builds on `read_only_args`, so the distiller gets the stronger pin automatically the moment the probe says yes; the workflow reviewer gets it too, since it resolves its own read-only pin through the same `read_only_args` via `adapters::read_only_args_for_agent_name`. When the flags cannot be added, `CodexAdapter::sandbox_residual_note` names the gap, and `adapters::announce_sandbox_residual_once` (a one-time-latch `zirv ▸` announcement, mirroring `poll::announce_keychain_prompt_once`'s shape) fires exactly once per process — wired into every production judgment-model call site (`handoff::run_model`'s callers across `handoff.rs`/`memory.rs`/`memory_optimize.rs`/`optimize.rs`, plus the reviewer's own `read_only_args_for_agent_name`). Claude's own `sandbox_residual_note` stays the trait default `None` — its argv is byte-for-byte unchanged. See [[Known Issues]].

Command shapes, per comments citing `docs/superpowers/notes/2026-07-31-codex-cli-facts.md` and `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md` (verified against `codex --help`/`codex exec --help`): `headless_cmd` builds `codex exec <prompt> <extra...>` (codex has no `--session-id` flag — it always mints its own id), `interactive_cmd` builds `codex [<prompt>] <extra...>`, `distiller_cmd` builds `codex exec [--model <model>] --sandbox read-only` (codex reads its prompt from stdin, so it's built the same way as claude's; `--model` is omitted entirely when `model` is empty — see the model-resolution paragraph below), `model_args` emits `-m/--model <model>` (verified present on top-level `codex --help` too, so the dashboard's orchestrator pane can select a model on codex the same way it does on claude), and `transcript_path` scans `~/.codex/sessions/<YYYY>/<MM>/<DD>/...` recursively by filename suffix, since codex nests transcripts under a date directory that a bare session id can't predict.

**Per-adapter distiller model default (2026-08-15).** `HandoffConfig.model` used to default to the literal `"haiku"` unconditionally, which reached `codex exec --model haiku` for a codex session and failed outright (falling back to codex's own empty `structural_context` for a near-empty handoff). It is now `Option<String>`, defaulting to `None`, and every caller (`handoff.rs`, `exec.rs`, `wrap.rs`, `optimize.rs`) resolves it through `handoff::resolve_distiller_model(explicit, adapter)` rather than reading the config field directly: the operator's own choice if set, else the resolved adapter's own `AgentAdapter::default_distiller_model()` (claude: `Some("haiku")`; codex: `None`, the trait default — zirv has no verified cheap-model name for codex's lineup). An empty result means "omit `--model` entirely," which `CodexAdapter::distiller_cmd` reads literally, letting codex's own `~/.codex/config.toml` default apply instead of zirv guessing a name that may not exist on the operator's account. No `session_pin_args` override either, for the same reason and one stronger: codex has no `--session-id` flag at all, so an interactive pane cannot be pinned and the trait default (empty) stands. No `resume_args` override: codex's own resume story (a `--last`/session-id flag for the interactive launch) is unverified against the real CLI, so the trait default (`None`) stands — `dash::roster::restore_argv` falls back to a plain prompt-carrying relaunch for this adapter.

**`review_model_below(seat)`** (2026-08-18) walks codex's own ladder, top to bottom: `gpt-5.6-sol` (the default when no `-m` is given) → `gpt-5.6-terra` → `gpt-5.6-luna` → `gpt-5.4-mini` (the older, hidden floor tier) — sourced from `codex debug models` in `docs/superpowers/notes/2026-07-31-codex-cli-facts.md`, captured on codex-cli **0.146.0** (brew), **not re-verified** against 0.105.0 (the npm-published build most operators actually get) — a version-split residual sibling to `distiller_cmd`'s existing `--ignore-rules`/`--ignore-user-config` gap; see [[Known Issues]]. Matched by substring on `seat`, lowercased first, same as claude's ladder; `gpt-5.4-mini` maps to itself; an absent, unrecognised, or cross-adapter seat (e.g. a claude `chat.model` value) is read as "assume the seat is at the top tier," so it returns `gpt-5.6-terra` — the tier one below `gpt-5.6-sol` — same spend-up-default rationale as claude's own ladder.

**`default_worker_model()`** (2026-08-18) returns `None`, the trait default: codex has no adapter-owned hard default for a delegated worker either, so its own CLI/config default applies untouched when `worker.codex` is unset — see "The delegated-worker model default" above. **`worker_system_prompt()`** (2026-08-19) is `None` for the same reason `base_system_prompt()` is: zirv has verified no codex-specific tool vocabulary to write either layer in, and codex has no injection mechanism to carry one anyway (`capabilities().system_prompt == false`).

**The Windows `cmd.exe`-shim gap is closed.** `CodexAdapter::base()` now routes `self.program` through `resolve_program`, exactly like claude's own `base()` (see "Windows launcher rewriting" above and [[Known Issues]]). `launches_through_cmd_shim` is overridden the same way claude's is (`super::launches_through_cmd_shim(&self.program)`), so an npm-installed `codex.cmd` on Windows is recognised as the shim shape. `headless_cmd_stdin` builds the same `codex exec <extra...>` invocation `headless_cmd` does but with the positional prompt token dropped — codex's own verified stdin fallback (`codex exec` with `[PROMPT]` omitted, or `-`, reads from stdin) — so `exec.rs`/`run_loop.rs`'s FIX B branch (see [[Ctx Supervisors]]) delivers a headless prompt on stdin instead of an argv token cmd.exe would reparse, on exactly the shim-launch shape. `guard_cmd_shim_reparse` remains the fail-closed backstop at the spawn seams, not the primary mechanism, for codex exactly as it is for claude. **`headless_cmd_stdin` also fires off a shim now (issue #220, v2.40.0):** `exec.rs::build_headless` — the one chokepoint every headless launch/relaunch/nudge/park reuses — routes to it whenever the WHOLE assembled `headless_cmd` argv (program plus every argument, the issue #213 system-prompt layer included) exceeds `prompt::INLINE_ARGV_PROMPT_BUDGET_BYTES`, not only on a shim reparse; `headless_cmd_stdin` itself is unchanged, only its caller gained a second reason to reach for it. See [[Ctx Subsystem]]'s "Chat, Agent and Mail" section.

**`launches_through_cmd_shim`'s trait default is now secure by default (issue #92, 2026-08-23).** The default body in `adapters/mod.rs` no longer returns a hardcoded `false`; it calls the free `launches_through_cmd_shim(self.program())` function directly — the same derivation both `ClaudeAdapter` and `CodexAdapter` already used in their own (still-present, now redundant but harmless) overrides. A third adapter that implements `AgentAdapter` and doesn't touch this method at all is now protected automatically: the default asks `resolve_program` whether the binary it actually resolved is a `.cmd`/`.bat` shim, rather than assuming it isn't. Both registered adapters' behaviour is unchanged (their explicit overrides call the identical free function). `guard_cmd_shim_reparse` is unaffected — still the fail-closed backstop, not the primary mechanism. Covered by `adapters::tests::an_adapter_with_no_override_is_still_protected_from_a_cmd_shim` (Windows-only) and `an_adapter_with_no_override_reports_no_shim_for_a_direct_program`, both against a minimal `NoOverrideAdapter` that implements only the trait's required methods.

## `policy_support` — translating zirv's policy honestly per launch mode (2026-08-24)

`AgentAdapter::policy_support(capability, stance, mode: LaunchMode)` is the per-adapter half of zirv's canonical permissions policy. An adapter answers with `Enforced` / `Degraded` / `Unsupported` / `OperatorControlled` plus the **named verified mechanism**, for the posture actually being launched. `PolicyReport` carries the same mode and renders the shipped interactive baseline only on interactive reports.

**The honesty rule is the point:** prompt text asking a session to respect a stance is advisory context, never enforcement, so an adapter with only that to offer reports `Unsupported` — whose own rendered label reads "not enforced (advisory only)". Never round a partial mechanism up to `Enforced`.

- **Claude:** `Deny` keeps the existing tool-pin answers. On an interactive launch, `Ask` for shell execution/approval is `Degraded` through `--permission-mode default` plus the `Bash|PowerShell` safety hook, and outside-repo writes are `Degraded` through the workspace-scoped native allow list; other tools still land on Claude's own settings. The hook and immutable policy snapshot are attested on every projected launch rather than depending on setup state. Headlessly the same asks are `OperatorControlled`—`dontAsk` cannot carry a prompt—while unverified network/git/path guarantees remain advisory.
- **Codex:** never reports `Enforced`. On an interactive launch whose capability probe supports `on-request`, shell/approval `Ask` is `Degraded`; when a second probe sees `--approve-for-me`, the mechanism text also names Codex's native security reviewer. The sandbox contains damage and Codex chooses escalation at its own boundary, with no per-command channel for Zirv's `[safety]` classification. If the probe cannot prove support, and on every headless launch, that ask mechanism is not claimed. Existing `Deny` descriptors remain scoped to what `read-only`/`never` actually do.

The asymmetry between the two is reported rather than smoothed over: `policy::evaluate` over one canonical policy yields two different, honest answers.

## `LaunchMode` and policy projection — applying policy to a real launch (2026-08-24)

`adapters::LaunchMode::{Interactive, Headless}` is the compiler-enforced answer to one question: is a human watching this harness and able to answer an approval? `policy_support`, `PolicyReport`, `compile`, `policy_launch_args`, and `default_sandbox_args` all receive that answer explicitly; none guesses from a TTY or adapter name.

| Real-launch seam | Mode | Why |
|---|---|---|
| `chat.rs::dash_orchestrator_pane` | Interactive | Dashboard orchestrator TUI is visible. |
| `wrap.rs` | Interactive | Wrap supervises the operator's TUI. |
| `dash/mod.rs::fulfill_spawn_request` | Interactive | Worker pane is visible inside the watched dashboard. |
| `handover.rs::resolve_swap_launch` | Interactive | Both callers swap a live interactive seat. |
| `exec.rs` | Headless | One supervised non-interactive run. |
| `run_loop.rs` | Headless | Fresh unattended session per cycle. |
| `agent.rs::worker_launch_flags` | Headless | Pane-less delegated-worker fallback; a dashboard worker instead uses the dash row. |

`policy_support` above answers the *report* question; `AgentAdapter::policy_args(&EffectivePolicy, LaunchMode)` and `AgentAdapter::default_sandbox_args(&SandboxConfig, &SafetyPolicy, LaunchMode)` answer the actual argv question. `adapters::policy_launch_args(cfg, adapter, flags, mode)` is the shared seam all seven call:

1. `flags_pin_policy(flags)` — if the operator's own trailing flags already name `--sandbox`/`-s`/`--ask-for-approval`/`-a`/`--permission-mode`/`--disallowedTools`/`--allowedTools` (bare or `=`-joined), nothing of zirv's own is prepended at all. The operator's own choice must demonstrably win, not merely survive because a CLI takes the last occurrence of a repeated flag.
2. Otherwise, `adapter.default_sandbox_args()` when `cfg.sandbox.enabled` (the shipped default since 2026-08-22 — see below), then `adapter.policy_args(&cfg.policy, mode)` for any *additional* restriction an explicit `[policy]` `Deny` stance asks for on top of the baseline. `policy_args` itself is unchanged from `[policy]`'s own honest-report semantics: `EffectivePolicy::default()` stays all-`Allow` ("zirv's per-capability policy declares nothing"), so it contributes nothing unless the operator has explicitly denied `repo_fs_write`/`shell_exec`. `policy_args` gained the `LaunchMode` parameter in issue #134 (2026-08-25) — see below — for the same reason `default_sandbox_args` already carries it: Codex's own projection is command-surface-dependent, not just posture-dependent.

The spec's interactive stance table is `EffectivePolicy::interactive_baseline()`, used for reporting only. It is deliberately not `EffectivePolicy::default()` and never enters `resolve`'s max fold: doing so would silently narrow headless launches and make an operator's `ZIRV_CTX_POLICY_*=allow` unable to loosen an inherited interactive ask.

**The shipped posture is now intentionally asymmetric:** interactive sessions minimize interruption—everyday and unknown commands run silently, a short closed list asks, and a shorter irreversible/self-destructive list denies—while headless sessions retain the fail-closed posture because nobody can answer.

- **Claude interactive:** `--permission-mode default`, non-command allow rules plus the scratchpad on `--allowedTools`, deny rules on `--disallowedTools`, and the ask set on neither. The inverted projection does not lengthen a finite Bash allow-list, because any finite list under `default` would prompt for the next unknown command. Instead the `Bash|PowerShell` safety hook is the sole per-command shell gate and emits explicit `"allow"` for ordinary/unknown commands. Every projected Claude launch now names fingerprinted atomic settings and policy-snapshot files under `~/.zirv/runtime/`: the hook verifies the SHA-256 snapshot, evaluates launch and current policies, and keeps the stricter answer, so tampering or partial attestation asks interactively/denies headlessly. The layer also denies common credential paths and scrubs cloud credentials from subprocesses. On macOS/Linux/WSL2 it enables auto-allow OS sandboxing and fails closed if it cannot start; native Windows gets the identical command classifier but omits Claude's unsupported kernel sandbox. Task 3's mandatory live probe used Claude Code 2.1.241 on 2026-08-24 and reached `permissionMode: default`, but the account rate limit fired before a Bash tool request, so ask-over-native-allow could not be established; the conservative **Design B** shipped—no blanket `Bash(*)` native allow, with the hook's explicit allow carrying ordinary commands.
- **Claude headless:** unchanged `--permission-mode dontAsk`; allowed commands are pre-approved and `deny ∪ ask` is folded into `--disallowedTools`, so an unanswerable prompt becomes a refusal.
- **Codex interactive:** `--sandbox workspace-write --ask-for-approval on-request` only when `ON_REQUEST_APPROVAL_SUPPORT` proves the installed CLI documents it; otherwise fail closed to `never`. An independent cached probe for `--approve-for-me` adds Codex's native automatic security reviewer when available, reducing boundary prompts without bypassing the sandbox; headless never enables it. `untrusted` was rejected because it prompts for everything outside Codex's narrow built-in trusted set—the exact polarity this work removes.
- **Codex headless:** `--sandbox workspace-write` paired with an approval-suppression argv from `approval_suppression_args` — see the exec-scoped probe below.

Both Codex probes run top-level `--help`, are cached per `ProbeKey`, bounded to three seconds, and treat absence/timeout/spawn failure as unsupported. No `[safety]` rule is projected onto Codex: there is no verified per-command channel. Its interactive `policy_support` is therefore `Degraded`, explicitly naming the sandbox-versus-classifier gap rather than implying Claude parity.

**Issue #134 (2026-08-25), the exec-scoped `--ask-for-approval` probe.** Current codex-cli (0.149.x) rejects `--ask-for-approval` outright on `codex exec` (`error: unexpected argument '--ask-for-approval' found`) even though the identical flag is still accepted on the top-level INTERACTIVE `codex [PROMPT]` launch — `zirv agent codex "..."` (a headless delegation, built via `headless_cmd`/`headless_cmd_stdin`) failed before the worker ever started. `ON_REQUEST_APPROVAL_SUPPORT` cannot answer this: it deliberately probes the TOP-LEVEL `codex --help`, gating whether the `on-request` VALUE is safe to pass on an interactive launch, a different command surface entirely. A new probe, `EXEC_ASK_FOR_APPROVAL_SUPPORT` (mirroring `IGNORE_FLAGS_SUPPORT`'s own `codex exec --help` shape exactly — same resolution, same fail-closed cmd-shim reparse guard, same three-second timeout, same "any doubt reads as unsupported" polarity), checks whether `codex exec --help` documents `--ask-for-approval` at all. `CodexAdapter::approval_suppression_args(mode, value)` is the shared helper both `policy_args` and `default_sandbox_args` now call: on a headless launch whose exec probe says unsupported, it emits `-c approval_policy=<value>` (verified to work on both interactive and `exec` surfaces, per `system_prompt_args`'s own `-c/--config key=value` doc comment) instead of the rejected flag pair; every other case (interactive, or headless where the flag is still documented) emits the plain `--ask-for-approval <value>` pair byte-for-byte unchanged. Interactive projection is completely unaffected — verified live on this machine's own installed codex-cli, which does not document the flag on `exec --help`, producing `--sandbox workspace-write -c approval_policy=never` for a real headless launch. Per repo convention, tests never assert an exact argv depending on the live probe; the forcing seam (`with_exec_ask_for_approval_forced`) pins both branches deterministically.

`adapters::SHIPPED_POSTURE_ALLOW`/`_ASK`/`_DENY` are the static source of the built-in classifier and Claude projection; issue #224's reserved zirv families are generated alongside them from `utils::RESERVED_COMMANDS`. Allow contains workspace/harness read-write scopes, web tools, everyday toolchain families/read utilities, plain `curl`/`wget`, and a launch-computed scratchpad. Ask is the short reversible-danger list. Deny contains irreversible publication/deletion, credential and privilege boundaries, pipe-to-shell, and zirv-self-destruction rules. They are an honest tripwire, not a sandbox: arbitrary-code interpreters can express effects a finite glob list cannot recognize. See [[Command Safety]] for the exact classification and SQL rules.

**Issue #224 (2026-08-31):** the former issue #98 `Bash(zirv *)` rule also pre-approved every repo-defined script. It is replaced by one generated rule per reserved name. Claude's launch-local settings now carry the same list in `permissions.allow` and `sandbox.excludedCommands`: reserved built-ins avoid the generic unsandboxed-retry prompt, while `zirv <script>` receives no native exception. `zirv report` itself is excluded rather than allowing `gh *`; its implementation invokes only fixed `gh auth token --hostname github.com`, captures the token, and sends through Zirv's fixed report path, so the credential file remains denied to arbitrary commands and direct `gh auth *` is not exposed. The independent PreToolUse hook remains in force, so repo `deny`/`ask` rules can still narrow built-ins. Codex has no matching per-command settings projection and is unchanged.

**Issue #111 (2026-08-23):** dangerous flag reordering and sibling-utility escapes remain covered by mid-string wildcard patterns. The 2026-08-24 split moved reversible git/find families to `Ask` while credential/irreversible `gh` families remain `Deny`; ordinary uses still stay `Allow`.

`cfg.sandbox.enabled` (`[sandbox] enabled = true`, `ZIRV_CTX_SANDBOX`) is `REPO_FORBIDDEN` — see [[Untrusted Configuration]] — the operator's own opt-out back to the pre-2026-08-22 behaviour (no zirv-applied argv at all; a launch's posture then comes entirely from the harness's own native config).

## `distiller_cmd` and the untrusted-CLAUDE.md trust boundary

`distiller_cmd` builds the command for a separate, usually cheaper model child process — spawned by `handoff::run_model` — whose only job is to read a distillation prompt from stdin and answer with plain text: either summarizing a session transcript into a handoff (`handoff::distill`/`distill_or_structural`) or making the judgment calls in `zirv ctx optimize`. That prompt embeds text that ultimately traces back to a repository's own `CLAUDE.md` (or similar repo-provided configuration) — content the ctx subsystem must treat as **untrusted input**, exactly like the general trust boundary described in [[Untrusted Configuration]].

`run_model` drains stdin, stdout, and stderr concurrently so no child pipe can deadlock the supervisor. Stderr is retained only up to 8 KiB, sanitized, reduced to a 2 KiB diagnostic, and any line copied from the model prompt is redacted. A non-zero child exit therefore reports both its status and a useful bounded reason (for example, a parent sandbox denying the nested CLI's home-state access) instead of the former opaque `status 1`; timeout and process-tree kill behavior is unchanged.

The concrete risk, and why it isn't just theoretical: this distiller child is otherwise launched with the operator's normal permission settings. If a hostile or careless `CLAUDE.md` can steer the distiller model's output (prompt injection) and that child still has tool access, the injection stops being "the model says something misleading" and becomes "the model actually writes a file, runs a shell command, or spawns further work" — a real code-execution path, not just a bad summary.

`ClaudeAdapter::distiller_cmd` closes that path for the claude adapter with one restriction, added and adversarially verified in what the code and notes call the "I6 fix round":

```
claude -p --model <model> --output-format text --disallowedTools=Write,Edit,Bash,NotebookEdit
```

Concretely, per `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`:

- **`--disallowedTools`** must name `Write`, `Edit`, `Bash`, and `NotebookEdit` together. Probing found that `Bash` alone, if left off the deny list, lets the model recreate a Write tool via a shell redirect (`echo ... > file`) even with `Write`/`Edit` blocked — so all four have to be denied, not just the two obvious ones.
- The value must be a **single `=`-bound argv token** (`--disallowedTools=Write,Edit,Bash,NotebookEdit`), never passed as two separate `Command::arg()` calls. The two-token form was verified against the real CLI to make claude's variadic tools parser swallow the *next* argv entry as part of the tool list, corrupting whatever followed it.
- Other candidate fixes were probed and rejected: an empty `--allowedTools=""` allow-list does **not** deny everything by default (a file was still created in the probe); `--permission-mode plan` doesn't complete cleanly in non-interactive `-p` mode at all (no `ExitPlanMode`/`AskUserQuestion`) and took 90+ seconds.
- The chosen restriction was re-verified adversarially: a prompt explicitly instructing the model to fall back to Bash, or to route around the restriction via Task/subagent delegation, still failed to create a marker file, with the model itself reporting it had exhausted every method.

The comment on `distiller_cmd` and the dedicated test `the_distiller_denies_the_tools_verified_to_matter` both exist specifically to keep this from regressing: the exact flag spelling, the exact four-tool set, and the single-token argv shape are all load-bearing, not stylistic. Codex's own `distiller_cmd` pins `--sandbox read-only` instead (verified against `codex exec --help`, codex-cli 0.105.0) — its own analogue of this restriction, and what backs `zirv ctx optimize`'s report-only guarantee for a codex judgment child. Not an identical guarantee, though: `--sandbox` restricts what a codex-*executed shell command* may touch, not which of codex's own tools may run at all, and this child's own repo AGENTS.md is still embedded in its prompt exactly like claude's distiller embeds CLAUDE.md.

This is verified against the real installed CLI (not just documentation), as recorded in `docs/superpowers/notes/2026-08-01-system-prompt-injection-facts.md`: the notes log the exact probe commands, exit codes, and file-creation outcomes for each candidate fix, including the baseline (no restriction) actually succeeding at writing a file, which confirms the risk is real under a normal user's own default permission settings before demonstrating the fix closes it.
