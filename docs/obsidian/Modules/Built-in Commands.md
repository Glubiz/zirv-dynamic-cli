# Built-in Commands

## Quick Reference

- **Files:** `src/main.rs`, `src/input.rs`, `src/commands/mod.rs`, `src/commands/create.rs`, `src/commands/init.rs`, `src/commands/setup.rs`, `src/commands/report.rs`, `src/commands/help.rs`, `src/commands/version.rs`, `src/commands/workflow/`, `src/settings.rs`
- **Used by:** entry point — nothing calls into these except the OS invoking `zirv`
- **Depends on:** [[Script Runner]] (`execute`), [[Utilities]] (`file_to_script`, `home_dir`, `Shortcuts`, `is_reserved_command`, `candidate_names_in_dir`, `suggest_matches`), [[Workflows]] (`workflow::dispatch`), [[Ctx Subsystem]] (`ctx::dispatch`, `ctx::memory_cli::dispatch`, `ctx::sessions::nesting_refusal`, intercepted before clap runs at all; `settings::set_operator_agent_enabled`, the first-run wizard's `.settings.toml` writer), GitHub's issue API (`report::dispatch`)
- **Tests:** inline `#[cfg(test)] mod tests` in each file (`main::tests`, `input::tests`, `create::tests`, `init::tests`, `help::tests`; `version.rs` has no dedicated module dependency beyond its own version string)
- **If changed:** [[Script Resolution]], [[Shortcuts]], [[Getting Started]], [[Ctx Supervisors]] (the dashboard `zirv chat` opens on a capable terminal)
- **Gotchas:** `zirv ctx …`, `zirv memory …`, `zirv setup …`, `zirv report …`, `zirv chat`/`zirv agent`, `zirv skill`/`workflow`/`test`/`verify`/`artifact`/`frontend`, a bare `zirv`, and top-level `zirv --help`/`-h` are all matched against raw `argv` *before* clap parses anything — a `.zirv/commands/ctx.yaml` (or `memory.yaml`/`setup.yaml`/`report.yaml`/`chat.yaml`/`agent.yaml`/`workflow.yaml`) script is permanently shadowed, and clap's own auto-generated help for the `Input` struct never fires. A bare `zirv` used to be a clap usage error (exit 2, missing the required `command` argument) — it is now an alias, a deliberate behavior change (see below).

## Purpose

`main.rs` is the CLI's dispatch table: a fixed set of built-ins (`help`, `version`, `init`, `create`, `setup`, `report`, `ctx`, `memory`, `chat`, `agent`, `skill`, `workflow`, `test`, `verify`, `artifact`, `frontend`) checked before anything falls through to "treat this word as a script name in `.zirv/commands/`" (issue #212, zirv 3.0 — see [[Script Resolution]]).

## How It Works

### Dispatch order (`main.rs`)

1. **Raw-argv `ctx` check** — `argv[1] == "ctx"` routes straight to `commands::ctx::dispatch`, bypassing `Input`/clap entirely. This is why `.zirv/commands/ctx.yaml` can never be reached as a script (see `help.rs`'s "shadowed" marker below) and why a malformed `.zirv/ctx.toml` never breaks script lookup — `main.rs` never gets that far for `ctx`.
2. **Raw-argv workflow command check** (`is_top_level_workflow_command`) — `skill`, `workflow`, `test`, `verify`, `artifact`, and `frontend` route to `commands::workflow::dispatch`, whose clap tree is independent of both `CtxCli` and the legacy script surface. These names are reserved, and `.zirv/verify.toml` (config at the `.zirv` root) is excluded from script resolution and listing.
3. **Raw-argv `memory` check** (`is_top_level_memory`) — `argv[1] == "memory"` routes straight to `commands::ctx::memory_cli::dispatch`, the same bypass-clap-entirely treatment as `ctx` above. Unlike the `chat`/`agent` aliases below, `memory` is not a 1:1 rewrite into a single `ctx` verb — it carries its own verb tree (`status`/`list`/`recall`/`remember`/`forget`/`verify`) and its own `clap::Parser` (`MemoryCli`), dispatched independently of `CtxCli`. See [[Ctx Subsystem]] for the verb-level detail.
4. **Raw-argv `setup` check** (`is_top_level_setup`) — `argv[1] == "setup"` routes to the guided AI onboarding/reset clap tree before a same-named repository script can be resolved.
5. **Raw-argv `report` check** (`is_top_level_report`) — `argv[1] == "report"` routes to `commands::report::dispatch` and its independent `bug|feature` clap tree before a same-named script can resolve.
6. **Raw-argv `chat`/`agent` alias check** (`top_level_ctx_alias`) — `argv[1] == "chat"` or `"agent"` rewrites argv (`rewrite_ctx_alias_args`) into `["ctx", <verb>, ...rest]` and routes through the same `ctx::dispatch` the raw `ctx` check above uses, so the alias gets the full ctx verb tree for free: subcommand parsing, `--help` exiting 0, and the same parse-failure classification `zirv ctx chat --help` would get. A literal `zirv chat` with no further arguments (`verb == "chat" && argv.len() == 2`) additionally calls `maybe_run_first_run_wizard` first — see "The guided first-run wizard" below; `zirv agent`, `zirv chat --help`, `zirv chat --allow-nested`, or any other flag skip straight to `ctx::dispatch` as before, never arming the wizard.
7. **Bare invocation** (`argv.len() == 1`, i.e. no arguments at all) — `stdin_is_tty`/`stdout_is_tty` are computed first and passed to `maybe_run_first_run_wizard` (see below) before anything else runs; `zirv_dir_present(cwd)` (**local `./.zirv` only, never `~/.zirv`**) is then (re-)checked *after* the wizard returns, so a local `.zirv` the wizard just scaffolded (its optional project-layer step) is picked up by this same invocation. `bare_invocation_target(zirv_dir_exists, stdin_is_tty, stdout_is_tty)` is a pure function of those three facts deciding `BareTarget::Chat` (routes to `ctx::dispatch(["ctx", "chat"])`) or `BareTarget::Help` (prints `show_help`, **exit 0**). This is the deliberate behavior change: before this, `Input::command` being a required positional meant a bare `zirv` was a clap usage error exiting 2. As of the dashboard sweep, the `chat` this routes to is no longer always a plain `wrap` passthrough — see the note below.
8. **Raw-argv top-level help check** (`is_top_level_help`) — `argv[1]` is exactly `--help` or `-h` (not a script's own `--help` parameter, which lands later). Bypasses clap so `zirv help`'s rich script listing runs instead of clap's generated help for `Input`. Argv length 2 here means this never overlaps with the bare-invocation check above (length 1) or the `ctx`/`memory`/workflow/alias checks (which match on `argv[1]`'s value, not `--help`).
9. **`Input::parse()`** — clap parses the rest.
10. **`misplaced_create_flag` guard** — `--name`/`--shortcut`/`--global` live on the shared `Input` struct so clap accepts them for *every* command; used outside `create`/`c` they are refused with a named error instead of being silently swallowed as (and eating) the next positional argument.
11. **Built-in match** on `input.command`: `help|h`, `version|v`, `init|i`, `create|c` each dispatch to their module and return.
12. **Fallback**: resolve `input.command` as a script via `Input::get_file_path`, parse it with `utils::file_to_script`, and run it through `script_runner::execute`.

An explicit `zirv chat`/`zirv agent` (step 4) is not subject to the bare-invocation's stdin-is-a-terminal rule (step 5) at all — they are different checks on different argv shapes, so a piped `zirv chat` still launches chat rather than falling back to help. `zirv memory` (step 3) and the workflow commands (step 2) are unaffected by the bare-invocation rule for the same reason.

### CLI shape (`input.rs`)

`Input` (derives `clap::Parser`): `command: String` (positional), `params: Vec<String>` (`num_args 0..`), `dry_run: bool`, and create-only `name`/`shortcut`/`global: Option<T>` — all `None` by default, which is also how `create` distinguishes "flag not given, prompt interactively" from "flag given". `misplaced_create_flag` returns the first of those three that's `Some` when the command isn't `create`.

`Input::get_file_path` resolution order: (1) the literal string as an existing path, (2) `./.zirv/commands/<command>.<ext>` for each of `SUPPORTED_EXTENSIONS`, (3) `./.zirv/.shortcuts.yaml` (root, not `commands/`) mapping `<command>` to a target file resolved inside `./.zirv/commands/`, (4) the same two steps under `~/.zirv` (i.e. `~/.zirv/commands/<command>.<ext>` then `~/.zirv/.shortcuts.yaml`). A `.shortcuts.yaml` that fails to read or parse is a warning, not a fatal error — lookup falls through to whatever else might match rather than taking down the whole command. A miss produces `not_found_error`, which offers up to three "did you mean" suggestions (via `utils::suggest_matches`) drawn from both local and global script/shortcut names, plus a pointer to `zirv help`. **Hard cutover (issue #212, zirv 3.0):** there is no fallback lookup at the `.zirv` root any more; if the root still has script-like files left over from the pre-3.0 layout, `not_found_error` names up to 10 of them (via `utils::script_like_files_at_root`) and says they need to move into `commands/`.

### `create` (`commands/create.rs`)

`CreateOptions { name, shortcut, global: Option<T> }` — any field left `None` prompts interactively via `dialoguer`; all three `Some` makes the whole command non-interactive (used by `--name`/`--shortcut`/`--global` on the CLI, and by tests). `validate_name` rejects path separators and a bare `".."` — the name becomes a path segment under `.zirv/commands/`, so `--name ../../escaped` must not be allowed to write outside it. A name or shortcut colliding with a reserved built-in command name (`utils::is_reserved_command`) warns and asks for confirmation interactively, or hard-errors non-interactively (nothing to confirm with). An existing `.shortcuts.yaml` that fails to parse is never silently rewritten — that would drop every shortcut it holds — so it's an error non-interactively and a confirm-to-replace prompt interactively. Writes `<name>.yaml` from a commented `DEFAULT_TEMPLATE` into `.zirv/commands/` (creating that directory if needed) and, if a shortcut was given, upserts it into `.zirv/.shortcuts.yaml` at the root — the shortcuts file itself never moves into `commands/`.

### `init` (`commands/init.rs`)

`init_zirv_with(confirm_fn)` always ensures `~/.zirv`, its `commands/` subdirectory, and its default `.shortcuts.yaml` exist, then asks (via the injected `confirm_fn`, real code uses `dialoguer::Confirm`) whether to also create `./.zirv` (with its own `commands/` subdirectory). `init_zirv` is the production wrapper. The two halves are now their own functions — `scaffold_global_zirv()` (home) and `scaffold_local_zirv(dir)` (a given directory) — `init_zirv_with` just calls both in sequence; the guided first-run wizard (below) reuses both directly instead of duplicating the creation logic.

### The guided first-run wizard (`commands::setup::run_first_run`, v2.25.0)

Bare `zirv` and a literal `zirv chat` (no further arguments) auto-launch a guided setup wizard the first time zirv has never been configured, gated by `main.rs`'s `maybe_run_first_run_wizard`: both stdin and stdout must be real terminals, `commands::setup::first_run_needed(~/.zirv)` must be true (neither `ctx.toml` nor `.settings.toml` exists there yet — a `~/.zirv` holding only `.shortcuts.yaml` still counts as first-run), and — for the `chat` entry point specifically — `ctx::sessions::nesting_refusal("chat", env, allow_nested: false)` must not already refuse the session (a wizard run from inside an existing agent session is silently skipped, the same as `chat` itself would refuse). `zirv chat --help`/`--allow-nested`/any other flag never reaches this check at all (see the dispatch-order note above); an operator inside a nested session or piping either invocation gets ordinary behavior, unchanged.

The wizard itself (`run_first_run`) is collect-then-apply: `collect_first_run_answers()` runs every `dialoguer` prompt and performs zero writes, returning a plain `FirstRunAnswers`; `apply_first_run_answers(&answers, home)` then performs every write, called only once collection has fully succeeded. An abort partway through (Ctrl-C, any `dialoguer` error) therefore leaves `~/.zirv` exactly as it was and simply re-offers the wizard next time; `run_first_run`'s own `Err` is caught by `maybe_run_first_run_wizard` and reported on stderr (`zirv: first-run setup did not finish (...); continuing without it.`) rather than swallowed silently, and the command the operator actually typed continues exactly as if the wizard had never run. Steps, all HOME-layer writes only (never the repo — most of the keys involved are `REPO_FORBIDDEN`, see [[Ctx Subsystem]]):

1. Scaffold `~/.zirv` (`init::scaffold_global_zirv`).
2. Per-harness enable/disable (probed via `executable_exists`, not `AgentAdapter::ready()` — `ready()` doesn't detect "not installed" on this platform) over `ctx::adapters::ADAPTERS`, written via the new `settings::set_operator_agent_enabled` (merge-safe: an existing `.settings.toml`'s other agents/keys survive); then a default-agent pick from whichever harnesses were enabled, written to `ctx.toml`'s top-level `agent` key.
3. Chat model: "harness default" (a no-op) or an entered name, written to `ctx.toml`'s `[chat].model`.
4. Memory: `memory.enabled` (default yes) and `memory.harvest` (default no) — both always written, which is what guarantees `ctx.toml` always exists once the wizard completes and so never re-triggers.
5. Optional local `./.zirv` scaffold (`init::scaffold_local_zirv`), offered only when the cwd has no `.zirv` yet and looks like a project directory (`.git`, or a manifest file — `Cargo.toml`/`package.json`/`pyproject.toml`/`go.mod`/`pom.xml`/`build.gradle[.kts]`/`Makefile`).
6. Optional hook integration: if a local `.zirv` exists at this point (step 5 just created one, or one already existed), runs the existing `setup::run_apply` against it exactly as `zirv setup`'s own "Apply full setup" menu item does; otherwise calls the home-scoped `install_claude_integration`/`install_codex_integration` directly so declining step 5 can never leave a `.zirv` created as a side effect of installing hooks.

Also reachable on demand — not just on a first run — as a new "Run first-run wizard" entry in `run_guided`'s own `zirv setup` menu (`zirv setup` → `Run first-run wizard`); re-running prints "Re-running zirv's guided setup." instead of the first-run greeting.

**Known residuals** (deferred past the review cap, not fixed): step 6's non-`.zirv` fallback branch installs *both* `install_claude_integration` and `install_codex_integration` unconditionally, regardless of which harnesses step 2 actually enabled; `zirv chat --allow-nested` never arms the wizard at all (the `argv.len() == 2` gate excludes it, a deliberate side effect of also excluding `--help`); and a nesting-guard skip (above) produces no output at all rather than a hint that `zirv setup` exists. See [[Known Issues]].

### `setup` (`commands/setup.rs`)

`zirv setup` guides the complete AI onboarding path. `apply` initializes `.zirv`, migrates native root instructions into `.zirv/context/` without deleting them, bootstraps bounded shared memory, and deep-merges Zirv hooks into Claude `settings.json` and Codex `hooks.json` without replacing unrelated values. Claude's command-safety `PreToolUse` entry uses the same `Bash|PowerShell` matcher as supervised launch settings, so a persistent hook started outside Zirv does not lose native-Windows coverage. Codex requires reviewing new hooks with `/hooks`. `status` reports both harnesses and every integration surface, including JSON output. `reset claude|codex|all` targets exact AI customization files only, requires `--yes` outside dry-run mode, refuses symlinks, writes a manifest-backed copy before deletion, and preserves auth/history/session/cache data unless `--include-auth` is explicit. Global-scope reset now covers Claude's `~/.claude/plugins` too, matching project scope's `.claude/plugins` (previously only project scope did); `~/.claude.json` (MCP server registrations, OAuth/account linkage, project trust state) is deliberately **never** touched by `reset` or `restore` — clearing it would sign the operator out — and both `reset --dry-run` and `restore --list` name it explicitly as a surface they do not cover.

`zirv setup profile` is the non-interactive, operator-owned routing surface added in issues #121/#125/#129. It merge-writes only requested keys in `~/.zirv/ctx.toml`: `--agent`, `--chat-model`, `--worker-claude`/`--worker-codex`, `--review-claude`/`--review-codex`, `--sandbox-enabled true|false`, and `--context-max-common-bytes`; each optional routing key has a matching `--clear-*` flag. `--system-prompt-file <path>` installs the operator's global orchestrator prompt at `~/.zirv/system-prompt.md`, while `--clear-system-prompt` removes it reversibly. `--wrap-claude-statusline` explicitly wraps a custom statusline even after the guided once-only offer was declined. `--dry-run` prints exact sources/targets plus old → new values or byte sizes and writes nothing; wet changes use the shared manifest backup system, preserve unrelated TOML/JSON values, refuse symlink targets/sources, and create no backup when already current. `setup status --json` schema version 3 adds the effective `profile` object (including `context_max_common_bytes` and `system_prompt_present`), while text status prints the same routing summary.

An interactive `apply` run (real terminal on both stdin and stdout, not `--dry-run`) now also offers two guided, once-only prompts, each gated on its own `[setup]` config flag so a decline is remembered rather than re-asked (issues #87, #93):
- **Memory harvest** (`maybe_offer_memory_harvest`): asks whether to turn on `memory.harvest` (default stays `false` either way — only an explicit accept flips it). Writes `memory.harvest` (on accept) and `setup.memory_harvest_offered` (always) to the operator's global `~/.zirv/ctx.toml`, never the repo layer (`set_home_ctx_toml_bool`).
- **StatusLine wrap** (`maybe_offer_statusline_wrap`): when Claude's `statusLine.command` is an existing custom command (not zirv's own tee, not already wrapping one), shows the before/after and asks to wrap it as `zirv ctx usage tee -- <existing command>` (`classify_statusline_command`/`wrap_statusline_command`). Wrapping is plain string prefixing, not re-quoting — `usage.rs`'s `run_chained` never re-invokes a shell on the trailing argv, so the platform shell that already splits Claude's configured command line is the only one that ever does, unchanged by the prefix. Idempotent (a `TeeWrappingCustom` command, including a hand-edited one, is left alone) and reversible: `wrap_claude_statusline_command` backs up `settings.json` before rewriting it, so `zirv setup restore` unwraps back to the exact original bytes. `zirv setup status`'s `claude_statusline` field (JSON) / statusline= line (text) reports one of `absent`/`tee-installed`/`tee-wrapping-custom`/`custom-not-wrapped` instead of a plain bool.

**Backups are one manifest-tracked system, shared by `apply`, `reset`, and `restore` (`write_backup_run`).** Every run — a `reset` removal, an `apply` merge into a harness settings/hooks file, or a `restore`'s own pre-overwrite safety copy — lands under `.zirv/backups/ai-reset/<epoch>-<provider>-<scope>[-NNN]/` (project-scoped runs under the repo, global-scoped runs under `~/.zirv`), each its own directory with `files/<relative-path>` copies plus a `manifest.json` (`schema_version`, `kind`: `reset`/`apply`/`restore`, `provider`, `scope`, `base`, `created`, and per-target `source`/`relative_path`/`existed_before`). `existed_before: false` records that the run *created* the file (an `apply` merge into a settings file with no prior `settings.json`) — restoring such a target means removing it, not copying anything back. `apply` no longer writes the old ad-hoc `*.zirv-backup-<epoch>` sibling file; nothing else in the codebase read it, so the tracked form fully replaces it. **Retention (issue #95):** every `write_backup_run` call ends with `prune_backup_runs(backup_root, resolve_backup_retention_runs(base))` — a count cap on `[setup] backup_retention_runs` (clamped like `workflow.telemetry_max_events`: `0` keeps the built-in default of 20, clamped above 500), applied only on write, never from `restore --list`. The single run with the oldest `manifest.created` is always pinned and excluded from the cap entirely, so `keep + 1` runs typically survive — reuses `discover_runs`'s existing enumeration rather than a second pruning implementation.

`zirv setup restore` reverses either kind of backup:
- `restore --list [--provider P] [--scope S] [--json]` — enumerates runs across both the repo-scoped and home-scoped `ai-reset` roots: id, human-readable timestamp, provider/scope/kind, file count, and a `status` of `absent`/`identical`/`differs`/`mixed`, computed by comparing each target's current on-disk state against its backup copy (`target_state`/`aggregate_state`) — `differs` means restoring would overwrite content that has since changed.
- `restore <id> [--dry-run] [--yes] [--include-auth]` — restores one run. Mirrors `reset`'s safety contract: refuses without `--dry-run`/`--yes`, validates every backup source and current destination for symlinks *before* writing anything (fail-closed, same order as `reset`), never restores a target under an auth filename (`.credentials.json`, `auth.json`) unless `--include-auth` is passed at restore time (independent of whether it was passed at backup time), and refuses a manifest whose `schema_version` isn't `SUPPORTED_MANIFEST_SCHEMA_VERSION`, naming the version. **Before writing anything it takes its own backup of the current state** (`kind: "restore"`, written into the same root the restored run came from) — so a restore is itself undoable via another `restore`. A restore that only partially completes (some target writes fail) reports every path it wrote and every path it didn't, rather than failing silently half-applied.
- `restore --latest [--provider P] [--scope S]` — resolves the most recent matching run instead of naming an id.

### AI-native workflow lifecycle

The top-level `workflow` tree now includes committed work-product inspection, provider-neutral agent inspection, PR-aware review, and the invoked maintain scanner. Key lifecycle verbs are `zirv workflow artifacts <id>`, `zirv workflow agents list|show|dispatch`, `zirv workflow review package|run|ingest-pr-comments`, and `zirv workflow maintain scan`. `workflow agents dispatch <id> --adapter <name> --prompt <task> [--model <provider-id>]` is the explicit provider-neutral seat execution surface; the manifest remains methodology, while effective canonical policy and the adapter enforce authority. The maintain verb is intentionally nested under `workflow`: it re-enters the same durable state machine at the Intent gate rather than creating a separate maintenance engine.

**`--frontend-root <path>` on `workflow start`/`workflow advance` (issue #214, v2.40.0).** A Frontend-profile workflow's own auto-run detector/render evidence gate normally scans the workflow's own `--repo` — wrong when the workflow is tracked in one repository but its frontend actually lives in a sibling checkout. `--frontend-root` (absolutized against the current directory, canonicalized, and hard-refused if it isn't an existing directory) sets `WorkflowState.frontend_target_root`, which the detector/render gate then scans instead of `state.repo`; `advance` persists the flag into state **before** the gate runs, so a fail-closed advance still records it rather than forcing the operator to pass it again on retry. `zirv workflow status` prints `frontend target root: <path>` (human-readable text; JSON already carried the field) whenever it is set. A gate failure now names the scanned root and suggests `zirv frontend check --all --repo <root>` / `zirv frontend render --repo <root>`, or `--frontend-root` if the frontend lives elsewhere. See [[Workflows]] for the Frontend-profile gate itself.

### `report` (`commands/report.rs`)

`zirv report bug|feature <title> [--body <text>|--body-file <path>]` creates an issue in the fixed `Glubiz/zirv-dynamic-cli` repository, applies `bug` or `enhancement`, and prints only the resulting issue URL. It appends Zirv version, OS, architecture, and—inside a supervised session—the harness and seat model; session identifiers are never included. Credentials resolve in order from `gh auth token --hostname github.com`, `GH_TOKEN`, `GITHUB_TOKEN`, then `[github].token` in the operator's `~/.zirv/.settings.toml`. Repository settings are never consulted for credentials. HTTP and credential lookup are injected in tests, so the suite never files a real issue or reads the operator's real token.

### `help` (`commands/help.rs`)

`show_help` writes: a builtins/usage block (hardcoded, not generated from clap — intercepting `--help` took away clap's auto-generated help, so this exists specifically to keep every flag discoverable), then local `.zirv/commands/` scripts (issue #212, zirv 3.0) and `.zirv/.shortcuts.yaml` shortcuts (still read from the root), then global `~/.zirv/commands/` scripts and `~/.zirv/.shortcuts.yaml` shortcuts. Script listing and shortcut listing are independent checks — a root with only a `.shortcuts.yaml` and no `commands/` directory yet still shows its shortcuts, and vice versa. The builtins block names `report`, `chat`, and `agent` alongside the older built-ins and states the bare-invocation rule in one line, so all are discoverable from `zirv help` and not just from this page — the wording was corrected (v2.25.0) to say a *local* `.zirv` plus both stdin **and** stdout being real terminals (it previously and incorrectly also claimed a global `~/.zirv` triggers chat), and now adds a line naming the first-run wizard. Script listing skips every name in `utils::RESERVED_ZIRV_FILES` (`.shortcuts.yaml`, `ctx.toml`, `.settings.toml`, `verify.toml`), compared case-insensitively (`utils::is_reserved_zirv_file`, since NTFS/APFS resolve file names case-insensitively too) — parsing one of these as a `Script` used to fail the whole listing (in practice these now live at the `.zirv` root rather than in `commands/`, but the guard still applies wherever it's checked). Any script file or shortcut whose name collides with a reserved built-in (`utils::RESERVED_COMMANDS`: `help`/`h`, `version`/`v`, `init`/`i`, `create`/`c`, `setup`, `report`, `ctx`, `memory`, `chat`, `agent`, `skill`, `workflow`, `test`, `verify`, `artifact`, `frontend`) is annotated `(shadowed by a built-in command, unreachable)`, since `main.rs`'s built-in match runs before `.zirv/` is ever consulted. Since issue #202 (v2.38.0), `show_help`'s output is styled through `style.rs` (see [[Technology Stack]]): bold section headers, command/script names painted `Tone::Accent` (cyan), descriptions `Tone::Muted` (dim), and every name/description table column-aligned by display width — gated on `console::colors_enabled()`, so piped `zirv help` output stays plain text with no ANSI codes.

### `version` (`commands/version.rs`)

One line: `Version: {CARGO_PKG_VERSION}`.

### `zirv frontend` (`commands/workflow/frontend*.rs`)

The reserved `frontend` family is an autonomous workflow-quality surface, not an initializer. `profile` lazily infers or refreshes bounded product/design evidence and adds the built-in quality contract; `capabilities --agent <name>` reports provider-neutral skill, surface-mode, detector, rubric, and capability provenance; `check` runs the 44-rule offline detector; `render` discovers a package script, starts/cleans the loopback server, and captures narrow/intermediate/wide PNGs; `review` stores the active AI agent's bounded verdict plus all 13 required UI/UX scores; and `benchmark` mutation-checks the detector corpus and complete rule inventory. A frontend workflow selects and runs these requirements automatically through its phase skills and evidence gates. See [[Workflows]] for trust boundaries, caps, freshness, and known rendering limits.

### `zirv memory` (`commands/ctx/memory_cli.rs`)

`init` implements the issue #36 bootstrap: deterministic validation/toolchain facts plus high-signal Markdown sections, optional `--source` file/directory/Obsidian import, strict entry/byte caps, dry-run, and refusal on a non-empty shared bank unless `--merge` adds only missing keys. Issue #103: each extracted section's key is `<page-slug>-<up to four slugged heading words>` (not the whole heading), disambiguated with a `-2`/`-3` suffix on collision, reusing `ctx::memory`'s own slug/key-validation helpers; its body is capped at the *configured* `memory.max_entry_bytes` (not a hardcoded byte count), cut on a sentence boundary rather than mid-word, with fenced code blocks stripped first and a section skipped outright if under 80 bytes once stripped.

A management surface for the repo-scoped memory bank (see [[Ctx Subsystem]]'s "Sessions and Memory" section for the store itself) that works without starting an AI session at all (issue #33): `status`, `list`, `recall <query>`, `remember <key> <text>`, `forget <key>`, `verify <key>`. Every verb defaults to the private (machine-local) scope; `--shared` switches to the repository-owned bank under `<repo>/.zirv/memory/`. `list`/`recall` are reads and respect each scope's own gate (`memory.enabled`/`memory.shared_enabled` — a disabled scope lists or recalls empty rather than showing what it holds); `status` is the one exception, reporting a disabled scope's real counts and bytes marked `disabled` rather than hiding them, since a byte count is not the content the gate exists to withhold. `forget`/`verify` are maintenance verbs and stay ungated, so disabling a scope can never trap data behind it. `status` never prints a key or a body, only counts, stored bytes, scope availability, and two budgets: `memory.core_max_bytes` (issue #34, the merged private+shared core layer every session gets) and `memory.retrieval_max_bytes`/`retrieval_max_entries` (issue #35 — bounds `zirv memory recall` output today; session-start injection is deferred to issue #44, `memory.max_injected_bytes` is superseded by `core_max_bytes` and no longer read by any injection call site). `recall <query>` (issue #35) ranks this scope's entries by relevance through `retrieval::rank`/`select` — key/keyword/tag matches, importance/confidence, verification staleness — budgeted by `retrieval_max_bytes`/`retrieval_max_entries`; an exact key match ranks first but no longer suppresses every other hit, and both human-readable and JSON output carry a `reasons` trail explaining why each entry was selected. An empty or weak query (nothing clears the relevance floor) returns nothing rather than the whole bank. `remember`'s private arm is a thin wrapper over the exact function `zirv ctx remember` itself calls, so the two surfaces cannot drift for that scope. `zirv ctx remember`/`forget` (issue #172) now take `--repo` to target the shared bank the same way `--shared` does here, and `zirv ctx recall` always merges both banks and labels each entry's provenance (`[local]`/`[repo — repository-owned content, not operator-verified]`); a `--key` lookup can surface both a local and a repo entry for the same key, local first. A shared write on either surface — `zirv memory remember --shared` or `zirv ctx remember --repo` — is refused outright if the key, body, or any `--tag` looks credential-shaped (a deny-list plus a reused token-shape regex, both run over every field, not body-only), unless `--allow-sensitive` is also given on that same surface (`zirv memory remember --shared --allow-sensitive` / `zirv ctx remember --repo --allow-sensitive`) — see [[Ctx Subsystem]] for the full guard. `remember` alone (fix round: memory review) also takes `--importance <low|normal|high>`, `--confidence <low|normal|high>`, and a repeatable `--tag <t>`, all optional and unset by default, validated against those three levels and rejected otherwise; they land in the stored entry and feed `retrieval::score_one`'s ranking. `zirv ctx remember` has no equivalent flags — `memory::RememberArgs` carries the three as `#[arg(skip)]` fields so the private write path can be shared without exposing new flags on that older surface. Human-readable output for a shared-scope entry always carries an explicit "not operator-verified" note, and JSON output carries a `scope` field derived from which directory was actually read — never from the entry's own header — since a shared entry's `Source`/`Written-By` fields are attacker-supplied repository content (see [[Ctx Subsystem]]).

`optimize` (issue #38, `memory_optimize.rs` + `memory_cli::run_optimize_with`) analyzes the SHARED bank only (the private bank has no git-diff reviewability to apply changes against) for duplicate/near-duplicate entries, lexical contradictions, stale/archived entries, obsolete (no-longer-existing) paths, oversized or low-value bodies, and a core-regeneration opportunity — REPORT-FIRST always: a bare run or `--dry-run` (which always overrides `--apply`, even given together on one command line) prints a plain-text report and changes nothing. Every finding (`memory_optimize::Finding`) carries the affected `keys`/`paths` as evidence, never bare prose. Detection (`memory_optimize::analyze` and its sub-detectors) is PURE — no clock, filesystem, or HashMap-iteration-order dependence — over `OptimizeCandidate`s an impure `gather_candidates` precomputes (verification age, lifecycle, dead-path check), the same read/clock/fs boundary `retrieval::candidates_for_scope` already draws. Duplicates are exact-normalized-body matches; near-duplicates and contradictions are lexical/structural (Jaccard word-overlap plus, for contradictions, an opposite-polarity word pair like "always"/"never") — no model involved in detection at all. `--apply` additionally runs ONE model-driven pass, consolidation: for each already-detected duplicate/near-duplicate group with no deliberate `Source: explicit` member, a model proposes a merged body for the group's (deterministically chosen) survivor entry, validated exactly like `init`'s proposals (`parse_harvest`, truncated to `memory.max_entry_bytes`, rejected if the answered key disagrees with the survivor's) before being upserted — every OTHER member of the group is left untouched on disk (consolidation never deletes or forgets anything), and a group with any explicit member is skipped before a model is ever touched. `--no-model` skips consolidation even under `--apply`, reporting findings only. `zirv memory optimize` never invokes git.

Lifecycle (issue #38, `retrieval::Lifecycle`/`classify_lifecycle`) is a derived-only concept, never stored on disk: `Active`/`Stale`/`Archived` is recomputed fresh from an entry's own `verified`/`importance`/`confidence`/`source` on every read, so re-verifying an entry immediately restores `Active` with no migration. Age alone never demotes anything — `importance: high` keeps an entry `Active` unconditionally, and only a LOW-value entry (`importance: low` or `confidence: low`, and not `Source: explicit`) past `retrieval::ARCHIVE_AFTER_DAYS` (365 days unverified) becomes `Archived`; anything else past `retrieval::STALE_AFTER_DAYS` (180 days unverified) is merely `Stale`. `retrieval::score_one` wires this into ranking directly (not a parallel path): `Archived` is excluded from a normal `recall`/injection outright unless `RetrievalContext::include_archived` is set; `Stale` only takes a further fixed down-rank penalty on top of the pre-existing gradual staleness penalty, so it stays selectable.

### `zirv context sync`

`zirv context sync` manages compatibility between canonical `.zirv/context/{common,claude,codex}.md` instructions and native `CLAUDE.md`/`AGENTS.md` files. Report mode is read-only; `--import` and `--generate` are explicit write modes, refuse unmanaged files unless the requested force/import behavior is explicit, and remain idempotent after a successful sync. `zirv context status` reports compiler provenance, raw/delivered bytes, estimated tokens, truncation, configured budgets, drift findings, and honest per-harness policy alignment without starting a session.

### `zirv chat`/bare `zirv` default to the dashboard on a capable terminal

`zirv chat` (and bare `zirv`, once step 4 above routes to it) no longer always lands on a plain `wrap` passthrough session: on a real terminal at least 80×20 with VT processing available and `cfg.dash.enabled` (the default), it opens the dashboard session multiplexer instead — see [[Ctx Supervisors]]'s "The dashboard (`dash`)" section for the pane model, prefix keys, and quit/restore roster. `--simple` (or a terminal too small, or `[dash] enabled = false`) falls back to today's plain `wrap` chrome unchanged; a too-small terminal that would otherwise qualify prints a one-line notice naming the floor before falling back. `[chat] model`/`ZIRV_CTX_CHAT_MODEL`, when set, selects the model for the orchestrator session either way (dashboard or plain `wrap`) and is shown in the launch banner/dashboard header — see [[Ctx Adapters]] and [[Untrusted Configuration]] for why this one model key is deliberately not repo-forbidden, unlike every other model key in `ctx.toml`.
