## Purpose

> "The endless permission prompts are THE pain point zirv must fix for every wrapped harness. Only truly dangerous commands may prompt; an arbitrary read command (or everyday dev command) must NEVER prompt — including commands zirv has never seen."

That operator acceptance criterion outranks classifier coverage. The built-in ask set is therefore a short, closed list; widening it is a product decision, not a hardening reflex. `the_product_requirement_no_everyday_or_novel_command_ever_prompts` is the executable gate: ordinary reads and mutations (`cargo build`, `npm install`, `git commit`, `mkdir`, in-repo writes, plain `curl`/`wget`) plus arbitrary unknown commands must all avoid `Ask` on an interactive launch.

Every harness zirv wraps has its own, incompatible way of deciding whether a command is safe to run unattended — claude's permission globs plus hooks, codex's sandbox/approval flags plus `.rules` execpolicy files. `safety.rs` gives zirv one harness-neutral classification. Claude receives its per-command verdicts through the wired `PreToolUse` hook; codex has no verified per-command projection, so its adapter reports that gap honestly and relies on its sandbox/approval boundary instead.

This builds on, rather than replaces, the foundation PR #96 shipped: `adapters::SHIPPED_POSTURE_ALLOW`/`_DENY` (the live-verified claude permission-rule list), `sandbox.extra_allow`/`extra_deny`, and `policy_launch_args`/`flags_pin_policy` wired into every launch seam (see [[Ctx Adapters]]). `[safety]` is the harness-neutral declaration and pure evaluator that was still open; the shipped posture constants are now the *source* the built-in default rule set is derived from, not a separate hand-maintained list.

## The model

```rust
pub enum Verdict { Allow, Ask, Deny }

pub struct Rule { pattern: String, origin: Origin }   // Origin: BuiltIn | Operator | Repo | Env

pub struct SafetyPolicy {
    deny: Vec<Rule>,
    ask: Vec<Rule>,
    allow: Vec<Rule>,
    escape_allow: Vec<Rule>,       // issue #147: cleared for a --dangerously-disable-sandbox retry only
    default: Verdict,              // headless unmatched command
    interactive_default: Verdict,  // interactive unmatched command
    sql: SqlMode,
}
```

`evaluate(policy, command, mode) -> Outcome { verdict, matched: Option<Rule> }` checks `deny`, then `ask`, then `allow`, first pattern match within a category wins; a command matching nothing gets `policy.default_verdict(mode)` with no matched rule. A matched rule is never softened by launch mode.

### Three verdicts, two defaults

The verdict vocabulary is shared, but an unmatched command deliberately has two answers:

| Launch | Config key | Shipped default | Consequence |
|---|---|---|---|
| Headless | `safety.default` | `ask` | Nobody can answer, so claude's `dontAsk`/codex's `never` posture fails closed. |
| Interactive | `safety.interactive_default` | `allow` | The operator is present, but an unknown command is not dangerous merely because zirv has never catalogued it; it runs silently. |

This asymmetry is the design, not a compatibility exception. Sharing the headless `ask` default would recreate endless prompting; sharing interactive `allow` with headless work would remove the fail-closed automation boundary. Deny always beats ask and allow because category order is fixed, not because of list ordering.

`glob_match(pattern, text)` supports only `*` (any run of characters, including none), case-sensitive, matched against one already-normalized command string (see below). It is the standard iterative two-pointer `fnmatch`-style algorithm with a saved star position, not recursive backtracking: a command string can originate from repository-influenced text (a prompt-injected shell command an agent was talked into proposing), so the matcher must not be a stack-depth or exponential-blowup DoS surface. Worst case is `O(pattern * command)` with no recursion.

### Structural executable-node analysis, and its explicit non-goals

`evaluate` does not treat `command` as one opaque string. Inspired by Dippy's strongest transferable property—visit every executable node and fold the most restrictive result—`normalize_segments(command)` derives a bounded candidate set and `evaluate_candidates` applies ordinary policy matching plus every semantic classifier to every candidate before taking `deny > ask > allow`:

1. The raw command, unmodified — always checked first, so a pattern written against the *whole* string (there are none in the shipped `deny` set today, but a repo/operator `[safety]` entry could still be one) keeps matching exactly as before this fix.
2. One entry per quote-aware shell-separator segment (`split_segments`: `;`, lone `&`, `&&`, `||`, `|`, newline), whitespace-collapsed (`collapse_whitespace`) and leading-directory-stripped (`strip_program_dir`, so `/usr/bin/rm -rf /` and `rm -rf /` compare identically). A separator inside quoted data is not treated as executable syntax; `2>&1` and `&>` remain redirections rather than fake executable nodes. The lone-ampersand case closes both native `cmd.exe` chaining and PowerShell's invocation-operator spelling.
3. Recursively unwrapped inline shells (`unwrap_shell_wrapper`: `sh`/`bash`/`zsh` flags containing `c`, `cmd /c`, PowerShell `-Command`), each split and normalized again.
4. Executable text inside `$()` and legacy backtick substitutions, including substitutions inside double quotes; single-quoted lookalikes remain inert data.

Depth is capped at 16 and the candidate set at 128, so repository-influenced hook input cannot grow recursion or work without limit. These ceilings are a parser-availability boundary, not a permission widening: Claude's/Codex's OS sandbox remains the containment layer beneath the semantic tripwire.

- **No encoding/obfuscation awareness.** Base64-encoded payloads piped into `sh`, `eval "$(...)"`, environment-variable reassembly of a command string, and similar obfuscation are not decoded or evaluated — the matcher only ever compares literal text.
- **No `eval`/`exec`/`source`/`.`-style indirection.** A command that reads and runs a file's contents at runtime is invisible to a static string matcher by construction; this is the same limit every static-glob classifier (claude's own `permissions.allow`/`deny`, codex's `.rules`) already has.

A determined adversarial actor can still express a destructive effect through an allowed interpreter or dynamic script in a form this analyzer cannot recognize. `[safety]` is therefore a high-signal classifier, never described as the security boundary; OS sandboxing and native permission rules contain what an unrecognized command can reach. Native Windows Claude is the honest exception because Claude's OS sandbox is unsupported there—see [[Known Issues]]. Zirv gives Unix, `cmd.exe`, and PowerShell the same *classification* contract; it does not falsely describe native Windows as having the same kernel containment.

### Opaque-literal carve-out (issue #136, 2026-08-25)

The candidate-matching pipeline used to feed a `git commit -m "<message>"` argument's own quoted prose straight through the deny/ask matcher as if it were executable text, so a commit message that documented dangerous primitives *by name* — "awk (system()) and sed (-i / e) can execute arbitrary commands; rm -rf too" — was denied even though nothing dangerous runs. Two pure transforms in `safety.rs` now redact known-opaque literal spans before a candidate is glob-matched, without touching `command_substitutions`'s own extraction logic at all:

- **`redact_opaque_message`** recognizes `git commit`/`git tag`/`git notes`/`hg commit` invocations carrying a `-m`/`--message` argument (separate `-m "..."`, attached `-m...`, or joined `--message=...`) and replaces the value with the stable placeholder `<opaque:message>` in every DIRECT-match candidate `push_executable_candidate` derives from that segment — including the raw whole-string candidate `normalize_segments` starts from. Deliberately blunt: the entire value is blanked, including any `$(...)`/backtick substitution it happens to contain, because `command_substitutions` is always called against the UNREDACTED original segment text (never the redacted candidate), so a live `$(rm -rf /)` inside a double-quoted message is still independently extracted and classified as its own candidate at `depth + 1` — issue #136's own explicit constraint.
- **`redact_single_quoted_heredocs`** blanks the body lines of a POSIX single-quoted heredoc (`<<'EOF' ... EOF`) — fully literal, no parameter/command substitution inside it, per POSIX — applied ONCE at the top of `normalize_segments` before any splitting/extraction runs, so a nested candidate `command_substitutions` pulls out of a live `$(...)` (the shape the issue's own reproduction used: `git commit -m "$(cat <<'EOF' ...prose... EOF)"`) sees the already-opaque body too, without this function needing to run again at every recursion depth. A bare or double-quoted heredoc delimiter (`<<EOF`, `<<"EOF"`) still permits substitution per POSIX and is deliberately left untouched.

Both transforms fail closed on doubt (a malformed/truncated heredoc with no terminator line is left alone) and are scoped narrowly: an ordinary quoted argument with no commit-message shape and no heredoc still classifies normally (`unrelated_quoted_arguments_are_still_classified_normally`, `a_live_command_substitution_inside_a_commit_message_still_escalates`).

## The built-in default rule set

`builtin_deny()`/`builtin_ask()`/`builtin_allow()` derive from `adapters::SHIPPED_POSTURE_DENY`/`_ASK`/`_ALLOW` by stripping each entry's `Bash(...)` wrapper (`command_pattern_from_bash_rule`). Non-`Bash` file/tool rules remain an adapter concern and are skipped by the command classifier. `SafetyPolicy::default()` combines those three lists with `default: Ask`, `interactive_default: Allow`, and `sql: On`.

`SHIPPED_POSTURE_ASK` is split from `_DENY` by **reversibility, not danger**. Recoverable-but-dangerous families such as force-push, hard reset, recursive deletion, destructive `find`, process termination, device formatting, registry mutation and shutdown ask before running interactively. Irreversible publication/deletion, credential exfiltration, privilege escalation and attacks on zirv's own supervisor/config stay denied. In particular, `taskkill*zirv*`, `Stop-Process*zirv*`, `pkill*zirv*`, `killall*zirv*` and zirv-targeting recursive deletes are specific deny entries; because evaluation walks all deny rules before ask rules, they beat the broader process-termination/deletion asks without a fragile within-list ordering rule.

Plain `curl` and `wget` moved to allow: fetching an API response or fixture is everyday development work. The actual high-risk shape is denied directly as `* | sh`, `* | bash` and `* | zsh` (including no-space pipe variants). Similarly, `find -exec grep` and `reg query` stay silent; only delete-executing `find` forms and registry mutation (`reg delete`/`add`/`import`) ask. Adding another ask family means adding an operator interruption and must be justified as a product change.

Order is preserved through derivation so the headless Claude projection can concatenate deny and ask as one fail-closed disallow set while the interactive projection keeps ask out of both native lists for the hook to decide.

### Cross-platform semantic floors (v2.28.0)

Finite globs are retained for native adapter projection, but the hook evaluator now adds case-folded, executable-basename-aware semantic floors. Paths such as `C:\Program Files\tool.exe`, `.cmd`/`.bat` shims, PowerShell cmdlets/aliases and ordinary Unix names therefore reach the same answer:

- **Recovery-aware deletion:** a simple recursive cleanup whose every target is a known relative generated directory (`target`, `node_modules`, `dist`, `build`, caches, coverage and virtual environments) is silent interactively. An absolute/parent/dynamic target, shell wrapper, substitution, compound command, or non-generated directory asks. Operator/repo deny and non-built-in ask rules still win. Headless cleanup remains fail-closed because nobody can inspect it.
- **Destination-aware network effects:** GET/download and loopback development requests stay silent; remote POST/PUT/PATCH/DELETE, body/form and upload shapes ask. Uploading `.env` or a known SSH/cloud/registry/harness credential file is denied before a prompt could disclose it.
- **Credential-file access:** direct reads, writes, copies, moves, deletion, archives and redirections involving known SSH, cloud, Kubernetes, Docker, package-registry, Git, Claude, Codex and OpenCode credential files are denied for Unix utilities, `cmd.exe`, and PowerShell spellings. Ordinary project-file access stays silent. Arbitrary interpreter code remains the containment layer's responsibility.
- **Infrastructure/service destruction:** Terraform/OpenTofu/Pulumi destruction, Kubernetes/Helm deletion, destructive Docker pruning/volume teardown, cloud delete/terminate families, Redis flush/shutdown, and Mongo drops ask; read/list and recognized dry-run forms stay silent.
- **Version-control loss:** force/delete refspec pushes, hard resets, interactive rebase/`filter-branch` history rewrites, forced branch deletion, stash/reflog destruction, and immediate GC pruning ask, unconditionally. `checkout [<rev>] -- <paths>`/`restore [<flags>] <paths>` ask only for a tree-wide or glob pathspec (`.`, `:/`, `*`, or a path containing `* ? [`) — every path operand naming one concrete tracked file or directory is silent. `clean -f...` asks only when it also carries `-x`/`-X` (removes gitignored files, not just untracked ones) or names no explicit path at all; a pathed, non-`-x` `clean` is silent. `worktree remove --force` asks unless the target sits under a `.claude/worktrees/`/`.zirv/worktrees/` root or the session scratchpad (`target_is_confined`) — an agent removing its own scratch worktree. Non-interactive `rebase` is silent; `-i`/`--interactive` still asks. Status/diff/log/list, staging-only restore, ordinary (no-path) checkout, and clean dry runs stay silent, as before. (Issue #306, 2026-09-03: these four narrowings removed the operator prompts an agent's own routine, local, agent-scoped git cleanup and history work used to trigger; `rebase`/`clean` no longer have a blanket `adapters::SHIPPED_POSTURE_ASK` glob entry either, since a glob cannot see the arguments this judgment needs — `safety::is_destructive_vcs_action` owns it fully, the same way it already owned `checkout`/`restore`/`worktree remove`/`branch -D`/`stash drop`/`clear`/`reflog expire`/`delete`/`gc --prune*` with no blanket entry of their own; `filter-branch` keeps its blanket entry since it has no narrower safe form.) **Issue #327 (v3.15.0) hardened two forms the narrowing above left open:** `git push --mirror`/`--prune` overwrite or delete remote refs outright, independent of any `-f`/`--force*` flag, so both now ask unconditionally; `git checkout -f`/`--force` discards uncommitted local changes and `git checkout -B <branch> [<start>]` force-resets an existing (possibly unrelated) branch to a new start point, so `checkout` now asks whenever `-f`/`--force`/`-B` appears, checked BEFORE the `-- <paths>` pathspec narrowing above (`-B` is read from the ORIGINAL-case argv, not `checkout`'s lowercased copy, since lowercasing would collapse it into the harmless `-b`). Every pre-existing Allow (plain checkout, `-b` new-branch, concrete-path `checkout -- <paths>`, a non-`--mirror`/`--prune` push) is unchanged.
- **Irreversible distribution:** crate/package publish/yank/unpublish/upload, NuGet/gem equivalents, and GitHub repository/release/API deletion are a hard deny across wrapper extensions. Local package/build/check operations stay silent.

These floors only add high-confidence `Ask`/`Deny`; they do not turn parser uncertainty or an unknown program into a prompt. The product acceptance corpus and the shell-specific parity corpus pin both halves of that contract.

**Issue #224 (2026-08-31) supersedes issue #98's blanket `Bash(zirv *)` allow.** `builtin_allow` now appends one `zirv <name> *` rule per case-insensitive name in `utils::RESERVED_COMMANDS`. Those names are dispatched before repo script lookup and cannot be shadowed, so `zirv ctx`/`agent`/`workflow`/`report` and the remaining built-ins are safe to pre-approve; a non-reserved `zirv <script>` is unmatched and keeps the normal gate. `evaluate_single` applies the same case-insensitive dispatch test after explicit `deny`/`ask`, so repo rules may still narrow this default and mixed-case forms such as `ZIRV CTX status` agree with main dispatch.

**Issue #111 (2026-08-23), argument-reordering and sibling-utility bypasses:** PR #107's review found the round-4 `git push`/`git reset` deny entries were flag-anchored (`Bash(git push --force *)`), so `git push origin --force` (the flag reordered away from the front) slipped past untouched, as did the short-flag spellings (`-f`/`-d`), an empty-src refspec delete (`git push origin :branch`), and a force-refspec push (`git push origin +branch`). Those entries are now mid-string-wildcard patterns (`git push*--force*`, `git push* -f *`/`git push* -f`, `git push*--delete*`, `git push* -d *`/`git push* -d`, `git push* :*`, `git push* +*`, `git reset*--hard*`) — `glob_match` already supports `*` anywhere, not only as a suffix, and `git push*--force*` also covers `--force-with-lease` since that flag's own text contains `--force`. The same reordering gap existed for `find`'s own `-delete`/`-exec`/`-ok` actions (the `find *` allow was read-only only up to those), for `head`/`tail`/`diff` reading the same credential paths `cat`'s four deny entries already covered, and for three `gh` escapes (`gh api -X DELETE`/`--method DELETE`, `gh secret`, `gh codespace ssh`) — all closed the same way. `evaluate_deny_survives_argument_reordering_issue_111` (`safety.rs`'s test module) pins every bypass form to `Deny` and confirms ordinary uses (`git push -u origin x`, `find . -name foo.rs`, `gh pr create --fill`) stay `Allow`. As `adapters::SHIPPED_POSTURE_DENY`'s own doc comment now states explicitly: with arbitrary-code toolchains (`python *`, `node *`, ...) allowed, this list is a tripwire for named destructive/credential command families, not a security boundary.

## Layering (`resolve`)

`[safety]` cannot use the ordinary deep merge (a later layer's array would replace an earlier one's) or `REPO_FORBIDDEN`'s all-or-nothing rejection (a repo must be able to *narrow* the policy). So `safety::resolve` folds the layers the way `policy::resolve` folds `[policy]` — lifted whole out of `ctx.toml` by `CtxConfig::load` (both `home_safety`/`repo_safety` removed via the same `SAFETY_SECTION` constant `POLICY_SECTION` already uses) before the ordinary deep merge, and is itself a `#[serde(skip)]` field on `CtxConfig`, resolved separately at the end of `load`:

- **`deny`/`ask`** are additive across layers: built-in, plus the operator's own `~/.zirv/ctx.toml` entries, plus the repo's own `.zirv/ctx.toml` entries, all unioned. Adding a `deny`/`ask` entry can only ever make a command *stricter* to evaluate (both are checked before `allow`), so a repo checkout contributing to either is always safe — the identical reasoning `sandbox.extra_deny`'s own union already established.
- **`allow`** may be extended only by the operator's own home layer. `config.rs`'s `REPO_FORBIDDEN` table rejects a repo `ctx.toml` that sets `safety.allow` at all — there is no narrowing reading of adding an allow entry (unlike `deny`/`ask`, evaluated *after* both) — mirroring `sandbox.extra_allow`.
- **`escape_allow`** (issue #147, 2026-08-26) is `allow`'s narrower sibling, resolved the identical operator-home-layer-only way and also `REPO_FORBIDDEN`, but it governs only a `--dangerously-disable-sandbox` retry, not the ordinary sandboxed path `allow` covers. Unlike `allow`, it always carries a non-empty built-in seed (`builtin_escape_allow`) on top of whatever the operator adds — see "The sandbox-escape gate" below.
- **`default` and `interactive_default`** are operator-only. The first controls unmatched headless commands; the second controls unmatched interactive commands. Both are `REPO_FORBIDDEN`, with `interactive_default` especially sensitive because `allow` is the loosest possible verdict.
- **`sql`** is also operator-only and `REPO_FORBIDDEN`: turning the conservative classifier off can remove an `Ask` narrowing that would otherwise protect a broad allow/default.
- **Environment** (`ZIRV_CTX_SAFETY_DENY`/`_ASK`/`_ALLOW`/`_DEFAULT`/`_INTERACTIVE_DEFAULT`/`_SQL`) sits above the fold and wins outright. It replaces only the operator+repo contribution to a list, never the built-in set: there is no environment variable that removes a built-in protection.

`resolve` never reads `allow`/`default`/`interactive_default`/`sql` from its `repo` parameter even defensively, though in production those values cannot reach it: `reject_untrusted_keys` hard-errors first. See [[Untrusted Configuration]] for the full table.

## Conservative SQL classification

With `safety.sql = "on"` (the default), `psql`, `mysql`, `mariadb`, `sqlite3`, `duckdb`, and `sqlcmd` invocations get a second pure classification. A statement is silent only when all four gates hold: the client exposes exactly one statement on argv; comments and quoting are balanced; after an optional trailing semicolon the statement begins with `SELECT`, `EXPLAIN`, or `SHOW`; and token scanning finds none of the write/escape words (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `CREATE`, `ALTER`, `TRUNCATE`, `GRANT`, `REVOKE`, `MERGE`, `REPLACE`, `CALL`, `COPY`, `VACUUM`, `ATTACH`, `DETACH`, `PRAGMA`, `WITH`, `INTO`, `OUTFILE`, `DUMPFILE`, `LOAD_EXTENSION`, large-object/file helpers, or `SYSTEM`). Anything else through a recognized client asks.

The classifier runs on every structural candidate, so `echo ok && psql -c 'DROP TABLE t'` and recursively shell-wrapped DB clients cannot inherit an outer interactive allow. It may always narrow an `Allow` to `Ask`. It may widen the result to `Allow` only when no ordinary rule matched, and it never overrides `Deny`; an operator/repo `ask = ["psql *"]` also wins over a provably read-only statement. This is deliberately not a SQL parser or obfuscation defense: stdin/script/interactive input, multiple statements, malformed quotes/comments and every CTE (`WITH`, including a read-only one) ask. Rejecting all CTEs is the conservative superset chosen instead of pretending to distinguish a write-wrapping CTE without a parser.

## The `zirv ctx safety` verbs

- **`check --mode <interactive|headless>`** (`-- <command>`): prints the verdict and matched rule, exits `Verdict::exit_code()` (`allow`→0, `ask`→1, `deny`→2). No network or adapter probing.
- **`list`** (`--json` for machine-readable output): the effective merged policy, one line per rule with its origin (`built-in` / `~/.zirv/ctx.toml` / `repo .zirv/ctx.toml` / `environment`) — what an operator reads to see what a repo checkout narrowed.
- **`explain --mode <interactive|headless>`** (`-- <command>`): names the rule/default and what that verdict actually does in the selected posture—prompt interactively, fail closed headlessly, or run silently; same exit codes as `check`. Interactive is the CLI default.

`check` is dual-mode, chosen by whether a trailing command was given:

- **CLI mode** (`-- <command>` present): the ordinary case above.
- **Hook mode** (no trailing command): reads a claude `PreToolUse` JSON payload from stdin instead (`{"tool_name": ..., "tool_input": {"command": ..., "dangerouslyDisableSandbox": ...}}`). `Bash` and `PowerShell` share the evaluator; any other tool, an empty command, or unparseable JSON fails open — print nothing, exit 0 — the same rule `hook.rs::run_pretool` already holds every hook in this codebase to. An explicit unsandboxed retry never inherits an ordinary allow: it asks interactively and denies headlessly — with two narrow, source-level carve-outs (below).

**Orchestrator-seat repository writes (issues #328/#334/#345/#346, 2026-09-04).** Before ordinary policy widening, hook mode denies a main-thread orchestrator Bash/PowerShell command whose structured write target lands in a git repository outside that repository's `.zirv/work` or `.zirv/memory`. Claude Code's own harness home remains writable even when it is itself a git repository: a non-empty `CLAUDE_CONFIG_DIR` selects it, otherwise `$HOME/.claude`; existing roots compare canonically (preserving a target's missing tail), and absent roots fall back to component-aware lexical containment. The environment lookup is the same injected hook lookup that carries `ZIRV_CTX_SEAT_ROLE`, not a process-environment read inside the classifier. `scan_redirection_targets` recognizes only path-bearing output redirects (`>`, `>>`, `>|`, `&>`, `&>>`, `N>`, `N>>`); `<`/heredoc/here-string/process-substitution inputs and `>&N`/`N>&M`/close-descriptor forms name no write target. `$()` and backtick bodies are recursively scanned, with their closing delimiter excluded from the exact target reported. A non-empty PreToolUse `agent_id` bypasses only this orchestrator-write rule because it proves the call is already inside the delegated native worker; all ordinary safety rules still evaluate unchanged.

**The `gh` read-only sandbox-bypass carve-out (2026-08-25).** `gh` always needs to read its own credential config, which the Claude Code sandbox denies outright — so every `gh` call zirv's Bash tool makes already arrives here as an unsandboxed retry, and the escalation rule above used to make even a plain `gh issue view` prompt or fail on every single invocation. `is_sandbox_bypass_safe_gh_command` narrows a specific exception instead of loosening the rule generally: a command qualifies only when it is a **single, simple** invocation — `split_segments` (`;`/`&`/`&&`/`||`/`|`/newline) yields exactly one segment, `command_substitutions` (`$(...)`, backticks) is empty, and no unquoted `>`/`>>`/`<` redirection appears — whose first token, resolved through the same directory-strip/lowercase/`.exe`-strip normalization every other program-name compare in this module uses, is literally `gh` (disqualifying a shell wrapper, a launcher like `env`/`sudo`/`timeout`, and an env-var prefix like `GH_TOKEN=x gh ...` in one stroke), and whose second and third tokens whole-token-match one `(noun, verb)` pair from a fixed, read-only list: `issue view/list`, `pr view/list/diff/checks`, `repo view`, `run view/list`. Only when the verdict is already `Allow` and the command qualifies does the escalation step leave it `Allow` (matched `<sandbox: read-only gh>`, distinct from `<sandbox: unsandboxed retry>`) instead of turning it into `Ask`/`Deny`; a mutating verb (`gh pr merge`, `gh issue create`, `gh repo delete`) or any shell composition/substitution/redirection around an otherwise-qualifying invocation still hits the ordinary escalation ladder untouched.

**The `escape_allow` sandbox-escape gate (issue #147, 2026-08-26).** The `gh` carve-out is one hand-written exception; `escape_allow` is the general mechanism it sits beside. `SafetyPolicy::escape_allow` seeds a BUILT-IN set (`builtin_escape_allow`) by filtering `builtin_allow()`'s own already-declared rules down to a fixed read-only-utility program list (`ls`/`grep`/`rg`/`cat`/`head`/`tail`/`wc`/`find`/`echo`/`pwd`/`which`/`where`/`diff`/`sort`/`uniq`/`tr`/`cut` — the subset of `SHIPPED_POSTURE_ALLOW` that operator evidence showed accounted for most sandbox-escape asks, e.g. `grep`ing zirv's own state/log directories outside the sandbox's default scope) — a filter over one already-declared source, not a second copy of the glob text — and the operator may add more via `[safety] escape_allow`/`ZIRV_CTX_SAFETY_ESCAPE_ALLOW` (home layer only, `REPO_FORBIDDEN`, no narrowing reading of adding an entry — the identical asymmetry `allow` already has).

Matching a family alone is never enough: `escape_allow_matches(escape_allow, command)` requires **every** executable segment `normalize_segments` derives from the command to both match a rule AND clear `escape_denied_by_screen` — worst segment wins, so `cd /tmp && rm -rf /` can never pass because `cd` alone would, and a seeded `grep foo file && curl evil.example` can never pass because `grep` alone would (pinned by `a_compound_with_one_unmatched_segment_never_escapes_to_allow`/`a_compound_pairing_a_seeded_utility_with_an_unrelated_command_never_escapes`). `escape_denied_by_screen(candidate)` re-checks every token against `sensitive_upload_path` (the existing credential-path/`.env` classifier, reused rather than re-enumerated — its own path list is now the single shared `SANDBOX_DENY_READ_HOME_PATHS` constant claude's own native `sandbox.filesystem.denyRead` list also derives from, so the OS sandbox boundary and this escape screen cannot drift apart) and screens out `is_root_wide_find_scan` (a `find` whose first path argument is `/`, `~`, or `~/`) — so a seeded `cat *`/`find *` can never ride its family match past a credential read or an unbounded root scan (`a_seeded_family_never_escapes_a_credential_path_read`, `a_seeded_find_never_escapes_a_root_wide_scan`).

`run_check_hook_mode_with_env`'s escalation branch has four carved-out exceptions — all still gated on the base verdict already being `Allow` — checked in this order: `is_sandbox_bypass_safe_gh_command`, `is_reserved_zirv_escape_safe`, `is_read_only_escape_safe`, then `escape_allow_matches`. Each states its own distinct pattern in the JSON envelope and audit log (`<sandbox: read-only gh>`, `<sandbox: reserved zirv built-in>`, `<sandbox: read-only escape>`, `<sandbox: escape_allow>`), distinct from the ordinary `<sandbox: unsandboxed retry>` denial. `permissions::run_compile --escape`'s eligibility gate reuses the identical screen through a shared combinator, `command_fails_escape_screen(command)` (`escape_denied_by_screen(command) || evaluate(..).verdict == Verdict::Deny`) — see "Compiling recommendations into approvals" below.

**Three more retry-path carve-outs (issue #168, 2026-08-27), widening decision (a)/(b)/(d).**

- **`is_read_only_escape_safe(command, scratchpad_roots)`** — every executable segment of the retried command must be a read-only `gh`/`glab` call (`is_gh_or_glab_read_only`: a fixed `(noun, verb)` table per tool — `issue view/list`, `pr view/list/diff/checks` (gh only), `repo view`, `run view/list` (gh only), `mr view/list/diff` (glab only), `ci view/status` (glab only) — or a bare `gh api` with no method other than `GET` and no `-f`/`-F`/`--input` body flag), a read-only `git` subcommand (`is_git_read_only`: `status`/`log`/`diff`/`show`/`fetch`/`ls-remote`/`rev-parse`/`describe`/`blame`/`shortlog` outright; `branch`/`remote`/`tag`/`stash`/`worktree` restricted to their non-mutating forms), a GET-only `curl`/`wget` (`is_curl_or_wget_get_only`: no `-X`/`--request` other than `GET` in either the separate-token or glued/`=`-attached spelling, no body-uploading flag, `-K`/`--config` disqualifies outright in every spelling (an unseen config file can itself set method/data/output), any `-o`/`--output` target — separate-token, `--output=X`, or glued `-oFILE` — must be `target_is_confined` to `/dev/null` or the session scratchpad — `-O`/`--remote-name` always disqualifies, its target is unprovable), a read-only `kubectl` verb (`is_kubectl_read_only`: `get`/`describe` EXCLUDING Secrets (`secret`/`secrets`, comma-joined, or `secret/<name>`-qualified) and excluding `--raw` (which bypasses the resource-name check with an arbitrary API path), `logs`/`version`/`api-resources` outright, or `config view` specifically excluding `--raw` (which prints embedded client certs/tokens) — never a bare `config`), or one of the pre-existing `SANDBOX_ESCAPE_BUILTIN_PROGRAMS`. Every candidate is still screened by `escape_denied_by_screen` first (credential paths, root-wide `find`, unquoted redirection), exactly like `escape_allow_matches` — this carve-out never bypasses that screen, only adds more qualifying command SHAPES on top of it. **Issue #329 (2026-09-03):** each candidate segment is now also accepted when `is_reserved_zirv_escape_safe_segment` (below) accepts it on its own — the single-segment body factored out of `is_reserved_zirv_escape_safe` so this function can reuse the identical per-segment judgment as one more acceptor. Closes a gap where a compound mixing a reserved `zirv ctx` call with a benign read-only filter (`zirv ctx inbox | tail; zirv ctx status --brief | tail`) used to clear neither whole-command check on its own: `is_reserved_zirv_escape_safe` requires EVERY segment to be zirv, and this function's own per-segment table knew nothing about zirv.
- **`is_reserved_zirv_escape_safe(command)`** (issue #168, renamed under issue #224) — every segment is `zirv ctx <verb>` for a verb in the explicit `ZIRV_CTX_ESCAPE_SAFE_VERBS` allow-list (`score`/`handoff`/`hook`/`status`/`usage`/`optimize`/`send`/`inbox`/`remember`/`recall`/`forget`/`nudge`/`safety`/`permissions`/`group`), a bare `zirv help`/`version`/`memory`/`context` (no further subcommand), or `zirv report` (issue #224). `zirv ctx` performs the very attestation/safety checks this module implements, so a broken launch snapshot must not lock zirv's own supervision commands out from correcting it — this carve-out is what lets `zirv ctx status`/`remember`/`send` keep working through a self-heal (above). **Code review fix (2026-08-27, CRITICAL), still in force:** this used to allow ANY `zirv ctx <verb>` unconditionally, including every verb that launches a subprocess of its own (`exec` — `-- <arbitrary command>`; `wrap`/`chat`/`resume`/`loop` — an interactive/headless agent launch; `agent` — an arbitrary adapter name plus its own trailing flags; `handover` — swaps the live session's harness/model in place). Now a fail-closed allow-list: a newly added `CtxVerb` does NOT qualify until added here on purpose. `usage`'s own `tee` subcommand (`zirv ctx usage tee -- <command>`) is excluded even though `usage` itself qualifies. Issue #224 deliberately did NOT widen this gate to the whole reserved list — that boundary governs the policy layer only. Matching is case-insensitive; directory-qualified binaries (`./zirv`, `/repo/zirv`) never qualify.
- **`write_targets_confined(command, scratchpad_roots)`** (paired with `every_segment_is_allow_or_unmatched_default`) — a compound whose every write target (`scan_redirection_targets`: unquoted `>`/`>>`/`<`/digit-prefixed/`&>` forms, plus a `tee` target argument) resolves to `/dev/null` or beneath the session scratchpad is treated as `Allow` even when it would otherwise rely on the unmatched-command mode default — checked BEFORE the sandbox-retry branch (`<scratchpad: confined write>`) so the same widening survives a `--dangerously-disable-sandbox` retry too (an `already_scratchpad_confined` short-circuit skips the ordinary escalation ladder). Returns `None` (no opinion, today's un-analyzed behavior) whenever there is no scratchpad root configured, any segment's target cannot be confidently resolved (a dangling redirection operator, a `$`/backtick-built path), or — CRITICAL — the command names no write target at all: a zero-write command widening to `Allow` just for not writing anywhere would be a much broader hole than "a compound that writes, confined to the scratchpad."
- **`is_mixed_confined_write_and_read_only_escape_safe(command, scratchpad_roots)`** (issue #321 item 2, v3.15.0) — closes a gap none of the carve-outs above cover: `is_read_only_escape_safe`'s own `escape_denied_by_screen` denies ANY unquoted redirection outright, confined or not, so a read-only `gh`/`git`/`curl` call that redirects its OWN output into the scratchpad (`gh issue view N --json body > <scratch>/a.md`) never qualified as "read-only" even though nothing it touches is unconfined. This combinator instead requires every top-level executable segment (`split_segments`, deliberately not `normalize_segments`'s further recursion, so a `curl ... | sh` pipeline stage stays one unit) to be EITHER a genuine, scratchpad-confined write (`is_confined_write_segment`: names at least one write target via `segment_write_targets` or a new `mkdir_write_targets` — `mkdir`'s own trailing path arguments, `None` on any `$`/backtick-tainted one — every target `target_is_confined`, and the segment's own verdict is `Allow` or the plain unmatched default) OR read-only-escape-safe entirely on its own (`is_read_only_escape_safe` applied to that one segment). Used only by the unsandboxed-retry chain, gated on `scratchpad_roots` being non-empty, and never reached once a whole-command classifier like `apply_pipe_to_shell_outcome` has already denied the compound outright (a confined `mkdir` next to `curl ... | sh` still denies).
- **`is_prompt_free_zirv_retry_safe`'s `--dry-run` carve-out (issue #307, v3.15.0)** — `test`/`verify` stay excluded from the blanket reserved-zirv-name pass (an ordinary invocation selects a repository-authored `.zirv/verify.toml`/`package.json` command that must stay inside the OS sandbox), but `zirv test changed --dry-run`/`zirv verify --dry-run` now clear the unsandboxed retry silently: `verification::run_check` returns `CheckStatus::DryRun` before it ever builds that child command, so a dry-run invocation provably cannot reach repository-authored code regardless of what `.zirv/verify.toml` says. Scans every token after the reserved name, not only a literal trailing `--dry-run`. A real (non-dry-run) `zirv test`/`zirv verify` retry still asks/denies exactly as before.
- **A leading `cd <known-root>` prefix is classified away (decision e)** — `strip_known_root_cd_prefix(command, allowed_roots)` recognizes a literal (no `$`/backtick/`~`/glob), single-token `cd <path>` segment followed by `&&`/`;`/newline whose `<path>` resolves under the session scratchpad, the hook process's own working directory, or anywhere containing a `.claude/worktrees` path component, and returns the remainder alone for classification — so `cd <worktree> && git log` is judged by `git log`, not dragged to the mode default by the unmatched `cd` segment. The ORIGINAL, unstripped command still reaches `hook_output`/`audit_hook_decision`, so the log and any denial message always name what was actually run. A `cd` containing `..`, an unproven/dynamic path, or an unknown root is left untouched.

**Review round 1 (2026-08-27, CRITICAL): `escape_denied_by_screen` also screens unquoted redirection.** A seeded family's own glob pattern (e.g. `"echo *"`) matched straight through a trailing ` > ~/.claude/settings.json` — an unsandboxed **write** via the built-in escape seed, in both interactive and headless mode, since the credential-path/root-scan checks above only looked at read targets. `escape_denied_by_screen` now also routes every candidate through `contains_unquoted_redirection` (the same primitive the `gh` carve-out already trusted, above): any unquoted `>`/`>>`/`<` denies the escape screen outright, seeded family or not. Applied identically to `command_fails_escape_screen`, so `permissions --escape` compile eligibility closes the same hole.

## Launch policy attestation, audit, and the wired `PreToolUse` hook

Every supervised Claude launch resolves one `SafetyPolicy`, serializes it canonically, hashes it with SHA-256, and atomically materializes two operator-owned files under `~/.zirv/runtime/`: `policies/<fingerprint>.json` plus `claude-launch-settings-<fingerprint>.json`. The settings layer exports both snapshot path and expected fingerprint to the hook. On every command, the hook verifies the snapshot, evaluates both that immutable launch policy and the policy resolved now, and keeps the stricter verdict. A repo narrowing can therefore take effect immediately, while an operator widening waits for a clean relaunch. A **valid but divergent** snapshot still keeps the stricter of the two verdicts, unchanged.

**Invalid attestation now self-heals instead of asking/denying the whole session (issue #168, decision c, 2026-08-27).** A partial (exactly one of the two env vars), missing, unreadable/unparseable, or hash-mismatched snapshot used to produce `attestation_failure(mode)` — a blanket `Ask` interactively / `Deny` headlessly on **every single command** for the rest of the session, with no way out short of a restart. `self_healed_evaluation` now falls back to evaluating the CURRENT in-process policy alone instead — the same policy this same launch already resolved from `~/.zirv/ctx.toml` and any repo `.zirv/ctx.toml`, so a self-heal can never loosen past what the operator's own current policy would already allow (`a_tampered_attestation_snapshot_still_honors_a_narrowed_current_policy`) — and best-effort re-materializes the snapshot file at the pinned path (`rematerialize_policy_snapshot`, the identical pretty-JSON-plus-newline shape `launch_settings_path` itself writes at launch) so the NEXT command in the same session attests cleanly again instead of re-detecting the identical broken file every command. `AttestedEvaluation.status` carries a new `"self-healed"` value, distinct from `"not-present"`/`"invalid"`(now unreachable in production, see below)/`"valid"`, read by `audit_hook_decision`'s log record. `attestation_failure` itself is kept, `#[allow(dead_code)]`, as the documented pre-#168 shape a few nearby doc comments still reference by name.

**Snapshot-divergence explanation (issue #139, 2026-08-25).** The stricter-answer fold above used to be invisible and, worse, actively misleading: when the pinned launch snapshot was stricter than the resolved-now policy for a given unmatched command, the hook's own explanation said "the interactive default (ask) applies" as if `ask` were the CONFIGURED posture, while `zirv ctx safety explain` for the identical command (which used to bypass attestation entirely) reported the current, wider policy's own answer — two surfaces disagreeing with no way for the operator to see why. `evaluate_with_attestation_evidence` now also computes a `SnapshotDivergence` (`Unchanged` | `SnapshotStricter { current_verdict }`, by comparing `verdict_rank` between the launch and current outcomes) and carries it on `AttestedEvaluation`. `explain_text` reads that divergence and, when `SnapshotStricter`, appends an explicit note naming the launch snapshot as the source and the current policy's own verdict: *"the launch snapshot (pinned at session start) is stricter than your current policy, which would `<verdict>`; restart the session (zirv chat) to adopt the widened policy."* `run_explain` (`zirv ctx safety explain`) is now routed through the SAME `evaluate_with_attestation_evidence` call the hook uses — always, not merely when the attestation env vars happen to be set, since that function's own "not-present" branch already degrades to a plain `evaluate` with `Unchanged` divergence, which is byte-for-byte the pre-fix behavior. The two surfaces cannot disagree any more.

**`zirv ctx status` surfaces a stale snapshot too.** `sessions::Record` gained `safety_policy_sha256: Option<String>` (`#[serde(default)]`), stamped at registration wherever a launch seam already resolves `cfg.safety` before building its own launch argv (`wrap.rs::run_with`, `exec.rs`, `run_loop.rs` — `dash/pane.rs::Pane::spawn` does not yet thread a `SafetyPolicy` parameter through and is a documented residual; its panes' `safety_policy_sha256` stays `None`, which the check below already treats as "nothing to compare"). `status.rs`'s `sessions_lines` compares each record's stored fingerprint against a freshly loaded `CtxConfig::load(&record.repo, env)`'s own `safety::policy_fingerprint`, appending "policy snapshot stale (current policy is wider); relaunch to adopt" to that session's line when they differ. `policy_snapshot_is_stale` degrades silently (no line, no error) on any doubt — no stored fingerprint, the record's own repo config failing to load, or fingerprinting failing — keeping every bit of I/O at `status.rs`'s own edge and never risking a fabricated stale claim.

The settings layer sets `disableAllHooks = false`, installs `zirv ctx safety check` for `Bash|PowerShell`, scrubs cloud credentials from subprocess environments, and denies common credential paths through both `permissions.deny` and `sandbox.filesystem.denyRead`. On macOS/Linux/WSL2 it also enables Claude's OS sandbox with auto-allow and sets `failIfUnavailable = true`; native Windows omits the unsupported sandbox key. A materialization failure adds no settings flag and no blanket shell allow, falling back to native prompts rather than widening.

**No native `dangerouslyDisableSandbox` ask rule any more (issue #147, 2026-08-26).** This layer used to also carry a native `permissions.ask = ["Bash(dangerouslyDisableSandbox:true)"]` rule. It is now gone outright, not merely narrowed: documented Claude Code behavior (code.claude.com/docs/en/permissions, "Extend permissions with hooks") is that a native settings rule is evaluated INDEPENDENTLY of a `PreToolUse` hook's own decision — a settings `ask` rule still prompts even when the hook returns `allow` — so that native rule silently defeated every hook-side `allow` for a sandbox-escape retry, including the `gh` carve-out and the new `escape_allow` gate above: an operator who pre-cleared a family kept getting re-prompted on every repeat regardless. The attested `safety check` hook (both carve-outs above) is now the SOLE zirv-side decision point for an escape; the operator's own native rules, if any, still apply on top, per that same documented precedence. `launch_settings_attest_the_safety_hook_and_no_longer_inject_the_native_sandbox_escape_ask_rule` (`claude.rs`) pins the rule's absence.

**`sandbox.filesystem.allowWrite` scoped to the mail directory (issue #147, 2026-08-26).** A sandboxed command may by default only write to the working directory and the session temp directory, which used to make `zirv ctx send` fail inside a sandboxed session. `ClaudeAdapter::launch_settings_path` resolves `state.mail()` (best-effort — a state-dir resolution failure just omits the entry) and `launch_settings_value` takes it as a third `mail_write_dir: Option<&Path>` parameter, adding `allowWrite: [<mail dir>]` to `sandbox.filesystem` only when present. Deliberately narrow: the policy-snapshot/attestation directory and the decision-log directory that sit alongside the mailbox under the same state root are never allow-listed (`launch_settings_allow_write_to_the_mail_dir_but_never_the_policy_snapshot_dir`).

**Issue #168 (2026-08-27) briefly widened this to memory/logs/groups/handoffs, then reverted on code review.** With `is_zirv_ctx_escape_safe` restricted to an explicit non-subprocess verb allow-list (above), every `zirv ctx <state-verb>` (`remember`/`recall`/`forget`/`nudge`/`group`/...) already rides the ALWAYS-ALLOWED unsandboxed retry, so no prompt is ever paid for those writes regardless of what this OS-sandbox allowlist says — the widening bought no operator-facing benefit. Reverting to mail-only keeps the safety audit trail (`logs/`), the cross-session memory bank, group budgets, and handoffs UNWRITABLE from inside the sandbox on any OTHER path (an unlisted/unmatched command that is not `zirv ctx` at all), a real defense-in-depth layer the widened list gave up. `launch_settings_value`'s third parameter is back to a single `mail_write_dir: Option<&Path>` (not `allow_write_dirs: &[PathBuf]`). This file lives inside `#[cfg(not(windows))]` code (Claude's OS sandbox is unsupported on native Windows); both the widening and the revert were verified on `rust:1-bookworm` as a non-root user per this repo's own Linux/Docker convention for `#[cfg(not(windows))]` changes.

**Durable interactive-mode pinning (issue #147 amendment, 2026-08-26).** `run_check_hook_mode_with_env` used to classify `LaunchMode` from Claude's self-reported `permission_mode` alone (`"default"`/`"plan"`/`"acceptEdits"` → `Interactive`, everything else → `Headless`) — so an operator whose native `defaultMode` is `"auto"` (field evidence that filed this) had every genuinely interactive session silently fail closed to `Headless`, asking on everything a human was right there to approve. `adapters::LAUNCH_MODE_ENV` (`ZIRV_CTX_LAUNCH_MODE=interactive`, the one value in `adapters::LAUNCH_MODE_INTERACTIVE_VALUE`) is now set into `turn_env` at every real zirv interactive-launch seam via `adapters::launch_mode_pin_env(mode)`: `wrap.rs::run_with` (covers both `zirv ctx wrap` and, through `chat.rs`'s call into it, `zirv chat`'s wrap-based fallback), `dash/mod.rs::run_dashboard`'s first/orchestrator pane (unconditional — that pane is always the human-attended one the operator is looking at), and `dash/mod.rs::fulfill_spawn_request`'s worker panes (gated on the identical `req.interactive` signal `worker_pane_extra_args`/`compose_worker_prompt` already use to pick that pane's own `LaunchMode`, never re-derived). The hook process is a child of the same claude process the pin was set on and inherits its environment the same way it already inherits `POLICY_FINGERPRINT_ENV`/`POLICY_SNAPSHOT_ENV`. `safety::launch_mode_pinned_interactive(env)` reads it with an exact-match comparison (absence, or any other value, reads as "not provably zirv-interactive-launched" — the fail-closed default) and the hook now classifies `Interactive` when EITHER the pin is present OR the self-reported mode is one of the three proven values, so the pin overrides an unproven self-report but never weakens the existing check. `adapters::LAUNCH_MODE_ENV` is listed in `sessions::SUPERVISION_ENV`, so it is scrubbed rather than inherited by a nested launch — a headless worker (`exec`/`loop`, or a non-interactive spawn request) spawned from inside an interactive session must prove its OWN interactivity fresh, never borrow its parent's.

Hook decisions with a session id are appended best-effort to UTC-day JSONL buckets under `<state>/logs/safety-decisions/`. Each record carries mode, verdict, matched synthetic/policy rule and origin, platform, attestation status, and current/launch policy fingerprints. The command is represented only by SHA-256, never raw text, so incident correlation does not create a second transcript containing source paths, tokens or shell secrets. Audit failure never changes the permission verdict.

`zirv setup apply` (`src/commands/setup.rs`) still installs the same hook persistently for Claude sessions started outside Zirv, as a distinct entry from the existing `Agent|Task` guard. That setup path is backed up and idempotent, but supervised-launch correctness no longer depends on it having run once in the past.

**Claude only.** `HARNESS_HOOKS` (the shared four-hook array `install_claude_integration`/`install_codex_hooks` both iterate) is untouched; the safety hook is a separate `CLAUDE_SAFETY_HOOK` constant wired only into `install_claude_integration`. Codex has no verified equivalent of the structured `permissionDecision` contract this hook relies on, so wiring it into the shared array would write a hook codex has no verified way to honor.

**Decision travels in the JSON envelope, not the exit code.** In hook mode, `hook_output` emits the same shape `hook.rs`'s own `pretool_output` already uses and this codebase has already verified against the installed claude CLI:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "`rm -rf /` is deny because it matched the deny rule `rm -rf *` from built-in."
  }
}
```

`permissionDecision` can be `"deny"`, `"ask"`, or `"allow"`. On an interactive launch the hook is the sole per-command prompting gate, so an everyday or unmatched command must emit explicit `"allow"`; silence would fall through to Claude's native prompt and violate the primary criterion. The hook always exits 0: the decision belongs in the structured envelope, where all three outcomes are expressible.

**An `"ask"` still falls through under `--permission-mode dontAsk` (issue #102), but zirv's own interactive launches no longer use that mode.** Under `dontAsk`, an active ask is an unsatisfiable prompt Claude converts into a denial, so `hook_output` emits nothing and preserves the operator's own native allow list. The remaining callers are exactly a headless zirv launch and an operator who explicitly pinned `dontAsk`; the adapter's real argv is covered end to end by `the_dont_ask_suppression_is_reachable_only_from_the_headless_posture`. `Deny` emits in every mode, while non-`dontAsk`/missing modes are treated as interactive for the explanation and keep a real ask.

## Loop breakers (issue #313, 2026-09-04)

`SafetyPolicy` gained three fields alongside `deny`/`ask`/`allow`/`default`/`interactive_default`/`sql`: `denial_breaker_threshold` (default 3), `identical_command_warn_after` (default 2), `identical_command_refuse_after` (default 5), all `u32`, all `0` meaning "disabled." They govern two additive, PreToolUse-hook-only behaviors that never change any command's underlying `Verdict::Allow`/`Ask`/`Deny` family — no existing rule, glob, or classifier changed for any command. Both live entirely inside `run_check_hook_mode_with_env`, computed from a fresh `HookOutputExtras { breaker_note, reason_override, additional_context }` and folded into the JSON envelope by `hook_output_with_extras` (the production call site now, threading `extras` through `hook_reason_text`/`hook_output_json`; the old five-argument `hook_output` survives only `#[cfg(test)]`, as a thin wrapper calling `hook_output_with_extras` with `HookOutputExtras::default()` — behaviourally identical to the pre-#313 envelope byte for byte when every extras field is `None`).

- **Consecutive-denial breaker.** When this decision's own verdict is `Ask` or `Deny` and `denial_breaker_threshold > 0`, zirv reads this SESSION's own recent safety-decision history via a new bounded reader, `log::read_recent_safety_decisions(state, session, limit)` — opens only the newest TWO day-bucketed `logs/safety-decisions/*.jsonl` files (bounded, unlike the unbounded `read_safety_decisions` the permission audit uses), filtered to `session`, oldest-first — and counts the trailing run of consecutive `ask`/`deny` verdicts. Read BEFORE `audit_hook_decision` appends this decision, so "this decision included" is `trailing + 1`, not a read of a record that doesn't exist yet. Once that total reaches the threshold, `breaker_note` is set to an explicit "N consecutive denials this session: stop attempting variations of this command; report the blocker ... or via `zirv ctx send`, then continue with other work" instruction, prefixed onto the ordinary `explain_text` narrative with ` -- ` (the operator still sees the original policy reason underneath). An intervening `Allow` resets the run to zero. Different sessions never share a count — `payload.session_id` scopes both the read and the log's own `session` field.
- **Identical-failing-command guard.** `HookToolPayload` gained `transcript_path: Option<String>` (`#[serde(default)]`, claude's real PreToolUse payload field; absent/unparseable just means the guard does not run — the same fail-open discipline the rest of this struct already follows). Only examined when the base verdict is already `Allow` and the command is NOT `is_read_only_escape_safe` (that carve-out exists precisely for benign, repeatable inspection commands, never the loop this guard targets). `trailing_same_command_failure_run(jsonl, command)` is a new pure function — a dedicated parser mirroring `adapters::claude::structural_context`'s own `Bash` `tool_use`/`tool_result` pairing by `id`/`tool_use_id`, but narrowed to EXACT command-text matches (no normalization) and folded into a trailing run (consecutive erroring invocations of the identical command text, reset by any intervening SUCCESSFUL invocation of it) rather than a full history. At `identical_command_warn_after` (default 2), the verdict stays `Allow` but `hookSpecificOutput.additionalContext` carries a "this exact command has failed N times in a row; change the approach" warning — this is the one case where an `Allow` still emits JSON under `dontAsk` (issue #102's silence rule stands for every OTHER `Allow`; staying silent here would hide the one signal that could break the loop). At `identical_command_refuse_after` (default 5), ONLY on a headless launch (`mode == LaunchMode::Headless`), the verdict itself flips to `Deny` (`matched: Rule { pattern: "<guard: identical failing command>", origin: BuiltIn }`) with a `reason_override` replacing the ordinary narrative outright ("refusing to run it again -- report the blocker"); an interactive launch never auto-refuses, only warns — an operator is watching and can decide.

**The narrowing fold, not `REPO_FORBIDDEN` (issue #313).** All three thresholds are folded by a new `narrow_threshold(home, repo)` in `safety.rs`, structurally like `config.rs`'s `narrow_max_nudges` (`verify_on_stop.max_nudges`) but with a different meaning for zero: `narrow_max_nudges` treats `0` as *unbounded*, so plain `home.min(repo)` is the whole fold; here `0` means *disabled*, so a plain `min` would let a repo turn a disabled breaker back on by naming any smaller nonzero value. `narrow_threshold` therefore special-cases both directions — `home == 0` always stays `0` regardless of `repo`, and `repo == Some(0)` is ignored as an attempted widening (treated like `None`) — with `home.min(repo)` only for the ordinary nonzero/nonzero case. None of the three keys is in `REPO_FORBIDDEN`: a repo checkout may make a breaker fire SOONER (narrower), never later or never at all. See [[Untrusted Configuration]] for the fold's place among `[safety]`'s other three shapes (union, `REPO_FORBIDDEN`, and now this one), and `.zirv/ctx.toml`'s own commented `[safety]` rows for the operator-facing key documentation.

## Delegation envelopes deny past the ordinary policy (issue #262, v3.17.0)

A delegated worker's `envelope::WorkerEnvelope` (see [[Ctx Subsystem]]'s `agent`/envelope entry for the full model — `principal`/`paths`/`tools`/`network`/`destructive`/`delegation_depth`/`expires_at`/`token_budget`, computed once at dispatch and travelling with the worker as `ZIRV_ENVELOPE`) is a SECOND, independent gate layered on top of the ordinary `[safety]` evaluation, not a replacement for it — it can only ever narrow what the policy already allows, never widen it. `evaluate`/`evaluate_with_scratchpad_roots` and the hook-mode escalation path both take an `Option<&WorkerEnvelope>` parsed pure from the `ZIRV_ENVELOPE` env var (`parse_envelope_env` — a present-but-malformed value falls back to `WorkerEnvelope::locked()`, the tightest possible grant, rather than treating a parse failure as "no envelope in force"), and `apply_envelope_outcome` runs after the base verdict is computed:

- **A command the base policy already allows becomes `Deny`** when the envelope's own `destructive: false` and the command is independently classified destructive by this module's own existing classifiers (`command_is_destructive`, an OR of `is_sandbox_bypass_safe_gh_command`'s inverse, `is_destructive_orchestrator_action`, `is_destructive_vcs_action` — the identical judgment `[safety]`'s own destructive-command asks already use, never a second, independently-drifting definition).
- **A command whose write target falls outside `envelope.paths` is also `Deny`** (`envelope_write_targets_confined`, checked via `PathScope::is_subset_of` — pure lexical prefix containment, never `std::fs::canonicalize`, mirroring `write_targets_confined`'s own scratchpad-confinement shape above). A command naming no write target at all, or one the resolver cannot confidently determine, is never penalized by this check — an envelope violation must be provable, not assumed.

**`zirv ctx safety explain` prints the envelope's own contribution unconditionally**, not only on commands it actually denied — `explain_text` appends `Delegation envelope '<principal>': paths [...], network <bool>, destructive <bool>, depth <n>.` whenever an envelope is in force, so the same verb also answers "what would this worker's own scope allow" for a command it happens to already allow for other reasons. This is a real, structural enforcement point (the hook denies, it does not merely advise), distinct from `screen.rs`'s advisory-only flagging described below. See [[Ctx Subsystem]] for the envelope model itself and [[Untrusted Configuration]] for `worker.default_depth`/`default_read_only`/`max_depth`/`deny_network`'s trust boundary.

## Adapter projection

`AgentAdapter::default_sandbox_args(&self, sandbox, safety, mode)` and `adapters::policy_launch_args(cfg, adapter, flags, mode)` receive an explicit `LaunchMode`; no call site infers posture from TTY state.

- **Claude interactive**: `--permission-mode default`; Design B ships, so there is no blanket native `Bash(*)` allow. Non-command allow rules and scratchpad paths are pre-approved, deny rules are natively disallowed, and ask rules are on neither list. The launch-attested `Bash|PowerShell` hook emits explicit allow/ask/deny and therefore carries everyday and unknown shell commands without making the finite native allow list a prompt surface.
- **Claude headless**: unchanged fail-closed shape, `--permission-mode dontAsk`; allow rules are pre-approved and `deny ∪ ask` is disallowed because nobody can answer.
- **Codex interactive/headless**: `--sandbox workspace-write` in both modes, with `--ask-for-approval on-request` only when the cached live probe confirms support, otherwise `never`; a second probe adds `--approve-for-me` interactively when the installed CLI advertises its native automatic reviewer. Headless always uses `never`. No `[safety]` rule reaches codex per command.

**Codex has no per-command approval mechanism (issue #222, v3.5.0).** Claude gets #224's pre-approval of reserved zirv built-ins (`safety.rs::builtin_allow`, `adapters/claude.rs::launch_settings_value`) — a real, per-command decision zirv makes and attests. Codex has nothing symmetric: its own approval posture (`approval_policy` in `~/.codex/config.toml`) is a single operator-owned setting codex itself consults, not a per-command hook zirv can answer. Headless codex is already prompt-free (`--ask-for-approval never` on every headless launch, above). Interactive codex under an `untrusted` posture gets the honest substitute instead of a fabricated enforcement layer: a one-time `zirv ▸` advisory naming the `approval_policy` fix (`adapters::codex::codex_approval_advisory`, emitted by `wrap::run_with` — see [[Ctx Adapters]]), never a config rewrite. Item #230 item 3's degraded-capability warnings (below) are the general-purpose version of the same "tell the operator honestly, don't pretend to enforce" instinct, applied to every capability rather than just approval.

**Prompt-injection/credential screening is a separate, orthogonal layer from this policy model (issue #243, v3.5.0).** `screen.rs`'s pure `screen(text) -> ScreenReport` flags prompt-injection marker phrases, credential shapes, and high-entropy runs in text reaching a session — mail, repo `system-prompt.md`/`.zirv/context/*.md`/shared `.zirv/memory/`, and transcript ingestion. It never blocks or narrows anything the way `[safety]`/`[policy]` do; it only extends an existing trust/label line with a flag summary. See [[Untrusted Configuration]]'s `screen.rs` subsection for the full surface list and [[Ctx Subsystem]] for the mail/status wiring.

## Permission audit (`permissions.rs`, issue #132, 2026-08-25)

Approving a command is not the same as the approval being *reusable*: issue #132's production evidence found a Codex session generating 33 escalated requests in one sitting, many of them saved as one-off literal-command approvals (a whole `gh issue create --body "..."` including the issue text) or as approvals of only a downstream `jq` expression rather than the read-only API query that actually needed the sandbox boundary lifted. `zirv ctx permissions audit --agent <codex|claude> --sessions <N> [--json]` is the transcript-backed audit this gap asked for: it groups every escalated/denied request by a normalized command **family** and reports whether the family's saved approval would plausibly match the *next* equivalent invocation.

**Audit scoping (issue #320, v3.15.0): no longer implicitly machine-wide.** `--session <id-or-prefix>` (conflicts with `--all-repos`) scopes to one session's own transcript plus its `subagents/` siblings (`session_transcripts`, walking the whole transcripts root since a session id already names an exact scope). Otherwise the default is one claude project directory — `resolve_scope_dirs` joins the transcripts root with `claude_project_dir_name(cwd or --repo)`, the same non-alphanumeric-to-`-` encoding Claude Code's own project directories use — and `--all-repos` restores the old machine-wide walk; codex has no per-project transcript directory at all, so a codex audit stays machine-wide regardless of these flags. The report gained a `## Sampled transcripts` section (`render_sources_section`) naming each sampled session's own source project directory, so a `--all-repos`/codex run that spans many projects is visible at a glance rather than assumed to be the operator's own current repo.

- **Codex extractor**: `response_item`/`custom_tool_call` records named `exec` under `~/.codex/sessions/**/*.jsonl` whose payload carries `sandbox_permissions: "require_escalated"` (the shape documented in issue #132's own reproduction section — `command` may be a string or a `["bash","-lc","..."]` array, and either may sit directly on the payload or inside a JSON-encoded `input` string).
- **Claude extractor**: a headless (`--permission-mode dontAsk`) `PreToolUse` denial under `~/.claude/projects/<slug>/*.jsonl`, grounded in real session files (never guessed): an assistant `tool_use` entry (`{"message":{"content":[{"type":"tool_use","id":..,"name":..,"input":{...}}]}}`) correlated by `id`/`tool_use_id` with a later `tool_result` entry carrying `"is_error":true` and text starting `"Permission to use <Tool> has been denied because Claude Code is running in don't ask mode."`. Every `PermissionRequest` also carries `permission_mode: String`/`is_sidechain: bool` (2026-08-26, issue #147), read straight off the transcript's own `{"type":"permission-mode","permissionMode":"..."}` event line and `isSidechain` field, not inferred.

**Correlated against zirv's own safety-decision log, not just transcript denial text (issue #147, 2026-08-26).** `extract_claude_requests` now takes a third argument, `log_records: &[SafetyDecisionRecord]` (`log::read_safety_decisions`, reading every day-bucketed `<state>/logs/safety-decisions/*.jsonl` file, read once per `audit_report` call and passed in — the function itself stays a pure fold over its two inputs). `correlate_safety_decision` joins a candidate command against that log on `session` + `command_sha256` (the identical hash the hook itself computed) + closest timestamp within `CORRELATION_WINDOW_SECS`, a match outside the window counting as no match. For an ordinary Bash/PowerShell `dontAsk` denial, the correlated record's own `verdict`/`matched_pattern` now name the real cause instead of a guess: `"headless dontAsk denial (sandbox-escape retry not escape_allow-cleared)"` for a denied `<sandbox: unsandboxed retry>`, `"headless dontAsk denial (zirv safety hook: <pattern>)"` for any other matched deny rule, and a distinct wording when a correlation exists but disagrees on verdict (a config change mid-session) or none exists at all (falls back to the old generic `"permission-mode dontAsk denial"` wording, degrading gracefully rather than failing the audit — `a_correlation_outside_the_time_window_falls_back_to_the_generic_cause`). A denial from a non-Bash/PowerShell tool is now labeled `"native denial (tool outside zirv's safety-hook scope: Bash/PowerShell only)"` rather than implying zirv's hook caused it.

It also now surfaces a case the text-only heuristic missed entirely: a second pass over every recorded `dangerouslyDisableSandbox` tool use (not the transcript again) correlates each against the log, and when the hook logged `ask`/`<sandbox: unsandboxed retry>` for it — an **interactive sandbox-escape ask**, which unlike a `deny` never produces an errored `tool_result` on its own — reports a new request: `cause: "interactive sandbox-escape ask"`, `result` one of `escalated-accepted`/`escalated-denied`/`escalated-pending` depending on whether/how that tool use's own `tool_result` later resolved. A silently-allowed escape (matched `<sandbox: escape_allow>` or the `gh` carve-out) still produces no request at all (`a_silently_allowed_sandbox_escape_produces_no_request`). `AuditReport` gained a `requests: Vec<PermissionRequest>` field (the ungrouped list `groups` is folded from) — `run_compile --escape`'s eligibility pass needs each request's own `cause`/`result`, which a `FamilyGroup` alone does not carry.

**A second, Read/Edit-shaped half of the audit reads `permission-prompts.jsonl` directly (issue #321/#307, v3.15.0), after the Bash-family groups above.** The pre-existing `zirv ctx hook permission` observer (registered on claude's `PermissionRequest`/`PermissionDenied` events) durably records every prompt to `<state>/logs/permission-prompts.jsonl` as `{ts, session, event, tool, family, command_sha256?, cwd, permission_mode, reason?}` — `family` is a Read/Edit/Write/MultiEdit/NotebookEdit call's parent directory, or a Bash/PowerShell call's `program subcommand`, with the full command kept only as a sha256, never in clear. `log::read_permission_prompts` (an owned, deserializable `PermissionPromptRecord` mirroring that row shape, added this batch) reads the file for the audited sessions (or every record machine-wide under `--all-repos`) and `ToolPromptReport::from_records` renders a `## Permission-prompt log (permission-prompts.jsonl)` section: a one-line `Bash/PowerShell: N PermissionRequest, M PermissionDenied` count (Bash/PowerShell prompts are counted per event only — the transcript-derived family groups above already cover them, so they are never re-grouped here), then every OTHER tool in `DIRECTORY_FAMILY_TOOLS` (`Read`/`Edit`/`Write`/`MultiEdit`/`NotebookEdit` — a `WebFetch` row's `family` is a URL host and every other tool's is its own name, neither of which is a directory) grouped by tool into `ToolTargetGroup { tool, count, directory, recommendation }` — `directory` is the shortest path prefix shared by every observed target in the group (`shortest_common_ancestor`, compared component-wise, rendered `~`-relative under the home directory or `//`-prefixed otherwise) — each carrying the recommendation `add this directory to permissions.additionalDirectories or [sandbox] extra_allow`.

Both extractors normalize through the SAME wrapper-unwrapping helpers `safety.rs` uses for classification (`pipeline_stages`, `unwrap_env_prefix`, `unwrap_shell_wrapper`, `strip_program_dir`, `sql_program_name` — all widened from private to `pub(crate)` for this reuse, no behavior change to `evaluate` itself), so `env -u FOO zirv setup apply --repo .` and the bare `zirv setup apply --repo .` collapse to the identical family instead of two separate one-offs. `unwrap_env_prefix` (2026-08-25 review round) also consumes `env -C DIR`/`--chdir DIR`/`--chdir=DIR`'s directory argument the same two-token way it already consumed `-u VAR`, and bails out (`None`) entirely on `-S`/`--split-string` — that flag re-splits its own argument by shell quoting rules into the real argv, so the simple "one flag, then a value or the command" walk cannot safely unwrap past it without risking a misparse; this changes live `evaluate()` behavior too, not just `permissions.rs`'s grouping. `family_of` then keeps the program name plus a per-program depth of leading non-flag tokens (`zirv` keeps 3 — `zirv setup apply`; `git`/`gh`/`cargo`/`npm`/`docker`/`kubectl`/`npx`/`pnpm`/`yarn` keep 2; everything else keeps just the program) and drops to the FIRST pipeline stage before any `|`, since a trailing `| jq ...` is a downstream formatting stage of the same request, not a different family.

A family is `reusable` only when every request folded into it is: `is_reusable` says no when the raw command's longest quoted span exceeds 80 characters (a one-off issue/PR body or commit message that will never repeat verbatim) or when the command pipes into `jq`/`grep`/`awk`/`sed` (the varying part is the filter's own argument, not the upstream command — `unwrap_wrappers`, 2026-08-25 review, peels an `env`/shell wrapper off the *last pipe stage too* before this check, so `... | env NO_COLOR=1 jq .` is still recognised as a `jq` target). A non-Bash claude tool (`Read`, `Write`, ...) has no command-shaped payload to judge, so it defaults reusable — granting the *tool*, not one invocation of it, is what a policy change there would mean.

**Reusability alone never drives the recommendation (2026-08-25 review, `is_protected_family`).** `git push --force origin main` is `reusable` by `is_reusable`'s own definition — no long literal, no filter pipe — which is exactly why a second, independent gate is needed: issue #132 requires that destructive git (force-push/-delete, hard reset, force clean/branch-delete, rebase/filter-branch, a tag push), publish/release actions (`cargo publish`/`install`, `npm publish`, `gh release`), credential/secret surfaces (`gh auth`, `git credential`, `ssh-keygen`, `security`, any command token matching `token`/`keychain`/`keyring`), global installs (`choco`, `winget`, `npm install -g`) and writes into a global install path (`Program Files`, `/usr/local/`, `/usr/bin/`, `/usr/sbin/`, `C:\Windows\`) stay recommended `ask`, never a standing allow, regardless of reusability. `is_protected_family(family, sample)` classifies on the actual command text (`family_of` strips flags, so `git push --force origin main` and `git push origin feature` share one family and only the sample text tells them apart); `group_requests` protects a whole family if ANY member's raw command classifies as protected, so a family that only sometimes looks destructive can't hide behind its first-observed routine member. `recommendation_for` returns a distinct "protected family" message instead of "Grant a standing allow" whenever `is_protected_family` is true, overriding an otherwise-reusable verdict.

**Surfacing a conflicting native claude rule (issue #147, design decision 7, 2026-08-26).** A recommended or compiled zirv family can still be blocked or re-prompted by the operator's own native `~/.claude/settings.json` (or a project `.claude/settings.json`) permission rule — zirv's own fix would then look like it did nothing. `read_native_claude_rules(home, repo)` is a best-effort, READ-ONLY parse of both files (never written to; a missing/unparseable file just contributes nothing, degrading to pre-#147 behavior) into `(pattern, "deny"|"ask")` pairs with the `Bash(...)` wrapper stripped; `native_conflict` glob-matches a family's sample command against them with the identical matcher (`safety::glob_match`) claude's own rules use. `render_report`/both compile-summary writers now take a `native_rules` parameter (empty for codex, which has no native-settings analogue, and for `--json` output) and print a `WARNING: your own native claude rule Bash(<pattern>) [deny|ask] would still block or prompt on this family` line next to any group it conflicts with — informational only, never suppresses a recommendation or a write.

`optimize.rs`'s `permission_noise_findings` runs the same audit, at the same `--sessions` sample size the rest of an `optimize` report already uses, against whichever agent that run's adapter resolved to, and appends one `"permission-noise"` `Finding` (pointing at the full `zirv ctx permissions audit` invocation rather than repeating every group inline) whenever `AuditReport.total_requests` exceeds `NOISE_FINDING_THRESHOLD` (5 — chosen well below the 33-per-session count issue #132's own evidence reports, so the finding fires long before a session gets there). No adapter resolved, or an adapter name the audit does not recognize, means no finding — the same fail-quiet posture every other `optimize` findings pass already holds to.

## Not the same "environment" as a verification check's own child process (issue #233)

This page's environment-scrubbing story (`SUPERVISION_ENV`, `LAUNCH_MODE_ENV`) is about what a *supervised agent* process inherits from zirv. It is unrelated to a *`zirv verify`/`zirv test` check's own shell child* — the process a `.zirv/verify.toml` command or discovered Cargo/npm check actually runs — which used to silently inherit zirv's whole process environment (never scrubbed, so a check's own harness shell simply lacked `SSH_AUTH_SOCK` whenever an operator's actual login-session agent socket wasn't already in zirv's own launch environment). `workflow::verification::run_check` now explicitly sets a small built-in allowlist (`SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `SSH_ASKPASS`, `GPG_TTY`, `GNUPGHOME`) on every check child, extendable only by the operator (`[workflow] check_env_passthrough`, `REPO_FORBIDDEN`) — see [[Untrusted Configuration]] and [[Workflows]]'s Verification section for the full resolution order and the `REPO_FORBIDDEN` rationale.

**What `check_env_passthrough` is, and is not (clarified 2026-08-31, review round).** The check child's inheritance of zirv's own full process environment is unchanged and by design — a repo check already runs as the operator, the same trust posture `repo_checks_enabled` already grants it once it's on. `check_env_passthrough`'s allowlist is a *guarantee that the named variables are present* for the check child (falling back to a macOS `launchctl getenv` read of the login session when zirv's own process lacks one), never an isolation or scrubbing boundary — it adds names the operator wants present, it does not remove or gate anything else the child already inherits. A codex cross-review round raised a finding that this "violates the operator-only trust boundary" by widening what a repo-triggered check can read from the operator's environment; the finding was dismissed on exactly this distinction — see the 2026-08-31 [[Decision Log]] entry for issue #233.

Regression fixtures: `tests/fixtures/codex-rollout-permission-requests.jsonl` and `tests/fixtures/claude-transcript-permission-requests.jsonl` cover every command shape above (a reusable file-backed `gh issue create`, a NOT-reusable inline-body `gh issue create`, an `env`-wrapped vs. bare `zirv setup apply` pair proving they fold to one family, a `&&`-chained validation batch, a `| jq` pipe, and — claude-side — a Bash denial, a non-Bash `Read` denial, a `git push --force` denial, plus a successful run and a non-permission failure that must both be excluded).

### Compiling recommendations into approvals (`zirv ctx permissions compile`, 2026-08-25)

`audit` stays strictly read-only, by design — its own doc comment promises that, and nothing about `compile` changes it. `zirv ctx permissions compile --agent <codex|claude> --sessions <N> [--dry-run]` runs the identical audit pipeline, then WRITES every eligible family into `[safety] allow` in the operator's home `~/.zirv/ctx.toml` — the residual half of issue #132's "compile operator-owned managed policy into reusable approvals" acceptance row.

- **Eligibility** is `!protected && reusable`. `FamilyGroup` now carries a `protected: bool` field (computed in `group_requests`, same fold as `recommendation_for` already used), but `run_compile`'s own `compile_eligibility` helper never trusts that cached field alone: it re-runs `is_protected_family(&family, &sample)` independently, at write time, for every group. This is a deliberate second gate, not redundancy — a `FamilyGroup` built some other way than `group_requests`'s own fold (a hand-built value, or JSON round-tripped through some future caller) still cannot smuggle a protected family into a standing allow by lying about the cached field. A protected family is never written regardless of flags, including `--dry-run`.
- **The written pattern** is `"<family> *"`, not the bare family string — verified against `glob_match`'s own suffix semantics (issue #106: a pattern ending in `" *"` also matches its own bare prefix with the trailing `" *"` stripped, so `"gh issue *"` matches both `"gh issue"` alone and `"gh issue create --title x"`). A regression test (`a_compiled_pattern_matches_the_next_equivalent_command_under_the_resolved_policy`) compiles a group, resolves the real `[safety]` policy from the written file, and asserts a DIFFERENT command in the same family — not the literal sample — evaluates `Allow`.
- **The writer** (`setup.rs`'s `union_home_safety_allow`, beside `set_home_ctx_toml_value`) targets ONLY the home layer, never a repo path — `safety.allow` is `REPO_FORBIDDEN` precisely so a repo layer could not do this to itself even if it tried. It UNIONS new patterns into the existing `[safety] allow` array (`union_allow_patterns`, a pure case-sensitive-exact-string dedupe against what's already saved and against the same batch), never removing or reordering an existing entry, and creates the table/key if absent. Before rewriting, it copies the pre-write file to `ctx.toml.bak`, best effort. Comments in the file are lost on rewrite — the same accepted trade-off every `set_home_ctx_toml_*` writer already makes (`toml::Table` round-trips values, not source text) — so `run_compile` prints a one-line warning about both the comment loss and the `.bak` whenever it actually writes.
- **Output** lists patterns added, families skipped as protected, and patterns skipped as duplicates, plus a fixed note: "takes effect for new sessions; running sessions will show 'policy snapshot stale' in `zirv ctx status` until relaunched" (the mechanism issue #139 added — see [[Ctx Subsystem]]). `--dry-run` computes and prints the identical summary without calling the writer at all.

### The `--escape` flag: compiling sandbox-escape asks too (issue #147, design decision 6, 2026-08-26)

`--agent claude` only (codex has no sandbox-escape-retry concept, so `escape_eligibility` always returns empty for it). `CompileArgs.escape: bool` (default `false`) controls a SECOND, independent compile pass over the same audit's `requests`, filtered to `cause == "interactive sandbox-escape ask"` (`escape_ask_groups`) and re-grouped by family:

- **Eligibility** (`escape_eligibility`) reuses `is_family_too_generic`/`is_protected_family` exactly like the `allow` pass above (no `reusable` check here, unlike the `allow` pass), plus a family-specific gate: the family is skipped, worst-member-wins, the moment ANY single observed invocation in it fails `safety::command_fails_escape_screen` — i.e. would itself be denied outright by the credential/root-scan screen or an ordinary built-in/operator `deny` rule.
- **Without `--escape`**, eligible families are only PRINTED, under a `# Sandbox-escape compile (preview only -- pass --escape to write to [safety] escape_allow)` heading and `would_add` (mirroring `[safety] allow`'s own preview-vs-write split above) — nothing is written, regardless of `--dry-run`.
- **With `--escape`** (and not `--dry-run`), eligible families are additionally written to `[safety] escape_allow` in the operator's home `~/.zirv/ctx.toml`, via the new `setup.rs` sibling writer/reader pair `union_home_safety_escape_allow`/`read_home_safety_escape_allow` (both a thin `key` parameter over the same shared `union_home_safety_key`/`read_home_safety_key` bodies `allow`'s own writer/reader now delegate to — no logic duplicated, same union/backup/comment-loss contract as `[safety] allow`'s writer).
- `run_compile_escape_previews_without_the_flag_and_writes_with_it` is the end-to-end regression: an accepted, recurring sandbox-escape ask prints as a recommendation without `--escape` and is actually written to `[safety] escape_allow` with it.

## Approved-prompt review and safe-list proposals (`zirv ctx permissions propose`, issue #178, 2026-08-28)

`audit`/`compile` above classify what got ESCALATED or DENIED; `propose` classifies the opposite: prompts the operator explicitly APPROVED, looking for the subset that was so clearly safe it should never have prompted at all. It never touches `[safety] allow`/`escape_allow` — the output is a GitHub issue proposing a pattern be marked safe, not a written approval.

**Capture, not a live-event pipeline.** Approval is inferred post-hoc, transcript-side, the same "correlated with subsequent execution" way for both agents, but by different mechanisms since only claude carries zirv's own hook verdict:

- **Claude** (`extract_claude_approvals`): every Bash/PowerShell command whose `correlate_safety_decision`-joined safety-decision-log record says `verdict == "ask"` AND whose own transcript `tool_result` later arrived WITHOUT an error — the operator said yes, and the command actually ran. A still-pending ask (no `tool_result` yet) or one that resolved as an error is not a completed approval. This generalizes the existing sandbox-escape-only correlation `extract_claude_requests`'s own second pass performs (issue #147, design decision 5) to every ordinary `ask` verdict, not only a `--dangerously-disable-sandbox` retry — same `correlate_safety_decision` primitive, wider filter. A standalone walk, not a refactor of `extract_claude_requests`'s own loop: that loop's denial-detection branch is separately reviewed, tested behavior this capture concern does not need to touch.
- **Codex** (`extract_codex_approvals`): codex's own transcript never records the operator's answer to an escalation (this module's top-of-file doc comment), so approval is inferred from a `custom_tool_call_output` record sharing the same `call_id` as an escalated `custom_tool_call`, appearing later in the file — grounded against `tests/fixtures/codex-rollout-permission-requests.jsonl`'s own `call_1`/`ctco_1` pair, the only escalation in that fixture with a matching output.

**Classify immediately, then discard the raw text.** `record_from_capture` runs the classifier (`is_irrelevant_approval`) while the raw command is still in memory, then builds an `ApprovalRecord` that never carries it — only `family` (`family_of`), an optional exact `verb` (`"gh pr create"`, only for a `gh`/`glab` collaboration command), a coarse `cwd_scope` (`"home"`/`"repo"`/`"unknown"`, derived from the transcript's own `cwd` field compared to the local `$HOME`, never a literal path), and the boolean `irrelevant` verdict. This is the global "never persist a developer path/one-off spelling" constraint made structural: the type that reaches `<state>/approvals/*.jsonl` (day-bucketed, same pattern as `logs/safety-decisions/`, via the new `StateDir::approvals()` accessor) cannot violate it, because it has no field to violate it with.

**The classifier (`is_irrelevant_approval`) is conservative by construction**, requiring every one of:

1. `is_safe_collaboration_verb` — the exact `(program, resource, verb)` triple ([`collaboration_triple`], NOT `family_of`'s coarser two-token family — `family_of("gh pr create ...")` and `family_of("gh pr merge ...")` both collapse to `"gh pr"`, and merge must never be conflated with create by a coarser check) matches one of a fixed `SAFE_COLLABORATION_VERBS` allow-list: `gh pr create/edit/comment`, `gh issue create/edit/comment`, `glab mr create/update/note`, `glab issue create/update/note` — the exact CLI-verb-level scope issue #178's own acceptance criterion 6 names. Merge, close/reopen, delete, release, auth, arbitrary `gh api`/`glab api`, and everything else is simply absent from the list, so it is never eligible by construction, not by a separate deny check.
2. `has_shell_composition_or_redirect` returns `false` — no pipe (any but the first `pipeline_stages` stage), `;`, `&`/`&&`, backtick, `$(...)`, or `>`/`>>`/`<` outside a SINGLE-quoted span. Double quotes do NOT neutralize command substitution in any POSIX shell, so a backtick/`$(...)` inside a double-quoted argument (`gh pr comment 12 --body "$(cat ~/.ssh/id_rsa)"`) still disqualifies — a regression this module's own tests pin explicitly, since an earlier draft of this scanner skipped that check while "inside quotes."
3. `is_protected_family` (reused unchanged from `audit`/`compile` above) says no — defense in depth, also catching a credential-bearing argument via its own `has("token"=...")`/`has("keychain")`/`has("keyring")` checks (exact-token or `key=value`-joined, not free prose containing the word).
4. `command_fails_escape_screen` (reused unchanged from the sandbox-escape gate above) says no.

Any single failure means "warranted" (keep prompting), never "irrelevant" — issue #178's own conservatism requirement.

**Persistence is idempotent, not append-only.** `run_propose_with` reads the existing store (`read_approvals`), builds a `(session, family)` seen-set from it, and only appends a newly captured approval whose `(session, family)` pair is not already recorded — so re-running `propose` over an overlapping transcript window never grows the store unboundedly.

**Escalation, deduplicated.** `group_proposal_evidence` folds every `irrelevant == true` record (never a warranted one) by family into a `ProposalEvidence` (family, deduped sorted verbs, approval count, distinct session count, deduped sorted agents — every field already portable). For each family: `find_open_issue_by_title(token, "safe-list-proposal", title)` (a new `report.rs` helper beside `create_issue`, an exact-title match over `GET .../issues?labels=safe-list-proposal&state=open`, never a substring/search-index match) either finds an existing open proposal and `add_issue_comment`s the new evidence onto it, or `create_issue`s a fresh one carrying the `safe-list-proposal` label — the dedicated label design ruling, keeping `bug`/`enhancement` untouched. The dedup key is the plain `family_of` string (`"gh pr"`), not the finer verb — deliberately: only SAFE verbs ever reach this stage at all (classification already filtered out merge/close/etc.), so one proposal issue per family, evidenced by which verbs were actually observed, is the right grain.

**Disabled by default, and structurally not repo-enable-able.** `run_propose` gates on `crate::settings::operator_propose_enabled(home)` before doing ANY capture/classify/escalate work — a function that mirrors `operator_github_token` exactly: it reads only the path it is handed, and every call site hands it the OPERATOR's own home directory, never a repository's. `PermissionsSettings.propose_enabled` (in `.settings.toml`'s `[permissions]` table, `settings.rs`) defaults `false`. This is a distinct trust mechanism from `ctx.toml`'s `REPO_FORBIDDEN` table (used by `[safety] allow`/`escape_allow` above) — no `ctx.toml` key was added for this at all; a repository `.settings.toml` `[permissions] propose_enabled = true` is not merely rejected, it is never even read for this decision, the "structurally unable" property issue #178 requires (`a_repository_settings_file_cannot_enable_propose` pins this directly: the same file, read as if it were the repo layer, says `true`; read via the actual operator-only call site, it has no effect at all).

**Review round 2 (2026-08-28, `9570d41`): no re-commenting unchanged proposals, and guidance for excluded families.** `run_propose_with` now persists a per-family `ReportedEvidence` watermark (`<state>/approvals/reported.json`, keyed by family) recording what was last reported; a repeat run with no NEW approvals/sessions/verbs for a family is a no-op — zero HTTP calls, no duplicate comment. When there IS new evidence against an already-open issue, `proposal_body` adds an explicit delta section ("N new approved occurrence(s) across M new distinct session(s)...") instead of silently repeating the running total. Separately, `is_irrelevant_approval`'s boolean collapsed too much: `classify_approval` now returns `ApprovalClassification::Eligible` / `Excluded(ExclusionReason)` / `OutOfScope` (not a `gh`/`glab` command at all — outside `propose`'s documented scope, no guidance owed) — every in-scope but excluded command (`Protected`, `TooGeneric`, `OneOffSpelling`, `ShellComposition`) now prints one concise, portable guidance line pointing at a non-escalating alternative (`render_excluded_guidance`), always, even when nothing else is eligible that run, closing the release plan's own "never silently drop it" constraint. A bug found while implementing the watermark: `family_depth` never listed `"glab"`, so every glab invocation collapsed to the single-token family `"glab"` and the new too-generic gate wrongly excluded every `glab mr`/`glab issue` collaboration command even though `collaboration_triple` already established exact specificity independently — fixed by adding `"glab"` alongside `"gh"` at depth 2.

**Fix (2026-08-28, `affb399`): `glab api` closed the same gap `gh api` was already protected against.** Giving `glab` a two-token family depth (the fix directly above) made `"glab api"` a reachable family for the first time, but `is_protected_family` had no protection arm for it — a mutating `glab api -X DELETE`/`POST` call could fall through to the catch-all `_ => false` and be auto-written into `[safety] allow` by `zirv ctx permissions compile`, contradicting the release plan's own "arbitrary API calls stay gated" constraint. `gh_api_call_is_mutating` is generalized to `api_call_is_mutating` (both tools share the same `--method`/`-X`/`-f`/`--field`/`--input` interface) and `is_protected_family` gained a `"gh api" | "glab api"` match arm calling it, closing both `audit`/`compile`'s recommendation surface and `propose`'s classifier at once (both call `is_protected_family`).

**GitHub helpers, DI-tested like the rest.** `report.rs`'s `create_issue`/`resolve_token`/`IssueRequest`/`gh_auth_token` are now `pub(crate)` (were module-private, issue #176 predates this reuse) so `permissions.rs` can call them directly; `find_open_issue_by_title`/`add_issue_comment` are new siblings in the same file, same `ureq`/token-header shape as `create_issue`. `run_propose_with`'s `ProposeIo` struct bundles the injected closures (`env`, `cli_token`, `find_issue`, `create_issue`, `comment_issue`) as OWNED `Box<dyn Fn>` rather than borrowed `&dyn Fn` — a test's own recording closures need to outlive the helper that builds the struct and be inspected afterward, which a borrowed reference cannot do without a temporary-lifetime error; `propose` is an operator-invoked, infrequent command, so the allocation is not a concern. The test suite never touches a real credential or the network, matching `report.rs`'s own module-doc promise.
