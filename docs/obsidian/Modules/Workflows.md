# Workflows

## Quick Reference

- **Files:** `src/commands/workflow/{mod,skill,capability,classify,engine,verification,review,artifact,telemetry,adoption,frontend,frontend_detector,frontend_render}.rs`
- **Commands:** `zirv skill`, `zirv workflow`, `zirv test`, `zirv verify`, `zirv artifact`, `zirv frontend`
- **State:** private platform state under `workflows/`, `verification/`, `artifacts/`, `workflow-telemetry/`, `adoption/` (issue #223, one `AdoptionRecord` per session — see [[Ctx Subsystem]]), and `frontend/`, each repository-scoped by the existing deterministic repo slug; accepted SDLC work products live in git under `.zirv/work/<workflow-id>/`
- **Repository inputs:** `.zirv/skills/*.yaml|yml|toml` and optional `.zirv/verify.toml` — both untrusted, and both gated by an operator-only `[workflow]` config key
- **Operator config:** `[workflow]` in `ctx.toml` — `repo_checks_enabled`, `repo_skills_enabled`, `telemetry_enabled`, `telemetry_max_events`, `telemetry_retention_days`, `adoption` (issue #223), every one `REPO_FORBIDDEN`
- **If changed:** [[Built-in Commands]], [[Architecture Overview]], [[Ctx Subsystem]] (the hook/agent delivery side of `adoption`), [[Usage and Pacing]] (cache-hit telemetry), [[Utilities]] when prompt-layer behavior changes, and [[Untrusted Configuration]] when trust/capability rules change

## Purpose

The workflow subsystem makes Zirv own the development lifecycle instead of asking every model to reconstruct a methodology in conversation. Skills describe concise judgment. Zirv owns deterministic mechanics, phase state, risk selection, verification, review limits, artifacts, and telemetry. The AI-native SDLC chain is a version-controlled work-product surface: adaptive workflows create `intent.md`, `spec.md`, and `plan.md` only when classification requires them, while private workflow state retains the acceptance authority.

Workflow state and skill context are deliberately different:

- durable state records completed/current steps, attempts, approvals, classification, and review findings outside model conversation context;
- the session prompt receives only the active step's resolved skill stack;
- moving to the next phase replaces the workflow prompt layer, so completed skills never accumulate after compaction or resume.

The shared Context Compiler consumes `engine::active_skill_context`/`render_current_context`, so every Zirv launch path receives the same active workflow layer without changing workflow state or skill manifests — but only the Orchestrator role does (issue #253, v3.8.0): a `zirv agent`-dispatched Worker/SubOrchestrator never composes this layer at all, so it can't hijack a dispatched brief with whatever step happens to be active in the repo. See [[Ctx Subsystem]]'s Context Compiler section.

## Skills

`SkillManifest` schema version 1 includes a stable id/version, triggers, applicable phases, required/optional logical capabilities, context budget, dependencies, and an instruction body. General built-ins are embedded in the binary: `brainstorm`, `design`, `write-plan`, `plan`, `worktree`, `implement`, `execute-plan`, `systematic-debugging`, `testing`, `tdd`, `review`, `verify`, `delegate`, `parallelize`, and `finish-branch`. Frontend work adds the built-in, repository-non-overridable `frontend-craft` floor and phase skills `frontend-{design,plan,implement,debug,test,review,verify}`. Every phase stack resolves the craft floor and its corresponding general engineering skill before the phase-specific frontend instructions.

The process-parity layer stays adapter-neutral. `write-plan` owns the durable plan format; the existing `plan` skill depends on it. Substantial implementation steps compose `execute-plan`, whose dependency stack adds `worktree` isolation plus the normal implementation discipline; trivial work does not pay that context or capability cost. `execute-plan` treats the plan ledger as resume state and verifies before ticking tasks. `finish-branch` is the Deploy-phase methodology behind structural deploy-tier gates. Development auto-advances the deploy step once evidence passes; Staging requires explicit deploy approval; Production requires approval plus at least one fresh independent `reviewer`-seat run and fresh final `zirv verify` evidence. Existing TDD/debug/delegate/parallelize/review/verify guidance was tightened around falsifiable evidence, independent review, worker result validation, and no completion claims from stale evidence.

**The `review` skill and `reviewer` agent require a concrete failure scenario per finding (wrapper behaviour redesign round 2, 2026-09-01 — `docs/superpowers/specs/2026-09-01-wrapper-behaviour-redesign.md`).** Every reported finding must name a concrete failure scenario — an input or state and the wrong result it produces — at a location the reviewer actually read; "no finding is better than a weak one," so style preferences, speculation, and restatements of the diff are omitted rather than reported. Findings scale with the change: a trivial diff usually has none. `skill.rs`'s built-in `review` manifest and `agents.rs`'s built-in `reviewer` manifest carry the identical rule (mirrored text, not a shared constant), closing a gap the round-1 audit found: review passes had no floor on finding quality, so a weak or speculative finding cost as much fix/re-review cycling as a real one. **`frontend-craft`/`frontend-review`/`frontend-verify` now scale their rubric by tier the same round:** `frontend-craft` opens with a proportionality note — a trivial fix only needs to match existing patterns and verify the states it touches, and the rest of the skill's floor is for new or substantially reworked UI. `frontend-review`'s thirteen-dimension scoring rubric (product-specificity, user-journey, hierarchy, system-coherence, typography, color-contrast, layout-rhythm, interaction-affordance, state-completeness, responsive-composition, accessibility, content-clarity, resilience) is scored in full only for substantial or new UI work; a trivial or bounded change is scored only on the dimensions it actually touches. `frontend-verify` mirrors the same scaling when it re-confirms every dimension the review scored ≥4.

Registry precedence is deterministic and asymmetric: an operator-global manifest (`~/.zirv/skills`) may replace a built-in, because the operator is trusted; a repository manifest (`.zirv/skills`) may only **add** an id it does not already occupy. A repository id that collides with a built-in or operator-global skill is ignored, and the collision is reported as a warning naming both sides (`SkillRegistry::warnings`, printed by `zirv skill list/show`) rather than silently replacing trusted methodology text. `zirv skill list/show --built-in-only` disables both custom layers; `zirv workflow start --built-in-only` persists that trust choice in the workflow state, so resume and prompt rendering cannot silently re-enable an override; and the operator-only `workflow.repo_skills_enabled` (`REPO_FORBIDDEN`, see [[Untrusted Configuration]]) drops the repository layer entirely. Both gates (`workflow::repo_gates`) fail **closed** on a genuine config load failure — an unreadable file, or a `REPO_FORBIDDEN` key a repo file tried to set, which still fails `CtxConfig::load` outright — disabling repo-provided skills *and* repo-provided checks and saying so on the `zirv ▸` channel. Since `repo_checks_enabled`/`repo_skills_enabled` are themselves `REPO_FORBIDDEN`, a repo layer could never set either one to begin with; a repo `ctx.toml` that merely fails to *parse* (a stray keystroke, not a forbidden key) no longer collapses the whole load into an error either, so it neither widens nor narrows these two gates — see [[Untrusted Configuration]] for the parse-vs-reject distinction. Files, directory entry counts, individual instructions, and dependency-resolved stacks are bounded; unknown schema fields/versions fail; symlinked manifests or parent directories and path escapes are refused; dependency cycles/missing dependencies fail before resolution.

A repository manifest that will not load takes the workflow prompt layer with it — composition still succeeds, and the loss is announced once on the `zirv ▸` channel (`Event::WorkflowLayerSkipped`) instead of disappearing silently.

## Agent registry

Workflow seats are provider-neutral data, not harness plugins. `AgentManifest` schema version 1 carries a stable id/version, role label, model-tier hint, read-only floor, capability requirements, bounded instruction body, and context budget. Built-ins are `implementer`, `reviewer`, `doc-keeper`, `security-scanner`, and `explorer`; `.claude/agents/vault-keeper.md` has been migrated to `.zirv/agents/vault-keeper.yaml`.

Layering intentionally mirrors skills but is stricter by default. Operator-global `~/.zirv/agents/*.{yaml,yml,toml}` may replace built-ins. Repository `.zirv/agents/*` is disabled unless the operator enables `workflow.repo_agents_enabled`, and when enabled may only add non-colliding ids; collisions with trusted ids are ignored with warnings. A repository seat therefore cannot rewrite `reviewer`, remove its read-only floor, or acquire authority from its manifest text.

`WorkflowStep.agent` addresses a seat by id. Implement/debug steps use `implementer`; independent review uses `reviewer`. `zirv workflow agents list|show` exposes the resolved registry and provenance, while `zirv workflow agents dispatch <id> --adapter <name> --prompt <task>` resolves that same seat and launches it through `AgentAdapter::dispatch_agent`; required capabilities are re-checked against effective policy and read-only pins are appended by the adapter. Capability preflight runs the seat through the same canonical effective policy as skills. Adapter dispatch adds provider-specific launch mechanics only after policy resolution, and a read-only seat appends the adapter's hard read-only arguments last. `model_tier` is a routing hint; Zirv does not invent provider model ids from it.

Repository skills are untrusted methodology. A manifest can request `repo.write`, `shell.exec`, or another logical capability, but it cannot grant one. `CapabilityReport::for_repo` loads the same effective canonical policy as an AI launch, maps logical workflow prerequisites onto it, and only narrows adapter support; it never promotes an unsupported operation. `zirv workflow start --agent <name>` and inherited supervised-session adapters resolve every selected step's required capabilities before persisting the workflow. `zirv skill show --agent` and `zirv frontend capabilities --agent --repo` expose the same policy-aware diagnostics.

## Capability vocabulary

Stable logical ids are `shell.exec`, `repo.read`, `repo.write`, `git.worktree`, `agent.spawn`, `test.run`, `artifact.render`, `browser.open`, and `network.access`. Reports distinguish `supported`, `degraded`, `unsupported`, and `operator-controlled`. Shell/filesystem/network access is operator-controlled for current harnesses; Zirv-owned supervision, verification, and static artifacts are reported separately.

Canonical `EffectivePolicy` authorization is production wiring, not prose: `deny` makes the mapped operation unavailable, `ask` reports it as operator-controlled, and the repository policy layer can only narrow the operator layer. Markdown skill instructions remain advisory and never claim enforcement.

## Workflow engine and classification

Schema-versioned built-in workflows are `feature`, `bugfix`, `refactor`, `spike`, and `review`. Steps declare a phase, skill, condition, approval gate, and hard attempt limit. Commands:

```text
zirv workflow list|show
zirv workflow classify --task "..."
zirv workflow start feature --task "..." [--agent claude] [--built-in-only] [--profile standard|frontend]
zirv workflow status [id]
zirv workflow context [id]
zirv workflow artifacts <id> [--json]
zirv workflow approve <id>
zirv workflow advance <id> --outcome success|failure [--accept-preexisting-findings]
zirv workflow reclassify <id> --profile standard|frontend
zirv workflow resume <id>
```

The committed artifact chain is structural rather than advisory. Artifact steps create fixed templates under `.zirv/work/<workflow-id>/`; `workflow approve` refuses an untouched template, pins the accepted SHA-256 digest and timestamp in private state, then advances the artifact step. Later steps fold only accepted, hash-matching artifacts into prompt context, under a shared byte cap and explicitly labeled as untrusted repository text. Missing or edited accepted files reopen the owning acceptance gate and invalidate later completed steps, so implementation cannot silently proceed against a plan that changed after approval. `workflow artifacts` exposes pending/accepted/drifted state without making repository text authoritative.

Adaptive defaults keep ceremony proportional: features always capture intent, add a plan for bounded work and a spec for substantial/high-risk work; trivial bugfixes retain the debug spine with no artifact ceremony, while larger bugfix/refactor work gains intent/plan gates; spikes capture intent; review-only workflows do not create planning artifacts.

**The Intent step resolves to one of two skills, chosen by `--brainstorm`/`--no-brainstorm` (issue #236, v3.5.0).** `WorkflowPhase::Intent` used to always use the provider-neutral `brainstorm` skill; it now selects between the rewritten `brainstorm` (asks the operator one clarifying question at a time, prefers multiple choice, proposes 2-3 approaches with trade-offs when viable, never self-answers, ends with a "here is what I understood" summary and waits for the operator before writing `intent.md` with the Q&A recorded under its own `## Brainstorm` section) and the new `write-intent` (carries the prior autonomous-writing text verbatim, unchanged behavior). `StartArgs::brainstorm_override()` reads `--brainstorm`/`--no-brainstorm` as an `Option<bool>`; unset, `default_brainstorm_for_kind` picks `true` for Feature/Spike and `false` for Bugfix/Refactor (Review has no Intent step). The choice is persisted as `WorkflowState.brainstorm: bool` and `zirv workflow status` prints `brainstorm: on|off` right after the risk line whenever the workflow has an Intent step at all. **Headless refusal:** `exec.rs`'s `apply_session_env` (the one choke point every headless launch/relaunch/nudge/park goes through) sets `ZIRV_CTX_HEADLESS=1` on every child it spawns; `engine::refusal_for(skill_id, headless)` is the pure decision — when the resolved skill is `brainstorm` and that variable is set, `render_current_context` substitutes a fixed refusal block telling the worker to stop and report that the workflow is waiting for an operator, instead of the Q&A skill instructions. A headless worker can never answer the brainstorm questions on the operator's own behalf.

Classification separates intent, work domain (`general` or `frontend`), complexity (`trivial`, `bounded`, `substantial`, `architectural`), and risk (`low`, `medium`, `high`, `critical`). Frontend selection is automatic from task language and changed frontend paths; there is no `--frontend` or init flag. **Task text alone can no longer select Frontend (issue #255, v3.8.0):** `infer_work_domain`'s task-language score is capped at 40, below the 45 selection threshold, so a task that only mentions "frontend" in passing (documenting a permission family, a CLI flag) stays General/Standard unless a real frontend path signal — an explicit `--path`, a measured changed-file input, or a path-boundary heuristic hit — is also present. Identical path/line/task inputs produce the same score and sorted reasons. Both tracked and untracked change surfaces contribute paths and size signals, measured against the same merge-base diff base `review` uses (`origin/main`, then `main`, then `HEAD^`), so classification and review agree on what "the change" is. Sensitive auth/security or database/schema surfaces raise a High floor; an explicit `--risk` below that floor is refused outright, and every other input can only ever be *raised* toward it:

- Declared inputs (`--path`, `--changed-lines`) no longer switch Git measurement off. Both are computed and the higher band wins — for risk *and* for complexity, since complexity selects the plan step on its own — with `declared_scope: true` recorded on the classification so a consumer can tell a stated surface from a measured one. When Git cannot be measured at all, the safety net fails safe rather than standing pat — see the `risk_measurement` bullet below.
- Classification is re-measured when a workflow advances *into* a review or verify step, and the band never drops (`engine::reclassify_at_gate`). Freezing it at `workflow start` measured an empty tree for the usual order of work — decide the plan, then write the code — so the review step was chosen before the change existed. If the new measurement requires a review or verify step the original materialization omitted, it is added; completed steps are never re-run, and no approval gate appears retroactively.
- `Classification.risk_measurement` (`RiskMeasurement::Measured` or `Unavailable { reason }`) makes the Git-based safety net's own success or failure an explicit, inspectable state rather than silence. When Git cannot be measured at all — no repository, or one with no commits — both the declared-scope path (`classify::from_args`) and the reclassify-at-gate path (`engine::reclassify_at_gate`) call `classify::mark_unavailable`, which escalates the risk band one step (`Critical` has nowhere further to go) instead of leaving whatever band was declared or previously measured standing unchallenged. An escalation at a gate also adds any Review/Verify step the raised band newly requires, through the same step-materialization path a successful measured increase uses. `risk_measurement` is part of `Classification`, so it is carried into `workflow status` (both text and JSON) and the review package without any separate plumbing. No behavior change when measurement succeeds. See [[Decision Log]].

Low-risk work omits design/reviewer ceremony; substantial or high-risk feature/refactor work keeps an approval-gated design step, and medium/high risk adds the explicit review depth defined by `review::depth_for_risk`.

The frontend profile overlays those same durable workflows rather than creating a parallel engine. Design/plan/implement/debug/test/review/verify steps select their frontend phase skill; frontend design does not pause for a theme vote or initialization approval. Existing risk-based independent code review and all permission policy still apply.

**An operator can force a workflow's profile instead of trusting classification (issue #255, v3.8.0).** `zirv workflow start --profile <standard|frontend>` applies the forced profile after classification has already materialized the default step list, and the new `zirv workflow reclassify <id> --profile <standard|frontend>` forces a *persisted* workflow's profile in place — the recovery path for a workflow already misclassified, which previously could only be fixed by abandoning it. Both call `WorkflowState::set_profile`, which relabels each not-yet-completed step's skill via the now-bidirectional `apply_profile` (Frontend selects `frontend-*` skills, Standard restores the plain ones) and marks `profile_source: OperatorOverride` — `zirv workflow status` prints `profile: <P> (classified|operator override)` accordingly. A profile change never adds, removes, or reorders steps, so `reclassify` preserves completed steps and already-accepted artifacts untouched; `sync_artifact_records` keeps the artifact map consistent with the (unchanged) step list, and the workflow's status recomputes from its current step rather than resetting.

State files are atomic private JSON. The `active` pointer names one running/approval-pending workflow. Completion/failure clears it, so a later session cannot redispatch finished work. A failed step stops after three attempts.

**`WorkflowStatus::Closed` and `zirv workflow close <id> [--reason]` give a stuck workflow an explicit exit (harness iteration round 2, 2026-09-02).** A workflow whose review/fix loop hits `MAX_FIX_REVIEW_ROUNDS` (review.rs) has no path to `Completed` and previously stayed `Running` forever — still reported as this repository's active workflow by `load_active`/`status`/`context`. `Closed` replaces the never-constructed `Cancelled` variant as a third terminal status alongside `Failed`/`Completed`. `close` refuses (fail closed) while any review finding is still `Open` — residual dispositions must be recorded first via `workflow review dispose` — or while the workflow is `AwaitingApproval`, since approval is itself a pending decision on the current step; otherwise it sets `status: Closed`, records `closed_reason`/`closed_at`, and persists with `active: false`. This is a deliberate operator/orchestrator action, never an automatic transition the engine triggers on its own at the review cap. Fixed alongside it: `resume` used to call `refresh_deploy_tier` — which unconditionally recomputes `status` from the current step's position — before checking whether the loaded status was already terminal, so a `Closed` or `Failed` workflow's status got silently overwritten back to `Running`/`AwaitingApproval` and then allowed to resume; the terminal check now runs first, against the as-loaded status.

**A read-only summary accessor for external readers (issue #209, v2.39.0).** `active_workflow_summary(state, repo) -> Option<ActiveWorkflowSummary>` (`kind`, current `step`, `awaiting_approval`) makes `engine::load_active`'s same active-workflow pointer/state read available to a caller that only needs enough to show a session's workflow position, without exposing `engine::WorkflowState` wholesale (artifacts, review findings, classification, attempt counts). Built for the dashboard's new footer signal row (see [[Ctx Supervisors]]'s "The dashboard header, sidebar and footer"), which calls it once per `FactsCache` throttle tick, keyed to the dashboard's own repo — no subprocess, no scan, the same cost as the plain file reads `zirv workflow status` already makes. `None` covers "no active workflow for this repo" and "failed to load" alike (a torn write, an unsupported schema version left by an older binary); a caller has no way to tell the two apart from this accessor, deliberately, since surfacing a parse error where a caller expects a status summary would be a worse failure mode than treating both as "nothing to show."

## Autonomous frontend quality

`zirv frontend` is zero-touch by construction: the ordinary workflow/task classification is the trigger, and every missing routine design decision belongs to the active AI agent. No human has to run an initializer, answer a questionnaire, create a context file, select among generated themes, start a dev server, register screenshots, or perform the visual review.

```text
zirv frontend profile [--refresh] [--json]
zirv frontend capabilities --agent claude|codex [--json]
zirv frontend check [--all] [--path <file>] [--json]
zirv frontend render [--json]
zirv frontend review [--agent <id>] [--model <id>] [--json]
zirv frontend benchmark [--json]
```

The profile scanner reads a deterministic, bounded subset of local frontend evidence (maximum 256 files, 64 KiB each, 1 MiB total), ignores dependency/build/state trees and symlinks, extracts compact type/color/geometry/motion signals, and persists only the synthesized profile plus capped evidence paths. Its fingerprint refreshes the profile automatically as the repository changes. Existing product language wins; a sparse repository gets an autonomous product-specific baseline, never a generic dashboard template. The prompt receives only the compact profile, the bounded task, and active skill stack. Quality contract v2 makes the agent classify the current surface as `persuade`, `operate`, `read`, or `experience`, then commit to the concrete subject/audience/job, product truth, design thesis, one signature, one justified risk, an anti-reference, a compact visual system, and the whole journey/state matrix. It preserves an established design world unless redesign is explicit and uses a counterfactual interchangeable-product test against generic output.

The offline detector is model- and network-free. Its 44 versioned rules report structured blocking accessibility hazards plus advisory high-signal problems across forms, content, visual craft, internationalization, media, motion, performance, responsive layout, touch, typography, and UX. Examples include missing alt/semantic controls, hostile zoom/paste/tab order, heading and live-region defects, generic actions/copy, gradient/glass/card/pill/glow monoculture, weak form and media contracts, brittle widths/safe areas/overflow masks, costly motion/layout reads, manual plurals/physical CSS properties, touch targets, and placeholder-only controls. Inputs, files, bytes, findings, and finding text are capped; symlinks and repository escapes are refused. `zirv frontend benchmark` runs 41 focused and framework-specific fixtures and fails if observed findings drift or any inventory rule loses coverage. A detector report is passing workflow evidence when it is non-truncated, matches the current change and profile fingerprints, and has no active blocking findings that the gate does not treat as accepted (see below); advisory findings remain context for the scored review rather than false-positive blockers. **A report with zero analyzed files is `not_applicable`, not missing evidence (issue #255, v3.8.0):** `analyzed_files.is_empty() && !truncated` sets `DetectorReport.not_applicable`, and `zirv frontend check`'s text/JSON output prints `frontend gate not applicable (0 frontend files in scope)` — a Frontend-profile workflow over a backend-only change can now pass its Test/Review/Verify gates instead of being structurally stuck (the old `analyzed_files.is_empty()` check in `advance_with_evidence` failed closed on exactly this shape). `latest_is_fresh_and_passing`, the freshness-cache check that decides whether the detector needs to re-run at all, still treats an empty scan as not-fresh, so an unchanged empty scope re-runs the (cheap, zero-file) detector at every gate check rather than caching the pass — a known, non-blocking residual, not yet fixed.

**The frontend gate is scoped to the since-base change set, and a full-surface scan tags what it already knew about (issue #251, v3.8.0).** `verification::changed_paths_since_base` (merge-base diff via `review::default_base`, union of the uncommitted diff and untracked-not-ignored files, existing-on-disk only) replaces `changed_paths` as the workflow-facing detector's own scope source — `changed_paths` alone goes uncommitted-only-against-HEAD blind to a frontend edit the moment an earlier workflow step commits it, which used to let a whole-repository fallback fire against a clean tree and fail the gate on unrelated pre-existing findings. The Test-phase gate (`detect_for_workflow(..., require_full_surface: false)`) now ALWAYS scans that since-base set directly — never a whole-repo fallback. Review/Verify (`require_full_surface: true`) still scan the whole repository, but every finding is tagged `DetectorFinding.preexisting` against the since-base set, and the report exposes `introduced_blocking_count()`/`preexisting_blocking_count()`/`preexisting_total_count()`. A blocking finding the current change introduced always fails the gate; a blocking finding that predates it can be accepted with `zirv workflow advance <id> --accept-preexisting-findings`, which records `WorkflowState.accepted_preexisting_findings { step, at, blocking, total }` and thereafter waives pre-existing blocking findings for the rest of that workflow (introduced findings still always fail). Without the flag, the failure message names it and the pre-existing count; `zirv workflow status` and the review package (`ReviewPackage.accepted_preexisting_findings`) both print `accepted pre-existing frontend findings: N blocking / M total at <step> (<rfc3339>)` once accepted. The repo-level waiver file (`.zirv/frontend-waivers.toml`, above) stays advisory-only — this acceptance is a separate, operator-issued, per-workflow record, not a repo-config narrowing. `collect_all` (the full-surface scan's file enumeration) now asks `git ls-files -z --cached --others --exclude-standard` when the root is a git work tree, so a `.gitignore`d build directory the hardcoded `DENIED_DIR_NAMES` deny-list never anticipated is excluded too; a non-git root falls back to the previous hand-rolled directory walk, which still applies the deny-list.

Waivers use schema-versioned TOML in the repository's `.zirv/frontend-waivers.toml` or the operator-owned `~/.zirv/frontend-waivers.toml`. Each entry requires `rule_id` and `reason`, and can narrow by an exact repository-relative `path` or `/**` prefix plus an exact evidence `value`. Applied and rejected waivers are persisted with source, config path, reason, and disposition. Repository configuration can waive advisory findings but cannot hide blocking accessibility findings; only the operator-owned file has that authority.

```toml
schema_version = 1

[[waivers]]
rule_id = "craft/gradient-text"
path = "src/marketing/**"
value = "linear-gradient"
reason = "The established campaign identity intentionally uses this treatment."
```

`zirv frontend render` performs bounded recursive discovery for plain HTML, Vite-based React/Vue/Svelte applications, Next, Astro, Nuxt, and Dioxus web targets, including packages nested in monorepositories. Plain HTML is captured directly; executable repository scripts remain behind the operator-only `workflow.repo_checks_enabled` gate. Known adapters receive direct argv loopback flags, while an unknown generic script is refused because Zirv cannot prove its binding contract. Zirv selects a free loopback port, starts and tree-cleans the process under hard timeouts, discovers up to eight static routes, and captures fixed 390×844, 768×1024, and 1440×1000 PNGs with a local Chromium-family browser. It parses each PNG and requires its actual dimensions to match the requested viewport. Browser DNS is mapped away from external hosts. Missing runners/browsers/scripts produce explicit `unavailable` evidence, not a pass; dynamic/authenticated routes are not guessed.

Zirv launches a configured agent as an isolated read-only reviewer; the caller cannot submit a verdict, scores, rubric, or findings. The bounded review package contains the task, profile, every emitted capture path and fingerprint, and detector evidence, and requires one strict JSON response. The required 1–5 rubric covers product specificity, user journey, hierarchy, system coherence, typography, color/contrast, layout rhythm, interaction affordance, state completeness, responsive composition, accessibility, content clarity, and resilience. A pass requires every score to be at least 4 and cannot contain an unresolved finding; a fail must name at least one. Review and verify steps automatically collect missing detector, render, and review evidence, then fail closed unless all evidence matches the current change and profile fingerprints and the review references the current render id. Test requires the detector; review/verify require all three. The workflow allows one batched fix pass and one confirmation review, preventing an unbounded self-polish loop.

Profiles, detector reports, render reports, captures, and visual reviews stay in private state under `frontend/<repo_slug>/`. Provenance records built-in schema versions, evidence paths/fingerprints, server argv origin, browser, capture fingerprints/dimensions, reviewer adapter/model, and render linkage. `zirv frontend capabilities` renders the same provider-neutral skill/provenance contract and logical capability matrix for Claude and Codex; permissions still come from adapter/policy resolution, never from skill text.

## Verification

`zirv test changed` maps Git-changed paths to checks; when impact is empty or cannot be mapped, it deliberately falls back to all eligible checks. `zirv test all` runs all checks and `zirv verify` runs final checks. Optional `.zirv/verify.toml` schema version 1 defines check id/kind/command/path patterns/phase eligibility/timeout. Without it, Cargo commands and `npm run <script>` scripts are discovered from the manifests present.

This is the one place repository text becomes an executed shell command, so each check carries its **source** in every report:

| Source | Command text written by | Gated by `workflow.repo_checks_enabled` |
|---|---|---|
| `repo-config` | the repository's `.zirv/verify.toml` | yes |
| `discovered-script` | the repository's `package.json` (`npm run <id>`) | yes |
| `discovered-toolchain` | zirv itself (the Cargo commands) | no |

`repo_checks_enabled` defaults to **true**, deliberately. Running a repository's own checks is the point of the feature, and it is the same trust posture zirv already takes by executing that repository's `.zirv/` scripts at all; the key exists as an operator kill-switch, the same shape as `mail.enabled` — off means off, and a checkout cannot turn it back on. What the gate does *not* try to do is judge whether a check is meaningful: a `final_check` whose command is `true` still satisfies `zirv verify`. That vacuity is made **visible rather than rejected** — the per-check `repo-config`/`discovered-script` source label is in every report — because "is this command a real test" is not decidable, and a check that looks real can be just as vacuous. The controls are the operator gate and the provenance label, not a heuristic about command bodies.

With the gate off, repo-supplied checks are still listed — with status `Skipped` and a `skipped: repo-supplied checks disabled (workflow.repo_checks_enabled)` note — and never executed. A skipped check is not a passing check, so a disabled gate cannot satisfy a step's evidence requirement. Three caps hold either way: a repo-supplied `timeout_secs` is clamped to 900s, repo-supplied checks are truncated to the first 32, and the whole repo-supplied set shares a 3600s wall-clock budget (whatever is left when it runs out is reported as skipped) — each noted in the report. The per-check source label is also what makes a vacuous `command = "true"` gate visible for what it is.

Checks run in the repository through a bounded shell child with stdout/stderr drained concurrently into a fixed-size tail and cross-platform process-tree cleanup on exit/timeout. Passing output is not retained; failures keep a capped actionable tail, with control characters scrubbed (newlines and tabs kept) so repository-controlled output cannot repaint the terminal into a forged summary. A stream that ends in a read error says so rather than looking complete.

**A check's own child process now gets a small, explicit environment passthrough allowlist instead of an unscrubbed full inherit (issue #233, 2026-08-31).** `run_check` never scrubbed the child's environment at all — the check process already inherited zirv's whole process environment, so the actual root cause of "a check can't reach my SSH agent" was that zirv's own launch environment simply lacked `SSH_AUTH_SOCK` (an operator's login-session agent socket, not something a supervised harness process carries by default). `DEFAULT_CHECK_ENV_PASSTHROUGH` (`SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `SSH_ASKPASS`, `GPG_TTY`, `GNUPGHOME`) is now explicitly set on every check child. The operator-only `[workflow] check_env_passthrough = ["VAR", ...]` key in `~/.zirv/ctx.toml` ADDS names to that built-in set (case-insensitive on Windows, case-sensitive elsewhere) — it is `REPO_FORBIDDEN` (see [[Untrusted Configuration]]), since a repo-owned `verify.toml` check already runs with the operator's real credentials and must not get to widen what environment reaches it. `ZIRV_CTX_WORKFLOW_CHECK_ENV_PASSTHROUGH` (comma-separated) REPLACES the merged TOML value rather than adding to it, the operator's final override. Resolution per allowlisted name: zirv's own process env first; if absent, on macOS only, a bounded (3s, no shell) `launchctl getenv <NAME>` shot — the login-session variable a macOS GUI-launched process often carries that a terminal-launched zirv does not — printing `zirv ▸ verify: <NAME> taken from the login session (launchctl)` to stderr when it fires; otherwise the variable stays unset. Never overrides a value already present in zirv's own environment, and the `launchctl` fallback never runs off macOS.

Reports are named with a leading zero-padded `finished_at` timestamp and pruned on every write via the same `telemetry::prune_expired_except` helper `workflow-telemetry/` uses (one shared pruner, not two): a report older than the resolved retention window is removed, except the file the `latest` pointer currently names, which always survives even if it is itself older than the window. Retention is resolved from `[workflow] telemetry_retention_days` — verification has no retention key of its own yet; see the Decision Log entry and the Known Issues residual for why.

Report files carry their own schema version (2), separate from `.zirv/verify.toml`'s (1), so an older build's report is rejected rather than reinterpreted. Reports include a change fingerprint over `HEAD`, raw change metadata, and content hashes for the tracked/untracked paths in the change set, plus compact per-check status. The fingerprint is taken **before** the checks run, so edits made during a long suite are not recorded as tested, and every Git call runs at the worktree root with `core.quotePath=false`, so root-relative paths and non-ASCII filenames both resolve (a `--repo <subdir>` run used to mix two path bases and see no content edits at all). A `--check`-narrowed run records what it was narrowed to and can never satisfy a step gate — a format-only run is evidence about formatting. Results are printed before they are persisted: a state-directory failure is a warning, not a lost run, and a closed pipe (`zirv verify | head`) costs the output but not the stored report. Every repository-controlled string a report prints — a check's `command` included, not just its captured output — is scrubbed of control characters, so an escape sequence in `verify.toml` cannot repaint the terminal into a forged summary. Test/verify workflow steps cannot advance on stale, narrowed, or failed evidence; report schema versions are checked when evidence is reloaded.

### Baseline-waivable test gate (issue #215, 2026-08-30)

Before this fix, `latest_is_fresh_and_passing` (the one shared function gating both a workflow's test step and its final Verify/Deploy gate) demanded an outright-passing report — **any** named test failure, however pre-existing, closed the gate for good on a host that carries known baseline failures (this dev machine's own documented `wrap`/`exec` set; see CLAUDE.md's "This Windows dev machine" section). A failing report now gets a second, narrower chance: `VerificationReport::evaluate_against_baseline` compares every `Unit`-kind check's `Failed` status against an operator-recorded `TestBaseline` for the repository, and the gate passes when every failing test *name* is a member of that baseline — a subset check, on names, never counts or check ids. Anything that isn't a specific named `Unit` failure (a `Format`/`Lint`/`Build`/`Typecheck`/`Custom` check, a `TimedOut`/`Skipped` status, or a `Failed` check whose output yields no parseable names) still blocks the gate outright, since none of those describe a failure an operator could have looked at and chosen to baseline. An empty or missing baseline reproduces the exact pre-fix strict behavior — nothing waives by default. Every waived name is printed as a loud `crate::output::warn` line naming exactly which failures let the gate through. A refinement round replaced text-parsing after the fact with capture-side scanning: a `FailureNameScanner` recognizes failing test names while each check's own output streams, recording them into `CheckResult.failure_test_names`, so the 16KiB-capped `failure_output` display tail (which a late output flood can evict entirely) can no longer lose them; text-parsing `failure_output` remains only as a fallback for older reports that predate this field.

The baseline itself is operator-owned state, never repository content: `TestBaseline` lives at `~/.zirv/test-baseline/<repo_slug>.json`, outside any checkout, and is written only by the new `zirv test baseline [--repo <path>] [--check <id>]... [--dry-run] [--json]` command (`TestCommand::Baseline`, sharing `RunArgs` with `changed`/`all`) — it runs the full `VerificationMode::All` suite, persists its report exactly like any other run, and then records the union of every `Unit` check's parsed failing test names as the new baseline (overwriting any prior one). Non-`Unit` or unparseable failures are warned as "not recorded in the baseline" rather than silently dropped. Only checks whose `source` is `CheckSource::DiscoveredToolchain` (zirv's own built-in Cargo checks) can contribute names at all — a repo-supplied check (`RepoConfig`/`verify.toml` or a `DiscoveredScript`) is always reported unrecordable, since a checkout is untrusted and must never widen the operator's own baseline with names of its own choosing. `zirv test changed`, `zirv verify`, and a workflow gate never write a baseline themselves — recording one is always an explicit operator action, taken after looking at what actually failed.

**One per-repository advisory lock covers every baseline write (issue #302, 2026-09-04).** `save_baseline` (streak recording), `update_baseline_after_run` (the per-run streak update), and `run_baseline_prune` all now hold a `BaselineLock` (`lock_baseline`, a stdlib `File::lock` on `~/.zirv/test-baseline/<repo_slug>.lock`, the same never-deleted-sibling-file shape `group::GroupLock` already uses) across their whole load/modify/write, so two `zirv test changed` runs in sibling worktrees — or a `--prune` overlapping a run — serialize instead of each writing back its own stale copy of the baseline file.

**The gate and the review package now share one baseline-evaluation code path (issue #238, v3.4.0).** Before this fix, `latest_is_fresh_and_passing` was the only caller of `VerificationReport::evaluate_against_baseline`, so a review package's own `VerificationEvidence` reported a raw, waiver-blind `passed:false` for a run the gate had already accepted via the baseline — every independent reviewer seat (claude and codex) filed a false Critical "test verification failed" finding on it each round, three times on the #223/#225 gate alone and again on PR #247. `evaluate_against_operator_baseline(report, repo)` (`verification.rs`) is the extracted seam: it loads the operator's baseline (`load_baseline`, degrading to "no baseline" on any load failure, same as before) and calls `report.evaluate_against_baseline` — `latest_is_fresh_and_passing` and `review::VerificationEvidence::from_report` both call this one function now, so they can never disagree about whether a failing report is actually gate-passing. `VerificationEvidence` gained `passed_with_baseline_waiver: bool` and `waived_failing_tests: Vec<String>` (sorted, deduplicated), computed only when the raw report failed (`passed:false`) — a genuine pass leaves both at their zero values, and `#[serde(skip_serializing_if = ...)]` on each means a genuine (non-waived) failure's JSON round-trips exactly as it did before these fields existed. `zirv workflow review package <id>`'s text-mode `verification:` line appends ` (passed via operator baseline waiver; waived: a, b)` when `passed_with_baseline_waiver` is true. The reviewer prompt (`build_reviewer_prompt`, extracted from `launch_reviewer` so its exact wording is unit-testable) now tells the reviewer explicitly: `passed:false` together with `passed_with_baseline_waiver:true` means every failing test is in the operator's recorded baseline and the gate passed — treat it as operator-acknowledged, never a regression or a blocking finding.

### `zirv verify` reuses fresh `zirv test` evidence for the same change (harness iteration round 1, 2026-09-02)

A workflow's Test step (`zirv test changed`) and its Verify step (`zirv verify`, `VerificationMode::Final`) used to re-run every check independently even when nothing had changed between them — the common case, since Verify usually follows Test with no further edits. `reusable_test_evidence(state, repo, fingerprint)` (`verification.rs`) is the new guard: `run_mode` in `Final` mode (never `dry_run`, which previews rather than reports history) looks up the latest persisted report, and reuses a per-check prior result only when that report is itself a `Changed`/`All`-mode run, is not itself `--check`-narrowed (`narrowed_to` empty — the same "a narrowed run is evidence about the checks it ran, not the change set" guard `latest_is_fresh_and_passing` already applies), matches the CURRENT change fingerprint exactly, and the specific check's own prior result was neither `Skipped` nor `DryRun` (neither actually ran, so reusing one would carry a stale non-answer forward — e.g. `workflow.repo_checks_enabled` toggled on between the two runs). Reuse is per-check, by id: a check the Test run never selected (a Verify-only `final_check`) still executes for real even though the fingerprint matches and a sibling check is reused. A reused check's result is copied verbatim into the `Final` report, and one note (`"reused test evidence from report <id> (fingerprint <hex>, finished_at <ts>) for: <ids>"`) records what was reused and from where. A tree edit between the two runs moves the fingerprint and forces every check to actually re-run, exactly as before this existed.

### A repeated verification attempt against an unchanged worktree is a no-op, not a re-run (issue #287, v3.11.0)

`verification.rs`'s `GateOutcome` grows a fourth variant, `Unchanged { fingerprint, since_attempt }`, alongside `Pass`/`Fail`/`Inconclusive`. `zirv workflow advance --run-checks` against a worktree whose current `change_fingerprint` equals the last FAILING report's own fingerprint skips executing any check at all and prints `"verification not re-run: the worktree is byte-identical to the previous failed attempt (attempt N/3). Edit source, tests, or record a blocker artifact before verifying again."` -- nothing has changed since that attempt, so re-running the suite could not produce a different answer. The attempt still counts: three consecutive `Unchanged` attempts fail the step at `MAX_STEP_ATTEMPTS`, so a stuck step cannot sit forever re-issuing `--run-checks` with no forcing function. `TelemetryEvent.verification_unchanged` (additive) records the outcome. `change_fingerprint` also now records `symlink:<target>` for a symlinked path instead of hashing through it (a related fingerprint-correctness fix, same change). See [[Decision Log]].

## Deploy tiers and PR lifecycle

`[workflow.deploy] tier = "development" | "staging" | "production"` is operator authority and `workflow.deploy.tier` is repo-forbidden. A repository may set only `workflow.deploy.minimum_tier`; config resolution folds the strictest home/repo minimum with the operator tier, while `ZIRV_CTX_WORKFLOW_DEPLOY_TIER` remains the operator's final override. Running workflows ratchet their persisted tier upward only, so tightening policy mid-run cannot be undone by later config drift.

Feature, bugfix, and refactor workflows end in `Deploy/finish-branch`. Production materialization inserts an independent Review step before Verify when risk classification would otherwise omit review, and tightening to Production rewinds completion after the newly inserted gate. The Deploy step records `DeployGateEvaluated` telemetry and production cannot pass with open findings, stale/missing reviewer evidence, or stale/missing final verification.

The review engine also accepts incoming GitHub PRs: `workflow review package <id> --pr <n> [--github-repo owner/repo]` and `review run ... --pr <n>` read PR metadata/diff through fixed `gh` argv, cap the diff to the normal review budget, and re-check the PR head after review. Remote PR review is inspection-only and never becomes local workflow completion evidence. `workflow review ingest-pr-comments <workflow-id> --pr <n>` imports inline/review bodies as deterministic-id open `ReviewFinding` obligations, making repeated ingestion idempotent.

## Workflow adoption: detect, nudge, enforce, measure (issue #223, v3.2.0)

A session can do substantial edit work with no active `zirv workflow` at all — the methodology this whole subsystem owns simply never gets invoked. `adoption.rs` is a pure detector (mirroring `rot.rs`'s own shape: no fs/clock/env/net, identical events always produce identical signals) over a transcript's `NormalizedEvent`s: `AdoptionSignals { edit_like_calls, turns }` counts `Edit`/`Write`/`MultiEdit`/`NotebookEdit`/`apply_patch` tool calls (case-insensitive; the last is codex's own edit tool) and turns, and `is_substantial` calls the work substantial once `edit_like_calls >= 5` on its own, or `turns >= 12` with at least one edit.

`AdoptionPolicy` (`Off < Advise < Nudge < Enforce`, default **`Nudge`**) is operator-only config, `[workflow] adoption` in `~/.zirv/ctx.toml`, env `ZIRV_CTX_WORKFLOW_ADOPTION`, and `REPO_FORBIDDEN` at the repo layer — a repo checkout must not be able to loosen its own adoption pressure to `off`, nor tighten it to `enforce` and hold an operator's own `zirv agent` dispatches hostage on the repo's own say-so. Detection runs inside the same `Stop`/`Notify`/`Prompt` (`UserPromptSubmit`) hook invocations `ctx::hook` already makes, folding signals incrementally into a per-session `AdoptionRecord` under the state dir's `adoption/` subdirectory rather than re-parsing a growing transcript every turn; a delegated worker (`ZIRV_CTX_WORK_GROUP` set) is exempt outright, since a worker is never the session an operator would start a workflow from. The first nudge fires as soon as work turns substantial; after that, at most every 5 turns.

Delivery differs by policy because `zirv ▸` announcements and mail never reach a model's own context:

- **`Advise`** — a one-shot `Stop`-hook `systemMessage`, operator-visible only.
- **`Nudge`** (default) — an `additionalContext` line on the `UserPromptSubmit` hook, model-visible; a live re-check on that same hook suppresses it the moment a workflow becomes active, even if the `Stop`-hook record hasn't caught up yet.
- **`Enforce`** — everything `Nudge` does, plus `zirv agent` refuses delegation outright (exit 1) while the calling session is substantial-without-workflow. An operator with no session identity at all (`adapters::SESSION_ENV` unset) is never blocked — see [[Ctx Subsystem]]'s `agent.rs` entry for the exact four-condition gate.

The nudge text names the detected edit/turn counts and the exact command to run, `zirv workflow start <kind> --task "<summary>"`, where `<kind>` comes from `zirv workflow classify` against the live git diff, falling back to `"feature"` when classification finds nothing to go on. See [[Ctx Subsystem]] for the hook-side wiring and state-dir record shape, and [[Untrusted Configuration]] for why the policy knob is repo-forbidden.

## Auto-spawn on gate transitions (issue #242, v3.5.0)

`workflow.auto_spawn_on_gate` (operator-only, `REPO_FORBIDDEN`, default **false**) auto-spawns a detached bounded worker the moment `zirv workflow advance` lands the workflow's new current step on Review, Test, or Verify — rather than waiting for the operator to run `review run`/`test changed`/`verify` by hand. `engine::auto_spawn_decision(&state, enabled, permit_available, default_agent) -> Result<AutoSpawn, AutoSpawnSkip>` is the pure decision: it fires only when the config flag is on, `state.status == Running` (never `AwaitingApproval`), the new current step's phase is Review/Test/Verify, and a heavy-operation permit is available (`AutoSpawnSkip::NoPermit` otherwise). Review additionally needs a recorded adapter (`state.adapter` from `workflow start --agent`, or the caller's own default) — a workflow with no adapter to hand the reviewer skips Review's auto-spawn outright (`AutoSpawnSkip::NoAgent`), since there is no principled default agent to pick. The spawned argv is `zirv workflow review run <id> --agent <adapter> --repo <repo>` for Review, `zirv test changed --repo <repo>` for Test, `zirv verify --repo <repo>` for Verify.

The thin I/O wrapper in `advance_with_evidence` acquires a real heavy-operation permit on the detached child's behalf, sets its `child_pid`, then deliberately leaks the `HeavyPermit` (`std::mem::forget`) rather than dropping it — dropping would delete the slot file before the detached child (which this process never `wait()`s on) has done any real work. The existing dead-owner sweep in `permit::live_records` frees the slot once the child's own pid is no longer alive, the same mechanism already designed for "parent dies before its supervised child." A successful spawn records `TelemetryKind::AgentDispatched` with `agent_id = "auto-spawn:<phase>"` and prints one `zirv ▸` advisory (`Event::AutoSpawned { phase, command }`); a skip past the `Quiet` cases (no permit, no agent) is announced too (`Event::AutoSpawnSkipped { phase, reason }`), since an operator who turned the flag on should see why nothing happened. `advance` never fails or blocks because of an auto-spawn refusal or a spawn error — it is a best-effort side effect layered on top of a transition that already succeeded.

## Maintain loop

`zirv workflow maintain scan [--repo <path>] [--json]` is an invoked scanner, not a daemon. It reads detectors only from operator-owned `~/.zirv/ctx.toml` under `[workflow.maintain.detectors.<id>]`; repository config is forbidden from defining detector commands. Each detector is deterministic: either a non-zero/timeout breach or a stdout line-count threshold. Commands are bounded, run with process-tree cleanup, and the scanner retains only exit code, timeout state, line/byte counts, never detector command/output bodies in committed artifacts, telemetry, or GitHub issues.

A breach creates one bounded incident cycle parked at the Intent acceptance gate. Zirv commits `.zirv/work/<workflow-id>/intent.md` with detector metadata, stores a private active-incident marker keyed by canonical repository + detector, and reuses that workflow while the breach persists. A clean scan clears the marker, so a later recurrence becomes a new incident. If operator-only `[report] repository = "owner/repo"` is configured, the scanner files an exact-title-deduplicated GitHub issue; a fresh machine also reuses an already-open issue by title. Issue filing failure does not discard the parked workflow and is retried on the next scan.

The ordinary `zirv report` command keeps its fixed Zirv repository destination; the generalized report transport is used only when an explicit operator-selected destination is supplied by maintenance. `MaintenanceScan` telemetry records pass/breach without source/output payloads, and `workflow stats` aggregates maintenance breaches alongside artifact acceptance, agent dispatch and deploy-gate outcomes.

## Review

`zirv workflow review package <id>` builds a reproducible package from task/classification, base/head SHAs, tracked and untracked changed paths, a streaming/capped relevant diff, summarized verification (including whether it is fresh), existing findings, and review round. It never includes the controller conversation or plan history. `review run --agent <name>` pipes that package to a fresh `zirv agent` worker; the worker does not share the controller conversation.

### Bounded reviewer workers (issue #235, v3.5.0)

`workflow.review_worker_budget_tokens: Option<u64>` and `workflow.review_worker_max_tool_calls: Option<u32>` (both operator-only, `REPO_FORBIDDEN`, unset by default — today's unbounded behavior) give a workflow's independent-reviewer seat a spend ceiling. When set, `reviewer_argv` appends `--budget-tokens <n>`/`--max-tool-calls <n>` to the `zirv agent <adapter> ...` launch — both land BEFORE the `--` separator, since they are `zirv agent`'s own clap flags, not adapter passthrough — and `build_reviewer_prompt` gains one paragraph stating the ceiling(s) and instructing the reviewer to conclude with its confirmed findings before running out, rather than leaving the review incomplete with no result at all. This bounds the reviewer's own spend; it does not raise implement-step rigor or add a self-review gate — that direction was considered and deferred (see the Decision Log). `frontend_render.rs`'s separate visual-review reviewer spawn (`launch_visual_reviewer`, not the code-review seat this issue is about) also calls `reviewer_argv` but passes `(None, None)` explicitly, so its own argv is unchanged.

**`reviewer_argv` now pins the reviewer's own launch to the resolved review model, not just the roster's advisory line (harness iteration round 3, 2026-09-02).** `reviewer_argv` calls `adapters::resolve_review_model(cfg, agent, adapter)` — the same `pub(crate)` function `review_roster_line` uses to build its "run every review on `{model}`" line (see [[Ctx Adapters]]) — and appends `adapter.model_args(&review_model)` to the reviewer's `zirv agent` argv, landing before the read-only floor pin so no later argument can weaken it. Previously the roster line was advisory only: an automated `review run` launch carried no `--model` of its own and ran on the adapter's bare CLI default, which could silently diverge from what the roster told the operator would run. With `chat.model` unset, this makes each adapter's ladder-top default (`opus` for claude) the review model a fresh install's reviewers actually run on — see the 2026-09-02 [[Decision Log]] entry for why that's recorded as an operator-visible decision rather than an invisible tightening.

**`review run` spawns its reviewer with an explicit `--headless` (`reviewer_argv`, review-round fix, 2026-08-31).** The reviewer's argv is `zirv agent <name> - --headless -- <read-only-pin flags>`. Without `--headless`, this branch's own #228 loud pane-flag refusal (see [[Ctx Supervisors]]'s dashboard section) would block `review run`'s own reviewer spawn the moment it runs from inside a dashboard pane, since trailing `-- <flags>` is exactly one of the flag shapes that gate now hard-errors on rather than silently demoting — a case this branch's own review gate found by running into it. **Gotcha for any future zirv-internal `zirv agent` caller that passes trailing harness flags: pass `--headless` too**, or a dashboard-hosted run of that caller breaks the same way.

**The reviewer prompt contract requires the `ZIRV_REVIEW_RESULT` line as plain stdout text, never through a harness findings tool (2026-08-31).** The prompt built in `launch_reviewer` now says explicitly: "Print that line as plain text in your final message: zirv reads ONLY your stdout, so do not deliver findings through a harness tool (ReportFindings or similar) or a code-review mode — a result sent any other way is lost." This was added after a real miss during the review round: a claude sonnet reviewer delivered its findings through Claude Code's own `ReportFindings` tool instead of printing the `ZIRV_REVIEW_RESULT` line to stdout, so zirv's relay never saw an envelope at all — the raw-output salvage path below (issues #229/#232) recovered the findings from the persisted raw output via `zirv workflow review add`, a working demonstration of that fix rather than a lost review round.

Untracked files are the working tree's own contents rather than anything a change author chose to commit, so they contribute their **path** always and their **body** only when it is safe: text (no NUL byte in the first 8 KB), at most 16 KB, and not matching a sensitive name (`.env*`, `*credential*`, `*secret*`, `*.pem`, `*.key`). Each exclusion is stated in the package, so a reviewer sees that the file exists and why its contents are absent.

A second, content-based gate runs behind the filename denylist, on every untracked file that already passes it and the size cap — the exact case a filename check alone misses (a bearer token pasted into `token.txt`, `notes.md`, or any other ordinary-looking name). It is deterministic and dependency-free of any network/service call: known credential shapes first (`sk-`/`ghp_`/`gho_`/`github_pat_`/`xox[baprs]-` prefixed keys, AWS `AKIA`/`ASIA` access key ids, PEM private-key blocks, JWTs — each anchored so it cannot fire mid-word), then a conservative Shannon-entropy check on long unbroken base64/hex-ish runs (pure-hex runs and `_`-broken identifier fragments are excluded outright, keeping ordinary source, prose, minified bundles, and lockfile hashes clear). A hit excludes the body with a reason recorded inline in the diff, the same channel the filename-based exclusion already uses — silent exclusion would be its own failure mode.

The reviewer is pinned read-only by its own adapter — `AgentAdapter::read_only_args`, the same flags `distiller_cmd` uses (claude `--disallowedTools=Write,Edit,Bash,NotebookEdit`, codex `--sandbox read-only`) — because its prompt embeds an untrusted repository diff. An adapter with no registered pin is refused rather than launched unrestricted.

Findings are persisted with severity, optional path/line, reviewer recommendation, and final disposition (`open`, `accepted`, `dismissed`, `fixed`, `residual`). A real reviewer must emit one bounded `ZIRV_REVIEW_RESULT` JSON line; Zirv validates it and persists concrete findings itself, while retaining the explicit `review add` command for manual/imported findings. Evidence is appended to freshly re-loaded state, refused if the tree changes while the reviewer is running, and becomes stale after later edits. A dashboard spawn-request acknowledgement (`ZIRV_CTX_DASH_REQUESTS`) exits 0 for a review that has not started yet — it is reported as a spawned pane and records no evidence at all. A review step cannot pass while any finding is still open or its required fresh review evidence is missing. Low risk uses self-verification, medium/high require one independent reviewer, and critical risk requires two fresh review runs. Fix/re-review is capped at three changed-fingerprint rounds; a recurring major/critical finding escalates medium/high work to a second independent review, while a dismissed repetition does not silently strengthen policy.

### `ZIRV_REVIEW_RESULT` ingestion is lenient per finding, and a failure never discards the reviewer's raw output (issues #229/#232, 2026-08-31)

A three-way review round against this batch's own ~2.2k-line `src/` diff (Sonnet, codex cross-review, and `zirv workflow review run` itself) surfaced three real ingestion bugs, filed as issue #229 and fixed here: the compact review package dropped every `src/` hunk outright for a diff this size, the `ZIRV_REVIEW_RESULT` parser rejected an otherwise-valid reviewer payload carrying one extra field, and editing the untracked `.zirv/work/<id>/plan.md` mid-run invalidated the evidence.

- **Parsing is lenient per finding, not `deny_unknown_fields` on the whole envelope.** An unknown field on a finding is now ignored rather than rejecting the envelope. `severity` and `recommended_disposition` accept documented synonyms case-insensitively — severity: `info`/`informational`/`nit`/`low`/`suggestion` → `note`, `medium`/`moderate`/`warning` → `minor`, `high`/`error` → `major`, `blocker`/`severe`/`fatal`/`p0` → `critical`; disposition: `needs-confirmation`/`needs_confirmation`/`pending`/`unresolved`/`unknown` → `open`, `accept` → `accepted`, `dismiss`/`wont-fix`/`wontfix` → `dismissed`, `fix`/`resolved` → `fixed`. A genuinely unrecognized value degrades rather than rejects: it becomes `major`/`open` with ` [severity: <raw>]`/` [disposition: <raw>]` appended to the finding's own summary, so the raw value survives for a human to see instead of being silently coerced or dropped. A single malformed finding is skipped with a stderr warning rather than failing the whole ingestion; only a non-object top-level envelope is rejected outright. The reviewer prompt itself now states the exact JSON shape, field list, and every allowed enum value, rather than leaving the schema to be inferred.
- **Every ingestion failure persists the reviewer's raw output instead of discarding it.** A parse failure, a staleness refusal, a reviewer that emitted no envelope at all, or a non-zero reviewer exit now writes the raw reviewer output to `.zirv/work/<workflow-id>/review/raw-<utc-timestamp>-<agent>.txt` and the resulting error names that path — findings are recoverable from it via `zirv workflow review add` rather than lost. A non-zero reviewer exit is now an explicit ingestion error instead of being silently passed through as if the review had simply produced no findings.
- **Staleness is judged against this run's own starting fingerprint, never a stale earlier one.** The change-set fingerprint a review's freshness is checked against is now captured at the START of the current run, not carried over from an earlier attempt — the exact "change set changed during review" false trip a mid-run `plan.md` edit used to cause.
- **`.zirv/work/**` no longer counts as part of "the change" for review purposes.** A new `classify::is_workflow_work_path` (narrower than the existing `is_zirv_owned_path` — see [[Known Issues]]'s resolved #214 entry) excludes zirv's own workflow-owned artifacts under `.zirv/work/` from both the review package and `change_fingerprint`, so editing an untracked in-progress `plan.md`/`spec.md` mid-run no longer looks like a change to the reviewed code.
- **Package truncation is code-first, not source-order.** When the review package exceeds its 96 KiB budget, hunks are now ordered `src/**` and code-extension files first, then tests/fixtures, then config (`Cargo.toml`, `*.toml`/`yaml`/`json`), then docs/markdown, then pure renames — so a large-but-important code diff no longer loses precisely the hunks a reviewer most needs while a small config/doc change survives. Hunks drop from the tail once the budget is exceeded, and a `TRUNCATED: <N> file(s) omitted: <paths>. Run: git diff <base>...HEAD -- <paths>` trailer names exactly what was cut and how to see it; if even the package's first hunk cannot fit, only that `git diff` command is included. The raw `git diff` behind the package is now read up to an 8 MiB ceiling before ordering/truncation runs, up from a smaller prior cap that could itself truncate the diff before the ordering logic ever saw the later, code-heavy hunks.

### Review package schema 2 -> 4: delta rounds and an accepted-spec excerpt (harness iteration round 1, 2026-09-02)

Before this round, a delta round (round 2+, intact evidence chain) already scoped its `diff` to what changed since the previously reviewed commit, but `changed_paths` and `existing_findings` still resent EVERYTHING since `base_sha`/every recorded finding on every round — a reviewer re-read the same unchanged findings each round. `ReviewPackage.schema_version` moved 2 -> 4 (T2 = 3, T3 = 4; the type is `Serialize`-only, no round-trip, so the version exists purely so a reviewer can tell an old package from a new one):

- **`changed_paths` is now a delta too.** On round 1, or any round whose diff fell back to the full change (`!diff_is_delta`), it is every path changed since `base_sha`, unchanged from before. On an intact-chain delta round it is computed against `diff_base_sha` instead — the same base the packaged `diff` is already scoped to — so a path a previous round already sent and that hasn't changed further since is left out. Untracked files have no sha to diff against and are always included in full.
- **`existing_findings` sends only what changed.** `previous_round_evidence(state)` (factored out of `delta_base`'s own "latest round, then latest completion within it" selection, so the two can never disagree about which round is "the previous one") now also carries a `finding_dispositions: BTreeMap<id, FindingDisposition>` snapshot on `ReviewRunEvidence`, taken AFTER a round's incoming findings are merged in. `delta_existing_findings(state)` compares each current finding's disposition against that snapshot: new (no entry) or disposition-changed findings are resent; everything unchanged is left out of `existing_findings` and only counted in a new `unchanged_existing_findings: usize` field. Round 1 and any broken-chain round still send every finding in full (`unchanged_existing_findings: 0`) — the caller decides which shape applies, since the function itself cannot tell "genuinely no previous round" from "previous round's snapshot was empty." The reviewer prompt's delta notice now names the omitted count explicitly (`"N earlier finding(s) unchanged since then and omitted here (see unchanged_existing_findings)"`), and `zirv workflow review run`'s own text output prints `existing findings: N (M unchanged, omitted)` when any were left out.
- **`accepted_spec_excerpt` gives a reviewer something more concrete than the one-line task.** `accepted_artifact_excerpt(state)` reads whichever of the workflow's accepted Spec/Intent/Plan artifacts exists (spec preferred, then intent, then plan — spec is the most concrete statement of what must be true of the change), splits it into markdown sections by heading, reorders `## Acceptance Criteria`/`## Goals` sections to the front, and caps the result at 2 KiB (`MAX_ACCEPTED_ARTIFACT_EXCERPT_BYTES`) — so a much larger preceding section (background/context prose) cannot crowd out the part that actually states what "done" means. `None` when nothing is accepted yet. The reviewer prompt gains one paragraph telling the reviewer to judge the diff against this excerpt's acceptance criteria/goals/non-goals, not only the one-line `task` description, whenever it is present.

### `zirv workflow advance --run-checks`, and `zirv workflow review dispose --apply-recommended` (harness iteration round 1, 2026-09-02)

**`--run-checks` collapses "run the gate, then advance" into one call.** `workflow advance <id> --run-checks` (in place of `--outcome`, now `Option<StepOutcome>` and `required_unless_present = "run_checks"`, the two flags mutually exclusive) runs the current step's own required evidence command in-process — `zirv test changed` for a `Test`-phase step, `zirv verify` for a `Verify`-phase step, through the identical functions the standalone CLI verbs call, never a subprocess — prints the evidence summary, and advances only on a passing result — "passing" judged by the same baseline-aware criterion the plain `advance` path applies to a persisted report (a run whose only failures are covered by the recorded test baseline passes, with the same warning), not by the raw exit code (dogfooding fix, 2026-09-02: the first cut refused every run on this repository because `zirv verify` exits non-zero on baselined failures); a genuinely failing result prints `"checks failed; step '<id>' was not advanced"` and exits 1 without advancing, and so does a run that persisted no new report (a swallowed persist error must never let an older passing report for the same fingerprint stand in for the run that just failed). Any other current phase is refused outright (`"--run-checks only applies to Test/Verify steps ... pass --outcome instead"`) rather than silently treating itself as satisfied.

**`zirv workflow review dispose <id> --apply-recommended`** (`DisposeFindingArgs.apply_recommended`, `engine::apply_recommended_dispositions`) applies every currently-`Open` review finding's own `recommended_disposition` in one call, instead of one `<finding_id> --disposition <d>` invocation per finding — the flag lives on the same `dispose` verb the single-finding form uses (`finding_id`/`disposition` become `required_unless_present = "apply_recommended"`, and the flag itself `conflicts_with_all` both: one shape or the other, never both in the same invocation). A finding that already carries a resolved disposition (`Accepted`/`Dismissed`/`Fixed`/`Residual`) is left untouched and not reported; an open finding with no recommendation is left `Open` but still reported (`"<id>: open (no recommendation)"`), so the caller sees it was considered rather than silently skipped.

## Artifacts

`zirv artifact render <path>` registers a repository-contained regular file and returns a stable id. Later steps use the id/path rather than reinjecting payload content. The repository path is canonicalized in one shared place (`artifact_dir`), so register/load/list agree on the state slug even where the OS reports two spellings of the same directory (macOS `/var` vs `/private/var`). `AgentAdapter::native_artifact_presentation` is the first presentation rung; current Claude Code and Codex CLI adapters honestly return none because accepting an image as model input is not a verified native output surface. Static presentation is therefore the current no-process default.

`artifact present --interactive` requires an explicit server command and an `http(s)://` URL on a **loopback** host (`localhost`, `127.0.0.0/8`, `::1` — no other scheme or host is dialed by zirv or handed to the platform opener), then applies the repository's effective canonical policy to `shell.exec`/`browser.open`: `deny` refuses and `ask` requires the explicit `--approve` confirmation. It enforces a 1–3600 second lifetime whose clock starts at spawn rather than after the blocking browser open. Success means a live server: the child must still be running and the URL's host/port must accept a connection within 5 seconds, and a command that exits first fails with its own stderr surfaced instead of reporting success. The server's stderr is drained continuously on its own thread (a bounded tail is kept for diagnostics), so neither a chatty server nor a slow-but-alive one can wedge the run. The process tree is killed on timeout, readiness failure, or browser-open failure.

## Telemetry

`zirv workflow stats` aggregates local structured events by phase: wall duration, exposed token counts and source, verification failures, finding disposition, fix rounds, artifact counts, worker counts, and frontend detector/render/visual-review run and failure counts. A workflow started inside a supervised Claude/Codex session checkpoints that harness transcript and automatically attributes bounded appended token deltas to each phase; explicit `workflow advance --input-tokens/--output-tokens` remains the override when another harness reports usage out of band. `--clear` removes this repository's telemetry. Controls live in the `[workflow]` config section — `telemetry_enabled`, `telemetry_max_events`, `telemetry_retention_days`, with `ZIRV_CTX_WORKFLOW_TELEMETRY*` as the operator's environment override — and all three are `REPO_FORBIDDEN`. `0`/`1` are accepted alongside `true`/`false`, and anything else is a loud error.

Each event is a separate private bounded JSON file, which avoids concurrent-writer corruption. Default retention is 1,000 events/30 days, with hard upper bounds even when configuration asks for more; free-form labels are capped before serialization. One unreadable event file is skipped with a warning rather than failing the whole `stats` command. Aggregates include per-adapter duration/token/failure comparisons and use each workflow's latest finding snapshot instead of double-counting the same findings across phases. The schema has no prompt, source-code, diff, model-response, or command-output field. Telemetry reports evidence; it does not silently weaken safety or review policy.

**`TelemetryEvent` schema v2 — raw token classes and session lineage (2026-08-27, issue #155 Phase 2).** `TELEMETRY_SCHEMA_VERSION` is now `2`. `input_tokens` keeps its pre-2.34.0 meaning (the combined "real context size" figure — see [[Ctx Adapters]]'s `TranscriptUsage::context_total()`), and the event gained the raw classes behind it as their own fields: `cache_creation_input_tokens`, `cache_read_input_tokens` (both `Option<u64>`). These two plus `input_tokens` are the ground truth for a cache-hit ratio — folding them together at the point of recording (the pre-2.34.0 behavior) made that ratio uncomputable from a stored event. A parallel set of four (`sidechain_input_tokens`, `sidechain_cache_creation_input_tokens`, `sidechain_cache_read_input_tokens`, `sidechain_output_tokens`) carries the same classes for subagent (`isSidechain`) spend over the same phase — its own bucket rather than folded into the main numbers, since a subagent's tokens are not part of "this session's own context" but are still charged to the account; dropping them entirely, as before this change, made a phase look cheaper than it was. Finally, `session_id`, `parent_session_id`, and `work_group_id` (all `Option<String>`) exist on the schema for attributing spend to a session, its delegator, and a work group — but as of this phase only `session_id` is actually populated (`engine.rs`'s `enrich_transition_evidence`, from the harness's own session identity); `parent_session_id`/`work_group_id` are reserved for a later phase and are never invented here. All new fields are `#[serde(default)]`, so an event written before 2.34.0 still deserializes with them `None`. `zirv workflow stats`'s existing aggregates are unaffected — they still read `input_tokens`/`output_tokens`, which kept their meaning.

`zirv ctx agent`'s one-shot delegations get a separate, denser lineage record on the same four raw classes — see [[Ctx Subsystem]]'s "One-shot delegation cost accounting" note. That record already carries its own `parent_session`/model/outcome per completed delegation; it is not layered on `TelemetryEvent`.

**Cost lines (issue #264, v3.12.0).** `TelemetryEvent::apply_price` prices each recorded event's raw token classes against the same `price::PriceTable` `zirv ctx spend`/`zirv ctx status` read (see [[Usage and Pacing]]'s "Cost ledger" section and [[Ctx Subsystem]]'s `spend` verb entry for the pricing mechanism itself); `zirv workflow stats` prints a `cost: ...` line per phase, per workflow, and overall (`telemetry::format_cost`/`overall_cost_line`), rendering `no data` rather than a manufactured `$0.00` when nothing in that group ever priced, and prefixing every figure with `~` whenever the price table is stale.

**Speed lines (issue #293, v3.12.0).** A `TurnLatencySampled` telemetry event is recorded once per Stop-hook scoring pass, carrying `score::derive_speed_metrics`' four fields (turn p50/max latency, time-to-first-text p50, tool-error rate — see [[Rot Engine]]'s "Speed metrics" section for how each is computed). `zirv workflow stats` aggregates every sampled event into one overall (not per-phase, not per-workflow) `speed: {N} samples, turn p50 ~{X}ms (max {Y}ms), ttft p50 ~{Z}ms, tool error rate ~{W}%` line — `"speed: no data"` with zero samples, `n/a` per field with no data for that field alone — printed right before the adoption line below. This is pure telemetry: `rot.rs`'s verdicts are unaffected (pinned by `rot::tests::timestamps_never_move_a_verdict`).

**Adoption and cache-hit telemetry (issue #223/#225, v3.2.0).** `TelemetryKind::AdoptionDetected` is recorded at most once per session, the moment `ctx::hook`'s adoption detector first calls a session's work substantial, carrying whether a workflow was already active at that instant (`workflow_active`); `TelemetryKind::AdoptionRecovered` follows for a session recorded as `AdoptionDetected` with no active workflow that later starts one — both are `workflow_id: None` and session-keyed rather than workflow-keyed, since the whole point is measuring sessions that never had one. `zirv workflow stats` aggregates these into `AdoptionStats` and renders them as the report's last line: `adoption: 4/5 substantial sessions ran a workflow (80%), 1 adopted after a nudge`, or `adoption: no substantial sessions observed` when nothing has crossed the threshold yet. Separately, schema v2's `cache_creation_input_tokens`/`cache_read_input_tokens` fields (see above) now back `TelemetryEvent::cache_hit_ratio()` and its `PhaseStats`/`AdapterStats`/`StatsReport` aggregates (`overall_cache_hit_ratio`, summed across raw counts, never an average of per-event ratios) — `zirv workflow stats` prints `cache hit: P% of combined input tokens were cache reads (schema v2 formula)` right after its token totals (`n/a` with no cache data in the aggregated set, never a manufactured 0%) and appends a `, cache hit P%` suffix to each per-adapter summary line under the same no-data rule.
